## 사용자 스토리 (US)

- **US1**: QA가 기준이 걸린 run의 측정결과 보고서를 팀에 넘길 때 — 성공하면 판정 문장·지표 칸의 목표 줄·그 밖의 기준 표·느림 문장에서 측정값과 기준값이 반올림 없이 찍힌다(예: "측정 3,040ms, 기준 3,000ms 이하"). 같은 숫자로 보이는데 "넘었습니다"라고 적힌 곳이 없다. 판정과 무관한 숫자는 지금 표기(3.0초) 그대로다.
- **US2**: 운영자가 어느 단계가 느린지 찾으려고 표준판의 「단계별 응답 속도 구간」 표를 볼 때 — 성공하면 단계마다 막대 한 줄과 구간별 비율 숫자, 맨 아래 「전체 요청」 행이 보인다. 느림 경계는 그 run의 응답 시간 기준값(단계 기준이 따로 있으면 그 단계 값, 행에 표기)이다. 표 아래 한 줄이 "기준 초과가 5% 이하여야 통과 — 이번엔 N%라 통과/미달"로 1쪽 판정과 같은 결론을 말한다. 흑백으로 뽑아도 숫자 칸과 빗금으로 구간이 구분된다.
- **US3**: 운영자가 실패가 섞인 run의 같은 표를 볼 때 — 성공하면 실패 비율이 막대 밖 별도 칸에 있다. 2절 표에서 ✕(오류율 기준 넘음)나 「▲ 오류 있음」(기준 없이 실패 있음)이 붙는 단계는 여기서도 같은 기호와 굵은 숫자가 붙고, "막대에는 실패한 응답의 시간도 들어 있다"는 안내가 표 아래에 있다. 빠른 실패로 막대가 「1초 미만」으로 가득한 단계도 좋은 단계로 읽히지 않는다.
- **US4**: QA가 응답 시간 기준이 없거나 1초 이하인 run을 인쇄할 때 — 성공하면 기준이 없는 run은 1초·3초로 나누고 "판정과 무관"이라 밝히며 초과 칸에 ▲가 없고 통과/미달 낱말도 없다(실패 칸의 ▲는 2절의 「오류 있음」 알림이라 남는다). 기준이 1초 이하면 「기준 이내 / 기준 초과」 두 구간으로 줄어든다. 단계가 많아도 표가 잘리지 않고 다음 쪽으로 이어진다(머리줄 반복).

> US 초안 대비 변경(사용자에게 고지함): US3의 ✕ 조건을 "실패율 1% 초과"에서 "2절 표와 같은 규칙(그 run의 오류율 기준을 넘은 단계)"으로 고침 — 코드 확인 결과 2절의 ✕는 고정 1%가 아니라 기준 기반(`stepStatus`의 `error` 태그)이다.

## 1. 의도와 이유

측정결과 보고서는 "설명 없이 스스로 읽히는 결과물"이 목적이다(슬라이스 1 §1). 두 군데가 그 목적을 깬다.

1. 판정에 쓰이는 측정값·기준값을 같은 표시 함수(`fmtMs`·`fmtPct`)로 반올림해서, 측정 3,040ms·기준 3,000ms가 "측정 3.0초, 기준 3.0초 이하 … 넘었습니다"로 찍힌다(§B43 (1), 사용자 결정: 자릿수를 늘리거나 원값 그대로).
2. 보고서에 "응답이 기준 안에 몇 %였나, 어느 단계가 느린가"가 없다. p95 한 숫자만으로는 행정 부서가 읽지 못한다.

사용자가 정한 원칙: **판정과 막대가 어긋나면 안 된다.** 그래서 구간 경계는 고정 눈금이 아니라 그 run의 기준값이고, 통과/미달 낱말은 서버 판정을 그대로 쓴다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 판정에 쓰이는 측정값·기준값 쌍을 구분되는 자릿수로 표기(UI만).
- 컨트롤러 리포트에 단계별·전체 응답 속도 구간 건수(`speed_bands`)를 싣는다.
- 표준판에 「3. 단계별 응답 속도 구간」 절(시안 그대로).

**비목표** (이번에 안 함 — 사용자에게 고지함, roadmap §B에 연기로 기록)
- 요약판(1장)에 이 표 넣기.
- 화면 리포트·CSV·XLSX에 구간 싣기.
- 비교 보고서(슬라이스 1 §14의 나머지).
- 실패 응답을 막대 안에서 따로 떼기 — 엔진이 실패 응답 시간도 같은 히스토그램에 기록하므로(`crates/engine/src/aggregator.rs` `StepWindow::record`) 엔진·proto·migration 변경이 필요하고, 떼어 낸 뒤의 "초과"는 실패 포함으로 계산하는 지금의 p95 판정과 다시 어긋난다.
- 가림 정책 변경(§B43 (1) 둘째 항목 — 이번 범위에 손댈 곳 없음).

**안티목표 (돌아가도 실패)**
- 막대·안내 줄의 결론이 1쪽 판정과 다르다(예: 판정은 미달인데 안내 줄은 "5.0% … 통과").
- 빠른 실패가 많은 단계가 좋은 단계로 읽힌다.
- 색만으로 구간을 구분한다(흑백 출력 시 정보 소실).
- 응답 시간 기준이 없는 run의 초과 칸에 ▲가 붙거나 통과/미달 낱말이 찍힌다. (실패 칸의 `▲`는 판정이 아니라 2절 「▲ 오류 있음」과 같은 알림이다.)
- 응답 시간 기준이 없는 기존 run의 리포트 JSON에서 `speed_bands` 외 다른 키가 바뀐다.

## 3. 사용자가 정한 것

1. 구간 경계는 그 run의 기준을 따른다(고정 1초·3초 기각 — "판정이 어긋나면 안 되지").
2. 막대는 속도만, 실패는 막대 밖 별도 칸(시안 방식).
3. 시안의 모양 그대로(색·빗금·숫자 칸·안내 줄·「전체 요청」 행).
4. 요약판 제외·절 위치(2절 다음)·p99만 있는 run의 처리·이번에 안 하는 것 목록 — 고지 후 이견 없음.

## 4. 접근 (검토한 길)

| 길 | 내용 | 버린/고른 이유 |
|---|---|---|
| **A. 컨트롤러가 경계를 정하고 건수를 센다 (채택)** | `build_report`가 `profile.criteria`에서 경계를 정해 병합된 HDR 히스토그램을 한 번 훑어 건수를 낸다. UI는 그대로 그린다 | 판정(p95)과 같은 히스토그램·같은 ms 버림 규칙으로 세므로 어긋날 수 없다. 예전 run도 리포트를 다시 만들 때 자동으로 나온다(저장 변경 없음) |

## 5. 기준·측정값 쌍 표기 (US1, UI만)

**대상** — 판정에 쓰이는 측정값·기준값이 함께 또는 대응해 찍히는 곳 전부:
- `ui/src/print/verdict.ts` `criterionValue`를 쓰는 곳: `kpiCards`의 목표 줄, `otherCriteriaRows`의 `target`·`actual`, `sentences.ts`의 판정 줄(`criterionValue` 호출).
- `ui/src/print/sentences.ts` 느림 줄(`S.slow(name, fmtMs(p95), fmtMs(thr))`)도 대상이다. 대체 줄(`S.fallback`)은 기준 없는 문장이라 대상이 아니다.
- **지표 칸**: 큰 숫자는 지금 표기(`3.0초`) 그대로 두고, 그 칸에 서버 판정 행이 있으면(통과·미달) 목표 줄 끝에 측정값을 쌍 표기로 덧붙인다 — `목표 3,000ms 이하 ✕ 미달 (측정 3,040ms)`. 큰 숫자만 보면 "3.0초 / 목표 3,000ms 이하 ✕ 미달"이 되기 때문이다(목표 줄에는 지금 기준값만 있다 — `verdict.ts` `kpiCards`의 `targetFor`). 판정 안 함·판정할 수 없음이면 덧붙이지 않는다.
- 새 절의 판정 표시가 붙는 칸과 안내 줄(§7.3·§7.5).

**대상이 아닌 것** — 지표 칸의 큰 숫자, 2절 표의 숫자, 측정 조건 상자 등 나머지는 지금 표기(`fmtMs`·`fmtPct`) 그대로.

**규칙** (새 순수 함수, `ui/src/print/format.ts`) — 쌍(측정값, 기준값)을 함께 받아 두 글자를 돌려준다.
- 시간(`*_ms`): ms에 천 단위 쉼표 — `3,040ms`·`3,000ms`·`0ms`. 측정값은 서버가 정수 ms로 준다. 단계 기준값은 소수일 수 있으므로(`Criterion.threshold`는 `f64`, 서버는 유한·0 이상만 검사) 소수가 있으면 소수 3자리까지 뒤 0을 떼고 적는다(`2,999.5ms`).
- 비율(`*_rate`): 퍼센트, 기본 자릿수(호출하는 곳이 정함 — 문장·표·목표 줄은 2, §7.3 표 칸은 1). 두 값이 수로는 다른데 글자가 같으면 글자가 달라질 때까지 한 자리씩 늘린다(상한 6자리). 두 글자는 같은 자릿수.
- 초당 요청(`rps`·`min_window_rps`): 같은 방식(기본 1자리, 상한 6).
- 건수(`*_count`): 지금 그대로(정수).
- **상한에서도 글자가 같은 경우**(예: 기준 입력 0.7%가 `0.006999999999999999`로 저장되고 측정이 정확히 0.007 — `ui/src/components/run/profileForm.ts` `buildCriteria`의 `/ 100`; 시간도 기준 2999.9999·측정 3000처럼 소수 3자리 글자가 같으면 해당): 두 값을 기본 자릿수로 적고 측정값 뒤에 `(기준과 차이가 아주 작음)`을 붙인다. 통과/미달 낱말은 서버 판정 그대로. 좁은 표 칸(§7.3)에서는 꼬리 대신 숫자 뒤에 `*`를 붙이고 표 아래 각주 한 줄 `* 기준과 차이가 아주 작은 값입니다.`을 낸다.
- **0에 가까운 비율**: 쌍 규칙으로 정한 자릿수에서 0이 아닌 값이 `0.0…%`로 찍히면 「미만」 표기로 바꾼다(0건과 헷갈리지 않게) — 그 자릿수의 가장 작은 단위로 적는다(1자리면 「0.1% 미만」, 2자리면 「0.01% 미만」).
- 기준값만 있고 측정값이 없는 자리(판정 안 함·판정할 수 없음)는 기준값을 기본 자릿수로.

**불변식(테스트로 잠금)**: 두 값이 수로 다른 모든 쌍에서, 찍힌 측정값 글자 ≠ 기준값 글자이거나 측정값에 「차이가 아주 작음」 꼬리가 붙는다. 특히 서버 판정이 미달인 쌍이 꼬리 없이 같은 글자로 찍히는 일이 없다.

**이번에 안 고치는 것**(roadmap §B에 기록): 화면 리포트의 기준·측정값 표기(`ui/src/components/report/` 쪽 판정 표시 — 비율 소수 2자리·ms 정수·rps 1자리 고정이라 드물게 같은 글자가 될 수 있다)와, 위 `0.7%` 입력이 저장 때 근소하게 작아져 정확히 0.7%인 측정이 미달로 판정되는 선재 동작(판정 로직 — 이 슬라이스는 표기만).

## 6. 컨트롤러 — `speed_bands` (US2–US4)

### 6.1 와이어

`ReportJson`에 최상위 필드 하나를 더한다(`crates/controller/src/report.rs`).

```rust
#[serde(default, skip_serializing_if = "Option::is_none")]
pub speed_bands: Option<SpeedBands>,

pub struct SpeedBands {
    pub overall: SpeedBandRow,          // 「전체 요청」 행
    pub steps: Vec<SpeedBandStep>,      // step_id 오름차순(리포트 steps와 같은 순서)
}
pub struct SpeedBandStep { pub step_id: String, #[serde(flatten)] pub row: SpeedBandRow }
pub struct SpeedBandRow {
    pub slow_ms: u64,        // 느림 경계(이 값 초과가 「초과」)
    pub basis: String,       // "p95" | "p99" | "p50" | "default"
    pub own: bool,           // 단계별 기준에서 온 경계면 true (overall은 항상 false)
    pub fast: Option<u64>,   // 1초 미만 건수. slow_ms <= 1000이면 None(두 구간)
    pub within: u64,         // fast가 Some이면 1초 이상 ~ 경계 이내, None이면 경계 이내 전체
    pub over: u64,           // 경계 초과
}
```

- 분모는 `fast.unwrap_or(0) + within + over` = 그 히스토그램에 기록된 건수. `ReportStep.count`와 다를 수 있다 — 보내지 않은 요청은 건수·에러에만 더해지고 히스토그램에는 없으며(`aggregator.rs` `StepWindow::record_not_sent`), 손상된 HDR blob도 건너뛴다. 그래서 건수를 따로 싣는다.
- 전체 히스토그램이 비어 있으면(`overall.is_empty()`) `speed_bands`는 `None`(키 생략). 표본이 없는 단계는 `steps`에 넣지 않는다.
- `flatten`을 쓰지 않고 필드를 펼쳐 적어도 된다(빌더 재량) — 와이어 모양만 위와 같으면 된다.

### 6.2 경계 정하기

run 수준(`Criteria`, `crates/controller/src/store/runs.rs`):
1. `max_p95_ms`가 있으면 그 값, `basis = "p95"`.
2. 없고 `max_p99_ms`가 있으면 그 값, `"p99"`.
3. 없고 `max_p50_ms`가 있으면 그 값, `"p50"`.
4. 셋 다 없으면 3000, `"default"`.

단계 수준: 그 단계를 `target`으로 하는 `step_criteria` 중 `op == "max"`이고 `metric`이 `p95_ms`/`p99_ms`/`p50_ms`인 것을 위와 같은 우선순위로 고른다. 같은 metric이 여럿이면 가장 작은 값(UI `stepThresholds`가 p95에 쓰는 것과 같은 "가장 작은 값" 규칙). 있으면 `own = true`. 없으면 run 수준 값을 그대로 쓰고 `own = false`.

단계 기준값은 `f64`다. `slow_ms = floor(threshold)` — 판정은 정수 ms를 `<= threshold`로 비교하므로 정수 `p <= t` ⇔ `p <= floor(t)`이고, 반올림하면 §6.3 불변식이 깨진다.

기준값 0도 유효한 경계다(전부 「초과」가 될 수 있다).

**2절과의 차이(받아들이고 roadmap §B에 기록)**: 2절 표의 「▲ 느림」은 p95 기준만 본다(`stepStatus.ts` `stepThresholds`). 그래서 두 절의 ▲가 어느 쪽으로든 다를 수 있다 — p99·p50 기준만 가진 단계는 2절에 ▲가 없는데 3절에는 붙을 수 있고, run에 p95 기준이 있고 단계에 자기 p99 기준이 있으면 2절은 run의 p95로, 3절은 단계의 p99로 본다. 2절 규칙은 이 슬라이스에서 바꾸지 않는다.

### 6.3 세는 규칙 — 판정과 같은 잣대

판정은 `percentiles_of`의 `value_at_quantile(q) / 1_000`(ms 버림)을 기준값과 `<=`로 비교한다(`report.rs` `evaluate_criteria`의 `push_max`). 구간도 같은 잣대로 센다.

- 병합된 히스토그램을 `iter_recorded()`로 한 번 훑는다. 각 기록 칸의 대표값은 `value_iterated_to()`(그 칸의 가장 큰 등가값 — `value_at_quantile`이 돌려주는 값과 같은 종류).
- `ms = 대표값 / 1_000`.
  - `ms > slow_ms` → `over`
  - 아니고 `fast`가 있고 `ms < 1000` → `fast`
  - 나머지 → `within`
- 히스토그램 하나당 한 번만 훑고 새 할당 없이 센다(working-rules §10). 이미 `build_report`가 만든 `overall`·`per_step` 히스토그램을 재사용한다 — 디코드·병합을 다시 하지 않는다.

**불변식(테스트로 잠금)**: 같은 히스토그램에서 `value_at_quantile(q)/1000 <= slow_ms` ⇔ `over`가 「q 분위 뒤에 남는 몫」을 넘지 않는다. 즉 basis가 p95인 행에서 판정 통과 ⇔ `over / total <= 0.05`(p99는 0.01, p50은 0.5). 코드에서는 부동소수 대신 같은 뜻의 정수식으로 비교한다 — p95 `20·over <= total`, p99 `100·over <= total`, p50 `2·over <= total`(컨트롤러 테스트와 UI의 ▲ 판정이 같은 식). 경계 근처 값(기준 ±1ms, 등가 범위 경계)과 무작위 히스토그램으로 확인한다. (spec 리뷰가 `hdrhistogram` 7.5.4 소스로 확인: `value_at_quantile`과 `value_iterated_to`는 같은 `highest_equivalent(value_for(i))`를 돌려주고, 칸이 단조라 통과 ⇔ `N − over >= ceil(q·N)`.) 이 불변식이 어떤 입력에서 깨지면 **구현을 멈추고 보고한다** — 안내 줄 문구(§7.5)가 이 관계에 기댄다.

### 6.4 함께 고칠 곳

- `ReportJson` 리터럴을 직접 짓는 두 곳 — `report.rs` `build_report`의 반환 리터럴(실제 값)과 `export.rs` 테스트 픽스처(`speed_bands: None`). `cargo build --workspace --tests`가 잡는다.
- `testdata/compare_golden.json`은 손대지 않는다(`serde(default)`라 키 없이 읽힌다).
- `build_report` 인자는 늘지 않는다(이미 받는 `run.profile.criteria`·히스토그램만 쓴다).
- 내보내기(`export.rs`)·인사이트·판정 로직은 무변경.

### 7.1 위치·제목

- `report.speed_bands`가 없으면(표본 없음·예전 응답) 절 전체를 내지 않고 뒤 절 번호도 지금 그대로(3·4·5) 둔다.
- 요약판(`summaryBlocks`)은 무변경.

### 7.2 스키마

`ui/src/api/schemas.ts` `ReportSchema`(`.strict()`)에 `speed_bands: SpeedBandsSchema.optional()`. 행 스키마는 `.strict()`, `fast: z.number().nullable()`(서버 `Option`에 `skip_serializing_if` 없음 → `null`로 온다), `basis: z.enum(["p95","p99","p50","default"])`.

### 7.3 표 구성 (시안 「경우 1–4」)

행 = 2절 표와 같은 단계·같은 순서·같은 이름 표기(`table.rows`), 맨 아래 「전체 요청」 행(위 테두리 굵게).

열:
| 열 | 내용 |
|---|---|
| 단계 (36mm) | 번호+이름. ✕ 단계는 앞에 `✕`와 옅은 붉은 바탕(시안 `tr.rowbad`). 단계 기준에서 온 경계면 이름 아래 작은 글씨 「이 단계 기준 5초」 — 실제로 쓰인 경계 `slow_ms`를 §7.4 경계값 글자로(소수 기준 2999.5면 `2,999ms`) |
| 응답 속도 비율 (62mm) | 막대. 조각 폭 = 그 구간 건수 ÷ 그 행 분모 |
| 1초 미만 | 비율 |
| 1초–3초 / 1초–기준 | 비율 |
| 3초 초과 / 기준 초과 | 비율. 머리 칸 아래 작은 글씨(§7.4) |
| 실패 (22mm) | 실패 비율. 머리 칸 아래 「막대와 별개」 |

- **세 구간 ↔ 두 구간**: 모든 행(전체 포함)의 `fast`가 `null`이면 두 구간 표(「{경계} 이내 / {경계} 초과」, 시안 경우 4). 하나라도 `fast`가 있으면 세 구간 표이고, `fast`가 `null`인 행(자기 기준이 1초 이하인 단계)은 「1초 미만」·「1초–기준」 두 칸을 합쳐(`colSpan=2`) 「이내」 비율을 적는다. 그 행 막대의 「이내」 조각은 가장 옅은 색(시안 `.s1`) — 경계가 1초 이하라 실제로 1초 미만이다(두 구간 표의 「이내」 조각도 같은 색, 시안 경우 4).
- **실행 안 된 단계**(2절에서 「– 실행 안 됨」)·**표본 없는 단계**(`speed_bands.steps`에 없음): 막대 칸과 구간 칸에 「—」. 실패 칸은 실행 안 된 단계면 「—」, 표본만 없는 단계(전부 보내지 않음 등)면 실패 비율 그대로.
- **비율 표기**: 소수 1자리. 0건은 `0.0%`를 흐린 글씨로(시안 `.muted`), 0이 아닌데 0.1% 미만이면 「0.1% 미만」(기존 `fmtPct`와 같음). **판정 표시(▲·✕·굵은 붉은 글씨)가 걸릴 수 있는 칸 — 실제로 표시가 붙었든 아니든, basis가 `default`가 아닌 행의 초과 칸과 오류율 기준이 있는 행의 실패 칸 전부 — 은 §5 쌍 규칙**으로 그 칸이 비교되는 값(초과 칸 → 허용 몫, 실패 칸 → 오류율 기준)과 글자가 구분되게 적는다(기본 1자리, 같아지면 자릿수를 늘림). 초과 몫 5.04%·허용 5%면 `▲ 5.04%`, 4.96%면 표시 없이 `4.96%` — "5.0%"가 ▲ 있는 칸과 없는 칸에 같이 찍히지 않는다. 비교값이 없는 칸(basis `default`의 초과 칸, 오류율 기준 없는 실패 칸)은 1자리 그대로.
- **실패 칸**: `errorCount ÷ count`(2절 표와 같은 수, `RankedRow.status.errorRate`). 표시는 2절 표의 태그를 그대로 따른다 — `error` 태그(오류율 기준 넘음) 단계는 `✕ 26.6%` 굵은 붉은 글씨 + 행 바탕(시안 `tr.rowbad`), `hasErrors` 태그(오류율 기준이 없는데 실패가 있음, 2절의 「▲ 오류 있음」) 단계는 `▲ 90.0%` 주황 굵게(행 바탕 없음). 그 밖은 숫자만. 「전체 요청」 행은 `summary.errors ÷ summary.count`이고, 서버 판정에 run 수준 `error_rate` 기준 행이 있고 미달이면 굵은 붉은 글씨.
- **▲ (초과 칸)**: 그 행의 `basis`가 `default`가 아니고 `over ÷ 분모`가 그 basis의 허용 몫(p95 0.05·p99 0.01·p50 0.5)을 넘으면 `▲ 32.0%` 주황 굵게. 판정 낱말이 아니라 건수에서 나오므로 중단·실패 run(서버 판정 없음)에도 붙는다 — 2절의 「▲ 느림」도 그렇다. 「전체 요청」 행은 ▲를 쓰지 않고, 서버 판정의 해당 run 수준 기준 행이 미달일 때만 굵은 붉은 글씨(시안 경우 1의 `7.0%`).
- **쪽 나눔**: 기존 `table` 블록 종류로 넣는다(제목·머리줄 높이 + 행 높이 목록 → 머리줄 반복·행 분할 금지). 「전체 요청」 행도 한 행. 범례·안내 줄·각주는 표 뒤 atomic 블록 하나.

### 7.4 열 머리·범례 문구

용어: **run 경계** = `overall.slow_ms`, **고른 표** = 모든 행(전체 포함)의 `slow_ms`가 같은 표(자기 기준 단계가 있어도 값이 같으면 고른 표), **섞인 표** = 그 밖.

경계값 글자: 0이면 `0ms`, 0이 아닌 1000의 배수면 「N초」(3000 → `3초`), 아니면 §5 ms 표기(`800ms`·`2,500ms`).

| 경우 | 가운데 칸 머리 | 초과 칸 머리 | 초과 머리 작은 글씨 | 범례 |
|---|---|---|---|---|
| 고른 표 · run basis ≠ `default` (시안 경우 1) | 「1초–{run 경계}」 | 「{run 경계} 초과」 | 「기준 넘음」 | 「1초 미만 / 1초–{run 경계} / {run 경계} 초과 (기준 넘음)」 |
| 고른 표 · run basis = `default` (경우 3) | 「1초–3초」 | 「3초 초과」 | 없음 | 「1초 미만 / 1초–3초 / 3초 초과」 |
| 섞인 표 · run basis ≠ `default` (경우 2) | 「1초–기준」 | 「기준 초과」 | 「{run 경계} (따로 적힌 단계 제외)」 | 「1초 미만 / 1초–기준 / 기준 초과」 |
| 섞인 표 · run basis = `default` (단계 기준만 있는 run) | 「1초–기준」 | 「기준 초과」 | 「기준 없는 단계는 3초」 | 위와 같음 |
| 두 구간 표 · 고른 표 (경우 4) | — | 「800ms 초과」 | 「기준 넘음」 | 「800ms 이내 / 800ms 초과 (기준 넘음)」 |
| 두 구간 표 · 섞인 표 | — | 「기준 초과」 | 「{run 경계} (따로 적힌 단계 제외)」 | 「기준 이내 / 기준 초과」 |

두 구간 표의 첫 구간 머리는 고른 표면 「{경계} 이내」, 섞인 표면 「기준 이내」. (두 구간 표는 모든 경계가 1초 이하라 run basis가 `default`일 수 없다.)

### 7.5 안내 줄·각주 (시안 `.rule`·`.note`)

**안내 줄** — run 수준 basis가 `default`가 아닐 때만. 통과/미달 낱말은 **서버 판정 행에서** 가져온다(`matchVerdict`가 맞춘 run 수준 `p95_ms`/`p99_ms`/`p50_ms` 행의 `passed`). 막대에서 다시 계산하지 않는다.

- 통과: `기준 「95% 응답시간 3,000ms 이하」는 3초 초과가 5% 이하여야 통과입니다. 이번 측정은 전체 요청의 3.10%가 3초를 넘어 이 기준은 통과입니다.`
- 미달: 같은 문장에 `… 7.00%가 3초를 넘어 이 기준은 미달입니다.` + 왼쪽 테두리 붉게(시안 `.rule.fail`). 테두리는 이 run 수준 줄이 미달일 때만 붉다 — 같은 상자에 담기는 단계 기준 줄의 미달은 테두리를 바꾸지 않는다(시안 경우 2·7). "이 기준은"을 넣는 이유: 다른 기준(p99·오류율) 때문에 1쪽 종합 판정이 다를 수 있다. (시안 문구에서 이 세 글자만 다르다.)
- 허용 몫과 이름: p95 → 「95% 응답시간」·5%, p99 → 「99% 응답시간」·1%, p50 → 「50% 응답시간」·50%. 이름은 기존 `ko.print.criteria.names`(띄어쓰기 없는 「응답시간」)를 쓴다.
- 초과 비율 글자는 §5 비율 쌍 규칙으로 허용 몫과 구분되게(기본 2자리, `5.00%`와 같아지면 자릿수를 늘림). 미달인데 「5.00% … 미달」처럼 찍히지 않는다.
- 서버 판정 행이 없으면(판정 안 함·판정할 수 없음 — 중단·실패 run 등) 뒤 문장을 `이번 측정은 전체 요청의 N%가 3초를 넘었습니다.`로 끝내고 통과/미달을 쓰지 않는다. 테두리는 기본색.
- **단계 기준 줄**: 자기 경계를 가진 단계(`own == true`)마다 한 줄 — 그 경계를 만든 기준 행 하나만(§6.2가 고른 metric·가장 작은 값과 같은 `(metric, threshold)`인 서버 판정 행). `단계 기준 「④ 첨부 업로드 95% 응답시간 5,000ms 이하」: 5초 초과 14.00% — 미달.` 같은 단계의 다른 응답 시간 기준 행은 여기 적지 않는다(1절 「그 밖의 기준」 표에 지금처럼 나온다 — 경계가 달라 이 표의 건수로는 말할 수 없다). 서버 판정 행이 없으면 낱말 없이 `… 5초 초과 14.00%.`로 끝낸다.
- 단계 기준 줄은 run 수준 basis가 `default`여도 낸다(단계 기준만 가진 run). 순서는 미달 먼저, 그다음 시나리오 순서. 5줄까지 적고 넘으면 마지막에 `그 밖의 단계 기준 N건은 「그 밖의 기준」 표를 보십시오.`

**각주**:
- run basis가 `default`이고 자기 경계 단계가 없으면: `※ 이 측정에는 응답 시간 기준이 없어 1초·3초로 나눠 보였습니다(판정과 무관).`
- run basis가 `default`이고 자기 경계 단계가 있으면: `※ 응답 시간 기준이 없는 단계와 전체 요청은 1초·3초로 나눠 보였습니다(판정과 무관).`
- 항상: `※ 막대에는 실패한 응답의 시간도 들어 있습니다.`
- 보내지 않은 요청이 있는 단계가 하나라도 있으면(`ReportStep.not_sent`): `※ 보내지 않은 요청은 응답 시간이 없어 막대에는 없고 실패 칸에만 들어 있습니다.`
- 실패 칸에 ✕ 또는 ▲가 붙고 막대가 있는(표본 있는) 단계 중 실패 비율이 10% 이상인 단계가 있으면 이어서: `✕ ⑤ 신청 제출은 요청의 26.6%가 실패했고, 실패한 응답은 금방 돌아오는 경우가 많아 막대가 빠르게 보일 수 있습니다. 어떤 응답 코드였는지는 2절 표를 보십시오.` — 실패 비율이 가장 큰 단계 하나를 그 기호와 이름으로 적고, 조건에 맞는 단계가 더 있으면 「외 N단계」.

문구는 전부 `ko.ts`(`ko.print.speed.*`) 경유. 보고서 문체(working-rules §8) — 질문형·구어체 금지.

### 7.6 모양

- 색·빗금·견본·굵기는 시안 CSS 값 그대로 `ui/src/print/print.css`에(`--b1:#d6e2f5`·`--b2:#7f9fd6`·`--b3:#27407f` + 45° 흰 빗금, 막대 높이 4.4mm·테두리 `var(--sub)`).
- 막대 색은 빠름→느림만 뜻한다. 초록/빨강을 막대에 쓰지 않는다.
- 인쇄 시 배경색이 꺼져도 읽히도록 숫자 칸이 항상 있고, 막대 조각에는 `print-color-adjust: exact`(기존 인쇄 표 색 칸과 같은 처리 — 구현 시 기존 규칙을 확인해 맞춘다).
- 화면이 처음 그려지는 task 직후 컨트롤러를 띄워 시안과 나란히 스크린샷 대조(working-rules §4).

## 8. 제약

- UI 문구는 `ko.ts`, 인쇄 화면은 `.p-root` 범위 CSS(기존 규약).
- 렌더 경로에서 `normalizeProfile` 금지(`ui/CLAUDE.md` 인쇄 보고서 절) — 기준은 이미 `buildPrintDoc`이 `safeParse`로 얻은 값을 쓴다.
- 판단 로직은 `ui/src/print/`의 순수 함수(새 파일 `speedBands.ts`), 컴포넌트는 그리기만.
- 엔진·proto·DB·워커 무변경.

## 9. 검증

**자동**
- 컨트롤러: 구간 세기 단위 테스트(경계 ±1ms, 두 구간, 기준 0, 단계 기준 우선순위, 빈 히스토그램) + §6.3 불변식 테스트 + 응답 시간 기준 없는 run의 JSON에서 새 키 외 무변경.
- UI: 쌍 표기 함수(구분 불변식·상한), `speedBands.ts`(세 구간/두 구간/혼합 행/표본 없음/▲·✕ 규칙/문구 갈래), 블록 목록(표준판에만·없으면 번호 그대로), 스키마(`fast: null` 통과).
- 회귀 가드로 쓰는 테스트는 되돌려 확인(teeth check)한다.

**라이브** (`/live-verify`, 워크트리 자체 바이너리)
| US | 절차 | 통과 신호 |
|---|---|---|
| US1 | p95 기준을 측정값 바로 아래(수십 ms 차)로 건 run 인쇄 | 판정 문장·목표 줄에 서로 다른 ms 숫자, "같은 숫자인데 넘었습니다" 없음 |
| US2 | 단계별 지연이 다른 응답기 + p95 기준 run | 안내 줄 낱말 = 1쪽 판정, 행 비율 합 ≈ 100%, 단계 기준 단계에 자기 경계 표기 |
| US3 | 한 단계가 빠른 5xx를 많이 내는 run | 그 단계 막대는 「1초 미만」 위주 + 실패 칸 ✕·굵게 + 각주에 단계 이름 |
| US4 | 기준 없는 run / 기준 800ms run / 단계 40개 run | 각주 「판정과 무관」·초과 칸 ▲ 없음·통과/미달 낱말 없음 / 두 구간 표 / 표가 다음 쪽으로 이어지고 머리줄 반복 |

- 극단값: 긴 단계 이름(40자+)·단계 40개·0.1% 미만 조각·전부 초과·자기 기준 단계 6개 이상. 쪽별 rect가 본문 한계 안, 칸 겹침·잘림 없음.
- 헤드리스 Chrome `--print-to-pdf` 쪽 수 == 화면 `.p-page` 수.
- 글꼴 폭: `letter-spacing: 0.12em` 주입으로 Windows 글꼴 폭을 흉내 내 좁은 머리 칸(22mm 「실패」 등)이 꺾이지 않는지 본다.
- 응답 파싱: 실제 `/report` JSON이 `ReportSchema`를 통과(S-D 갭).
- 요약판: 지표 칸 목표 줄이 길어졌으므로(§5) 기준이 걸린 run의 요약판이 여전히 1장인지, 목표 줄이 칸 밖으로 넘치지 않는지 본다.
- 단계 기준만 가진 run(run 수준 기준 없음)·오류율 기준 없이 한 단계가 대부분 실패하는 run도 한 번씩 인쇄해 머리 문구·각주·`▲` 실패 칸을 확인한다.

## 10. 내가 정한 것 (사용자가 읽으며 확인)

1. 자기 기준이 1초 이하인 단계가 세 구간 표에 섞이면 두 칸을 합쳐 「이내」로 적는다(§7.3).
2. 기준 우선순위 p95 → p99 → p50(§6.2). p50만 건 run의 안내 줄은 "초과가 50% 이하여야 통과".
3. 안내 줄의 초과 비율은 소수 2자리부터(§7.5), 표 안 비율은 1자리 — 단 판정 표시가 걸리는 칸은 기준과 글자가 같아지면 자릿수를 늘린다.
4. 「전체 요청」 행에는 ▲를 쓰지 않고 판정 미달이면 굵은 붉은 글씨만.
5. 단계 기준 줄은 5줄까지, 단계마다 그 경계를 만든 기준 하나만.
6. `speed_bands`가 없는 응답이면 절을 내지 않고 번호를 밀지 않는다.
7. 「1초」 빠름 경계는 고정(설정 없음).
8. 지표 칸의 큰 숫자는 그대로 두고 목표 줄 끝에 `(측정 3,040ms)`를 덧붙인다(§5).
9. 안내 줄 끝말은 「이 기준은 통과/미달입니다」(시안의 「통과/미달입니다」에서 바꿈 — 다른 기준 때문에 종합 판정이 다를 수 있어서).
10. 오류율 기준이 없는 run에서 실패가 있는 단계는 실패 칸에 `▲`(2절의 「▲ 오류 있음」과 같은 규칙). 이름을 적는 각주는 실패 비율 10% 이상인 단계가 있을 때만.
11. 기준·측정값 글자가 소수 6자리에서도 같으면 `(기준과 차이가 아주 작음)`을 붙인다.

## 10b. 계획에서 챙길 것 (spec 리뷰가 짚은 구현 함정)

- `PrintDocument.tsx`는 모르는 표 id를 2절 표로 그린다(조각 렌더 두 곳) — 새 표 id를 그 두 곳과 `standardBlocks`에 함께 넣는다.
- 측정 시트 id는 새 접두사로(`row:${stepId}`와 겹치지 않게).
- 절 제목이 컴포넌트 안 고정 문자열이라, 번호를 조건부로 미는 데 `doc`(구간 유무)을 제목까지 내려야 한다.
- 리뷰가 "쌍 표기(US1)와 속도 구간(US2–4)은 독립이니 두 슬라이스로"를 권했다. 사용자가 한 범위(B)로 골랐으므로 한 슬라이스로 두되, 계획은 US1 task를 앞에 두고 각각 독립 green 커밋으로 나눈다.
