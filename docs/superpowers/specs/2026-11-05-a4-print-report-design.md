# A4 인쇄 보고서 슬라이스 1 — 측정결과 보고서 (고정 양식) 설계

- 날짜: 2026-11-05 · 슬라이스: `a4-print-report` · 유형: `user-path`
- 전체 기능은 2개 슬라이스로 나눈다(사용자 결정 2026-11-05):
  - **슬라이스 1(이 문서)**: 인쇄 화면 + 쪽 나누기 + 측정결과 보고서 표준판/요약판. UI만(컨트롤러·엔진 0-diff).
  - **슬라이스 2(후속)**: 비교 보고서 표준판/요약판 + 응답 속도 구간(컨트롤러 `speed_bands` 신규 필드) — §14에 이월 사항.
  - 그 다음: 섹션·문구 편집 + 팀 공유 저장(별도 슬라이스, 사용자 결정 = 서버 저장).
- 시안(사용자 확인 완료): `docs/superpowers/specs/assets/2026-11-05-a4-print-report/`
  - `measure-report-v3.html` — 측정 1쪽 **확정본**
  - `measure-report-v1.html` — 측정 2쪽 참고(§5 "단계별 응답 속도 분포"는 슬라이스 2로 이월, 이 슬라이스엔 없음). v1의 1쪽은 v3로 대체됨.
  - `compare-report-v2.html` — 슬라이스 2 참고(화살표 규칙 수정판 + 경계 사례 패널). `compare-report-v1.html`은 화살표 결함이 있는 구판(보관용).

## 사용자 스토리 (US)

- **US1**: QA가 종료된 run의 결과를 팀·발주처에 넘길 때 리포트 화면에서 측정결과 보고서를 A4로 출력해 — 성공하면 설명을 덧붙이지 않아도 되는 A4 세로 문서(종이/PDF)를 얻고, 1쪽만 읽어도 종합 판정·기준 대비 지표·문제 단계가 보인다. 쪽 경계·꼬리말을 넘거나 잘리는 내용이 없고, 흑백으로 출력해도 ●▲✕와 글자로 정상/주의/문제가 구분된다. 단계가 30개를 넘거나 이름이 길어도 표가 잘리거나 겹치지 않고 다음 쪽으로 이어지며(머리줄 반복), 요약판은 문제 큰 상위 최대 8개 + 나머지 한 줄로 1장을 지킨다.
- **US2**: 운영자가 여러 단계에서 서로 다른 오류가 섞인 run의 보고서를 볼 때 — 어느 단계에서 어떤 응답 코드가 몇 건, 언제부터 났는지(예: "⑤ 신청 제출 — 503 2,880건, 4분부터")를 단계별 표와 시간 차트에서 바로 찾는다. 응답 코드 열은 그 측정에서 실제로 나온 코드만이고, 도구가 오류로 세지 않은 응답·세었는지 확정할 수 없는 응답은 오류로 센 응답과 구분돼 보인다.
- **US4(측정 절반)**: QA가 행정 부서에 돌릴 요약만 필요할 때 요약판을 골라 — 측정 보고서 1쪽 내용(종합·지표·단계 표)만 담긴 A4 1장을 얻는다. *(US3 비교 보고서와 US4의 비교 절반은 슬라이스 2.)*

> US 원안 대비 변경(사용자에게 고지함): "상위 8개" → "상위 최대 8개"(1장을 지키려 6·4개로 줄일 수 있음, §9), US2의 "오류로 세지 않은 응답"에 "세었는지 확정할 수 없는 응답" 추가(§6.1 — 엔진이 코드별 오류를 기록하지 않음).

## 1. 의도와 이유

사용자(QA)는 측정 결과를 넘기려다 "각각이 뭘 의미하는지 설명할 생각에" 결국 넘기지 못했다. 목표는 공공기관 제출 양식 자체보다 **설명 없이 스스로 읽히는 결과물** — 행정 부서를 포함한 여러 사람이 같이 보고 어디가 문제인지 한눈에 잡는 문서다. 결과를 볼 때 가장 아팠던 점은 오류를 "에러"로 퉁쳐서 **어느 단계에서 어떤 코드(503 등)가 났는지 모르는 것**.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 측정결과 보고서 **표준판**(여러 쪽)·**요약판**(1장)을 A4 세로로 화면 미리보기 + 브라우저 인쇄(PDF 저장 포함).
- 단계 × 응답 코드 표, 오류가 처음 나타난 시점, 오류 집계에서 빠진(또는 불확실한) 응답의 경고.
- 숫자 옆 쉬운 말 풀이 상시 표기, 결론 문장을 데이터에서 결정론적으로 생성.

**비목표**
- 비교 보고서, 응답 속도 구간(→ 슬라이스 2).
- 섹션 켜기/끄기·순서·문구 편집·단계 별칭·팀 공유 저장(→ 그 다음 슬라이스).
- 실시간(running) 화면의 오류 단계별 표시(별도 영역, 사용자 동의).
- 서버 PDF 생성, 로고, 표지, 데스크톱 셸(`desktop/`) 코드 변경, 엔진/컨트롤러 변경.

**안티목표 (돌아가도 실패)**
- 미리보기와 실제 출력이 다르다(인쇄 때만 쪽이 더 생기거나 잘림).
- 숫자는 있는데 읽는 사람이 해석을 물어봐야 한다.
- 도구가 오류로 세지 않았거나 확정할 수 없는 이상 응답이 "정상"처럼 보인다.
- 색만으로 의미 전달(흑백·배경색 미출력 시 정보 소실).
- 외부로 나가는 문서에 환경 변수 값·토큰·URL 크리덴셜이 찍힌다.

## 3. 사용자가 정한 것

1. HTML 인쇄 전용 화면 + 브라우저 인쇄/PDF 저장.
2. 시안 내용·배치(measure v3 1쪽 + v1 2쪽 구성).
3. 오류율 풀이: "전체 요청 중 실패한 비율. 실패 N건 / 전체 M건"("요청 100건 중" 금지).
4. 응답 코드 열은 실제 나온 코드만(500번대 고정 금지).
5. 단계가 많으면: 표준판은 다음 쪽으로 이어짐(머리줄 반복·행 분할 금지), 요약판은 상위 최대 8개 + 나머지 한 줄. 긴 이름은 줄바꿈/말줄임.
6. 측정 요약판 = 표준 1쪽 내용.
7. 슬라이스 분할(측정 먼저, 비교+속도 구간 다음), 이번엔 고정 양식만.
8. 아래 "내가 정한 것"(§12) 1–9번은 사용자에게 고지 후 이견 없음.

## 4. 진입점과 화면

- `ReportView` 헤더(다운로드 메뉴 옆)에 [보고서 인쇄] 링크 버튼 → `/runs/:id/print`. `ReportView`는 terminal run에서만 렌더되므로 진입은 자연히 terminal 한정.
- 경로 `/runs/:id/print`는 `routes.tsx`에서 **`Layout` 밖** 최상위(선례: `/monitors/:id/display`). 직접 URL로 열었을 때:
  - run 조회 → status가 terminal(`completed`/`failed`/`aborted`)이 아니면 보고서를 만들지 않고 "측정이 끝난 뒤 출력할 수 있습니다" + 돌아가기.
  - 리포트 fetch 실패: `role="alert"` 배너에 사유. 로딩: `role="status"`.
- 화면 상단 도구 줄(인쇄 시 숨김, `@media print { display:none }`): [표준판 | 요약판] 전환(URL `?kind=standard|summary`, 기본 standard), [인쇄 / PDF 저장](`window.print()`), [돌아가기](`/runs/:id`), 안내 한 줄 "인쇄가 안 되면 브라우저에서 이 주소를 여세요" + 주소를 **선택 가능한 텍스트**로 표시 + [주소 복사](데스크톱 셸 대비 — §10). `navigator.clipboard`는 보안 컨텍스트에서만 있으므로(LAN 바인드 `http://192.168.…` 컨트롤러, ADR-0041) 없거나 실패하면 버튼을 숨기고 텍스트만.
- 회색 배경 위에 A4 쪽들을 세로로(시안과 동일).
- 데이터: 기존 `GET /api/runs/:id` + `GET /api/runs/:id/report`(기존 훅). 새 API·필드 없음.

## 5. 문서 구성

**공통 머리**(표준판 1쪽·요약판): 작은 글씨 "성능 측정 결과 보고서" · 제목 = 시나리오 이름(`scenario_yaml` 스냅샷의 `name` — 측정 당시 이름, 파싱 실패 시 `GET /api/scenarios/:id`의 현재 이름) + " 부하 측정" · 오른쪽 "문서번호: ______ / 작성일 <출력 날짜>" · 메타 4칸:
- **대상 시스템**: 시나리오 http 단계 URL마다 `resolveForDisplay` 결과를 `new URL()`로 파싱해 성공하면 `host`(호스트+포트)만 취한다(userinfo·경로·쿼리·프래그먼트는 URL 객체에서 아예 읽지 않음). 파싱 실패(미해결 토큰 등)면 **풀지 않은 원형 템플릿**에서 `scheme://`가 있으면 그 뒤부터, 없으면 맨 앞부터 첫 `/`·`?`·`#` 앞까지를 잘라 그중 마지막 `@`까지를 지운 문자열(예: `${BASE_URL}/x` → `${BASE_URL}`, `http://{{h}}:8080/a` → `{{h}}:8080`). 결과가 빈 문자열(상대 경로 `/login` 등)이면 건너뛴다. 중복 제거 후 최대 2개 + "외 N곳", 없으면 "–". 단위 테스트: 미해결 호스트 + `?token=${TOKEN}`, `https://u:p@h/x` → `h`.
- **측정 일시**: `started_at`–`ended_at`(같은 날이면 끝은 시각만, 둘 중 null이면 그 자리 "–" — pending 중 중단된 run), 상태가 aborted/failed면 뒤에 "(중단됨)"/"(실패)".
- **부하 조건**: §5.4 요약 한 줄(예: "동시 사용자 200명 · 10분", "초당 50회 목표 · 5분", "동시 사용자 곡선 최대 300명 · 15분").
- **측정 식별**: `#끝6자` + 라벨이 있으면 `· "라벨"`(시안 표기).

**공통 꼬리말**: "<제목> · #끝6자" · "Handicap 부하 테스트 도구로 생성" · "n / N".

### 5.1 표준판 구성 (순서 고정)
1. **종합 결과**
   - 판정 상자 상태 — "기준 있음" = `profile.criteria`에 값이 하나라도 있음(서버 `Criteria::has_any` 미러: `rps_warmup_seconds`는 제외, `step_criteria`는 비어있지 않을 때만 — 순수 함수 `criteriaHasAny(profile)` 신설, 폼 상태용 `criteriaHasValue` 재사용 금지):
     - `summary.count == 0` → verdict 유무와 무관하게 **판정 안 함**("요청이 실행되지 않아 판정하지 않았습니다") — 서버는 0건 completed run에도 오류율 0·p95 0으로 통과 verdict를 만들 수 있다(`report.rs`), 그걸 초록 "적합"으로 찍지 않는다.
     - verdict 있음 → **✕ 부적합**(빨강, "평가한 기준 N개 중 M개 미달") / **● 적합**(초록, "평가한 기준 N개 모두 달성"). N = `verdict.criteria.length`. 기준은 있었으나 평가되지 않은 항목(서버가 건너뛴 `min_window_rps`·실행 0회 단계 기준 등 — `profile.criteria` 항목 중 verdict에 대응 행이 없는 것)은 "그 밖의 기준" 표에 "평가 불가(데이터 부족)"로. 대응 판정 키 = `(metric, target ?? null, op, threshold)`; run-level 필드→verdict metric 이름 매핑은 `max_p50_ms→p50_ms`·`max_p95_ms→p95_ms`·`max_p99_ms→p99_ms`·`max_error_rate→error_rate`·`min_rps→rps`·`max_4xx_rate→4xx_rate`·`max_5xx_rate→5xx_rate`·`max_4xx_count→4xx_count`·`max_5xx_count→5xx_count`·`min_window_rps→min_window_rps`(정확한 문자열은 plan에서 `report.rs::evaluate_criteria`로 확정 — threshold는 rate 분수·ms 정수를 f64로 비교).
     - verdict 없음 ∧ 기준 있음 ∧ status가 aborted/failed → **판정 안 함**(회색, "측정이 중단되어(또는 실패해) 판정하지 않았습니다").
     - verdict 없음 ∧ 기준 있음 ∧ completed → **평가 불가**(회색, "평가할 수 있는 기준이 없었습니다(데이터 부족)") — `report.rs`는 모든 기준이 건너뛰어지면 completed여도 verdict를 만들지 않는다.
     - 기준 없음 → **기준 미설정**(회색, "판정 기준을 정하지 않은 측정").
   - 요약 2–5줄(§7, "(자동 작성)" 표기 — "수정 가능" 문구 없음).
   - 지표 4칸: 처리량(건/초) · 평균 응답시간 · 95% 응답시간 · 오류율. 각 칸 = 이름 · 값 · 쉬운 말 풀이 · 목표 줄("목표 3초 이하 ● 달성 / ✕ 미달", 판정 상자가 판정 안 함이면 "목표 3초 이하 (판정 안 함)", 평가 불가이거나 그 기준 행이 verdict에 없으면 "목표 3초 이하 (평가 불가)", 기준 없으면 "목표 없음 (참고값)"). 칸↔기준 매핑: 처리량↔`rps`, 95%↔`p95_ms`, 오류율↔`error_rate`, 평균↔없음(항상 참고값).
   - **그 밖의 기준** 표(해당 시만): 4칸에 매핑되지 않는 run-level 기준(`p50_ms`·`p99_ms`·`4xx_rate`·`5xx_rate`·`4xx_count`·`5xx_count`·`min_window_rps`)과 step-level 기준(상한 `max`·하한 `min` 모두) — 열: 기준(쉬운 말 이름, 단계 기준이면 "<단계> · ") · 목표 · 측정값 · 판정. 측정값·판정은 **verdict의 해당 행에서만** 읽는다(UI가 서버 공식을 재구현하지 않음 — `min_window_rps`의 warm-up/첫·끝 초 제외, 4xx/5xx 율의 HTTP-only 분모는 서버 전용). verdict가 없거나 그 행이 없으면 측정값 "–", 판정 "판정 안 함"/"평가 불가"(판정 상자 규칙과 같은 문구). 행이 6개를 넘으면 미달 행 먼저, 나머지는 "외 N개 기준 모두 달성"(표준판 마지막 쪽 부록에 전체).
2. **어디가 문제인가 — 단계별 결과**: 단계 × 응답 코드 표(§6) + 범례 + 경고 상자(§6.4, 해당 시) + 열 묶음 각주(§6.2, 해당 시).
3. **시간에 따른 변화**: §6.6 차트 + "읽는 법" 문장 1줄(§7.2).
4. **측정 조건** 상자(§5.4 전체) / **이 결과로 말할 수 있는 것·없는 것** 상자(`report.narrative.can_claim`/`cannot_claim` 코드 → 기존 `ValidityBanner`가 쓰는 ko 매핑 재사용, 두 목록이 모두 비었거나 `narrative` 키 부재면 상자 생략).
5. **용어 풀이**: 문서에 실제 등장한 용어·코드만(처리량, 평균/95% 응답시간, 오류율, 등장한 각 응답 코드, 응답 없음, 응답 받은 뒤 실패, 검사 없음, 확인 불가).
6. **부록: 그 밖의 기준 전체**(1.의 표가 잘렸을 때만).
7. 서명란(시험자·검토자·확인자) — 마지막 쪽 끝.

### 5.2 요약판
공통 머리 + 1.(종합: 판정·요약·지표 4칸, "그 밖의 기준"은 미달 행만 최대 3행) + 2.(단계 표, §8 상위 규칙). **반드시 1장**(§9).

### 5.3 표시 단위
- 시간: 1초 이상 = 소수 1자리 "2.4초", 1초 미만 = 소수 2자리 "0.84초", 0.01초 미만 = 정수 ms "7ms"(0이면 "1ms 미만"). 기준 목표도 같은 함수.
- 건수: 천 단위 쉼표. 비율: 소수 1자리 %, 0이 아닌데 0.1% 미만이면 "0.1% 미만".

### 5.4 측정 조건 상자
`normalizeProfile`은 throw하므로 `ProfileSchema.safeParse(report.run.profile)` 사용, 실패 시 상자에 "설정 정보를 읽을 수 없음". 내용: 부하 모델(`deriveLoadMode` — 동시 사용자 고정/곡선, 초당 목표 고정/곡선) · 크기(VU 또는 RPS, 곡선이면 최대값·단계 수) · 기간(`profileDurationSeconds`) · 시작 늘림(ramp_up, 있으면) · 단계 사이 쉼(think time, 있으면) · 요청 제한 시간 · 워커 수(`report.worker_breakdown.length` ≥ 2면 그 수, 아니면 open-loop `worker_count` > 1이면 그 수, 둘 다 아니면 생략) · 데이터 바인딩 수(있으면 "데이터 N개 연결"). **환경 변수는 값을 찍지 않는다** — "환경 변수 N개 사용"만.

## 6. 단계 × 응답 코드 표

### 6.1 오류 분류 (엔진 의미론 기반)
엔진(`executor.rs`)은 응답 코드로 오류를 판정하지 않는다. 오류가 되는 경우: ① 전송 실패(코드 0) ② 본문 읽기 실패(실제 코드 보유) ③ status 검사 불일치 ④ status 검사 통과(또는 없음) 후 값 꺼내기(extract) 실패. 리포트는 단계별 `status_counts`(코드별 건수)와 `error_count`(총 오류)만 있고 **코드별 오류 수는 없다**(`aggregator.rs`). 그래서 단계마다 시나리오 YAML(**그 run 자신의 `scenario_yaml`**)에서 두 사실을 읽고:
- `S` = status 검사 코드 집합(status 검사 항목 전부 — 저장 형태 `{status: N}`, 아래 참조; 코드는 `Number()`로 변환하고 유한 정수가 아니면 그 항목은 무시), `E` = **실패할 수 있는** extract 존재 여부 = `from`이 `body`·`header`·`cookie`인 extract가 하나라도 있음(`from: status` extract는 실패 경로가 없어 제외 — `scenario.rs` `Extract::Status`).
- 이 두 사실은 **관대한 YAML 읽기**로 얻는다: `yaml` 패키지로 파싱한 일반 객체를 `steps`/`do`/`then`/`elif[].then`/`else`/`branches[].steps`로 재귀하며 `id`·`name`·`request.method`·`request.url`·`assert`·`extract`만 읽는다(현재 Zod 모델이 거부하는 옛/새 스냅샷에도 분류가 살아남게). YAML 자체가 깨졌을 때만 "파싱 실패" 취급.
- **저장된 YAML의 assert 형태는 `{status: 200}`**(엔진 수동 직렬화 `scenario.rs` `impl Serialize for Assertion`, UI 작성기도 같음) — `{kind:"status", code}`는 UI 정규화(`yamlDoc.ts::normalizeAssertion`) **이후**의 모델 형태다. 관대한 읽기는 각 assert 항목에 기존 `normalizeAssertion`을 적용(필요 시 export)하거나 `{status: N}`을 직접 읽고, `{kind, code}`도 허용한다. extract는 `from` 태그(`body`/`header`/`cookie`/`status`). **단위 테스트는 손으로 만든 모델 객체가 아니라 실제 저장 YAML 문자열**(엔진 직렬화 형태)을 입력으로 — 형태 오인 시 S가 늘 비어 모든 4xx/5xx가 "안 셈"으로 찍히는 회귀를 잡는다(이빨 실증).

셀(단계, 코드 c) 분류:
| 조건 | 분류 | 표시 |
|---|---|---|
| c = 0 | **오류로 셈** | 열 "응답 없음 (코드 없음)" |
| S 비어있지 않음 ∧ ∃w∈S, w≠c | **오류로 셈** (검사 불일치 — 엔진은 첫 불일치에서 오류) | 빨강 계열 |
| S 비어있지 않음 ∧ ∀w∈S, w=c | **기대한 응답** (이 코드 자체는 오류 아님) | 일반 칸 |
| S 비어있음 ∧ c는 4xx/5xx ∧ ¬E | **오류로 안 셈** | 빗금 + 점선 테두리 + 셀 안 "안 셈" |
| S 비어있음 ∧ c는 4xx/5xx ∧ E | **확인 불가** (값 꺼내기 실패로 셌을 가능성 높음) | 점선 테두리 + 셀 안 "?" |
| S 비어있음 ∧ c는 2xx/3xx | 일반 칸 | 일반 칸 |
| c < 100 (0 제외)·1xx·c ≥ 600 (비표준) | S 있으면 위 S 규칙 그대로. S 비어있음 ∧ ¬E → **오류로 안 셈**, S 비어있음 ∧ E → **확인 불가** (즉 4xx/5xx와 같은 취급) | 열은 §6.2 "기타 코드" 계열 |

- **잔차 열** "그중: 응답 받은 뒤 실패(값 꺼내기·본문 읽기)" = `error_count − (오류로 셈 셀 합)`, 잔차 < 0 이면 0. 값 자체는 정확하다(응답을 받은 뒤 실패한 건수 전부). 불확실한 것은 **어느 코드 칸의 응답이었는지**뿐이므로, "확인 불가" 칸이 있는 단계는 잔차 칸에 "(일부는 ? 칸과 같은 응답)" 접미.
- **잔차는 분할이 아니라 겹침(subset) 열**이다: 코드 칸들의 합 = 그 단계 요청 수이고, 잔차는 그 칸들 중 일부를 다시 센 것. 표에서 잔차 열 앞에 굵은 세로 구분선 + 머리줄 "그중"으로 시각 분리하고, 범례에 "‘그중’ 열은 앞 칸들에 이미 포함된 건수입니다(더하지 마세요)".
- 본문 읽기 실패(②)는 어떤 코드에서도 날 수 있어, 엄밀히는 "오류로 안 셈"·"기대한 응답" 칸 중 일부가 오류일 수 있다. 그 몫은 잔차에 정확히 잡히고 칸 분류는 바꾸지 않는다 — 잔차 열 소제목에 "(어느 코드였는지는 기록되지 않음)" *(내 판단: 본문 읽기 실패는 드물고, 엔진이 코드별 오류를 기록하지 않는 한 이 이상 정확할 수 없다)*.
- 2xx/3xx 열 이름은 "2xx", "3xx"(소제목 "성공 계열"/"이동 계열") — "정상"이라 부르지 않는다(검사가 201을 기대하면 200이 오류이기 때문).
- **시나리오 파싱 실패** 또는 단계가 YAML에 없음: 그 단계는 S·E 미상 → 4xx/5xx 셀 = "확인 불가", 코드 0만 오류로 셈, 표 아래 각주 "시나리오를 읽지 못해 일부 응답의 오류 여부를 확정하지 못했습니다".

### 6.2 열 구성
- 열 = run 전체에서 >0인 코드. **고정 열**: 2xx 전체 한 열, 3xx 전체 한 열, "응답 없음"(코드 0), 잔차(어느 단계든 >0일 때만) — 각각 해당 건수가 있을 때만. **개별 코드 후보 K**: 4xx 각 코드, 5xx 각 코드, 비표준 코드(1xx·<100·≥600) 각 코드. 정렬: 2xx, 3xx, 4xx 오름차순, 기타 4xx, 5xx 오름차순, 기타 5xx, 기타 코드, 응답 없음, 잔차.
- **열 상한 7개**(고정 열 포함 전체). 접기 알고리즘(결정론적, 순수 함수):
  1. `B = max(7 − 고정 열 수, 3)`. `|K| ≤ B`면 접지 않는다.
  2. K를 run 전체 건수 내림차순(동률은 코드 오름차순)으로 정렬. `f = 1`부터 반복: 앞 `B − f`개를 개별 열로 두고 나머지를 접힌 집합 F로; F에 등장하는 계열 수(4xx / 5xx / 기타 코드)를 `f'`라 할 때 `f' ≤ f`면 종료, 아니면 `f = f'`로 다시(최대 3회에 수렴).
  3. 계열별로 F에 속한 코드가 1개뿐이면 접지 않고 그 코드 이름 그대로 한 열("기타 4xx" 이름을 1개짜리에 붙이지 않음), 2개 이상이면 "기타 4xx"/"기타 5xx"/"기타 코드" 한 열.
  4. 접힌 칸의 분류 = 구성 셀 중 가장 강한 것(오류로 셈 > 확인 불가 > 오류로 안 셈 > 기대한 응답), 표 아래 각주에 접힌 코드 목록과 각 건수.
  - 예(단위 테스트 표에 그대로 포함): 고정 열 = 2xx·응답 없음·잔차(3개) → B = 4. K 건수 = 503:2880, 404:120, 500:60, 504:40, 400:10, 401:5, 403:3, 502:2. f=1 → 개별 3개(503·404·500), F = {504,400,401,403,502} → 계열 2개(4xx·5xx), f' = 2 > 1 → f=2 → 개별 2개(503·404), F = {500,504,400,401,403,502} → 계열 2개 ≤ 2 종료. 결과 열: 2xx · 404 · 기타 4xx(400·401·403) · 503 · 기타 5xx(500·502·504) · 응답 없음 · 그중 잔차 = 7개.
- 코드 풀이 사전(ko.ts): 400 잘못된 요청 · 401 인증 필요 · 403 권한 없음 · 404 없는 주소 · 405 허용 안 된 방식 · 408 요청 시간 초과 · 409 충돌 · 413 요청이 너무 큼 · 415 지원 안 하는 형식 · 422 처리할 수 없는 내용 · 429 요청이 너무 많음 · 500 서버 오류 · 501 지원 안 함 · 502 중계 서버 오류 · 503 서버가 바쁨 · 504 중계 시간 초과. 그 외 = 숫자만(용어 풀이 "표준 HTTP 응답 코드").
- "응답 없음"은 연결 거부·시간 초과·DNS 실패 등을 포함(용어 풀이에 명시). run 전체 `error_kinds`가 있으면 용어 풀이 아래 "응답 없음 내역: 시간 초과 N · 연결 거부 M …"(단계별 분해는 데이터에 없음).

### 6.3 단계 상태 (여러 개면 두 줄로 함께)
기준값은 **`profile.criteria`에서 읽는다**(verdict 유무와 무관 — 중단된 run에도 같은 잣대; 판정 상자만 verdict 기준).
- **✕ 오류**: 단계 오류율 > 그 단계 오류 기준. 오류 기준 = step-level `error_rate` **상한(`op:"max"`)** 기준(target=그 단계) → run-level `max_error_rate` → 없음.
- **▲ 느림**: 단계 p95 > 느림 기준. 느림 기준 = step-level `p95_ms` **상한** 기준 → run-level `max_p95_ms` → 없음. (p50/p99 기준, 하한 `op:"min"` 단계 기준은 ✕/▲를 만들지 않고 "그 밖의 기준" 표에서만 다룬다.)
- **▲ 오류 있음**: 오류 기준이 없고 단계 오류율 > 0.
- **▲ 안 센 응답 / ▲ 확인 불가**: 그 단계에 "오류로 안 셈"/"확인 불가" 셀이 있음.
- **● 정상**: 위 해당 없음. 오류가 0이 아니면 아래 작게 "오류 0.25%".
- **– 실행 안 됨**: 시나리오엔 있으나 `report.steps`에 없음(분기 미진입 등) — 한 행, 숫자 "0", 문제 아님.
- 행 배경: ✕ = 연한 빨강, ▲ = 연한 주황. 셀: 오류로 셈 = 연한 빨강, 그 단계 "오류로 셈" 중 최대 = 진한 빨강(흰 글자).
- **흑백·배경 미출력 생존**: 인쇄 CSS에 `print-color-adjust: exact`(+`-webkit-`)를 두되, **배경 없이도 의미가 남게**: 상태 = 기호+글자, "오류로 셈" 최대 칸 = 굵은 글자 + 실선 테두리, "안 셈" = 점선 테두리 + 글자 "안 셈", "확인 불가" = 점선 + "?". 빗금 색은 명도 대비가 남는 진한 주황(`#c77700` 계열 2px 선).
- 범례: 표 아래 한 줄, 나타난 분류만.

### 6.4 경고 상자 (해당 시, 표 바로 아래)
- "오류로 안 셈" 셀이 있으면: "**확인 필요:** '<단계>'의 <코드> 응답 N건은 응답 코드 검사가 없어 오류율에 포함되지 않았습니다. 포함하면 오류율은 A% → B%가 됩니다. 이 단계에 응답 코드 검사를 추가하길 권합니다."(여러 단계면 건수 큰 순 2개 + "외 N곳", B = 전체 기준 재계산).
- "확인 불가" 셀이 있으면: "'<단계>'의 <코드> 응답 N건은 오류로 세었는지 확정할 수 없습니다(응답 코드 검사 없이 값을 꺼내는 단계). 응답 코드 검사를 추가하면 정확히 셀 수 있습니다."

### 6.5 행·이름
- 순서: 시나리오 순서(`flattenHttpSteps`), YAML에 없는 `report.steps` 항목은 맨 뒤(id 그대로 표시).
- 번호: 1–20 = ①–⑳, 21부터 "21.". 요약판에서 일부만 보여도 원래 번호 유지.
- 이름: 최대 3줄 줄바꿈, 넘으면 말줄임. 이름 아래 작은 줄 = `METHOD path` — path는 **풀지 않은 원형**(`{{id}}` 그대로)에서 scheme+host를 떼고(경로가 `${BASE_URL}/x`면 `/x`), 쿼리 문자열은 `?…`로 줄임, 1줄·가운데 말줄임(앞 60%·끝 40%). (§10 보안)
- 숫자 열 폭 고정(이름 열이 줄어들고 숫자 열은 안 줄어듦).

### 6.6 시간에 따른 변화 차트 (인라인 SVG)
- 데이터: `report.windows`(초·단계별 `count`·`error_count`). X축 = run 시작 기준 경과 시간.
- 묶음: 막대 수 ≤ 120이 되도록 초를 N초로 묶음(N ∈ {1,2,5,10,15,30,60,120,300}, 최소값). 값은 묶음 평균 건/초.
- 선 = 처리량(전체 count/초, 왼쪽 축). 막대 = 오류/초(오른쪽 축), 2계열 쌓기: "가장 오류가 많은 단계"(진한 빨강, 범례에 단계 이름) + "그 밖의 단계"(연한 빨강). 오류 0이면 막대·오른쪽 축 없음, 범례에 "오류 없음".
- 시작 표시선: 오류 상위 단계 최대 **3개**에 대해 첫 오류 묶음 위치에 점선 + 라벨 "N분: <단계 번호> 오류 시작"(라벨이 겹치면 세로로 엇갈림, 그래도 겹치면 뒤 것 생략). 
- 축 눈금: 시간 = 길이에 맞춰 30초/1분/2분/5분/10분/30분 간격(눈금 ≤ 8). 값 축 = 1·2·5×10ⁿ 간격(눈금 ≤ 5).
- 크기 고정: 폭 180mm × 높이 55mm.

## 7. 자동 문장 (결정론적, ko.ts)

### 7.1 요약 (최대 5줄, 순서 고정, 해당 없는 줄은 생략)
1. **판정**(verdict 있을 때): 미달 기준이 있으면 기준 종류에 맞는 동사 — 상한 기준 "**<기준>이 기준을 넘었습니다** (측정 X, 기준 Y 이하)", 하한 기준(`rps`·`min_window_rps`) "**<기준>이 기준에 못 미쳤습니다** (측정 X, 기준 Y 이상)". 미달 여러 개면 가장 위 1개 + "외 N개". 모두 달성이면 "기준 N개를 모두 지켰습니다". 판정 상자가 **판정 안 함**이면 "측정이 중단되어(실패해) 기준 판정은 하지 않았습니다", **평가 불가**면 "기준은 있었지만 평가할 데이터가 부족했습니다".
2. **문제 단계**(항상, ✕/▲ 단계가 있으면): "문제 단계: ⑤ 신청 제출(오류), ④ 첨부 업로드(느림)" — 우선순위 순 최대 3개 + "외 N개". *(US1 "1쪽만 읽어도 문제 단계가 보인다" 보장 — 오류가 흩어진 30단계 시나리오에서도.)*
3. **오류 정체**(오류가 있을 때): 오류가 가장 많은 단계 T와 그 단계의 가장 큰 "오류로 셈" 코드 c(코드 0 포함):
   - c가 있으면: "오류의 X%는 '<T>'에서 났고, 대부분 <c>(<풀이>)입니다. 시작 N분 뒤 처음 나타났습니다." 시점 = `windows` 중 step_id=T인 행에서 `status_counts[c] > 0`인 첫 초(**코드 기준**, 단계의 첫 오류 아님). 그 시점 이후 묶음(§6.6)의 50% 이상에서 c가 >0이면 "…뒤부터 계속 났습니다". 60초 미만이면 "N초 뒤".
   - T의 오류가 전부 잔차뿐이면(오류로 셈 코드 없음): "오류의 X%는 '<T>'에서 났고, 응답은 받았지만 값을 꺼내거나 본문을 읽지 못했습니다." 시점 = T의 첫 `error_count > 0` 초.
   - 점유율 < 50%면 대신: "오류가 여러 단계에 흩어져 있습니다(가장 많은 곳: '<T>' X%)."
4. **숨은 오류**("오류로 안 셈"이 있을 때): "'<단계>'에서 <코드> 응답 N건이 있었지만 응답 코드 검사가 없어 오류로 세지 않았습니다." ("확인 불가"만 있으면 "… 오류로 세었는지 확정할 수 없습니다.")
5. **느림**(▲ 느림이 있을 때): "'<단계>'는 느립니다 (95% 응답 X, 기준 Y)" + 여러 개면 "외 N개".
**맨 앞 특수 줄**(있으면 1번보다 먼저, 이 경우 나머지 줄은 해당 시에만):
- `summary.count == 0`: "요청이 하나도 실행되지 않았습니다." + run `message`(`GET /api/runs/:id`)가 있으면 " 사유: <message>" (판정·지표 칸은 그대로 "–"/0 표시).
- status가 aborted: "측정이 도중에 중단되었습니다(<경과>까지 측정)." — 경과 = `ended_at − started_at`, `started_at`이 null이면 괄호 없이 "측정이 시작되기 전에 중단되었습니다." / failed: "측정이 실패로 끝났습니다." + `message`가 있으면 사유.
줄이 하나도 없으면(정상 완료·오류 0): "오류 없이 끝났습니다. 95% 응답시간은 X입니다."

### 7.2 차트 "읽는 법" (1줄)
오류 있음: "<시작 표시선 1번>부터 빨간 막대(오류)가 생깁니다" + 그 시점 전후 처리량이 10% 이상 떨어졌으면 ", 같은 시점에 처리량 선이 내려갑니다". 오류 없음: "측정 내내 오류가 없었습니다. 선은 1초에 처리한 요청 수입니다."

모든 문장·풀이·라벨 = `ko.ts`(ADR-0035), 조사 병기형(`(으)로`·`(이)가`) 규칙 준수.

## 8. 요약판 상위 단계 선택

- 정렬 키(내림차순): 상태 등급(✕=3, ▲=2, ●=1, 실행 안 됨=0) → 오류로 셈 건수 → 안 셈/확인 불가 건수 → p95. 동률은 시나리오 순.
- 상위 N개(기본 8, §9로 6·4까지)를 고른 뒤 **시나리오 순서로** 표시.
- 아래 한 줄: 남은 단계의 상태별 개수(0인 항목은 생략) — "나머지 22개 단계: 오류 1 · 주의 2 · 정상 18 · 실행 안 됨 1 (전체 목록은 표준판)". 남은 단계가 모두 정상이면 "나머지 22개 단계: 모두 정상".

## 9. 쪽 나누기

- **브라우저 자동 분할에 맡기지 않는다.** 계약: 블록 목록(쪼갤 수 없는 블록 / 행 단위로 쪼갤 수 있는 표 블록[머리줄 높이 + 행 높이 배열]) + 쪽 본문 높이 → 쪽 배열. 이 배치 함수는 **순수 함수**(jsdom 단위 테스트 대상). 블록 높이 측정은 화면에서 숨은 측정 컨테이너(쪽과 같은 mm 폭·같은 글꼴)로 하고 `document.fonts.ready` 뒤 1회 — 측정 훅은 **라이브 전용 검증**(jsdom 레이아웃 0).
- 쪽 = 210×297mm 고정 `<div>`. 본문 높이 = 297 − 상 14 − 하 12 − 꼬리말 8 − **안전 여유 4mm**(인쇄 반올림·줄바꿈 차이 흡수).
- 인쇄 CSS: `@page { size: A4; margin: 0 }`, 쪽마다 `break-after: page`(**마지막 쪽 제외**), 쪽 `overflow: hidden` 금지 대신 측정 결과가 본문 높이를 넘는 블록은 배치 단계에서 다음 쪽으로(단일 블록이 한 쪽보다 크면 표는 행 분할, 비표 블록은 축소 없이 그 쪽 단독 배치 + 개발 콘솔 경고).
- 표 행 분할: 남은 높이에 들어가는 행까지, 다음 쪽 첫머리에 머리줄 반복 + 표 제목 옆 "(이어짐)". 범례·경고 상자는 표 마지막 조각 뒤.
- **요약판 1장 규칙**: 배치 결과가 2쪽 이상이면 아래 사다리를 한 칸씩 적용하며 매번 재배치, 1장이 되는 첫 칸에서 멈춘다.
  1. 열 묶음 각주 제거 → 2. 범례를 기호 3개만 남긴 한 줄로 → 3. 경고 상자(§6.4)를 한 줄 요약("확인 필요: 응답 코드 검사가 없는 단계 N곳 — 표준판 참조")으로 → 4. "그 밖의 기준" 표를 미달 1행으로 → 5. "그 밖의 기준" 표 제거(지표 칸 아래 "그 밖의 기준 N개 중 M개 미달 — 표준판 참조" 한 줄) → 6. 요약 문장을 특수 줄 + 1·2번 줄만 → 7. 상위 N = 6 → 8. N = 4. (장식·부가 정보를 먼저 줄이고, 문제 단계 수는 마지막에 줄인다 — US1 "문제 단계가 보인다" 우선.)
  - **단계 표(상위 N + 나머지 한 줄)·판정 상자·지표 4칸·문제 단계 줄(§7.1의 2번)은 어느 칸에서도 생략하지 않는다.**
  - 8칸 뒤에도 넘치는 경우는 이 규칙상 구성 불가(머리+판정+지표+4행 표+요약 3줄은 A4 1장의 절반 이하)로 보고, 개발 콘솔 경고 + 그대로 2쪽 출력(단위 테스트로 사다리 각 칸이 높이를 줄이는지 검증).
  - 화면 도구 줄에 적용된 칸이 있으면 "1장에 맞추려고 일부를 줄였습니다(표준판에 전체)" 안내.
- 쪽번호 `n / N`은 배치 후 확정.

## 10. 제약

- **오프라인 CSP**: 외부 폰트·스크립트 금지. 시스템 글꼴 스택 `"Malgun Gothic","Apple SD Gothic Neo","Noto Sans KR",sans-serif`. 차트 = 인라인 SVG(Recharts 미사용 — 인쇄 크기 결정성).
- **보안(외부로 나가는 문서)**: 환경 변수 **값**·데이터셋 값·헤더·본문은 어디에도 출력하지 않는다. 단계 요청 줄은 풀지 않은 원형 경로(§6.5), 대상 시스템은 호스트만(§5). `resolveForDisplay` 결과에서 호스트만 뽑을 때 userinfo(`user:pass@`)·쿼리·프래그먼트는 버린다. 시나리오 이름·단계 이름·run 라벨은 사용자가 쓴 텍스트이므로 그대로(HTML 이스케이프는 React 기본).
- **흑백**: §6.3.
- **데스크톱 셸**: 데스크톱 창은 `http://127.0.0.1:<port>`를 로드한다. Windows(WebView2)는 `window.print()`가 동작할 것으로 예상하되 라이브 검증 대상이 아님(환경 없음) — 도구 줄의 "브라우저에서 열기" 안내 + [주소 복사]가 대비책. `desktop/` 코드·권한 변경 없음.
- 기존 화면 무변경(`ReportView`는 링크 버튼 1개 추가, `routes.tsx` 경로 1개 추가).
