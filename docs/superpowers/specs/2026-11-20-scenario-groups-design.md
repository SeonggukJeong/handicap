# 시나리오 그룹 (scenario-groups) — 설계

- 날짜: 2026-11-20
- 유형: `user-path`
- 크기: 정식 슬라이스 1개 (migration 1 + 컨트롤러 API + UI 목록·편집·선택 칸 + TUI 거울 1필드)
- 엔진·워커·proto·시나리오 YAML: 무변경

## 배경

시나리오가 늘면서 서비스가 다른 같은 기능의 시나리오(예: 서비스A 로그인 / 서비스B 로그인)가 한 목록에 섞여 구분이 어렵다. 사용자는 지금은 **서비스 기준**으로 나누고 싶고, 서비스 하나가 내려간 뒤에는 **업무 기준**으로 다시 나누고 싶어질 것이라고 했다(2026-11-20 대화). 즉 분류 기준은 고정이 아니고 나중에 통째로 바뀐다. 핵심 기능은 아니므로 작게 만든다.

지금 상태: 목록 화면(`ui/src/pages/ScenarioListPage.tsx`)은 검색·정렬·분류가 없는 평평한 표이고, `scenarios` 테이블은 `id,name,yaml,created_at,updated_at,version`뿐이다(`crates/controller/src/store/migrations/0001_initial.sql`).

## 사용자 스토리 (US)

- **US1**: QA가 시나리오 목록에서 서비스가 다른 같은 이름의 시나리오를 구분하려 할 때 — 성공하면 그룹에 넣은 시나리오는 위쪽에 그룹 이름 머리가 달린 접이식 묶음 상자로(폴더가 위에 오는 익숙한 순서), 그룹에 넣지 않은 시나리오는 그 아래에 상자 밖으로 지금처럼 머리 없이 나열된 것을 본다. 상자 테두리와 들여쓰기 덕에 상자 밖의 행이 위 묶음의 일부로 읽히지 않는다. 그룹을 하나도 만들지 않았으면 묶음 상자가 없고 행과 순서가 지금과 같다(「그룹 없음」이라는 묶음은 없다). 목록의 검색 칸·체크 칸과 편집 화면의 그룹 버튼은 그룹이 없어도 보인다(그래야 첫 그룹을 만들 수 있다).
- **US2**: QA가 시나리오를 만들거나 고치면서 분류하려 할 때 — 성공하면 그룹 칸에서 기존 그룹을 고르거나 새 이름을 바로 입력할 수 있고, 저장 뒤 목록에서 그 그룹 묶음 아래에 그 시나리오가 있는 것을 본다. 그룹을 미리 만들어 두는 절차는 없다.
- **US3**: QA가 분류 기준을 서비스에서 업무로 바꾸려 할 때 — 성공하면 목록에서 여러 시나리오를 체크해 한 번에 다른 그룹으로 옮기고, 그룹 이름도 한 번에 바꿀 수 있으며, 옮긴 뒤 목록이 새 묶음으로 보인다.
- **US4**: QA가 많은 시나리오 중 하나를 찾으려 할 때 — 성공하면 검색 칸에 이름 일부를 넣었을 때 맞는 시나리오만(접힌 그룹 안의 것도 펼쳐져) 보인다.
- **US5**: QA가 스케줄·모니터 보드에서 시나리오를 고를 때 — 성공하면 선택 칸의 항목이 그룹 이름 아래 묶여 보여 같은 이름의 시나리오를 구분해 고를 수 있다.

## 목표 / 비목표 / 안 되는 것

- 목표: 위 US1–5.
- 비목표(이번에 안 함):
  - 태그(시나리오당 여러 분류)·중첩 폴더·그룹 순서 직접 정하기·그룹 색.
  - 보드 파일(`handicap-bundle` v1)에 그룹 싣기 — 모르는 키 거부 형식(ADR-0054)이라 형식 변경이 필요하다. 가져온 시나리오는 그룹 없이 들어온다. roadmap §B에 연기로 기록.
  - 터미널 모니터(TUI)에서 그룹 보여 주기 — TUI는 응답 거울에 필드만 받는다(아래 §와이어).
  - 실행 목록·리포트·비교·내보내기에 그룹 표시.
  - 정렬 기준 바꾸기(목록 안 순서는 지금처럼 최근 수정 순).
- 안 되는 것(이렇게 되면 실패):
  - 그룹을 쓰지 않는 사용자의 목록에서 행·순서·기존 동작(복제·삭제·실행 목록)이 달라지는 것. 새로 보이는 것은 검색 칸·체크 칸·편집 화면의 그룹 버튼뿐이어야 한다.
  - 그룹을 바꿨다고 시나리오가 「수정됨」이 되거나 버전이 올라가는 것(그룹은 내용이 아니라 정리용 표지다).
  - 그룹 이름을 바꾸거나 옮기는 중 시나리오가 사라지거나 다른 그룹에 섞이는 것.

## 접근 (검토한 것과 고른 것)

| 접근 | 장단 | 결정 |
|---|---|---|
| **A. 시나리오당 그룹 이름 1칸 + 여러 개 한꺼번에 옮기기** | 가장 작다. 접이식 묶음이 「섞임」을 직접 푼다. 기준 전환은 일괄 이동·이름 바꾸기로. 한 시점에 기준 1개 | **채택** (사용자 선택 2026-11-20) |
| B. 태그 여러 개 + 필터 | 두 기준 공존. 입력·관리 UI가 크고 입문자에게 어렵다. 서비스 축은 곧 사라질 예정이라 과하다 | 기각 (나중에 A의 칸을 태그로 넓히는 길은 남는다) |
| C. 이름 규칙(`서비스A/로그인`)으로 자동 묶기 | DB 변경 0. 기준을 바꾸려면 시나리오 이름을 전부 고쳐야 하고 이름은 run 기록·스케줄 표시에도 쓰인다 | 기각 |
| D. 서비스 칸 + 업무 칸 고정 2개 | 세 번째 기준이 생기면 다시 고쳐야 한다 | 기각 |
| E. 폴더 트리 | 별도 테이블·트리 UI·이동 규칙. 가장 크다 | 기각 |

그룹을 **별도 테이블로 두지 않는다**. 그룹은 시나리오 행의 글자 칸 하나이고, 「그룹 목록」은 시나리오 목록에서 서로 다른 값을 모은 것이다. 그래서 빈 그룹은 존재하지 않고(마지막 시나리오가 빠지면 그룹도 사라진다), 그룹 만들기·지우기 절차가 없다. 선례: run 라벨(ADR-0052, 단일 TEXT 칸).

## 설계

### 1. 저장 (migration 0026)

- `scenarios.group_name TEXT`(NULL 허용, 기본 NULL). SQL 예약어 `GROUP`을 피해 칸 이름은 `group_name`.
- Rust 가드 ALTER(`ensure_scenarios_group_name`) — `ensure_runs_label`(migration 0021, `crates/controller/src/store/mod.rs`)과 같은 모양: `pragma_table_info('scenarios')`에 칸이 없을 때만 `ALTER TABLE scenarios ADD COLUMN group_name TEXT`. `connect()`의 0025 뒤에 배선. 멱등 테스트 1건(`ensure_runs_label_is_idempotent` 모양).
- NULL = 그룹에 넣지 않음. 빈 문자열은 저장하지 않는다(정규화에서 NULL로).

### 2. 그룹 이름 규칙 (서버가 단일 소스, UI는 같은 규칙으로 미리 안내)

`normalize_group(input: Option<&str>) -> Result<Option<String>, String>`:

1. `None` → `None`.
2. 앞뒤 공백을 자른다 — 자르는 글자는 `char::is_whitespace` 또는 U+FEFF(JS `trim()`이 U+FEFF도 자르므로 양쪽을 맞춘다). 비면 `None`. UI는 `trim()`을 부르지 않고 같은 글자 집합을 직접 자른다 — `trim()`은 U+0085를 안 잘라 서버와 판정이 갈린다.
3. 글자 수(유니코드 코드 포인트) 40 초과 → 거부. UI는 `[...s].length`로 센다(`.length` 아님).
4. 금지 글자가 있으면 거부 — 기존 `is_forbidden_text_char`(`crates/controller/src/monitor/config.rs`: 제어 문자·U+2028/2029·방향 제어)를 그대로 쓰고, 추가로 안쪽에 남은 U+FEFF도 거부한다. UI 거울은 기존 `isForbiddenTextChar`(`ui/src/scenario/jsonPath.ts`).
   - 서버·UI가 같은 판정을 내는지는 같은 입력 표(공백 종류·U+0085 앞뒤·U+FEFF 앞뒤/안쪽·40/41 코드 포인트·보조 평면 글자·금지 글자)를 양쪽 테스트에 넣어 확인한다.
5. 대소문자는 그대로 둔다(`서비스a`와 `서비스A`는 다른 그룹).

거부는 400(`ApiError::BadRequest`, 한국어 사유 — 레거시 CRUD 관례).

### 3. API

**응답 필드 추가** — `ScenarioResponse`에 `group: Option<String>`. `skip_serializing_if` 없이 **항상 직렬화**(없으면 `null`). `GET /api/scenarios`, `GET /api/scenarios/{id}`, `POST`, `PUT` 응답 모두.

**만들 때** — `CreateRequest`에 `#[serde(default)] group: Option<String>`. 없으면 지금과 같다. `normalize_group` 적용. 저장 함수는 `scenarios::insert`(호출 19곳)의 인자를 바꾸지 않고 그룹을 받는 새 함수를 두고 `insert`가 그것을 `None`으로 부른다.

**내용 저장(`PUT /api/scenarios/{id}`)은 그룹을 건드리지 않는다.** 요청에 그룹 필드를 추가하지 않고, UPDATE 문도 `group_name`을 쓰지 않는다. 그룹은 아래 전용 길로만 바뀐다 — 그래서 내용 저장의 버전 충돌(409)과 그룹 변경이 서로 얽히지 않는다. 단 **`PUT` 응답의 `group`은 DB에 있는 값**이어야 한다: `store::scenarios::update`는 지금 응답 행을 입력값으로 조립하므로(`created_at`만 다시 읽는다) 같은 트랜잭션에서 `group_name`도 읽어 싣는다. 화면이 `PUT` 응답을 단건 캐시에 그대로 넣기 때문에(`ui/src/api/hooks.ts` `useUpdateScenario`), `None`으로 채우면 내용을 저장할 때마다 편집 화면의 그룹 표시가 사라진다.

**그룹 옮기기** — `POST /api/scenario-groups/assign`

```json
{ "scenario_ids": ["01H…", "01H…"], "group": "서비스A" }
```

- `group`은 문자열 또는 `null`(그룹에서 빼기). **키 자체가 없으면 거부**한다 — 키를 빠뜨린 요청이 조용히 「그룹에서 빼기」가 되면 안 된다. 방법: `#[serde(deserialize_with = "Option::deserialize")] group: Option<String>`(키는 필수, 값은 `null` 허용 — `Option<Option<String>>`은 serde가 없는 키와 `null`을 구분하지 못한다). 이때 거부는 axum `Json` 추출기의 **422**다(화면은 항상 키를 보내므로 사용자에게 보일 일은 없다). `normalize_group` 적용.
- `scenario_ids`: 1개 이상 500개 이하(범위 밖 400). 한 트랜잭션에서 `UPDATE scenarios SET group_name = ? WHERE id IN (…)`.
- **`version`·`updated_at`을 바꾸지 않는다.**
- 응답 200 `{ "updated": <WHERE에 맞은 행 수> }`(값이 이미 같아도 센다). 없는 ID는 조용히 빠진다(그 사이 지워진 시나리오 — 화면은 응답 뒤 목록을 다시 읽는다).
- 한 개 옮기기(US2의 편집 화면)와 여러 개 옮기기(US3)가 같은 길을 쓴다.

**그룹 이름 바꾸기** — `POST /api/scenario-groups/rename`

```json
{ "from": "서비스A", "to": "주문" }
```

- `from`·`to` 각각 `normalize_group`을 거치고 **각각 비어 있지 않아야 한다**(어느 한쪽이라도 비면 400 — 그룹을 없애는 것은 `assign`의 `null`로 한다). `from == to`면 400.
- `UPDATE scenarios SET group_name = ? WHERE group_name = ?` 한 문장. 응답 200 `{ "updated": n }`. `from` 그룹이 없으면 `updated: 0`(오류 아님).
- `to`가 이미 있는 그룹이면 **합쳐진다**. 서버는 막지 않고, 화면이 합쳐진다는 것을 확인받는다(§4.2).

경로를 `/api/scenarios/…` 아래가 아니라 `/api/scenario-groups/…`에 두는 이유: 시나리오 한 개가 아니라 여러 개에 걸친 동작이라 `/scenarios/{id}/…` 경로들과 따로 읽히게 하려는 것이다(기술적 충돌 때문은 아니다). 두 길 모두 axum `Json` 추출기를 쓴다(`Content-Type: application/json` 검사 유지).

**그대로인 것**: 삭제(cascade 목록 무변경 — 새 테이블 없음), 보드 파일 가져오기(`insert_with_id`는 `group_name`을 쓰지 않아 NULL), 실행·스케줄·프리셋.

**복제**: 화면이 복제본을 만들 때 원본의 그룹을 `group`으로 함께 보낸다(같은 그룹에 생긴다). 복제 호출은 두 곳(`ScenarioListPage`·`ScenarioEditPage`, 둘 다 `useCloneScenario`)이고 `useCreateScenario`·`useCloneScenario`의 입력에 그룹이 추가된다.

- **순서**(사용자 결정 2026-11-20 — 폴더가 위에 오는 익숙한 순서): 그룹 묶음들이 먼저, 그 아래에 그룹에 넣지 않은 시나리오(머리 없음, 지금 모양 그대로). 그룹은 이름순(`localeCompare(…, "ko")`), 묶음 안은 서버가 준 순서(최근 수정 순) 그대로.
- **묶음의 경계를 눈으로 구분한다**(사용자 결정 2026-11-20): 펼친 묶음 아래에 오는 머리 없는 행이 그 묶음의 일부로 읽히면 안 된다. 세 가지를 함께 쓴다 — ① 묶음마다 **테두리 상자**(둥근 테두리, 머리 행은 옅은 바탕) ② 묶음 안의 행은 **들여쓰기** ③ 마지막 묶음과 그룹 없는 행들 사이에 **간격**. 그룹 없는 행은 상자 밖, 들여쓰기 없이 표의 왼쪽 끝에 붙는다. 색만으로 구분하지 않는다(테두리·들여쓰기가 주 신호). 묶음 안팎의 열(버전·수정·동작)은 같은 세로줄에 맞는다 — 행을 CSS grid로 그리고 모든 행이 같은 열 폭을 쓴다(`<tbody>`에는 둥근 테두리를 줄 수 없고 묶음마다 표를 따로 두면 열이 어긋난다). 목업: `docs/superpowers/specs/2026-11-20-scenario-groups-mockups/scenario-groups.html`.
- **그룹이 하나도 없으면** 묶음 상자가 없으므로 행과 순서는 지금과 같고, 달라지는 것은 검색 칸과 체크 칸뿐이다.
- **접기**: 그룹 머리의 **전용 접기 버튼**(`▾`/`▸` + 그룹 이름 + 개수, `aria-expanded`)을 누르면 접히고 펼쳐진다. 머리 행 전체를 누르는 영역으로 만들지 않는다(체크 칸·「이름 바꾸기」 버튼과 겹친다). 기본은 펼침. 접힘 상태는 브라우저별로 기억한다(localStorage `handicap:scenarios:collapsed-groups:v1`, 접은 그룹 이름 배열; 읽기 실패·모양 틀림은 조용히 기본값 — `editorPrefs` 관례). 지금 없는 그룹 이름은 저장 때 정리한다.
- **검색**(US4): 이름 또는 그룹 이름에 검색어가 들어 있으면(대소문자 무시) 보인다. 그룹 이름이 맞으면 그 그룹의 시나리오 전부가 보인다. 검색어가 있는 동안에는 접힘 상태를 무시하고 맞는 묶음을 펼쳐 보이고(저장된 접힘 상태는 바꾸지 않는다), 맞는 것이 없는 묶음은 숨긴다. 결과가 0이면 「검색 결과가 없습니다」 한 줄. 검색어는 URL에 싣지 않는다(화면 상태).
- **체크와 일괄 이동**(US3): 행마다 체크 칸, 그룹 머리에 그 묶음 전체 체크 칸(일부만 체크면 `indeterminate`), 표 머리에 「전체」 체크 칸 — 대상은 지금 검색에 맞는 시나리오 전부이고 접힌 묶음 안의 것도 포함한다(개수 표시로 알 수 있다). 목록을 다시 읽었을 때 사라진 시나리오는 선택에서 뺀다. 1개 이상 체크하면 표 위에 띠가 나타난다: `N개 선택됨 · [그룹 변경] · [선택 해제]`. 접힌 묶음 안에서 체크된 것도 개수에 들어가고, 검색으로 가려진 행의 체크는 유지된다(개수 표시가 「보이지 않는 선택」을 알려 준다).
- 선택이 500개를 넘으면 「그룹 변경」 버튼을 막고 띠에 「한 번에 500개까지 옮길 수 있습니다」를 보인다(서버 상한과 같은 수 — 화면이 나눠 보내지 않는다. 일부만 옮겨진 상태를 만들지 않기 위해서다).
- 「그룹 변경」 → 작은 창(기존 `Modal`): 그룹 칸(§4.3) + 「적용」. 적용하면 `assign` 호출 → 성공 시 창 닫기·체크 해제·목록 다시 읽기. 실패하면 창 안에 사유.
- 복제·삭제·실행 목록 링크, 온보딩 안내, 빈 상태는 그대로.

#### 4.2 그룹 이름 바꾸기 — US3

그룹 머리의 「이름 바꾸기」 → 작은 창: 새 이름 입력 + 「바꾸기」. 새 이름이 이미 있는 다른 그룹이면 창 안에 「이미 있는 그룹입니다. 바꾸면 두 그룹이 합쳐집니다(N개 + M개).」를 보이고 버튼 글자를 「합치기」로 바꾼다. 성공 시 접힘 기억에서 옛 이름을 새 이름으로 옮긴다.

#### 4.3 그룹 칸 (공용 `GroupField`) — US2

한 줄 입력칸 + 기존 그룹 이름 자동 완성(`<input list>` + `<datalist>` — `KeyValueGrid` 선례). 비우면 「그룹에 넣지 않음」. 기존 그룹 이름은 `useScenarios()` 목록에서 모은다(별도 API 없음). 40자 초과·제어 문자는 칸 아래 사유를 보이고 적용 버튼을 막는다(서버 규칙과 같은 문구). 자동 완성이 동작하지 않는 환경에서도 직접 입력은 된다.

쓰는 곳 3곳: 일괄 이동 창, 편집 화면, 새 시나리오 화면.

#### 4.4 편집 화면·새 시나리오 화면 — US2

- **편집 화면(`ScenarioEditPage`)**: 머리 줄의 이름 옆에 `그룹: 서비스A` 버튼(없으면 `그룹 지정` — 「그룹 없음」이라는 말은 쓰지 않는다). 누르면 작은 창에서 `GroupField` + 「적용」. 적용은 **바로 저장**(`assign` 1개)되고 시나리오 내용의 「저장 안 됨」 상태·버전과 무관하다. 성공 시 그 시나리오·목록 캐시를 다시 읽는다.
- **새 시나리오 화면(`ScenarioNewPage`)**: 저장 전이라 ID가 없으므로 같은 버튼이 화면 상태만 바꾸고, 「저장」 때 `POST /api/scenarios`의 `group`으로 함께 간다. 버튼은 편집기 단계에서만 보인다(템플릿 고르기 단계에는 없다).
- 가져오기(HAR) 화면(`ScenarioImportPage`) 자체에는 그룹 칸을 두지 않는다. 가져오기는 끝에 새 시나리오 화면의 편집기로 넘어가므로 거기서 같은 버튼으로 그룹을 정한다.

#### 4.5 시나리오 선택 칸 — US5

시나리오를 고르는 `<select>` 3곳: `ScheduleForm`(스케줄), 모니터 `PanelEditor`·`GroupBox`. 항목을 §4.1과 같은 순서로 보인다 — 그룹은 `<optgroup label="서비스A">` 아래로 먼저, 그룹 없는 시나리오는 그 뒤에 `<optgroup>` 밖의 `<option>` 그대로(브라우저가 `<optgroup>` 안 항목만 들여 써서 구분된다). 그룹이 하나도 없으면 지금과 같은 DOM이다. `ScheduleForm`은 지금 `{id, name}`만 받으므로(`ScenarioOption`) 타입에 `group?: string | null`을 더하고 `SchedulesPage`의 변환에서 함께 넘긴다(없어도 되는 필드라 기존 `ScheduleForm` 테스트 픽스처는 그대로 유효).

`CheckRecordDialog`는 시나리오를 ID로 찾기만 하고 고르는 칸이 없어 대상이 아니다. 시나리오가 정해진 화면(실행 창·실행 목록·비교)도 대상이 아니다.

#### 4.6 묶는 규칙의 단일 소스

`ui/src/scenario/grouping.ts`(순수 함수 — 기존 `ui/src/scenario/` 폴더):

- `groupScenarios(list) → { ungrouped: T[], groups: { name: string, items: T[] }[] }` — 순서 규칙(§4.1)을 여기 한 곳에.
- `groupNames(list) → string[]` — 자동 완성용.
- `filterScenarios(list, query)` — 검색 규칙.
- `validateGroupName(input) → { ok: true, value: string | null } | { ok: false, reason }` — 서버 `normalize_group`과 같은 규칙.

목록 화면과 선택 칸 3곳이 모두 `groupScenarios`를 쓴다(화면마다 따로 묶지 않는다).

#### 4.7 문구

전부 `ui/src/i18n/ko.ts` 경유(ADR-0035, `aria-label` 포함). 번역투 명사구를 피한다(working-rules §8) — 예: 「그룹 변경」 창의 안내는 「고른 시나리오 N개를 옮길 그룹을 정해 주세요. 비워 두면 그룹에서 뺍니다.」

### 5. 와이어 (1:1로 맞출 곳)

| 서버 | UI Zod | TUI 거울 |
|---|---|---|
| `ScenarioResponse.group: Option<String>` 항상 직렬화 | `ScenarioSchema.group: z.string().nullable()` | `crates/tui/src/wire.rs` `ScenarioResponse`에 `pub group: Option<String>` |
| `CreateRequest.group`(없어도 됨) | `createScenario(yaml, group?)` — `group`이 없으면 키를 보내지 않는다 | 해당 없음 |
| `assign` 요청/응답 | `assignScenarioGroup(ids, group)` / `{updated: number}` | 해당 없음 |
| `rename` 요청/응답 | `renameScenarioGroup(from, to)` / `{updated: number}` | 해당 없음 |

- TUI 거울은 `#[serde(deny_unknown_fields)]`라 **필드를 추가하지 않으면 TUI가 시나리오 응답을 읽지 못한다**. TUI는 컨트롤러를 같은 프로세스에 넣어 함께 배포하므로 버전 어긋남은 없다. 거울을 안 고쳤을 때 알려 주는 것은 `deny_unknown_fields`다 — 실제 컨트롤러를 같은 프로세스에 띄워 `scenario()`·`put_scenario()`를 부르는 `crates/tui/tests/edit_api_test.rs`와 `save_flow_test.rs`가 서버의 새 키에서 실패한다(`app_test.rs`는 `json!`으로 응답을 지어 쓰므로 그대로 통과한다). 손으로 쓴 `Debug`에 `group`을 그대로 넣는다(비밀 아님).
- UI Zod는 `.nullable()`(서버가 항상 `null` 또는 문자열을 보냄 — `.optional()`이면 `null`을 거부한다, `ui/CLAUDE.md` S-D 함정). 기존 RTL 픽스처의 시나리오 객체에 `group: null` 추가가 필요하다(필수 필드라 없으면 파싱 실패). 시나리오 객체를 짓는 테스트 파일이 20개 안팎이라 **이 전수 갱신은 독립 task**로 두고(가능하면 공용 픽스처 도우미 경유), 타입 붙은 mock은 `tsc -b`가, fetch mock은 실행 중 Zod 파싱이 잡으므로 `pnpm test` 전체와 `pnpm build`를 둘 다 돌려 확인한다.

### 6. 보안·성능

- 새 입력은 그룹 이름 글자 하나. React가 글자로 그리고(`dangerouslySetInnerHTML` 없음) SQL은 바인딩만 쓴다. `IN (…)` 자리표시는 개수만큼 `?`를 만들고 값은 바인딩한다(`yaml_by_ids` 선례). 상한 500.
- 요청 실행·템플릿·환경·데이터셋·업로드·trace 뷰어를 건드리지 않는다. 그래도 `finish-slice` §0 grep은 그대로 돌린다(하한선).
- 목록 응답은 필드 하나가 늘 뿐이다. 묶기·검색은 화면에서 한 번 훑는 계산(`useMemo`)이다.

### 7. 테스트·검증

- 서버 단위: `normalize_group` 표(공백·빈 값·40/41자·제어 문자·방향 제어 문자·대소문자 보존).
- 서버 통합(`crates/controller/tests/`): 만들 때 `group` 저장·응답 / 목록·단건 응답에 `group` 키가 **있다**(`contains_key` — `Value` Index는 없는 키도 `Null`을 준다, controller CLAUDE.md §테스트) / `assign` 여러 개·`null`로 빼기·없는 ID 섞임·0개와 501개 400 / `assign` 뒤 `version`·`updated_at` 불변 / `rename` 일반·합치기·없는 그룹 0·같은 이름 400 / 내용 `PUT`의 **응답 본문** `group`이 저장된 그룹과 같다(뒤이은 GET만 보면 응답 조립 결함을 놓친다) / `assign`에 `group` 키가 없으면 422이고 그룹이 안 바뀐다 / migration 멱등.
- UI 단위: `grouping.ts` 표(순서·검색·이름 규칙), 목록 화면(그룹 0개일 때 묶음 상자 없음·행 순서 그대로 · 500개 초과 선택 시 버튼 막힘 · 묶음 접기와 기억 · 검색 중 펼침 · 체크와 띠 개수 · 묶음 체크 `indeterminate` · 일괄 이동 호출 인자 · 이름 바꾸기 합치기 안내), 편집·새 화면의 그룹 버튼, 선택 칸 3곳의 `<optgroup>`(그룹 0개면 `<optgroup>` 없음).
  - 회귀를 지킨다고 내세우는 테스트는 되돌려 확인(teeth check)을 한다 — 특히 「그룹 0개면 묶음 상자가 없고 행 순서가 같다」·「`assign`이 버전을 안 올린다」·「`PUT` 응답이 그룹을 싣는다」.
- 라이브(필수 — 응답 파싱 경로를 바꾼다): US1–5를 실제 컨트롤러에서. 극단값 = 40자 그룹 이름(한글·영문 연속 글자), 그룹 30개, 한 그룹 200개, 긴 시나리오 이름과 함께 — 목록 머리 행·띠·선택 칸에서 겹침·잘림을 rect로 잰다. 진입 화면 전부: 목록 / 편집(저장된 것) / 새 시나리오 / 스케줄 폼 / 모니터 보드 편집(칸 편집기·묶음 상자). TUI는 시나리오 응답을 읽는 화면이 뜨는지 1회(그룹 있는 시나리오가 든 DB로).

## 구현자에게 맡기는 것

- 일괄 이동 띠·작은 창의 정확한 배치와 간격(기존 프리미티브 `Modal`·`Input`·`Button` 사용, 인접 화면과 일관되게).
- 묶음 상자의 세부 마크업·역할 속성 — §4.1의 세 신호(테두리 상자·들여쓰기·간격)와 열 맞춤(grid), 접근성(머리 버튼의 `aria-expanded`, 체크 칸 이름에 그룹 이름 포함)을 지키면 된다. 라이브에서 「펼친 묶음 바로 아래의 그룹 없는 행」 화면을 찍어 경계가 보이는지 확인하고, 극단값(40자 그룹 이름·긴 시나리오 이름)에서 잘림과 함께 **묶음 안팎 열의 왼쪽 좌표가 같은지**도 잰다.
- 서버 `normalize_group`을 둘 모듈 위치와 방향 제어 문자 검사 재사용 방식.
