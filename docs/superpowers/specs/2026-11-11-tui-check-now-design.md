# 터미널 모니터 — 지금 점검 (`r`) (tui-check-now) — 설계

- 날짜: 2026-11-11 · 유형: `user-path` · 상위 설계: [tui-monitor 설계](2026-11-07-tui-monitor-design.md) — **그 문서의 슬라이스 2a-2 "미리 실행"(§6.5, 메뉴 `p`)을 이 문서가 대체**한다(§6) · 결정 기록: [ADR-0053](../../adr/0053-ops-monitor-mode.md)·[ADR-0055](../../adr/0055-tui-monitor.md)(새 ADR 없음 — §11)
- 범위: `crates/controller`(점검 루프에 깨우기 신호 + REST 길 하나) + `crates/tui`(키·화면 연결) + 문서. 엔진·proto·DB·GUI(`ui/`) 0-diff.
- 상태: 설계

## 사용자 스토리 (US)

사용자 원문(앵커, 2026-11-11): "지금 tui 용도 상 미리 실행 보다는 메뉴 이름을 판정 조건 변경이나 다른 이름으로 하는게 나을거 같은데 … 그리고 단축키 r 추가해서 즉시 실행 같은 기능도 있으면 좋을거 같아 간격 보다 빠르게 요청을 보내보는 거지 사용자가 원할 때." → 질문 2개의 답: ① `r`의 결과는 **실제 점검으로 막대·상태·기록에 남는다** ② **메뉴 `p`는 없애고 `r` 하나로**. 이후 "지금 당장은 그 방향이 맞아, US 4개로 spec 써줘. 나중에 판정을 수정하거나 할 일이 생기면 p를 요청하던가 할게."

- **US1**: 운영자가 주기가 긴(예: 60초) 칸이 실패 상태일 때 서버 조치가 끝났다는 연락을 받았다 — 모니터 화면에서 그 칸을 고르고 `r`을 누르면 다음 주기를 기다리지 않고 점검이 돌아, 수 초 안에 막대가 하나 늘고 칸 상태가 새 결과로 바뀌며 오류 보기 기록에도 그 회차가 남는다.
- **US2**: 운영자가 칸 설정을 보거나 고친 뒤 지금 값으로 어떻게 판정되는지 자세히 보려 한다 — 칸 설정에서 `r`을 누르면 점검이 돌고, 끝나는 대로 그 회차의 자세히 화면(결과·응답 시간·사유·판정 상세·스텝 표, 묶음 칸은 그 칸의 스텝만)이 열리며 `Enter`로 요청·응답까지 본다. (상위 설계 US4의 "미리 실행" 문장을 대체.)
- **US3**: 운영자가 묶음 칸에서 `r`을 누른다 — 같은 묶음의 칸들이 한 번의 시나리오 실행으로 함께 점검되어 모두 같은 시각의 막대가 하나씩 늘고, 대상 서버에는 요청이 한 벌만 간다.
- **US4**: 운영자가 `r`을 연타하거나, 점검이 이미 도는 중이거나, 보드 점검이 꺼진 상태에서 누른다 — 요청이 겹쳐 나가지 않고(도는 중이면 그 점검 하나로 끝, 연타해도 한 실행 단위는 1초에 한 번보다 자주 돌지 않는다), 꺼진 보드에서는 점검되지 않고 꺼져 있다는 안내가 보인다.

## 1. 목표 / 비목표

**목표**: US1~US4.

**비목표**
- **기록에 남기지 않는 1회 실행("미리 실행", `preview-check`)을 TUI에 넣기** — TUI는 값을 고치는 즉시 실제 점검에 반영되므로 "미리" 돌려 볼 다른 설정이 없다(사용자 결정). 서버의 `preview-check` 길과 GUI의 미리 실행은 그대로다.
- **GUI 보드 화면의 "지금 점검" 버튼** — 서버 길은 GUI도 부를 수 있는 모양이지만 `ui/`는 건드리지 않는다.
- **응답에서 값을 골라 성공 조건·표시 값 추가(상위 설계 2b, US9)** — 다음 슬라이스. 이 문서는 그 진입점이 "미리 실행 결과"에서 "요청·응답 기록 화면"으로 바뀐다는 것만 상위 설계에 적는다(§6).
- 자세히·요청·응답 화면에서 `r`로 다시 점검 — `Esc`로 칸 설정에 돌아가 `r`(§10 연기).
- 점검 중(`running`)을 칸에 그리기 — 지금도 그리지 않는다. 눌렀다는 표시는 머리 줄 알림으로(§4.2).

## 2. 동작 규칙 (정본)

"실행 단위" = 감독자가 루프 하나로 돌리는 것(흐름 전체 칸 하나 / 단독 스텝 칸 하나 / 점검 묶음 하나 — `monitor/supervisor.rs` 머리 주석).

1. **지금 점검 요청은 그 칸이 속한 실행 단위를 깨운다.** 주기 대기 중이면 대기를 끝내고 다음 회차를 곧 시작한다. 그 회차는 정기 회차와 똑같다 — 같은 설정, 결과는 소속 칸 모두의 막대·기록에 들어가고(묶음은 trace 1회 공유), 동시 점검 상한(`MAX_CONCURRENT_CHECKS`) 허가도 똑같이 받는다.
2. **바닥 간격 1초**: 깨운 회차는 직전 회차 **시작** 뒤 `min(주기, 1초)`가 지나야 시작한다(그 전에 온 요청은 버리지 않고 그때까지 미뤄 1회로). 주기의 최솟값이 1초(`validate_panel` 1~3600)이므로, 지금 점검을 아무리 눌러도 한 실행 단위는 설정으로 허용된 가장 빠른 주기(1초)보다 자주 돌지 않는다.
3. **점검 중에 온 요청은 아무 일도 하지 않는다**(예약하지 않는다) — 돌고 있는 그 회차의 결과가 곧 나온다.
4. **대기 중 여러 번 와도 1회.**
5. **다음 정기 회차는 깨운 회차의 시작 + 주기**(기존 "시작-시작 간격" 규칙 그대로 — 깨운 회차가 새 기준).
6. 꺼진 보드(실행 중 아님)는 깨울 루프가 없다 → 거절(§3.3 409).
7. 설정 저장(reconcile)·정지·종료 동작은 바뀌지 않는다.

## 3. 컨트롤러

### 3.1 점검 루프 (`monitor/supervisor.rs` `unit_loop`)

`unit_loop`에 인자 `kick: Arc<tokio::sync::Notify>`를 더한다(실행 단위당 하나). 회차 뒤 대기를 세 갈래로:

```rust
/// 지금 점검으로 깨운 회차와 직전 회차 시작 사이의 최소 간격(주기 최솟값과 같다).
pub(crate) const CHECK_NOW_MIN_GAP: Duration = Duration::from_secs(1);

loop {
    let started = tokio::time::Instant::now();
    // … running 켜기 → check() (취소 select) — 지금과 같다 …
    // 결과를 버퍼에 넣기 **전에** 만든다: 이 결과를 본 뒤에 온 요청을 놓치지 않게(§3.2 순서).
    let kicked = kick.notified();
    tokio::pin!(kicked);
    // … 결과·기록 push — 지금과 같다 …
    let floor = started + interval.min(CHECK_NOW_MIN_GAP);
    tokio::select! {
        biased;
        _ = token.cancelled() => return,
        _ = tokio::time::sleep_until(started + interval) => {}
        _ = async { kicked.as_mut().await; tokio::time::sleep_until(floor).await } => {}
    }
}
```

- 깨우는 쪽은 **`notify_waiters()`** — 허가를 저장하지 않으므로 점검 중(`Notified`가 없는 구간)에 온 요청은 사라진다(규칙 3). `Notified`는 만들어진 뒤의 `notify_waiters()`를 폴링 전이어도 받는다(tokio 문서의 보장 — §12; 구현 첫 단계에서 가상 시계 테스트로 확인하고, 다르면 STOP).
- 첫 회차 즉시·겹침 없음·취소 시 즉시 종료·`running` 가드는 그대로.
- 호출 사이트: `spawn_loop`(→ `spawn_unit` 2갈래)와 테스트 도우미 `panel_loop`·테스트의 직접 호출(§12 명령 — 구현 중 컴파일러가 전부 짚는다). 테스트 도우미는 안 쓰는 `Notify`를 넘긴다.

### 3.2 감독자 (`MonitorSupervisor::check_now`)

- `BoardView`에 `kicks: HashMap<칸 id, Arc<Notify>>`를 더한다. `reconcile_slot`이 실행 단위마다 `Notify` 하나를 만들어 그 단위의 모든 칸 id로 넣고 `spawn_unit`에 넘긴다(묶음 칸들은 같은 `Arc`).
- 새 메서드(동기, `.await` 없음):

```rust
pub enum CheckNow {
    /// 깨웠다(또는 점검 중이라 할 일 없음). `last_at_ms` = 요청 시점에 그 칸 버퍼의 가장 새 결과 시각.
    Requested { last_at_ms: Option<i64> },
    /// 실행 중이 아니다(꺼짐·없는 보드·종료 중).
    Off,
    /// 실행 중인 보드에 그 칸이 없다.
    NoPanel,
}
pub fn check_now(&self, board_id: &str, panel_id: &str) -> CheckNow
```

- **`existing_slot`만** 쓴다(모르는 id로 슬롯을 만들지 않는다 — `record()`와 같은 이유).
- 순서: `view` 락에서 그 칸의 버퍼·`Notify`를 복제 → `view` 락 해제 → 버퍼 락에서 `results`의 마지막 `at_ms`를 읽고 해제 → `notify_waiters()`. 락 순서는 머리 주석의 3번(짧은 동기 구간)만 쓰고 겹쳐 잡지 않는다.
- `last_at_ms`가 왜 필요한가: 요청한 쪽이 "이 요청 **뒤에** 나온 결과"를 골라낼 기준(§4.3). 클라이언트의 1초 폴링 사본으로 기준을 잡으면, 설정 저장 직전에 끝난 옛 설정 회차가 아직 폴링되지 않은 순간에 그 회차를 새 결과로 오인할 수 있다. 서버가 읽은 값이면 그 뒤 버퍼에 들어오는 결과는 모두 요청 뒤의 것이다(§3.1에서 `Notified`를 결과 push **전에** 만들므로 "기준에 이미 들어간 결과를 본 뒤의 요청이 버려지는" 틈도 없다 — 기준을 읽은 뒤 push된 경우엔 그 결과가 기준보다 새것이라 요청한 쪽이 그것을 받고, 깨우기도 걸려 1회 더 돈다. 드문 덤 1회, 수용).

### 3.3 REST

`POST /api/monitor-boards/{id}/panels/{panel_id}/check-now` — 본문 없음.

| 결과 | 응답 |
|---|---|
| 깨웠다 / 점검 중 | `200` `{"last_at_ms": 1731312345678}` 또는 `{"last_at_ms": null}`(결과가 아직 없음 — 키는 항상 있다) |
| 보드 없음 · 그 보드에 그 칸 없음(`NoPanel`) | `404` |
| 보드가 꺼져 있음(행 `enabled = false` 또는 `Off`) | `409` `{"error": "점검이 꺼져 있습니다"}` |

- 핸들러: `monitor_boards::get`으로 행을 읽어 없으면 404, `enabled`가 거짓이면 409, 그 뒤 `state.monitor.check_now` 결과를 위 표로. 설정 저장 직후 reconcile이 `view`를 갈아 끼우는 찰나에는 `Off`(409)가 날 수 있다 — 그때는 저장이 첫 회차를 즉시 돌리므로 실해 없음(수용).
- 응답 구조체 `CheckNowResponse { last_at_ms: Option<i64> }`(`skip_serializing_if` 없이 — `null`을 직렬화).
- 라우트는 `app.rs`의 `…/panels/{panel_id}/records/{at_ms}` 옆. axum 0.8 `{…}` 경로 문법.

## 4. TUI

### 4.1 키·문구

| 화면 | 키 | 동작 |
|---|---|---|
| 모니터 | `r` (`R`·한글 `ㄱ` 포함 — 기존 `normalize_char`) | 선택 칸 지금 점검(§4.2). `e`·`Enter`와 같은 조건(칸이 그려져 있고 선택 칸이 있을 때) |
| 칸 설정 메뉴(위에 뜬 창 없음) | `r` | 지금 점검 후 그 회차 자세히 열기(§4.3) |

### 4.2 모니터 화면의 `r` (US1·US3·US4)

1. `r` → 조회 작업자에 요청 `FetchReq::CheckNow { board_id, panel_id }`를 넣는다(작업자는 차례로 처리 — 기존 기록 조회와 같은 통로). 작업자는 `api.check_now`(요청 제한 = `POLL_TIMEOUT` 3초)를 부르고 `Fetched::CheckNow { board_id, panel_id, result }`를 돌려준다. `result` = `Ok(last_at_ms)` 또는 `Err(HTTP 상태 Option<u16>)` — **서버 문구는 싣지 않는다**(화면 문구는 TUI 상수).
2. 결과가 오면 머리 줄 알림(5초 — 기존 `저장됨`과 같은 시간):
   - 성공 → 초록 `지금 점검 HH:MM:SS`(시각 = TUI가 결과를 받은 때). `저장됨 HH:MM:SS`와 **같은 자리·같은 축약 단계**(문구만 다름).
   - 409 → 빨강 `점검이 꺼져 있습니다` / 그 밖(404·연결 실패·시간 초과) → 빨강 `지금 점검을 요청하지 못했습니다`. 기존 파일 경고와 **같은 자리·같은 축약 규칙**.
3. 알림 우선순위(머리 줄 알림 자리는 하나): 파일 경고(`파일에 저장 못 함…`·`보드 파일이 밖에서 바뀌었습니다…` — 계속 떠 있어야 하는 것) > 지금 점검 알림(5초) > `저장됨`. 지금 점검 알림은 파일 알림과 **다른 칸에 보관**해 서로 덮어쓰지 않는다.
4. 막대·상태는 다음 `/status` 폴링(1초)에 새 결과가 들어오면 바뀐다 — TUI가 따로 그리지 않는다.
5. 연타: 누를 때마다 요청을 보낸다(서버가 규칙 2~4로 합친다). 알림은 마지막 결과로 갱신.

TUI는 세션을 시작할 때 모든 보드를 켠다(`session.rs`가 보드마다 `start` 호출) — 그래서 TUI 안에서는 409가 평소에 나지 않는다(밖에서 그 보드를 끈 경우만). 409 문구는 그 경우와 GUI·curl 호출자를 위한 것.

### 4.3 칸 설정의 `r` → 자세히 (US2)

1. 메뉴에서 `r` → 대기 창 `Overlay::Checking { after: None }` + 4.2-1과 같은 요청. 대기 창은 한 줄 `점검 결과를 기다리는 중…`, 키 줄 `Esc 뒤로`(기존 `KEYS_BACK`).
2. 요청 결과:
   - `Ok(last)` → `after = Some(last)`.
   - `Err(409)` → 안내 창 `Overlay::Notice(점검이 꺼져 있습니다)` / 그 밖 → `Notice(지금 점검을 요청하지 못했습니다)`(기존 안내 창 — 다음 키 하나로 닫힘).
   - 칸 설정에서 보낸 요청은 **머리 줄 알림을 띄우지 않는다**(대기 창·안내 창이 표시). 판별: 결과가 왔을 때 편집 상태의 창이 `Checking { after: None }`이고 보드·칸이 같으면 이 경로, 아니면 4.2-2.
3. 매 화면 갱신(`pump`)에서 `Checking { after: Some(last) }`이면 그 칸의 현재 결과 목록(폴링 사본)의 **가장 새 결과**를 본다 — `at_ms > last`(또는 `last`가 없고 결과가 하나라도 있음)이면 대기 창을 닫고 그 결과로 **자세히 화면**을 연다(기록 조회 요청은 기존 `FetchReq::Record`).
4. 대기 중 키: `Esc` = 대기 창만 닫고 메뉴에 남는다(점검은 서버에서 그대로 돌고 결과는 막대에 들어간다 — 취소가 아니다). `q`/`Ctrl+C` = 종료 확인. 그 밖 = 무동작. 대기에 제한 시간은 두지 않는다 — 5분 무입력 복귀(기존 `idle_drop`이 저장 중이 아닌 창을 버린다)가 뒷문.
5. 저장 중(`저장 중…` 창)에는 `r`이 닿지 않는다(창이 떠 있으면 창 규칙이 먼저 — 기존). 저장이 끝난 뒤 누른다.

### 4.4 칸 설정에서 연 자세히 화면

- 화면 내용·`Enter`(요청·응답)·`↑↓`는 1b 그대로. 묶음 칸은 그 칸의 스텝만(기존 `step_lines`가 칸의 `step_id`로 거른다 — US2).
- **`Esc`는 온 곳으로**: 오류 목록에서 열었으면 목록(지금과 같다), 칸 설정에서 열었으면 칸 설정 메뉴(편집 상태·메뉴 커서 유지). 키 줄도 `Esc 목록으로` ↔ `Esc 칸 설정으로`.
- 요청·응답 → `Esc` → 자세히는 그대로.
- 5분 무입력 복귀는 그대로 모니터로(자세히·요청·응답은 이미 대상 화면).

### 4.5 루프백 메서드·거울

- `api.rs` `check_now(board_id, panel_id) -> Result<CheckNowResponse, ApiError>`.
- `wire.rs` `CheckNowResponse { last_at_ms: Option<i64> }` — `deny_unknown_fields` + in-process 실응답 역직렬화 테스트(기존 거울 규칙).
- `--check`·세션 시작·파일 저장·폴링은 바뀌지 않는다.

## 7. 테스트

**컨트롤러 — 루프(가상 시계, `start_paused`, DB 없음 — 기존 `panel_loop` 테스트와 같은 방식)**
- 대기 중 깨우기: 주기 60초, 점검 1초 → t=10초에 깨우면 다음 시작이 10초(60초가 아님), 그다음 정기 시작이 70초(규칙 1·5). **이빨 실증**: 깨우기 갈래를 지우면 RED → 원복 GREEN을 구현 중 실행해 기록.
- 바닥 간격: 점검 0.1초 → t=0.3초에 깨우면 다음 시작이 정확히 1.0초(규칙 2). **이빨 실증**: `floor` 대기를 지우면 RED.
- 점검 중 깨우기: 점검 5초, t=2초에 깨움 → 그 회차 뒤 추가 회차 없음, 다음 시작 60초(규칙 3). **이빨 실증**: `notify_waiters`를 `notify_one`으로 바꾸면 RED.
- 대기 중 3번 깨움 → 1회(규칙 4).
- 주기 1초에서 깨워도 시작 간격이 1초보다 짧아지지 않는다.
- 취소: 깨운 뒤 바닥을 기다리는 중 취소 → 즉시 종료.
- 기존 루프 테스트(§12의 호출 사이트)는 인자만 더해 그대로 통과.

**컨트롤러 — 감독자·REST**
- `check_now`: 모르는 보드·꺼진 보드 → `Off`(슬롯을 만들지 않는다 — 호출 뒤 슬롯 수 불변), 없는 칸 → `NoPanel`, 켜진 보드 → `Requested`이고 `last_at_ms`가 그 칸 버퍼의 마지막 결과 시각.
- 묶음: 칸 2개 묶음(주기 3600초)에서 한 칸으로 `check_now` → 두 칸 모두 결과가 1개씩 늘고 `at_ms`가 같다(US3). 실시간 1초 남짓 대기(가상 시계는 sqlx 풀 시간 초과와 충돌 — 컨트롤러 함정 문서).
- REST(`tests/monitor_boards_api_test.rs`): 404(없는 보드)·404(없는 칸)·409(끈 보드, 본문 `error` 문구)·200(본문에 `last_at_ms` 키가 **있음** — `as_object().contains_key`로, 값은 수 또는 null). 주기 3600초 보드에서 200 뒤 2초 안에 `/status`의 그 칸 결과 수가 늘어난다(US1의 서버 쪽).

**TUI — 순수 함수·그리기(기존 테스트 파일들)**
- 키: 모니터 `r`·`R`·`ㄱ` → 지금 점검 동작, `Ctrl+R` → 없음, 시작 오류 화면 `r` = 다시 시도 그대로. 칸 설정 메뉴 `r` → 지금 점검, 하위 목록·변수 화면 `r` → 없음, 입력줄 `r` → 글자.
- 대기 창: `Esc` 닫힘·`q` 종료 확인·그 밖 무동작. 결과 `Ok(last)` → `after` 채움, `Err(Some(409))` → 꺼짐 안내, `Err(None)` → 실패 안내. 다른 칸의 결과·창이 없을 때의 결과 → 편집 상태 불변.
- 새 결과 판정: `at_ms > last`만 열림(같거나 작으면 대기), `last` 없음 + 결과 있음 → 열림, 결과 없음 → 대기.
- 자세히 뒤로: 칸 설정에서 열었으면 `Esc` → 칸 설정(편집 상태·커서 유지), 오류 목록에서 열었으면 목록(회귀).
- 키 줄: 모니터·칸 설정 메뉴에 `r 지금 점검`, 자세히 키 줄이 온 곳에 따라 다름, 대기 창 키 줄. 좁은 폭에서 기존 "앞 조각부터 통째로" 규칙 유지(기존 폭 스윕 테스트에 조각 추가).
- 머리 줄: `지금 점검 HH:MM:SS`가 `저장됨`과 같은 단계로 줄어듦, 꺼짐·실패 경고가 파일 경고와 같은 규칙, 우선순위 3단(파일 경고가 있으면 지금 점검 알림이 안 보임 — 파일 경고는 그대로).
- 도움말: 11줄, `r` 줄 있음(기존 `HELP_KEYS.len() == 10` 단언 갱신).
- 5분 복귀: 대기 창이 버려진다.

**TUI — in-process 컨트롤러(기존 `edit_api_test.rs`·`session_test.rs` 방식)**
- `api.check_now` 실응답이 `CheckNowResponse`로 읽힌다(`deny_unknown_fields`), 끈 보드 → `ApiError.status == Some(409)`.

## 9. 보안 표면

- **요청 실행 길이 하나 늘어난다** — 다만 실행하는 것은 이미 저장되어 주기적으로 돌고 있는 그 설정 그대로다(새 URL·본문·경로 입력 없음, 경로 변수 둘은 조회 키로만 쓰인다).
- **증폭 한도**: 규칙 2로 한 실행 단위는 초당 1회를 넘지 않는다 — 주기를 1초로 저장하면 얻는 것과 같은 상한. 동시 점검 상한(32)도 그대로 적용된다. 점검 중 요청은 예약되지 않아 밀린 요청이 쌓이지 않는다.
- **본문 없는 POST라 교차 사이트 요청이 preflight 없이 닿는다**(라우터에 CORS 없음) — 기존 `…/start`·`…/stop`과 같은 부류(선재 — 둘 다 본문 없는 POST). 이 길로 할 수 있는 일은 "이미 켜진 칸을 초당 1회 한도로 한 번 더 점검"뿐이다. 응답은 시각 하나(`last_at_ms`)뿐.
- 404/409 응답·TUI 화면에 서버 내부 문자열을 싣지 않는다(TUI는 상태 코드만 보고 상수 문구).
- 기록(`CheckRecord`)의 인증 값 가림·본문 상한은 정기 회차와 같은 경로라 그대로 — "미리 실행 응답을 TUI가 직접 가려야 하는" 상위 설계 §6.5의 숙제가 사라진다.
- `finish-slice` §0 grep이 지배 — 매치하면 `security-reviewer` 필수(요청 실행 경로를 건드리므로 매치 예상).

## 10. 알려진 한계 / 연기

- **GUI에는 지금 점검이 없다** — 서버 길만 있다(재개 신호: 사용자가 GUI 보드 화면에서 요청).
- **자세히·요청·응답 화면에서 다시 점검 키 없음** — `Esc`로 칸 설정에 돌아가 `r`(재개 신호: 사용자 불편 보고).
- **꺼진 보드는 지금 점검이 안 된다**(옛 "미리 실행"은 꺼진 보드에서도 돌았다) — TUI는 늘 보드를 켜므로 TUI 안에서는 드러나지 않는다.
- **지금 점검도 막대를 하나 쓴다** — 막대 시각 줄의 간격이 그 구간에서 고르지 않게 보인다(상위 설계 §5.1의 "점검이 밀리거나 끊긴 구간"과 같은 모양).
- **대기 창에 제한 시간 없음** — 폴링이 끊긴 채로는 `Esc`나 5분 복귀까지 대기 창이 남는다(머리 줄이 `서버 응답 없음`을 보인다).
- 기준을 읽은 직후 결과가 들어온 드문 순간엔 덤 회차가 1회 돈다(§3.2).
- **메뉴 `p`·판정 조건 추가**는 사용자가 필요해지면 새 요청으로(US 앵커 원문).

## 11. 판단 기록 (설계자 몫)

- **이름 `지금 점검`**: 화면 낱말이 전부 "점검"(점검 중·점검 주기·점검 꺼짐)이고, "미리"는 TUI에 맞지 않는다는 사용자 지적. "판정 조건 변경"은 11번 "성공 조건"과 겹쳐 쓰지 않음(사용자 동의).
- **새 ADR 없음**: 저장·와이어 모델·점검 실행 방식은 그대로이고 주기 대기에 깨우기 신호 하나를 더한 것 — ADR-0053("주기 점검 보드")의 범위 안.
- **`Notify::notify_waiters`**: 채널·플래그보다 작고, "점검 중 요청은 버린다"가 그 의미와 정확히 맞는다(허가 저장 없음).
- **바닥 1초**: 새 상한을 발명하지 않고 주기 최솟값을 그대로 쓴다 — "설정으로 이미 허용된 것보다 빠르지 않다"는 한 문장으로 보안 판단이 끝난다.
- **기준 시각을 서버가 준다**(`last_at_ms`): §3.2의 오인 틈을 닫는 가장 작은 방법. 응답에 "깨웠는지/점검 중이었는지"는 넣지 않았다 — 쓰는 곳이 없다.
- **조회 작업자 재사용**: 요청이 즉시 끝나는 루프백 POST라 새 작업자를 만들지 않는다. 세션을 내릴 때 정리도 기존 그대로.
- **화면 문구는 TUI 상수, 서버 문구는 싣지 않음**: 머리 줄은 폭 계산이 엄격하고(축약 단계), 서버 문자열을 싣지 않으면 가림·정리 규칙을 새로 따질 필요가 없다.
