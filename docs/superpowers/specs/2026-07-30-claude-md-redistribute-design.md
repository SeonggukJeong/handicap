### 1.3 재비대의 메커니즘 — 규칙은 있었고 지켜지지 않았다

root에는 이미 세 규칙이 문서화돼 있다: 상태줄은 "한 줄 교체(append 금지)", ADR 인덱스는 "한 줄만(번호+제목+핵심 한 마디)", Subagent dispatch 섹션은 "여기엔 **규칙 요약만** — 서사는 `docs/dev/subagent-dispatch.md`". 셋 다 위반 상태다:

- 상태줄: 5,028 B(머리 332 + 카탈로그 1,762 + `최신 =` 문단 2,377 + 포인터 꼬리 557)
- ADR 인덱스: 13줄이 180 B 초과(최대 510 B — 0044). 13줄 합 4,333 B

### 3.2 도구 2개

기존 `scripts/check-release-versions.sh` 컨벤션(레포 스크립트 + `just` 레시피 + 로컬 실행 가능)을 따른다.

**`scripts/check-doc-budget.sh`** — `just doc-budget`
- 파일별 `현재 / 예산 / 사용률` 표 출력 · root 상태줄 크기 검사 · L1 검사(R9)
- 종료 코드: 초과 1건이라도 있으면 `exit 1`; 없고 ≥90%면 WARN 배너 + `exit 0`; 그 외 `exit 0`

**`scripts/check-doc-coverage.sh <base-ref>`** — `just doc-coverage`

초안의 "코퍼스 전체에서 토큰을 찾는다"는 설계는 **폐기**한다. 리뷰 FR1을 직접 재현한 결과, §3.1 이동 집합의 **9개 불릿 중 4개(L122 765 B·L134·L136·L138)는 목적지에 아무것도 안 쓰고 삭제해도 GREEN**이고, 최대 이동분인 카탈로그 1,762 B는 추출 토큰이 4개(`ADR-0039`·`ADR-0042`·`ADR-0043`·`docs/build-log.md`)뿐이라 **100% 불가시**였다. 원인은 코퍼스가 1.4 MB이고 그중 `build-log.md` 단독으로 base 토큰의 57.4%를 이미 포함하는 것(마스킹), 그리고 한국어 산문에는 추출 가능한 토큰이 없다는 것이다.

→ **1차 방어선 = manifest 기반 목적지-지향 검증** (`scripts/doc-move-manifest.tsv`, R16):

```
# source_anchor <TAB> dest_file <TAB> required_marker <TAB> min_dest_gain_bytes
```

행마다 4개를 검사한다:
1. `source_anchor`가 **base root에 존재**(manifest가 base에 대해 정직한가)
2. `source_anchor`가 **현재 root에 부재**(정말 제거됐는가)
3. `required_marker`가 **`dest_file`에 존재**(정말 도착했는가) — 코퍼스 전체가 아니라 *선언된 목적지 한 파일*에서만 찾는다
4. `dest_file`의 base 대비 바이트 증가 ≥ `min_dest_gain_bytes`(한 줄 스텁이 아니라 실체가 왔는가)

**`min_dest_gain_bytes = 0` 행의 한계와 처리** (리뷰 2차 Hole B): #1 카탈로그·#4 ADR은 내용이 *작업 전부터* 목적지에 있으므로 검사 1·3이 base 시점에 이미 참이고 검사 4는 `≥0`이다 — 실질적으로 검사 2(root에서 제거됐는가)만 남아, **커버리지 검사의 옷을 입은 제거 검사**가 된다. 처리는 둘 다 한다:

- `required_marker`를 **표본 다항 marker**로 확장한다 — #1은 카탈로그 항목 중 5–8개, #4는 **ADR 13번호 전부** — 각각이 선언된 목적지에서 해석돼야 한다. 항진명제가 표본 포함 검사로 바뀐다.
- 그럼에도 이 두 행의 no-forget 증거는 **스크립트가 아니라 §1.6·§3.1의 전수 대조**임을 §3.2에 명시한다. 나중에 green을 증명으로 오독하지 않게.

**불릿 개수 불변식** (R17 — 리뷰 2차 Hole A): manifest는 *선언된 행*만 검사하므로, 불릿을 지우고 **manifest 행을 아예 안 만들면 어떤 검사도 발화하지 않는다**. 실패 모드가 "이관을 잊음"에서 "선언을 잊음"으로 한 칸 옮겨갔을 뿐이고 후자도 똑같이 불가시다(L134·L136·L138은 토큰이 0개라 2차 그물도 무력). → 손댄 섹션의 불릿 개수를 base와 대조한다. 규칙 하나가 사라지면 개수가 준다. **형태는 등호가 아니라 `current >= base`이고, 기준값은 `<base-ref>`에서 매번 센다**(오늘은 Subagent 27·ADR 49). 등호+하드코딩이면 **root 자신이 지시하는 행동에 게이트가 RED를 낸다** — "새 ADR는 인덱스에 한 줄만"이 규칙인데 최근 3주에 ADR이 5건(0045–0049) 늘었으니 다음 ADR에서 50이 되어 즉시 깨진다(리뷰 3차 NEW-A). 정당한 **병합**(예: "…도 가설이다" 계열 3건을 한 규칙으로 합치기)은 manifest `kind=merge` 행으로 선언해 바닥을 낮춘다 — R16 기구를 재사용하므로 새 메커니즘이 없고 결정이 감사 가능하다.

**남는 구멍(수용)**: 불릿 하나를 지우고 채움용 불릿 하나를 새로 만들면 개수가 맞는다. 다만 이건 사고가 아니라 고의 날조여야 하고 diff에 그대로 드러난다 — 잔여 위험으로 수용하고 여기 적어둔다(나중에 이 검사를 전수로 오해하지 않게).

→ **3차 방어선 = 보조 토큰 차분**(초안 설계 유지, 격하 — 1차 manifest·2차 R17 개수 불변식 뒤): base root에서 사라진 토큰 중 코퍼스 어디에도 없는 것을 보고. manifest가 빠뜨린 것을 줍는 그물이지 주 방어선이 아니다. 추출 규칙을 스크립트에 고정한다 — inline-code span `` `[^`\n]{2,80}` `` · `docs/[A-Za-z0-9/_.-]+\.md` · `ADR-\d{4}`. (리뷰 F3: 초안의 "수치+단위"는 단위 목록이 정의되지 않아 반증 불가능했고, 그래서 "416개"가 재현되지 않았다 — 세 규칙만 쓰면 434개.) 예외는 `scripts/doc-coverage-allowlist.txt`(R10).

**이 스크립트도 이빨을 증명해야 한다**(R11 시나리오 2건): ① L122를 목적지 기입 없이 지운 트리 ② manifest 행과 그 불릿을 함께 지운 트리 — 둘 다 RED가 안 나오면 스크립트가 틀린 것이다(②는 R17이 없으면 통과해버린다).

### 3.3 예산 — 두 역할을 분리한다

초안(그리고 1차 리뷰 반영본)은 **절대 예산 하나로 두 가지 다른 일**을 시키려 했고, 그래서 순환에 빠졌다: R5가 "도입 시점 WARN 0건"을 요구하면 예산은 현재치 ÷ 0.9로 역산되고, 그 역산값의 정당화는 다시 R5뿐이다. 같은 수를 다음번에 또 적용하면 130→145, 90→100으로 **예산이 영원히 현재치를 뒤따라간다**. 게다가 그 값들은 한 슬라이스도 못 버틴다 (리뷰 2차 Q3 실측):

```
controller  82,481 / 92,160(90 KiB) = 89.5%  → WARN 발화점 82,944  헤드룸   463 B
            실측 성장 +625 ~ +884 B / 커밋   → 다음 controller 커밋에 즉시 WARN
ui         116,129 /133,120(130 KiB) = 87.2% → WARN 발화점 119,808 헤드룸 3,679 B
            실측 성장 +1,483 B / 커밋        → 2~3 커밋 뒤 WARN
```

→ **역할을 분리한다.**

**(a) root = 절대 예산** (초과 `exit 1`, ≥90% WARN)

| 대상 | 현재 B | 착지 | 예산 | 착지 사용률 | 근거 |
|---|---:|---:|---:|---:|---|
| `CLAUDE.md` | 54,719 | ~41,106 | 51,200 (50 KiB) | **80%** | 확립된 임계값. 목적에서 파생된 상한(매 프롬프트 로드 비용)이고, §4가 손댈 수 있게 허용하는 유일한 파일 |
| root 상태줄(단일 라인) | 5,028 | ~980 | 1,229 (1.2 KiB) | 80% | 구조 분리의 강제점 |

(리뷰 N1: 41,106/51,200 = 80.3%다. 초안의 "82%"는 `41.0 K`를 10진으로 읽어야 나오는 값이었다.)

**(b) 도메인 CLAUDE.md = 성장 래칫** (절대 상한 없음, WARN만, `exit 0`)

스크립트에 **커밋된 baseline**(머지 시점 바이트)을 두고, `현재 − baseline > 10 KiB`면 WARN한다. 절대 크기가 아니라 **성장 속도**를 재므로 현재치를 뒤따라갈 수 없고, baseline을 올리려면 **커밋 diff에 드러나** 리뷰어 눈에 걸린다.

| `deploy/CLAUDE.md` | 8,594 | 18,834 |
| `desktop/CLAUDE.md` | 8,101 | 18,341 |

**10 KiB의 근거**(리뷰가 요구한 "쓰여진 도출 규칙"): 실측 성장은 controller ~750 B/커밋, ui ~1,483 B/커밋이므로 10 KiB ≈ 7–14 커밋 = 대략 한 분기. root도 같은 주기다(`(46,080−41,106)/709 ≈ 7` 슬라이스 후 WARN) — 두 메커니즘이 한 박자로 움직인다.

**baseline 인상은 기계적으로 막는다** (R18 — 리뷰 3차 Q2). "파일을 실제로 압축했을 때만 재설정한다"를 산문으로만 두면 방어선이 리뷰어의 눈뿐인데, 래칫 WARN은 `exit 0`이라 **거짓 baseline은 green을 낸다** — §3.2가 `min_gain=0`에서 막 고친 "green을 증명으로 오독" 함정과 같은 구조다. 그래서 `baseline↑ ⇒ 그 파일 바이트 감소`를 `check-doc-coverage.sh <base-ref>`에서 검사하고 위반 시 `exit 1`. 이 비대칭(성장=경고, 거짓 보고=오류)을 `root-doc-maintenance.md`에도 적는다.

이 구조에서는 "도입 시점 WARN 0건"이 요구가 아니라 **결과**다(성장 0 = WARN 0). R5의 순환이 해소된다.

`MEMORY.md`는 레포 밖(`~/.claude/projects/…`)이라 예산·래칫·L1 전부에서 제외 — 자체 `/curate-memory` 스킬과 24 KB 한도를 이미 갖고 있다. 이 사실을 `root-doc-maintenance.md`에 명시한다.

R1의 합격선(42 KiB)과 root 예산(50 KiB)이 다른 것은 의도적이다: 42는 *이번 슬라이스의 수용 기준*, 50은 *상시 게이트*다.

### 3.4 구조 분리

**상태줄 3부 구조** (`**상태:` 시작 유지 — R4):
1. 현재 단계 한 마디(MVP1 + post-MVP1 영역 요약)
2. `최신 = <slug> (<날짜>, 머지 <sha>) — 상세는 docs/build-log.md`
3. 포인터 꼬리(build-log / roadmap-status / roadmap / ADR / specs / plans)

기능 카탈로그는 build-log가 단일 소스이므로 root에서 제거한다. 1.2 KiB 예산이 이 구조를 기계적으로 강제한다.

**`docs/dev/root-doc-maintenance.md` 신설** — 다섯 가지:
1. splice 함정 4건(Python 스플라이스 필요성 / imbalance-vs-HEAD 검증 / 앵커 구분자 char-identity / end_anchor 꼬리 오염)
2. 예산표와 근거(§3.3) + 두 스크립트 사용법 + manifest 작성법 + **baseline 재설정 규칙**("파일을 실제로 압축했을 때만 재설정, 인상은 커밋 diff로 드러난다")
3. **이관 판단 기준**: ① 완료 기록 → 안전 ② 명확한 활동 트리거가 있는 함정 → 안전 ③ 편집-트리거 함정 → 인라인 유지(Move D 거절 선례)
4. 재분배 절차(manifest → 이관 → 축약 → `just doc-coverage` → `just doc-budget`)
5. **ADR 상태 갱신 규칙**(R14 재발 방지, 신설 규약): 결정이 구현되면 **ADR 파일**을 갱신한다 — 구현 상태를 root 인덱스 줄에 덧붙이지 않는다(그렇게 쌓인 것이 §1.6의 0039·0044 모순이다). 갱신 위치는 변경의 범위로 갈린다:
   - **문서 전체**의 상태 변화(대체·완결) → **헤더 Status만**. 레포 선례: `0040`(접근 1 → ADR-0042로 대체, 본문 무수정), `0027`(A3a+b+c 머지 완결). 헤더는 결정 전체를 가리키므로 본문이 현재형으로 오독될 여지가 없다
   - **절 단위** 변화(결정은 유효한데 연기 항목 하나가 나중에 출하됨 — 0044형) → **헤더 + 해당 문장 인라인 주석**. 헤더 한 줄은 *어느 절*을 고치는지 말할 수 없어서, 헤더에 "슬라이스 3 완료"를 쓰고 본문에 "슬라이스 3 연기"를 남기면 §Decision이 틀린 답을 준다
   - **본문 문장은 다시 쓰지 않는다** — ADR 본문은 결정 시점의 기록이다. 다시 쓰면 ADR이 자기 결정을 오보하게 되어 거짓을 다른 거짓으로 바꾸는 셈이다. (`docs/adr/`에 인라인 주석 선례는 아직 없다 — 이 규약이 그 선례를 만든다)

3번이 이 파일의 두 번째 목적이다 — 지금 이 기준은 레포 밖 메모리 파일에만 있어서, 그 메모리를 회상하지 못한 세션은 기준 없이 재분배한다.

### 3.5 회귀 테스트 4층

| 층 | 겨누는 실패 | 수단 | 수명 |
|---|---|---|---|
| L1 | 포인터·앵커 파손(옮겼는데 못 찾음) | `check-doc-budget.sh` 내장(R9) | 영구 |
| L2 | 지식 소실(옮겼다고 적었지만 실은 안 옮김) | `check-doc-coverage.sh`: manifest 목적지-지향(1차, `kind=merge`는 `absorbed_marker`로 검증) + **불릿 개수 비감소 R17**(2차, 미선언 삭제) + 토큰 차분(3차) | 영구 |
| L2′ | **거짓 보고**(게이트 기준선을 실제 압축 없이 올림) | `check-doc-coverage.sh`의 R18 — L2와 겨누는 실패가 다르므로 분리 | 영구 |
| L3 | 게이트 자체가 공허(항상 통과) | **두 스크립트 모두** 고의 회귀→RED→원복→GREEN (R11) | 1회, build-log 기록 |
| L4 | 불변식 미검증(파일은 맞지만 소비자가 못 찾음) | fresh subagent 회상 프로브 + 양성 대조 (R12) | 1회, build-log 기록 |

**L4 프로토콜**: 컨텍스트 없는 fresh subagent(`Explore` 타입 충분)에게 제거된 지식을 묻고, repo만 보고 근거 경로와 함께 답하는지 본다. 프로브 ≥4문항 + **양성 대조 1문항**(레포에 존재하지 않는 사실 — "모름"이 나와야 프로브가 유효함이 증명된다). 대조가 통과해버리면 프로브 설계가 잘못된 것이므로 프로브를 고쳐 다시 돌린다. **프로브 1문항은 US4를 겨눈다**(리뷰 C6): "root CLAUDE.md가 다시 커졌을 때 무엇을 어디로 옮겨야 하나?" → `docs/dev/root-doc-maintenance.md`의 3분류에 도달해야 한다.

**L2가 못 보는 것**: 토큰은 남기고 *의미*를 버리는 압축(요약하다 뉘앙스 소실)은 manifest도 토큰 검사도 잡지 못한다. 이 한계는 최종 리뷰(base 대비 규칙 줄 단위 대조)에 위임한다.

## 4. 비목표

- `MEMORY.md` 재구성 — 별도 스킬·한도 보유. 예산·L1 검사 대상도 아님
- 도메인 CLAUDE.md(ui 116 KB 등) **내용** 압축 — 래칫 baseline 등록만 한다(§3.3b)
- 로컬 dev 실행 함정·검증 자동화 섹션 이동 — 편집/실행 트리거 함정이라 Move D 거절 선례와 같은 클래스(§5 예비 레버로만, 그것도 사용자 확인 후)
- **ADR 파일 전면 수정** — 단 **R14가 요구하는 범위는 안에 있다**: `0039` 헤더 Status(3요소 페이로드) + `0044` 헤더 및 **본문 `:19`·`:29` 인라인 주석**. "상태 한 줄"이 아니라 R14가 명시한 편집 전부다(리뷰 3차 N6 — 좁게 쓴 예외 문구가 R14를 구현 불가로 만들고 있었다. C2: 초안의 "ADR 파일 수정 금지"는 no-forget 불변식과 정면 충돌했다)
- pre-commit 훅 편입 — 함정 한 줄 추가가 커밋을 막는 마찰을 피한다(사용자 선택)
- 새 절대 임계값 정책 발명 — root만 확립된 50 KiB를 그대로 쓰고, 도메인 파일은 절대 상한 없이 성장 래칫만 둔다(§3.3b)

## 9. 열린 질문

없음. 사용자 확정 4건(범위=압축+재비대 방지 / 강제력=기계적 측정+구조 분리, pre-commit 차단 기각 / 목표 ~42–45 KB / US1 합격선 42 KiB) + 리뷰 1–4차 must-fix 18건·nice-to-have 18건 전건 반영(기각 0, N9는 측정 방식 병기).

**설계 리뷰에서 반복 관찰된 결함 클래스**(구현·최종 리뷰가 같은 눈으로 봐야 할 것): *선언된 예외를 아무도 검증하지 않는다.* 네 번 나왔다 — `min_gain=0`의 marker가 작업 전부터 참 / 래칫 WARN이 `exit 0`이라 거짓 baseline이 green / `kind=merge`가 바닥만 낮추고 병합 여부 미검증 / R18이 신규 행을 인상으로 오해. 새 예외를 만들 때마다 "그 예외 선언 자체는 무엇이 검증하나"를 물어야 한다.
