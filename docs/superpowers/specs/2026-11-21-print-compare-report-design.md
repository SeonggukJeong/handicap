## 사용자 스토리 (US)

- **US1**: QA가 같은 시나리오의 종료된 run 둘을 "고치기 전후"로 넘길 때, 비교 화면에서 비교 보고서를 A4로 출력해 — 1쪽 맨 위에서 나아졌는지의 답(개선 / 악화 / 엇갈림 / 비슷)과 판정 변화(예: ✕ 부적합 → ● 적합), 핵심 지표별 이전 → 이후 값·변화율·좋아짐/비슷/나빠짐을 본다. 먼저 잰 run이 항상 "이전"이고, run을 3개 이상 골랐으면 인쇄 화면에서 짝을 고른다. 쪽 경계를 넘거나 잘리는 내용이 없고, 흑백으로 출력해도 기호와 글자로 좋아짐/나빠짐이 구분된다.
- **US2**: 운영자가 고친 뒤 어느 단계가 얼마나 달라졌고 무엇이 아직 남았는지 볼 때 — 단계별 95% 응답시간 변화 그림, 단계 × 응답 코드별 "2,880 → 0" 표, 시간에 따른 변화 겹쳐 보기, 응답 속도 구간 비교를 본다. 그림과 표에는 단계마다 이전 → 이후 값과 좋아짐/비슷/나빠짐이 찍혀 있고, 겹쳐 보기와 속도 구간은 두 측정을 나란히 보여 준다. 「남은 문제」 상자에서 이후에도 줄지 않은 오류(단계와 코드)와 여전히 ✕/▲인 단계를 본다.
- **US3**: QA가 조건이 다른 두 run을 비교하게 됐을 때 — 보고서가 부하 조건·환경 변수·시나리오 내용·판정 기준 중 다른 항목을 1쪽에서 ▲로 짚고 비교 결과 상자에 "조건이 달라 참고용"이라고 밝혀, 받는 사람이 불공정한 비교를 개선으로 오해하지 않는다. 한쪽에만 응답 코드 검사가 있어 오류율을 그대로 비교할 수 없는 단계도 표에 표시된다. 서로 다른 시나리오의 run이면 보고서를 만들지 않고 이유를 알려 준다.
- **US4**: QA가 행정 부서에 돌릴 한 장만 필요할 때 요약판을 골라 — 비교 결과, 공정 비교 점검, 핵심 지표 표, 남은 문제(위에서부터 몇 개)가 담긴 A4 1장을 얻는다. 단계나 남은 문제가 많아도 1장을 지킨다.

## 1. 의도와 이유

슬라이스 1의 목적은 "설명 없이 스스로 읽히는 결과물"이었다. 측정 한 번의 결과는 넘길 수 있게 됐지만, QA가 실제로 자주 받는 질문은 "고친 뒤 나아졌나"다. 지금 비교 화면(`/scenarios/:id/compare`)은 숫자 표와 Δ%라서 받는 사람에게 설명이 필요하고 인쇄도 안 된다. 이 슬라이스는 run 둘의 비교를 측정 보고서와 같은 품질의 A4 문서로 만든다.

사용자가 정한 방향: run이 3개 이상인 비교는 **나중에 별도 문서**(추이 보고서)로 만든다. 이번 설계는 그때 재사용할 수 있게 한다(§4, §11).

## 2. 목표 / 비목표 / 안티목표

**목표**
- 비교 보고서 표준판(여러 쪽)·요약판(1장)을 A4 세로 미리보기 + 브라우저 인쇄/PDF.
- 변화 판정(좋아짐/비슷/나빠짐)과 종합 답, 공정 비교 점검, 남은 문제를 데이터에서 결정론적으로 생성.
- 쪽 나누기 틀을 측정 보고서와 공용으로 분리(측정 보고서의 출력은 그대로).

**비목표** (roadmap §B에 연기로 기록)
- run 3개 이상을 한 문서에 담는 추이 보고서.
- 이전/이후 순서를 손으로 뒤집기.
- 계단 시험(`stair`) run의 계단별 비교, 조건 반복(`loop_exits`·`loop_split`) 비교, 단계별 응답 속도 구간 비교(전체 요청 한 줄만 한다).
- 화면 비교(`ScenarioComparePage`의 표·차트)·비교 CSV/XLSX의 변경. `compareReports.ts`·`export.rs` 무변경(골든 패리티 계약).
- 가림 정책 변경(§B43 (1) 둘째 항목), 섹션·문구 편집, 팀 공유 저장.
- 컨트롤러·엔진·proto·migration 변경(UI만).

**안티목표 (돌아가도 실패)**
- 조건이 다른 비교가 조건이 같은 비교와 똑같은 "개선"으로 찍힌다.
- "이전"이 실제로는 나중에 잰 run이다.
- 한쪽에서 오류로 세지 않은 응답 때문에 오류율이 낮아 보이는 것을 "좋아짐"이라고 단정한다.
- 미리보기와 실제 출력의 쪽 수·잘림이 다르다.
- 색만으로 좋아짐/나빠짐을 구분한다.
- 환경 변수 **값**·데이터셋 값·헤더·본문이 찍힌다.
- 틀 분리 뒤 측정 보고서(`/runs/:id/print`)의 쪽 수·배치가 달라진다.

## 3. 사용자가 정한 것 (2026-11-21, 다시 묻지 않는다)

1. 보고서는 항상 run 2개 비교. 3개 이상 골랐으면 인쇄 화면에서 짝을 고른다.
2. 낱말은 "이전/이후", 순서는 **측정 시각**(먼저 잰 run = 이전). "기준/비교"는 판정 기준과 낱말이 겹쳐 기각. 문서 머리 두 상자에 run 라벨·`#끝6자`·일시·판정을 함께 찍어 어느 측정인지 확인할 수 있게 한다.
3. 3개 이상 비교는 필요할 때 별도 문서로 만들되, 이번 구현이 그 가능성을 염두에 둔다.
4. 구현 방식 A — 쪽 나누기 틀을 떼어 공용으로(§4).
5. US 네 줄과 거기 넣은 판단 셋("엇갈림" 추가 · 조건이 달라도 경고만 하고 만든다 · 요약판 구성) — 이견 없음. 그 밖의 세부는 진행하며 판단(§12에 고지 목록).

## 4. 접근 (검토한 길)

| 길 | 내용 | 버린/고른 이유 |
|---|---|---|
| **A. 틀을 떼어 공용으로 (채택)** | 높이 재기 → 쪽 배치 → 쪽 그리기를 문서 종류와 무관한 틀로 분리. 측정·비교 보고서는 "블록 목록 + 블록 그리는 법"만 넘긴다 | 쪽 나누기 규칙이 한 곳. 추이 보고서도 블록만 얹는다. 비용: 출하된 측정 보고서를 건드리므로 회귀 확인 필요 |
| B. 틀을 복사 | 비교용 문서 컴포넌트에 재기·배치 로직 복사 | 같은 로직 두 벌(추이 때 세 벌), 쪽 넘침 수정이 따로 논다 |
| C. `PrintDoc`에 비교 갈래 추가 | 기존 모델·분기에 끼워 넣기 | 측정용·비교용 필드가 한 타입에 섞여 서로 깨뜨린다 |

내용 계산은 두 층이다.
- **run별 측정 모델**: 기존 순수 함수(`readScenarioFacts`·`buildStepTable`·`stepStatus`·`verdictBox`·`matchVerdict`·`expandCriteria`)를 run마다 **자기 `scenario_yaml`·자기 `profile.criteria`**로 부른다.
- **쌍 계산**(`ui/src/print/compare/`, 신규): 두 run의 측정 모델을 받아 변화 판정·공정 비교·남은 문제·표/그림 모델을 내는 순수 함수. 입력은 `(before, after)` 한 쌍뿐이라 추이 보고서가 이웃한 쌍마다 다시 부를 수 있다.

## 5. 진입점과 화면

- `ScenarioComparePage` 머리(내보내기 버튼 옆)에 [비교 보고서 인쇄] 링크 → `/scenarios/:id/compare/print?runs=<ids>&baseline=<id>`(현재 주소의 `runs`·`baseline`을 그대로 넘김).
- 경로는 `routes.tsx`에서 **`Layout` 밖** 최상위(`/runs/:id/print` 선례).
- 주소 파라미터: `runs`(쉼표, 선택한 run 전체 — 추이 보고서가 같은 진입점을 쓸 수 있게 보존) · `pair`(쉼표로 run id 2개, 선택) · `kind=standard|summary`(기본 standard) · `baseline`(선택).
- **run 목록이 먼저다**: 화면은 `useScenarioRuns(:id)`(그 시나리오의 run 목록 — `RunSchema`에 `status`·`label`·`message`·`started_at`·`created_at`)를 먼저 읽고, `runs`의 각 id를 그 목록에서 찾는다. 짝 정하기·선택 칸 표시·terminal 확인·`message`는 전부 이 목록에서 온다(`ReportRunSchema`에는 `message`가 없다).
- **짝 정하기**: `pair`가 있고 두 id가 서로 다르며 둘 다 `runs`에 있으면 그 둘. 아니면 기본값 = `runs`가 2개면 그 둘, 3개 이상이면 `baseline`(없거나 `runs`에 없으면 측정 시각이 가장 이른 run)과 **나머지 중 측정 시각이 가장 늦은 run**.
- **이전/이후**: 짝 안에서 측정 시각 키 `(started_at ?? created_at, created_at, id)` 오름차순으로 앞이 이전. 사용자가 고른 순서·`baseline`은 순서에 영향이 없다.
- 도구 줄(인쇄 시 숨김): [표준판 | 요약판] · [인쇄 / PDF 저장] · [돌아가기](비교 화면, `runs`·`baseline` 유지) · 주소 안내 + [주소 복사](`RunPrintPage`와 같은 규칙) · `runs`가 3개 이상이면 **「비교할 측정」 선택 칸 두 개**(각 run의 표시 이름 = 라벨 또는 `#끝6자` + 측정 일시; 같은 run을 둘 다 고를 수 없음; 바꾸면 `pair` 갱신) · 요약판 축소 안내(§10).
- 만들지 않는 경우(보고서 대신 안내 + 돌아가기):
  - `runs`가 2개 미만 → "비교하려면 측정을 2개 이상 고르세요".
  - run 목록·리포트 fetch 실패 → `role="alert"`에 사유. 로딩 → `role="status"`.
  - `runs`의 id 중 하나라도 이 시나리오의 run 목록에 없음 → "이 시나리오의 측정이 아니거나 없는 측정이 있어 비교 보고서를 만들 수 없습니다"(슬라이스 1 §14 이월: 비교 화면은 이를 검사하지 않는다). 리포트는 요청하지 않는다.
  - 짝 중 하나라도 terminal(`completed`/`failed`/`aborted`)이 아님 → "측정이 끝난 뒤 출력할 수 있습니다". **리포트는 요청하지 않는다** — `/report`는 서버에 terminal 검사가 없고 `useReports`·`useRunReport`가 같은 캐시 키(`queryKeys.runReport`)에 `staleTime: Infinity`로 넣으므로, 실행 중 run의 리포트를 받으면 덜 된 리포트가 run 상세 화면에까지 남는다.
- 데이터: `useScenarioRuns(:id)` → (위 검사를 통과한 뒤에만) `useReports([이전 id, 이후 id])` + `useScenario(:id)`(제목 폴백). 새 API·필드 없음.

## 6. 변화 판정 (인쇄 전용 순수 함수)

`compareReports.ts`의 `computeDelta`는 쓰지 않는다(평균·건수를 다루지 않고 "비슷" 구간이 없으며 골든 패리티 계약이라 확장 금지). 변화율 식 `(after − before) / before`만 같다.

### 6.1 지표와 방향

| 지표 | 값 | 방향 | 주요 지표 |
|---|---|---|---|
| 오류율 | `count==0 ? 0 : errors/count` | 낮을수록 좋음 | ○ |
| 99% 응답시간 | `summary.p99_ms` | 낮을수록 좋음 | ○ |
| 95% 응답시간 | `summary.p95_ms` | 낮을수록 좋음 | ○ |
| 평균 응답시간 | `summary.mean_ms` | 낮을수록 좋음 | ○ |
| 처리량 | `summary.rps` | 높을수록 좋음 | ○ |
| 전체 요청 수 | `summary.count` | 중립(좋고 나쁨 없음) | ✕ |

### 6.2 한 지표의 분류 `classifyChange(direction, before, after, floor)`

1. `before == after` → **비슷**.
2. `|after − before| < floor` → **비슷**. floor: 오류율 0.0005(0.05%p) · 응답시간 5ms · 처리량·건수 0. (아주 작은 값에서 상대 변화율만 커지는 것을 막는다: 오류율 0.01% → 0.02%는 +100%지만 비슷.)
3. `before > 0`이고 `|after − before| / before ≤ 0.05` → **비슷**.
4. 그 밖: 방향에 따라 **좋아짐/나빠짐**, 중립 지표는 **늘어남/줄어듦**(좋고 나쁨 낱말·색 없음).
- 변화율 표시: `before > 0`이면 `round(|after − before| / before × 100)`% + 지표별 낱말(응답시간 "단축/증가", 오류율·건수 "감소/증가", 처리량 "증가/감소"). `before == 0 ∧ after > 0`이면 % 없이 "새로 생김"(∞% 금지). 0%로 반올림되는데 분류가 비슷이 아니면 "1% 미만".
- 값 표시는 슬라이스 1 §5.3 함수(`fmtMs`·`fmtPct`·`fmtRps`·`fmtCount`). **두 값이 같은 글자로 찍히는데 분류가 비슷이 아니면**(예: 1,060ms → 1,140ms가 둘 다 "1.1초") 그 행의 두 값만 자릿수를 늘린다: 응답시간은 ms 정수(`fmtMsExact`), 오류율과 처리량은 두 글자가 달라질 때까지 소수 자릿수를 하나씩 늘린다(최대 6자리). 같은 숫자 옆에 "나빠짐"이 찍히지 않게 하는 것이 목적이다(print-speed-bands와 같은 원칙). 판정 쌍 함수(`fmt*Pair`)는 기준값과의 쌍 전용이라 쓰지 않는다.
- **오류율 "참고용"**: 어느 단계든 `*`(§9.2 — 두 측정에서 오류로 세는 방식이 다른 칸)가 있으면 run 전체 오류율 행의 분류 칸은 좋아짐/나빠짐 대신 **"참고용"**이고, §6.3 신호에서 뺀다(좋아짐·비슷·나빠짐 어느 개수에도 세지 않고, 상자 둘째 줄은 "주요 지표 4개 중 …"이 된다). 요약 문장 2·3번 줄의 후보에서도 뺀다. 한쪽에서 세지 않은 응답 때문에 오류율이 낮아 보이는 것을 개선으로 치지 않는다.

### 6.3 종합 답 (비교 결과 상자)

신호 = 주요 지표의 분류("참고용"인 오류율은 제외 — §6.2) + **판정 변화**(둘 다 판정 상자가 적합/부적합이고 **판정 기준 카드가 ● 같음일 때만**: 부적합 → 적합 = 좋음, 적합 → 부적합 = 나쁨, 그 밖 = 없음; 판정 상자는 슬라이스 1 `verdictBox` 5상태를 run별로 그대로). 기준이 다르면 판정 변화는 기준을 바꿔서 생긴 것일 수 있으므로 신호로 치지 않는다(요약 문장 1번 줄에는 그대로 적는다).

| 조건 | 답 | 기호 |
|---|---|---|
| 둘 중 하나라도 `summary.count == 0` | **비교 불가** ("요청이 실행되지 않은 측정이 있어 비교하지 않았습니다") | – |
| 좋음 ≥ 1 ∧ 나쁨 = 0 | **개선** | ▼ |
| 나쁨 ≥ 1 ∧ 좋음 = 0 | **악화** | ▲ |
| 좋음 ≥ 1 ∧ 나쁨 ≥ 1 | **엇갈림** | ◆ |
| 모두 비슷·없음 | **비슷** | = |

- 상자 둘째 줄: "주요 지표 T개 중 N개 좋아짐 · M개 비슷 · K개 나빠짐" — T는 5, 오류율이 "참고용"이면 4(N + M + K = T). (0인 항목도 "0개 나빠짐"처럼 찍는다 — 시안). 판정 변화가 신호로 쓰였으면 뒤에 " · 판정 ✕ → ●"(또는 "● → ✕")를 붙인다 — 지표가 모두 비슷인데 답이 "악화"인 경우에도 이유가 상자 안에 보이게.
- 공정 비교(§7)에 ▲가 하나라도 있으면 상자에 **"조건이 달라 참고용"** 줄을 붙이고 상자 색을 회색 계열로 바꾼다(개선의 파랑·악화의 빨강을 쓰지 않는다). 답 낱말은 그대로 둔다.
- 비교 불가면 지표 표·그림은 그대로 값만 찍고 분류 칸은 "–".

### 6.4 요약 문장 (최대 4줄, 순서 고정, 해당 없는 줄 생략, "(자동 작성)")

1. **판정**: 두 run의 판정 상자 낱말 — 바뀌었으면 "판정이 ✕ 부적합 → ● 적합으로 바뀌었습니다.", 같으면 "판정은 두 측정 모두 ● 적합입니다." 이후가 적합이면 "기준 N개를 모두 지켰습니다."(N = 이후 run이 평가한 기준 수)를 잇는다. 한쪽이라도 기준 미설정·판정 안 함·평가 불가면 그 낱말 그대로("이전: 기준 미설정, 이후: ● 적합").
2. **가장 크게 달라진 것**: 종합 답의 방향(개선이면 좋아짐, 악화면 나빠짐, 엇갈림이면 좋아짐)에 속한 주요 지표 중 순위가 가장 높은 것 1개 — "오류율 2.6% → 0.3% (88% 감소)." 그 방향의 지표가 없으면(답이 비슷이거나, 개선·악화가 판정 변화만으로 정해진 경우) 이 줄은 생략한다. 순위: "새로 생김"(이전 0)이 맨 위, 그다음 변화율 큰 순, 동률은 §6.1 표 순서. 그 지표가 오류율이면, 건수 차이(|이전 − 이후|)가 가장 큰 (단계, 코드)를 잇는다 — 이후 0건: "'<단계>'의 <코드> <풀이> N건이 0건이 되었습니다." / 줄었음: "… N건이 M건으로 줄었습니다." / 늘었음: "… N건이 M건으로 늘었습니다." / 이전 0건: "… M건이 새로 생겼습니다."
3. **반대 방향**(엇갈림일 때만): 나빠짐 지표 중 같은 순위 규칙으로 1개 — "반면 95% 응답시간은 1.6초 → 2.4초로 늘었습니다." 나빠짐 지표가 없으면(나쁨이 판정 변화뿐) 생략한다.
4. **조건**: 공정 비교 ▲가 있으면 "두 측정의 <항목>(이)가 달라 이 비교는 참고용입니다."(항목 여러 개면 앞 2개 + "외 N개").
- 비교 불가면 1번 줄 대신 "요청이 실행되지 않은 측정이 있어 비교하지 않았습니다." + 그 run의 `message`(run 목록에서)가 있으면 사유(슬라이스 1과 같은 sink). 요약판에서는 이 사유를 1줄로 자른다(말줄임 — §10의 1장 보장).
- 모든 문장·낱말은 `ko.ts`(ADR-0035), 조사 병기형. 보고서 문체(working-rules §8).

## 7. 공정 비교 점검 (1쪽 카드 4장 + 2쪽 대조 표)

카드마다 `● 같음` 또는 `▲ 다름` + 한 줄. 값은 두 run의 `report.run.profile`(`ProfileSchema.safeParse` — 실패하면 그 카드 "▲ 설정을 읽을 수 없음")·`report.run.env`·`scenario_yaml`에서.

| 카드 | 같음 조건 | 다름일 때 한 줄 |
|---|---|---|
| **부하 조건** | `ProfileSchema.safeParse` 결과(기본값이 채워진 **유효 값**)에서 `criteria`·`think_seed`를 뺀 나머지 **전체**가 깊은 비교로 같음(`null`과 키 없음은 같은 것으로 본다; 옛 단일 `data_binding`과 `data_bindings`는 `seedBindingsFrom`으로 한 배열로 맞추고 원래의 두 키는 비교에서 뺀다) + 워커 수(슬라이스 1 §5.4 규칙)가 같음 | 이름 붙은 항목 중 다른 것 앞 2개 + "외 N개" (예: "동시 사용자 · 기간 다름"). 이름 붙은 항목: 부하 모델 · 크기(VU / RPS / 곡선) · 기간 · 시작 늘림 · 단계 사이 쉼 · 요청 제한 시간 · 연결 제한 시간 · 동시 요청 상한(`max_in_flight`) · 워커 수 · 데이터 연결 · 계단 시험 설정. 그 밖의 필드가 다르면 "그 밖의 설정" 한 항목 |
| **환경 변수** | 키 집합이 같고 키마다 값이 같음 | "N개 다름: `BASE_URL`, `TIMEOUT` 외 2개" — **키 이름만**, 값은 어디에도 찍지 않는다 |
| **시나리오 내용** | 두 `scenario_yaml`을 `yaml`로 읽은 일반 객체에서 **시나리오 최상위의 `name`·`notes`와 각 단계 객체(`steps`·`do`·`then`·`elif[].then`·`else`·`branches[].steps`의 원소)의 `name`·`notes`만 지운 뒤 깊은 비교로 같음**(주석은 파싱에서 사라진다). 그 밖의 `name`(본문 JSON의 필드, 값 꺼내기의 변수 이름, 병렬 분기 이름 등)은 지우지 않는다 — 부하나 동작을 바꾸는 값이다. 쉬는 시간·반복 횟수·조건·헤더·본문·단계 구조가 전부 비교에 들어간다(메모리 안에서만, 찍지 않는다) | 먼저 `StepFacts`로 설명할 수 있는 차이를 센다 — 단계 추가/삭제/순서 바뀜 · 요청(방식·주소) 바뀜 · 응답 코드 검사 추가/제거/바뀜 · 값 꺼내기 추가/제거 → "N곳 다름: ④에 응답 코드 검사 추가됨"(앞 1개 + "외 N곳"). 그런 차이가 없는데 깊은 비교가 다르면 "그 밖의 설정 다름(쉬는 시간·반복·조건·헤더·본문 등)" |
| **판정 기준** | `expandCriteria` 결과를 키 `(metric, target, op)`의 집합으로 보고, 키 집합과 키별 기준값이 같음(순서 무시, 둘 다 없음 포함) | "기준 N개 다름"(N = 한쪽에만 있는 키 수 + 값이 다른 키 수) / "한쪽만 기준 있음" |

- 카드 아래 한 줄(해당 시, run마다): `aborted`면 "▲ <이전|이후> 측정은 도중에 중단되었습니다(4분 12초까지 측정)", `failed`면 "▲ <이전|이후> 측정은 실패로 끝났습니다" — 이것도 ▲로 센다(§6.3 "참고용").
- 시나리오를 YAML로 읽지 못하면(한쪽이라도) 시나리오 카드 = "▲ 시나리오를 읽지 못해 확인하지 못함".
- `StepFacts`(`scenarioFacts.ts`)에는 이미 `id`·`method`·`url`(원형)·`statusCodes`·`fallibleExtract`가 있고 배열 순서가 시나리오 순서다. 그 파일은 고치지 않는다.
- 계단 시험(`stair`) run도 비교한다. 계단 설정이 다르면 부하 조건 ▲. 계단별 표는 넣지 않는다(비목표).
- **측정 조건 대조 표**(표준판): 열 = 항목 · 이전 · 이후. 행 = 위 "이름 붙은 항목" 전부(값 문구는 슬라이스 1 `conditionsBox`에 있는 것은 그 문구, 없는 것 — 연결 제한 시간·동시 요청 상한·데이터 연결 내용·계단 설정 — 은 이 슬라이스에서 한 줄 문구를 더한다) + 환경 변수 개수 + 판정 기준 개수 + 시나리오 차이(있을 때 종류별 한 행) + "그 밖의 설정"(다를 때만, 값 대신 "다름"). 다른 행은 ▲ + 굵게. 양쪽 다 없는 선택 항목(시작 늘림 등) 행은 생략.

## 9. 절별 규칙

### 9.1 단계별 95% 응답시간 변화 (덤벨)

- 행 = 단계. 두 run의 단계를 **단계 id로 맞춘다**. 순서 = 이후 run의 시나리오 순서(`buildStepTable` 행 순서), 그 뒤에 이전 run에만 있는 단계. 번호는 이후 run 기준 ①–⑳·"21."(이전에만 있는 단계는 번호 없이 이름 뒤 "(이후 측정에 없음)", 이후에만 있으면 "(이전 측정에 없음)"). 한쪽에만 있거나 한쪽이 실행 0회면 그 점만 찍고 화살표·분류 없음.
- 한 행 = 이름 칸(최대 2줄 줄바꿈, 넘으면 말줄임) · 그림 칸(이전 점 회색 ○, 이후 점 ●, 사이 화살표) · 글자 칸("2.1초 → 1.5초 (−29%)").
- 분류는 §6.2(`floor` 5ms, 방향 = 낮을수록 좋음). 색·모양: 좋아짐 = 파랑 화살표(왼쪽), 나빠짐 = 빨강 화살표(오른쪽), 비슷 = 회색 점 둘 + 글자 "= 비슷". **흑백 생존**: 글자 칸에 항상 부호 붙은 %와 낱말(빨라짐/느려짐/비슷)이 있다.
- 간격이 좁으면(두 점 사이 < 점 지름 + 12 단위) 선 대신 이후 점 **진행 방향 바깥**에 작은 삼각형. 삼각형·점이 이름 칸을 침범하지 않게 그림 칸 왼쪽 여백을 점 반지름 + 삼각형 크기 이상으로 둔다.
- 축: 0부터 두 run 전 단계 p95 최댓값을 덮는 1·2·5×10ⁿ 눈금(≤ 6칸). 최댓값이 1초 미만이면 ms 눈금("200ms"). `before == 0`(서브 ms)이면 % 없이 "1ms 미만 → 12ms".
- 기준선: 두 run의 run-level `max_p95_ms`가 **같은 값**이고 **어느 run에도 단계별 `p95_ms` 기준이 없을 때만** 점선 + "기준 3초". 그 경우 글자 칸에 이전 > 기준 ≥ 이후면 "기준 안으로", 이전 ≤ 기준 < 이후면 "기준 초과"를 덧붙인다. 그 밖에는 선·문구 없음(단계 기준이 따로 있으면 그 단계의 ✕/▲와 선이 어긋날 수 있다).
- 구현: 쪽을 넘기려면 그림이 행마다 따로여야 한다 — 행 하나 = SVG 하나(같은 x 눈금 공유), 머리줄 = 눈금 축 SVG. 시안의 통짜 SVG를 그대로 옮기는 일이 아니다(계획에서 별도 작업).
- 범례 1줄: "○ 이전 · ● 이후 · ┊ 기준 · 화살표 왼쪽 = 빨라짐, 오른쪽 = 느려짐".
- 시안 「화살표 방향 점검」의 6사례(같음 · 비슷 4% · 조금 빨라짐 · 조금 느려짐 · 많이 느려짐 · 많이 빨라짐)를 순수 모델 함수의 단위 테스트 표로 쓴다.

### 9.2 단계별 오류 변화 표

- 열: 단계 · 오류율(이전 → 이후) · 응답 코드별 건수(이전 → 이후) 열들 · 변화.
- **코드 열** = 두 run 중 한쪽이라도, 어느 단계에서든 분류가 `counted`·`uncounted`·`unknown`인 칸(슬라이스 1 §6.1 — run별로 자기 시나리오 사실로 분류)이 있는 코드 + "응답 없음"(코드 0) + "보내지 않음"(`not_sent`) + "응답 받은 뒤 실패"(잔차) — 각각 양쪽 합이 > 0일 때만. 정렬은 슬라이스 1 §6.2. **상한 5열**: "응답 없음"·"보내지 않음"·"응답 받은 뒤 실패"는 있으면 항상 제 열을 갖고 5에 포함된다(접지 않는다). 남은 자리(최소 1)에 실제 코드를 양쪽 합 건수 큰 순으로 넣고, 코드가 자리보다 많으면 마지막 자리를 "그 밖의 코드" 한 열로 쓴다(각주에 코드 목록과 이전 → 이후 건수). 5는 라이브에서 7자리 건수("1,234,567 → 2,345,678")로 폭을 재서 확정한다 — 넘치면 4로 줄인다.
- 칸 = "2,880 → 0", 양쪽 0이면 "–".
- **`*`(세는 방식이 다른 칸)**: 양쪽에 다 있는 단계에서, 어느 한쪽이라도 건수가 > 0인 코드마다 **두 측정 각각의 시나리오 사실로 `classifyCell(code, 그 run의 사실)`을 부른다 — 그쪽 건수가 0이어도 부른다**(`buildStepTable`의 `perCode`는 건수 > 0인 코드만 담으므로 거기서 읽으면 "600* → 0" 같은 경우를 놓친다). 분류를 "오류로 세는가"로 옮긴다: `counted` = 센다 · `plain`·`expected`·`uncounted` = 안 센다 · `unknown` = 알 수 없음. **두 측정의 이 값이 다르면** 건수가 > 0인 쪽(둘 다면 둘 다) 숫자에 `*`를 붙인다. 예: 이전에는 검사 없이 502가 600건(안 셈), 이후에는 검사가 있고 0건(센다) → "600* → 0". 이전에는 `status: 201` 검사 때문에 200이 전부 오류(센다), 이후에는 검사를 지워 200이 오류가 아님(안 셈) → 양쪽 200 칸에 `*`. 두 측정이 똑같이 세지 않는 칸(`expected` ↔ `uncounted` 포함)은 `*`가 아니다 — 방식이 같으니 비교는 공정하고, 세지 않은 응답은 각 측정 보고서가 경고한다. 한쪽에만 있는 단계에는 `*`가 없다. `*`가 2xx/3xx 코드에 붙으면 그 코드도 코드 열 대상이다.
- 단계 오류율 칸: "27.0% → 0.2%". 그 단계에 `*` 칸이 있는 쪽은 오류율에도 `*`("0%* → 0%").
- 변화 칸: 단계 오류율을 §6.2로 분류(floor 0.0005, 낮을수록 좋음) → "▼ 좋아짐 / = 비슷 / ▲ 나빠짐". `*`가 있는 단계는 분류 낱말 대신 **"참고용"**(오류로 세는 방식이 두 측정에서 달라 단정하지 않는다). 남은 문제(§9.5)에 해당하는 단계는 아래 줄 "남은 문제".
- 행 = §9.1과 같은 단계 맞춤·순서. 오류가 양쪽 다 0인 단계도 한 행("0% → 0%", "= 비슷").
- 각주(해당 시): `*` 설명 — 별이 붙은 쪽의 값에 따라: 안 센다 → "'<단계>'의 <코드> N건은 <이전|이후> 측정에서 오류율에 포함되지 않았습니다(다른 측정에서는 오류로 셉니다). 이 단계의 오류율 비교는 참고용입니다." / 알 수 없음 → "…<이전|이후> 측정에서 오류로 세었는지 확정할 수 없습니다. …" / 센다(상대 쪽이 안 셈) → "…<이전|이후> 측정에서만 오류로 세었습니다. …". 한 칸의 양쪽에 별이 있으면 "안 센다" 쪽 문장 하나만 쓰고, 그런 쪽이 없으면(센다 ↔ 알 수 없음) "알 수 없음" 쪽 문장을 쓴다. 단계 여러 개면 건수 큰 순 2개 + "외 N곳". · "그 밖의 코드" 내역.

### 9.3 시간에 따른 변화 — 겹쳐 보기 (인라인 SVG)

- X축 = 각 run의 시작 기준 경과 시간, 길이는 둘 중 긴 쪽. 묶음 크기는 긴 쪽 기준 슬라이스 1 `pickBinSeconds`(두 run에 같은 묶음).
- 선 2개 = 처리량(건/초): 이전 = 회색 점선, 이후 = 파랑 실선(흑백에서 선 모양으로 구분). 막대 2계열 = 오류(건/초): 이전 = 연한 빨강(빗금), 이후 = 진한 빨강, 묶음마다 나란히. 오류가 양쪽 다 0이면 막대·오른쪽 축 없음 + 범례 "두 측정 모두 오류 없음".
- 축 눈금·크기(180mm × 55mm)는 슬라이스 1 §6.6 함수 재사용.
- "<N분> 지점" = 그 run에서 오류가 처음 0보다 큰 (두 run 공통 크기의) 묶음의 시작 시각, `fmtElapsed` 표기.
- 읽는 법 1줄(결정론): 이전에 오류가 있고 이후 오류 합이 이전의 5% 이하 → "이전에는 <N분> 지점부터 오류가 쌓였지만, 이후에는 거의 없습니다." / 양쪽 다 있음 → "두 측정 모두 오류가 있습니다(이전 <N분>부터, 이후 <M분>부터)." / 이후에만 → "이후 측정에서 <M분> 지점부터 오류가 생겼습니다." / 없음 → "두 측정 모두 오류가 없었습니다. 선은 1초에 처리한 요청 수입니다."
- 기간이 다르면 범례 끝에 "(측정 시간이 다릅니다: 이전 10분, 이후 5분)".

### 9.4 응답 속도 구간 비교 (전체 요청)

- 두 줄(이전·이후), 각 줄 = `speed_bands.overall`의 구간 막대 + 구간별 % 숫자 칸 + **막대 밖 실패 칸**(print-speed-bands의 원칙·색·빗금 그대로: 막대는 속도만, 실패는 별도 칸). 「전체 요청」 행은 지금 `buildSpeedModel` 안에 인라인으로 있고 단계 구간·판정에 따라 머리글과 빨강이 정해진다. 그래서 `overall`과 `summary`만 받는 **독립 함수**를 `speedBands.ts`에 떼어 내 쓴다: 두/세 구간 여부와 머리글은 `overall`만으로 정하고, 판정 색(빨강·✕)은 넣지 않는다. 이 함수는 비교 보고서 전용이고, 측정 보고서의 `buildSpeedModel`은 고치지 않는다(구간 건수 → 비율 계산처럼 글자 그대로 같은 작은 조각만 함께 쓴다).
- 두 run의 경계(`slow_ms`·`basis`·두/세 구간 여부)가 **같으면** 머리줄 하나를 공유하고 구간 이름 한 벌. **다르면** 줄마다 자기 경계를 이름에 적고("이전: 3초 기준", "이후: 2초 기준") 표 아래 "▲ 두 측정의 응답 시간 기준이 달라 구간을 그대로 비교할 수 없습니다."
- 통과/미달 낱말·안내 줄은 넣지 않는다(각 run의 측정 보고서에 있다).

### 9.5 남은 문제

항목(위에서부터 이 순서, 같은 종류 안은 건수·등급 큰 순):
1. **이후에도 문제인 단계**: 이후 run에서 슬라이스 1 `stepStatus` 등급이 ✕ 또는 ▲인 단계 — "<번호 이름>: <상태 낱말>"(예: "② 민원 목록: 오류 있음 (0.75%)").
2. **줄지 않은 오류**: (단계, 코드) 중 이후 건수 > 0 이고 이전 건수 > 0 이며 이후 ≥ 이전 × 0.95 — "<단계>의 <코드> <풀이> N건은 그대로입니다."(늘었으면 "N건 → M건으로 늘었습니다").
3. **새로 생긴 오류**: 이전 0 → 이후 > 0 — "<단계>의 <코드> <풀이> N건이 새로 생겼습니다."
- 대상 코드 = §9.2의 코드 열 대상(오류로 셈·안 셈·확인 불가 + 응답 없음 + 보내지 않음). 같은 단계가 1번과 2·3번에 다 걸리면 2·3번 문장을 1번 항목 뒤에 이어 한 항목으로 합친다.
- 표준판: 최대 8항목 + "외 N개". 요약판: 최대 5(§10으로 3·1까지), 요약판에서는 항목 하나를 2줄로 자른다(말줄임).
- 하나도 없으면 상자 제목 "남은 문제 없음" + "이후 측정에서 문제 단계와 줄지 않은 오류가 없습니다." (▲ 색 없이 회색 테두리).
- 비교 불가(§6.3)면 이 상자는 "요청이 실행되지 않은 측정이 있어 확인하지 않았습니다."

## 10. 쪽 나누기와 공용 틀

- **틀 분리(동작 불변 리팩터, 첫 작업)**: `PrintDocument.tsx`에서 문서 종류와 무관한 부분 — 숨은 측정 시트 렌더 → `document.fonts.ready` 뒤 `[data-measure]` 높이 수집 → 배치 → 쪽 렌더(`.p-page`·`p-page--last`·꼬리말)·`data-layout-ready` 표지 — 을 공용 컴포넌트로 떼고, 측정 보고서는 자기 블록 목록·시트·쪽 항목 렌더·꼬리말·사다리 선택만 넘기도록 바꾼다. 구체 인터페이스는 빌더가 정한다. 조건: 측정 보고서의 기존 테스트 전부 **무수정** green — 그래서 `PrintDocument` 모듈 경로와 export(`RunPrintPage.ladder.test.tsx`가 모킹), `.p-doc`·`data-layout-ready`·`aria-hidden` `.p-sheet` 마크업은 그대로 둔다. `paginate.ts`의 `paginate`·`PAGE_BODY_MM` 무변경.
- `chooseSummaryLevel`은 사다리 칸 수가 8로 굳어 있다(`l <= 8`). **마지막 칸 번호를 선택 인자(기본 8)로** 받게 일반화한다 — 기존 호출(인자 2개)과 테스트는 그대로다.
- 비교 보고서의 표 블록(행 분할·머리줄 반복 + "(이어짐)"): 덤벨(§9.1), 오류 변화 표(§9.2), 측정 조건 대조 표(§7). 나머지는 쪼갤 수 없는 블록. 각주는 표 마지막 조각 뒤.
- **비교 요약판 1장 사다리**(2쪽 이상이면 한 칸씩 적용해 재배치, 1장이 되는 첫 칸에서 멈춤):
  1. 핵심 지표 표의 "한눈에 보기" 열 제거 → 2. 남은 문제 최대 3개 → 3. 요약 문장을 1·4번 줄만 → 4. 공정 비교 카드 4장을 한 줄로("조건 점검: 부하 조건·환경 변수 같음 / 시나리오 내용·판정 기준 다름") → 5. 남은 문제 1개 + "외 N개".
  - **비교 결과 상자·핵심 지표 표(6행)·공정 비교 결과(카드든 한 줄이든)·남은 문제 최소 1개(또는 "없음")는 어느 칸에서도 생략하지 않는다.**
  - 길이가 정해지지 않은 글(run `message` 사유, 남은 문제 항목, 공정 비교 한 줄, run 라벨, 핵심 지표 표 아래 `*` 각주)은 요약판에서 줄 수를 자른다(각 1·2·1·1·1줄, 말줄임). 그래서 5칸의 높이는 상한이 있고 1장에 들어간다. 그래도 넘치는 것은 버그로 본다: 개발 콘솔 경고 + 그대로 출력(슬라이스 1과 같은 처리), 라이브 극단값에서 1장을 확인한다. 적용된 칸이 있으면 도구 줄에 슬라이스 1과 같은 "1장에 맞추려고 일부를 줄였습니다(표준판에 전체)" 안내.
- 쪽 크기·여백·본문 높이·인쇄 CSS는 슬라이스 1 그대로(`print.css` 공용, 비교 전용 규칙은 같은 파일에 `p-cmp-` 접두로).

- **흑백·배경 미출력**: 좋아짐/나빠짐/비슷은 기호(▼ ▲ = ◆) + 낱말, 차트 계열은 선 모양·빗금으로 구분. `print-color-adjust: exact` 유지.
- **렌더 경로에서 throw 금지**: `normalizeProfile`(=`ProfileSchema.parse`) 대신 `safeParse`(ui/CLAUDE.md §인쇄 보고서).
- **추이 보고서 대비**: 쌍 계산 함수는 `(before, after)` 측정 모델만 받고 주소·화면 상태를 모른다. 주소는 `runs` 전체를 보존한다.
- 성능·깜박임: 쌍 계산은 `useMemo` 한 번. 의존값은 **두 리포트 객체 · 짝의 두 run에서 뽑은 원시값(`id`·`status`·`label`·`message`·시각) · `now`** 뿐이다. run 목록 전체(`runs.data`)를 의존값에 넣지 않는다 — `useScenarioRuns`는 그 시나리오에 실행 중인 run이 있으면 5초마다 다시 읽고, 문서 객체가 바뀌면 틀이 높이를 다시 재므로 5초마다 화면이 깜박인다. 측정 모델은 run당 한 번 만들고 절마다 다시 만들지 않는다.

## 12. 내가 정한 것 (사용자 고지 목록)

1. 시안의 "가장 느린 응답(최댓값)" 행은 **99% 응답시간**으로 바꾼다 — 리포트 요약에 최댓값이 없다(`ReportSummarySchema`: count·errors·rps·duration·mean·p50·p95·p99). 그래서 주요 지표는 5개(오류율·99%·95%·평균·처리량), 전체 요청 수는 중립.
2. 종합 답에 "엇갈림"·"비슷"·"비교 불가" 추가, 판정 변화를 신호에 포함(§6.3).
3. "비슷" 판정에 절대 하한(오류율 0.05%p, 응답시간 5ms) 추가 — §14 이월의 ±5%만으로는 아주 작은 값의 +100%가 "나빠짐"이 된다(§6.2).
4. 조건이 달라도 보고서를 만들고 상자를 회색 + "조건이 달라 참고용"으로(§6.3). 막는 것은 다른 시나리오·끝나지 않은 run뿐.
5. 공정 비교 카드는 부하 조건 · 환경 변수 · 시나리오 내용 · 판정 기준 4장. 시안의 "같은 시나리오" 카드는 뺐다(다른 시나리오는 아예 거부). 시안의 "같은 환경 stg"는 환경 **이름**이 run에 저장되지 않아 "환경 변수 같음/N개 다름(키 이름)"으로.
6. 제목은 "— 이전·이후 비교"(시안 "개선 전후 비교"는 악화일 때 거짓). 시안의 "(수정 가능)" 문구 제거.
7. 오류 변화 표에서 `*` 단계의 변화 칸은 "참고용"(§9.2). 코드 열 상한 5 + "그 밖의 코드".
8. 남은 문제에 "새로 생긴 오류" 추가. 시안의 "200명까지만 확인했습니다" 같은 범위 문장은 넣지 않는다(각 측정 보고서의 해석 상자에 있다).
9. 속도 구간 비교는 전체 요청 한 줄씩, 경계가 다르면 경고(§9.4). 용어 풀이 절은 넣지 않는다(코드 풀이는 표 머리에 있다).
10. 3개 이상일 때 기본 짝 = 기준 run + 나머지 중 가장 늦은 run(§5).
11. 요약판 사다리 5칸(§10).
12. 시안은 「측정 조건 대조」와 「남은 문제」를 좌우로 나란히 두지만, 표가 길어지면 쪽을 넘겨야 해서 위아래로 둔다.
13. 시안의 속도 구간 막대는 실패를 막대 안에 넣지만, print-speed-bands에서 정한 대로 막대 밖 별도 칸에 둔다.
14. 한쪽에서만 오류로 세지 않은 칸이 있으면 run 전체 오류율도 "참고용"으로 하고 종합 답에서 뺀다(§6.2). 판정 기준이 다르면 판정 변화도 종합 답에서 뺀다(§6.3).
15. 공정 비교의 부하 조건·시나리오 내용은 이름 붙은 항목만이 아니라 설정 전체를 비교한다(쉬는 시간·반복 횟수·헤더·본문 포함, 찍지는 않음) — 이름 없는 차이는 "그 밖의 설정 다름"(§7).
16. 구현을 두 슬라이스로 나눈다(머리말). US2 문장 끝을 "변화를 찾는다"에서 "값과 분류가 찍혀 있다"로 고쳤다(확인 가능한 표현).
