# 준비 스텝 — VU당 한 번만 실행하는 구간 (vu-setup-steps) 설계

- 날짜: 2026-11-22
- 유형: `user-path`
- 결정 기록: ADR-0062(슬라이스 A1에서 새로 씀)
- 슬라이스: **A1**(엔진·와이어·저장·리포트 — §3–§6, §7-1) → **A2**(에디터·test-run 화면·사이징·실행 창과 스케줄 폼 안내·모니터 표시·인쇄/비교 주변 — §7-2, 화면 + 엔진 한 곳[D16]) → **모니터 가림 문구**(§10-0, 자기 spec) → **B**(§9) → **주기 재실행**(§10)
- A1과 A2 사이에는 릴리즈하지 않는다(A1만으로는 QA가 화면에서 준비 스텝을 만들 수 없다). A2와 「모니터 가림 문구」 사이에도 릴리즈하지 않는다(사용자 결정 2026-11-22 — 준비 스텝 값의 가림 수단이 그 슬라이스에 있다).
- 상태: **A1 구현 완료**(2026-11-22, 코드 `f9e0e13c`..`e57ecdce`, 판단·연기 roadmap §B85). **A2 범위 확정**(2026-11-22 — §7-2를 다시 썼다: D14 문구에서 「로그인」 제거, D15 모니터는 표시만 하고 칸 대상 선택과 가림 문구는 별도 슬라이스). **A2 구현 완료**(2026-11-23, 코드 `a30a7cb9`..`9f514737`, 판단·연기 roadmap §B86 — plan과 달라진 것: test-run 결과는 준비 행이 있으면 모든 행에 이름, 준비 실패 측정·준비만 실행한 run의 리포트 머리 문구 추가, 규칙 파일 이름 `setupNoticeRules.ts`). 모니터 가림 문구·B·주기 재실행은 남음. 구현 중 달라진 것: trace는 변수가 비어 있는 준비 요청을 보내지 않는다(D11 보강) · open-loop의 「준비 중 종료」 문구는 「슬롯 n개는…」(D12) · 안내 줄에서 「(로그인된)」 제거(D12).

## 사용자 스토리 (US)

- **US1**: QA가 로그인이 필요한 API의 시나리오를 만들 때 로그인을 「준비 스텝」에 두고 run을 돌린다 — 성공하면 대상 서버에 로그인 요청이 VU당 한 번만 나가고, 뒤 스텝은 그때 받은 토큰(또는 세션 쿠키)으로 run 내내 성공한다.
- **US2**: QA가 그 run의 리포트를 본다 — 성공하면 요약 숫자(RPS·지연·오류율)와 SLO 판정에 로그인이 섞이지 않고, 로그인은 「준비」로 따로 보인다.
- **US3**: QA가 계정이 틀리는 등 로그인이 실패하는 run을 돌린다 — 성공하면 준비에 실패한 VU는 본 스텝을 보내지 않고, 리포트에서 「준비 실패 VU n개」와 실패 사유를 본다.
- **US4**: QA가 에디터에서 test-run을 누른다 — 성공하면 준비 스텝 → 본 스텝 순서로 한 번 실행된 결과를 보고, 준비에서 추출한 값이 본 스텝 요청에 들어간 것을 확인한다.
- **US5**: 개발자가 같은 시나리오를 YAML로 연다 — 성공하면 준비 구간이 YAML에 보이고, 아웃라인과 YAML 어느 쪽에서 고쳐도 다른 쪽에 반영된다. 준비 구간이 없는 기존 시나리오는 결과가 예전과 같다.

슬라이스별 증명 범위:

| | A1 | A2 |
|---|---|---|
| US1 | YAML로 만든 시나리오로 증명 | 화면(「준비 스텝으로 옮기기」)으로 만든 시나리오로 증명 |
| US2 | 전부 | — |
| US3 | 전부 | — |
| US4 | trace 응답(API)으로 증명 | 화면으로 증명 |
| US5 | 「YAML에 보임 · 기존 시나리오 불변」 | 「아웃라인 ↔ YAML 양방향」 |

아웃라인 준비 구획의 추가 버튼·끌어 옮기기는 슬라이스 B다.

## 1. 배경과 목적

사용자 원문(2026-11-22): "로그인이 필요한 api는 시나리오에 로그인을 넣고 매번 다시 로그인을 해야해서 로그인 후의 기능에 대한 단독 측정이 어려워." 불편의 내용은 **측정 오염**이다. 주 대상은 토큰 인증이고 세션 쿠키 시스템도 남아 있다.

지금 동작:

- VU의 쿠키 저장소는 run 내내 유지된다(ADR-0018). 그러나 "첫 반복에만 실행"을 표현할 방법이 없다.
- 추출한 변수는 반복마다 새로 만든다(`runner.rs`의 `run_vu`·`run_vu_curve`·`run_arrival`이 반복 머리에서 `seed_iter_vars`를 부른다). 토큰은 매 반복 다시 받아야 한다.
- 리포트 요약·SLO 판정·계단 판정은 모든 스텝의 행을 합산한다. 로그인이 섞인다.

목적: 시나리오에 「준비 스텝」 구간을 둔다. VU가 시작할 때 한 번 실행하고, 거기서 얻은 변수와 쿠키를 그 VU의 모든 반복이 이어받고, 준비 스텝의 요청은 본 측정 숫자에 들어가지 않는다.

### 목표가 아닌 것

- 토큰 만료 처리(주기 재실행) — §10.
- teardown(로그아웃·데이터 정리) — roadmap §A13-f.
- 모든 VU의 준비가 끝난 뒤 동시에 출발하는 장치 — 사용자 결정(2026-11-22)으로 roadmap에 후보로만 남긴다(§11).
- 401을 감지해 준비를 다시 돌리는 것 — 진짜 401을 가리므로 만들지 않는다.

### 하면 안 되는 것

- 준비 스텝이 없는 시나리오의 run·리포트·와이어가 달라지는 것.
- 준비에 실패한 VU가 빈 토큰이나 기본값으로 본 스텝을 보내는 것.
- 준비에 실패해 부하가 설정보다 적었는데 리포트가 그것을 알리지 않는 것.
- 틀린 계정으로 로그인을 run 내내 되풀이하는 것(계정 잠금).

## 2. 방법 비교 (사용자가 A안을 골랐다)

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 시나리오에 준비 구간** | `setup:` 목록. VU당 1회, 변수·쿠키 이어받기, 집계 분리 | **채택** — 실행과 집계 양쪽에서 로그인을 걷어낸다 |
| B. 스텝마다 「VU당 한 번만」 스위치 | JMeter 방식 | 측정 대상 경계가 스텝마다 흩어져 리포트 분리가 흐려진다 |
| C. 리포트에서만 제외 | 스텝에 표시만 | 서버는 여전히 로그인 부하를 받는다 |

준비 스텝 숫자를 본 측정에서 떼는 방법:

| 안 | 내용 | 판단 |
|---|---|---|
| ㉠ 엔진이 따로 센다 | 준비 스텝은 본 집계기에 기록하지 않고, 별도 통계로 보내 별도 표에 저장 | **채택** — 요청 수·지연·오류·상태 코드를 읽는 지금의 모든 집계가 손대지 않아도 준비 요청을 볼 수 없다 |
| ㉡ 컨트롤러가 스텝 id로 걸러 낸다 | 기록은 그대로, 읽는 곳마다 준비 스텝 id를 뺀다 | 읽는 곳이 여덟 군데 이상이고 한 곳만 빠뜨려도 숫자가 섞인다 |

㉠의 비용: proto 필드·저장 표·마이그레이션이 는다. 준비 스텝의 1초 단위 시계열은 없다(스텝별 run 전체 합계만). ㉠으로도 **준비에 걸린 시간**은 다른 길로 본 숫자에 닿는다 — §4 D7이 길마다 처리를 정한다.

### 2-1. 최소 버전과 뒤에 올 것 (사용자 요청 2026-11-22: 확장 가능성 고려)

이 슬라이스는 최소 버전이다. 뒤에 올 것을 지금 만들지는 않되, 나중에 **형식을 깨지 않고** 더할 수 있게 다음을 지금 정한다.

| 뒤에 올 것 | 지금 정해 두는 것 |
|---|---|
| 주기 재실행(N분마다) · 401 시 재실행 같은 구간 설정 | `setup`을 객체로 둔다 → `setup: { steps, every: 25m }`처럼 키만 더한다. 성공·실패 수를 「실행 횟수」로 정의한다 |
| teardown(끝날 때 한 번) | 최상위에 `teardown: { steps }`를 같은 꼴로 더할 수 있다. 통계 메시지·저장 표·trace 표지에 구간 이름(`section`)을 둔다 → 새 표·새 proto 메시지 없이 받는다. 구간 실행 함수가 구간 이름을 받는다 |
| run당 한 번(모든 VU가 토큰 하나를 공유) | `setup` 객체에 `scope` 키를 더할 수 있다(지금은 없음 = VU마다) |
| 준비 구간의 loop·if | 엔진 타입은 `Vec<Step>`이고 거절은 읽기 단계 한 곳 → 형식은 그 한 곳만 풀면 된다. 구간 실행 함수와 구간 통계는 그때 넓혀야 한다 |
| 모든 VU 준비 후 동시 출발 | 워커가 「마지막 준비 완료 시각」을 이미 보낸다(D8) |

지금 만들지 않는 것은 위 표의 왼쪽 칸 전부다. 오른쪽 칸은 형식(YAML·proto·표)에 한정한다 — 쓰이지 않는 실행 코드는 넣지 않는다.

## 3. 시나리오 모델

### D1. `setup:` 키

```yaml
version: 1
name: 주문 조회
setup:                       # 선택. VU당 1회
  steps:
    - id: 01J...
      name: 로그인
      type: http
      request: { method: POST, url: "${BASE_URL}/login", body: { json: { id: "{{user}}", pw: "{{password}}" } } }
      assert: [ { status: 200 } ]
      extract: [ { var: token, from: body, path: "$.token" } ]
steps:                       # 반복 — 측정 대상
  - id: 01J...
    name: 주문 조회
    type: http
    request: { method: GET, url: "${BASE_URL}/orders", headers: { Authorization: "Bearer {{token}}" } }
```

- `setup`은 목록이 아니라 **객체**이고 스텝은 그 안의 `steps`에 둔다. 나중에 구간 설정(주기 재실행 간격 등)을 같은 객체에 키로 더할 수 있게 하기 위해서다(§2-1). 지금 허용하는 키는 `steps` 하나이고 모르는 키는 거절한다.
- 엔진 `Scenario`에 `setup: Option<SetupSection>` 필드(`SetupSection { steps: Vec<Step> }`, `deny_unknown_fields`)를 더한다. `#[serde(default, skip_serializing_if = "Option::is_none")]` — 없으면 YAML에 키가 없고, 기존 시나리오의 `to_yaml` 출력은 글자 그대로다. `steps`가 빈 `setup`은 「준비 없음」과 같게 다룬다.
- **준비 구간에는 http 스텝만 둔다.** 이유: 로그인은 http 한두 개다. 제어 흐름을 허용하면 조건 반복·분기 통계까지 준비용으로 따로 날라야 한다(§11).
  - UI Zod: `setup: z.object({ steps: z.array(HttpStepModel) }).strict().optional()` — http 아닌 스텝은 Zod가 문서 오류로 거절한다.
  - 엔진: `SetupSection.steps`를 읽을 때(`deserialize_with`) http 아닌 스텝이 있으면 역직렬화 오류를 낸다. `Scenario::from_yaml`을 부르는 모든 곳이 같은 방식으로 실패한다 — 시나리오 생성·수정은 기존 경로로 **400**, test-run은 기존 경로로 **422**, 보드 파일 가져오기·워커도 기존 파싱 실패 경로. 따로 검증 함수를 두지 않는다.
- **준비 스텝의 추출 기본값(`default:`)은 쓰지 않는다.** 준비 스텝에서 못 뽑으면 기본값이 있어도 실패다(D6). 「기본 토큰으로 본 스텝을 보내지 않는다」를 지키기 위해서다. UI는 준비 스텝의 Inspector에서 기본값 칸에 「준비 스텝에서는 쓰이지 않습니다」를 표시한다(A2).
- 스텝 id는 `setup`과 `steps`를 통틀어 겹치면 안 된다. UI 검증(`collectProblems`)에 id 겹침을 더한다(A1). 서버에는 지금 스텝 id 유일성 검사가 없고, 이 슬라이스에서 새로 만들지 않는다.
- UI에서 최상위 키를 더할 때의 세 곳(`ui/src/scenario/CLAUDE.md`): Zod `ScenarioModel`, `yamlDoc.ts`의 `normalizeForModel` 허용 목록, 그리고 문서 쓰기 경로. 쓰기 규칙 — 준비 스텝이 처음 생길 때만 YAML 문서에 `setup:` 키를 만들고, 마지막 준비 스텝이 지워지면 `setup:` 키를 통째로 지운다(빈 `setup`을 남기지 않는다). 준비 스텝의 YAML 경로는 `["setup", "steps", i]`다.
- `setup:`만 쓰고 값이 없는 YAML(`null`)은 「준비 없음」으로 읽는다 — 엔진은 `None`, UI는 `normalizeForModel`이 없는 것으로 바꾼다. `steps` 키가 없는 `setup: {}`는 엔진과 UI 둘 다 거절한다(어느 쪽도 `steps`에 기본값을 두지 않는다).
- 「준비가 있는가」는 어디서나 `setup_steps()`가 비었는지로 판단한다(`setup` 키의 유무가 아니다) — 엔진 진입점, 리포트의 `setup` 블록 유무, 화면 구획.
- `cookie_jar: off`이면 쿠키는 이어지지 않는다(지금 반복 사이의 규칙과 같다).

### D2. `scenario.steps`를 훑는 코드의 분류

- **모든 스텝이 대상**: 검증(think time·분기 이름), 변수 탐색, 스텝 이름 붙이기, think 제거(`maybe_strip_think`), 요청 단위 생성기 계획(`RequestGenPlan::build`), 실행 전 신뢰도 점검, 모니터의 스텝 훑기(`collect_http_steps`·`step_judge`·`unit.rs`), **모니터의 인증 변수 가림(`step_judge.rs`의 인증 출처 훑기)**, TUI 이름 훑기(`names.rs`).
- **반복 본문만 대상**: 반복 시간 추정·사이징, SLO 스텝 기준의 대상 스텝, 「요청 없는 스텝」 인사이트, 유효성의 스텝 점검.

엔진 `Scenario`에 `setup_steps()`(없으면 빈 조각)와 `all_steps()`(setup → steps 순서)를 두고, UI `model.ts`에도 같은 뜻의 헬퍼를 둔다. 분류표는 plan이 §12의 전수 명령으로 만든다.

인증 변수 가림을 「모든 스텝」에 넣는 이유: 준비 구간이 로그인 추출의 표준 자리가 되므로, 훑기에서 빠지면 모니터 사유 글에 인증 값이 드러난다. 본문에서 뽑은 토큰(`$.token`)이 가림 대상이 아닌 것은 이 기능 전부터의 공백이다 — 이 슬라이스는 그 공백을 넓히지도 좁히지도 않으며, roadmap에 적는다(§11).

## 4. 엔진 동작

### D3. 실행 시점 — VU의 첫 반복 머리에서 한 번

| 진입점 | 준비 실행 시점 | 준비 상태를 두는 곳 |
|---|---|---|
| `run_vu`(VU 고정·상승 시간) | 첫 반복의 변수를 만든 직후, 첫 본 스텝 전 | 태스크 지역 변수 |
| `run_vu_curve`(VU 곡선) | 슬롯을 등록한 뒤 첫 활성화의 첫 반복 머리. park 뒤 재개 때는 다시 하지 않는다 | 태스크 지역 변수(park을 넘어 유지) |
| `run_arrival`(open-loop) | 그 슬롯을 처음 받은 도착의 머리 | 슬롯마다 `Mutex<SlotSetup>`(대기 없음 — 빈 슬롯 큐가 한 번에 한 도착에만 슬롯을 준다) |

- 준비는 run의 실행 시간 안에서 돌고 deadline·중단을 그대로 따른다. 준비 중 run의 deadline이나 중단이 오면 그 VU는 반복 없이 끝나고 「준비 중 종료」(`interrupted`)로 한 번 센다(준비 성공으로도 실패로도 세지 않는다).
- VU 곡선에서 준비 도중 은퇴 취소(즉시 ramp-down·graceful 상한)가 오면 준비는 「안 됨」으로 남고, 다음 활성화 때 처음부터 다시 한다. 이것은 `interrupted`로 세지 않는다(그 VU는 아직 끝나지 않았다). 준비가 실패하면 그 VU는 `clear_slot` 뒤 끝난다(지금의 영구 종료 경로와 같다).
- open-loop의 빈 슬롯 큐는 FIFO라 모든 슬롯을 돌아가며 쓴다. 로그인 횟수는 약 `min(max_in_flight, 도착 수)`다 — 슬롯을 넉넉히 잡으면 그만큼 로그인한다. D14 안내가 이것을 알린다.
- 준비 스텝의 스텝별 think time과 시나리오 기본 think time은 본 스텝과 같은 규칙으로 적용된다. `maybe_strip_think`는 준비 스텝도 뗀다.
- 준비 스텝이 비어 있으면 세 진입점 모두 지금 코드 경로 그대로다.

### D4. 준비 스텝이 보는 변수 — 그 VU의 첫 반복과 같다

준비는 **첫 반복의 머리에서, 첫 반복의 변수 그대로** 실행한다. 첫 반복의 변수 = 시나리오 `variables` + 그 반복이 받은 데이터셋 행(모든 바인딩, 정책 무관).

- 규칙이 하나다: 「준비 스텝은 그 VU의 첫 반복이 쓰는 값을 본다.」 데이터셋 정책에 따라 보이는 열이 달라지지 않고, 정책 때문에 준비가 실패하는 일이 없다.
- 행은 반복마다 하던 선택을 그대로 한 번 한다. 준비를 위해 행을 따로 고르지 않으므로 `iter_sequential`·`unique`의 공유 카운터는 준비가 없을 때와 똑같이 전진한다. 첫 반복의 본 스텝은 준비가 쓴 것과 같은 행을 쓴다.
- test-run도 같은 규칙이다(준비 = 첫 행, D11). test-run과 실제 run이 다르게 동작하는 경우가 없다.
- `unique` 바인딩이 첫 선택에서 이미 소진됐으면 그 VU는 지금처럼 조용히 끝나고 준비도 실행하지 않는다. open-loop에서 준비 안 된 슬롯의 도착이 이 경우에 걸리면, 끝내기 전에 `Launched`를 기록한다(지금 그 도착이 「시작」으로 세어지는 것과 같게).
- VU 곡선에서 준비 도중 은퇴 취소로 준비를 다시 하게 되면(D3) 다음 활성화의 첫 반복이 새로 받은 행으로 한다. 앞서 받은 행 하나는 버려진다(지금 deadline에 잘린 반복이 행을 버리는 것과 같은 크기).
- `${vu_id}`·`${iter_id}`는 첫 반복의 값이다(VU 부하는 `iter_id` 0, open-loop는 그 도착의 번호).
- 요청 단위 재평가 변수(`refresh: request`): 생성기 계획이 준비 스텝도 포함하고(D2), 준비는 첫 반복의 `ReqGen`으로 스텝마다 `refresh`를 부른다.
- 계정처럼 VU마다 고정이어야 하는 값은 'VU별 고정'(`per_vu`) 바인딩이 맞다. 다른 정책이면 준비는 첫 행의 계정으로 로그인하고 뒤 반복은 다른 행의 값을 쓴다 — 실패는 아니지만 뜻한 바가 아닐 수 있어 run 생성 창이 알린다(D14).

### D5. 이어받기

- **쿠키**: 준비와 반복이 같은 `VuClient`를 쓴다.
- **변수**: 준비 스텝이 **실제로 추출한 이름과 값**만 VU 변수로 보관한다. 매 반복 머리의 순서:
  1. `seed_iter_vars`(시나리오 변수, 생성기는 반복마다 새로)
  2. 준비 추출 변수를 덮는다. 그 반복의 `ReqGen`에 `mark_written`으로 「받은 값」 표시를 한다(같은 이름의 요청 단위 생성기가 덮지 않게).
  3. 데이터셋 바인딩(선언 순서)
  4. 반복 중 추출
- **첫 반복**도 같은 순서다. 준비는 「1 + 3」으로 만든 변수의 사본 위에서 돌고, 끝나면 첫 반복의 변수를 「1 → 2 → 3」으로 다시 짠다 — 이때 **이미 만든 1의 결과와 이미 고른 3의 행을 다시 쓴다**(`seed_iter_vars`를 다시 부르지 않고 행을 다시 고르지 않는다). 생성기 값은 준비와 첫 반복이 같고, 공유 카운터는 한 번만 전진하고, 준비 추출과 데이터셋 열의 이름이 겹치면 다른 반복과 똑같이 데이터셋이 이긴다.
- 반복 중에 같은 이름을 다시 추출하면 그 반복에서만 덮인다. 다음 반복은 준비 때 값으로 돌아간다.
- 비움 표(`BlankTable`)는 지금처럼 반복마다 새로 만든다. 준비 추출 변수는 실제로 뽑은 값이라 표에 오르지 않는다. 준비 실행은 비움 표를 쓰지 않는다(엄격 추출 + 첫 실패에서 멈춤이라 비워진 값이 생기지 않는다).
- 보관 비용: VU당 맵 하나, 반복마다 준비 추출 개수만큼 복제. 준비가 없으면 빈 맵 검사 한 번.

### D6. 준비 실패

준비 실패 = 다음 중 하나. 첫 실패에서 준비를 멈춘다(뒤 준비 스텝을 보내지 않는다).

| 종류(`kind`) | 조건 |
|---|---|
| ADR-0050의 전송 실패 kind 그대로 | 요청 전송 실패 |
| `read_body` | 본문 읽기 실패 |
| `status_assert` | 상태 검증 불일치 |
| `extract` | 선언한 추출을 못 뽑음(기본값이 있어도), 또는 **뽑은 값이 빈 문자열**(JSON `null` 포함 — 엄격 추출은 `null`을 `""`로 만든다) |
| `unknown_var` · `malformed_template` · `cast_failed` | 렌더 단계 엔진 오류 |

- 종류를 문자열 앞머리로 가리지 않는다. `ExecOutcome`에 구조화된 분류 필드(`error_class`)를 더해 `error`를 채우는 자리마다 함께 채운다. 본 스텝 경로는 이 필드를 읽지 않는다.
- 준비 스텝의 추출은 새 추출 방식 「기본값 없는 엄격」으로 한다. 지금 `execute_step`은 엄격 방식에서도 기본값 선언이 있으면 `evaluate_with_defaults`로 간다 — 그 갈래를 타지 않고 항상 `evaluate`를 쓰는 방식을 `ExtractMode`에 더하고, trace 쪽 사본(`execute_step_traced_with`)에도 같은 방식을 둔다. 빈 값 검사는 준비 실행 함수가 추출 결과를 받아서 한다. 로그인 실패를 `200 {"token": null}`로 답하는 서버에서 빈 토큰으로 본 스텝이 나가는 것을 막는다.
- 새 오류 변형 `EngineError::SetupFailed { step_id, kind, var: Option<String> }`. `var`는 `unknown_var`·`cast_failed`일 때의 변수 **이름**(값 아님). `safe_cause` 허용 목록에 넣는다 — 문구 `준비 스텝 <step_id> 실패: <kind>[ (<var>)]`.

실패한 뒤 — 세 부하 모델 모두 **다시 시도하지 않는다**(틀린 계정을 되풀이하지 않는다):

- **VU 고정·VU 곡선**: 그 VU는 반복을 시작하지 않고 끝난다. `failed` 수에 들어간다. 한 워커의 모든 VU가 준비에 실패하면 기존 `AllVusFailed` 경로로 run이 `failed`가 되고 메시지에 첫 준비 실패 사유가 실린다. 일부만 실패하면 run은 `completed`이고 리포트가 알린다(D10·D12).
  - 워커가 여럿일 때: `AllVusFailed`는 지금도 워커마다 판정하고, 한 워커가 실패를 알리면 run 전체가 `failed`가 된다. `per_vu` 행은 전체 VU 번호를 따르므로 틀린 계정이 한 워커 몫에 몰리면 「일부 실패」가 run 실패로 끝날 수 있다. 이 슬라이스는 그 규칙을 바꾸지 않는다(run 전체로 판정하는 것은 §11).
- **open-loop**: 그 슬롯은 run에서 빠진다. 그 도착은 준비 통계의 「실패」로만 센다 — 시작(`launched`)·완료(`completed`)·보내지 않음(`dropped`) 어디에도 넣지 않는다. `dropped`에 넣으면 계단 판정(`dropped != 0`이면 그 계단 실패)과 「슬롯을 늘리라」 인사이트가 틀린 원인을 가리킨다. 슬롯이 줄어 정말로 보내지 못한 도착은 지금처럼 `dropped`다. **모든 슬롯이 빠지면** run을 `AllVusFailed`와 같은 방식으로 `failed`로 끝낸다(`failed = total = max_in_flight`, 첫 사유). 준비 실패 로그는 슬롯당 한 줄이다.
  - 구현 방식: ① 슬롯마다 「준비됨」 표시(원자 불리언)를 두고, 스케줄러는 준비된 슬롯을 받았을 때만 지금처럼 그 자리에서 `Launched`를 기록한다. 준비 안 된 슬롯이면 기록하지 않고 태스크를 띄우고, 태스크가 준비에 성공한 뒤 `Launched`를 기록하고 본 스텝으로 간다. ② 슬롯을 돌려주는 가드(`SlotGuard`)에 「돌려주지 않음」 표시를 둔다 — 준비 실패 때 세운다. ③ 빠진 슬롯 수를 공유 원자 계수로 두고, 스케줄러 루프가 `exhausted` 검사 옆에서 `빠진 수 == max_in_flight`를 보면 루프를 끝내고 `AllVusFailed`를 돌려준다. 첫 사유는 공유 `OnceLock`에 둔다(closed-loop의 방식).
- 재시도 없음은 VU(슬롯) 단위다. 계정 수가 VU 수보다 적으면(`per_vu`는 행을 돌려 쓴다) 틀린 계정 하나가 그 계정을 받은 VU 수만큼 로그인에 실패한다. D14 안내가 알린다.

상태 검증이 없고 추출도 없는 로그인은 401을 받아도 실패로 잡히지 않는다. 본 스텝과 같은 성질이고, 실행 전 신뢰도 점검(ADR-0049)의 「상태 검증 없음」이 준비 스텝도 보게 해서 알린다(D2).

### D7. 준비가 본 숫자에 닿는 길과 처리

**요청 통계**: 준비 실행은 본 `Aggregator`를 건드리지 않는다. 준비 전용 통계에 기록한다 — 스텝별 요청 수·오류 수·상태 코드별 수·지연 HDR·실패 종류별 수, 준비 성공 수·실패 수·중단 수, 마지막 준비 완료 시각. 따라서 `MetricWindow`·오류 종류·지연 단계·분기·반복 통계·`/metrics` 요약·실행 중 진행 차트는 코드 변경 없이 준비 요청을 보지 못한다. 제약: 본 스텝의 요청 경로(`execute_steps`의 http 가지)에 준비 여부 분기를 넣지 않는다. 준비는 별도 함수가 `execute_step_with`를 「기본값 없는 엄격」 추출 방식(D6)으로 직접 부른다. 이 함수는 구간 이름과 스텝 목록을 받는 꼴로 만든다(지금 부르는 곳은 준비 하나).

**시간이 닿는 길** — 길마다 정한다:

| 길 | 닿는 방식 | 처리 |
|---|---|---|
| 유지 구간 창(ADR-0061) | 창 시작 = run 시작 + 상승 + 버림. 준비가 그보다 오래 걸리면 창 앞부분에 준비 중인 VU가 있다 | **VU 고정**: 워커별 창 시작을 `max(지금 계산값, 그 워커의 마지막 준비 완료 시각을 초로 올림)`으로 한다(`steady.rs`의 워커별 시작 계산). 준비 통계가 없으면 지금 계산 그대로. 마지막 준비 완료 시각은 워커 시작 시각과 같은 방식으로 시계 타당성을 걸러서 쓴다. **open-loop**: 준비가 run 중간에도 일어나므로 창을 바꾸지 않고, 리포트 준비 구획에 「유지 구간 안에서도 준비가 실행됐을 수 있습니다」를 적는다. (VU 곡선은 유지 구간 표시와 함께 쓸 수 없다 — 지금 규칙) |
| open-loop 계수(시작·완료·버림) | 준비 실패 도착 | D6 — 세 계수 어디에도 넣지 않고 준비 통계에만 센다. 따라서 「예정 도착 수 = 시작 + 버림 + 준비 실패 + 준비 중 종료」다 |
| open-loop 슬롯 점유 | 슬롯의 첫 도착은 준비 시간만큼 슬롯을 더 잡는다 | 그대로 둔다(실제로 일어난 일). 슬롯당 한 번이다 |
| 계단 감시·자동 정지(ADR-0059) | open-loop 완료 수로 달성률 계산, `dropped`가 있으면 계단 실패 | D6 처리로 준비 실패 도착은 완료에도 `dropped`에도 없다. 추가 변경 없음. 준비 실패로 달성률이 떨어지면 계단 판정이 그것을 그대로 보인다(실제로 덜 보냈다) |
| test-run `total_ms` | 사이징 도우미가 `total_ms`를 반복 한 번의 점유 시간으로 쓴다 | `ScenarioTrace`에 `setup_ms`(선택 필드)를 더한다. 사이징 도우미(`SlotSizingHelper`·`VuSizingHelper`)는 `total_ms − setup_ms`를 쓴다(A2). 운영 모니터는 `total_ms` 그대로 쓴다 — 점검 한 번은 로그인을 포함한 한 바퀴다 |
| 연결 통계(dns·connect·재사용 비율) | 준비가 연결을 먼저 열어 본 스텝의 새 연결이 준다 | 그대로 둔다. 로그인 뒤 상태의 측정이 이 기능의 목적이다. 리포트 한 줄 안내(D12)에 포함 |
| 시작 감시(startup watchdog) | 첫 `MetricBatch`가 제한 시간 안에 와야 한다. 준비가 길면 본 지표가 늦다 | 준비 통계를 **주기 flush에도** 싣는다(마지막 flush만이 아니다). 준비 통계만 든 배치도 보낸다(D8 가드) |
| 활성 VU 표본(VU 곡선) | 준비 중인 VU도 활성으로 센다 | 그대로 둔다(슬롯을 차지하고 요청을 보내는 VU다) |

```proto
  …
  repeated SectionStepStat section_step_stats = 14;  // 반복 밖 구간(지금은 "setup")의 스텝 통계 (delta, controller가 더한다)
  repeated SectionOutcome section_outcomes = 15;     // 구간 실행 결과 수 (delta). 보낼 것이 없으면 비운다
}
message SectionOutcome {
  string section = 1;          // 지금은 "setup"만
  uint64 ok = 2;               // 끝까지 성공한 실행 횟수
  uint64 failed = 3;           // 실패한 실행 횟수
  uint64 interrupted = 4;      // deadline·중단으로 끝난 실행 횟수
  int64 last_done_ms = 5;      // 이 배치 구간에서 마지막으로 성공한 실행의 완료 epoch ms, 0 = 없음
}
message SectionStepStat {
  string section = 1;                      // 지금은 "setup"만
  string step_id = 2;
  uint64 count = 3;
  uint64 error_count = 4;
  map<string, uint64> status_counts = 5;   // "0" = 전송 실패
  bytes hdr_histogram = 6;                 // 본 스텝과 같은 bound
  map<string, uint64> failure_kinds = 7;   // D6의 kind별 수
}
```

- 두 메시지 모두 구간 이름(`section`)을 싣는다 — 나중에 다른 구간(teardown)이 같은 메시지와 같은 표를 쓴다. 엔진·컨트롤러 안에서는 문자열이 아니라 열거형(`Section::Setup`, 와이어 글자 `setup`)으로 다룬다. 컨트롤러는 모르는 구간 이름의 행을 버리고 경고를 남긴다.
- 성공·실패·중단 수는 「구간 **실행** 횟수」다(지금은 VU당 한 번이라 VU 수와 같다). 주기 재실행이 생기면 같은 필드가 실행마다 는다.
- 두 필드 모두 반복 필드라 비어 있으면 인코딩되지 않는다 — 준비 없는 run의 배치 바이트가 변하지 않는다. 세 수가 모두 0이고 `last_done_ms`도 0인 `SectionOutcome`은 보내지 않는다.
- 값(변수 값·URL·응답 조각)은 어디에도 싣지 않는다. `failure_kinds`의 키는 D6의 고정 목록이다.
- 엔진 `MetricFlush`에 준비 통계가 는다. 드레인 여섯 곳 전부, 송신 가드 전부(이번에는 open-loop 포함 — 주기 flush에도 실리므로), 워커 전달 건너뛰기 가드(`crates/worker/src/lib.rs`)에 「준비 통계가 비었는가」 항을 더한다. 가드를 빠뜨리면 준비 통계만 든 flush가 버려지고 시작 감시가 run을 죽인다.
- `RunAssignment.scenario_yaml`은 문자열이라 시나리오 전달에는 proto 변경이 없다.

### D9. 저장 — 마이그레이션 0027 (추가만 하는 표 둘)

```sql
CREATE TABLE IF NOT EXISTS run_section_step_metrics (
  run_id TEXT NOT NULL, worker_id TEXT NOT NULL DEFAULT '',
  section TEXT NOT NULL, step_id TEXT NOT NULL,
  count INTEGER NOT NULL, error_count INTEGER NOT NULL,
  status_counts TEXT NOT NULL, failure_kinds TEXT NOT NULL, hdr_histogram BLOB NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_run_section_step_metrics_run ON run_section_step_metrics(run_id);
CREATE TABLE IF NOT EXISTS run_section_outcomes (
  run_id TEXT NOT NULL, worker_id TEXT NOT NULL DEFAULT '', section TEXT NOT NULL,
  ok INTEGER NOT NULL, failed INTEGER NOT NULL, interrupted INTEGER NOT NULL,
  last_done_ms INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_run_section_outcomes_run ON run_section_outcomes(run_id);
```

- 배치마다 행을 **추가**하고 읽을 때 합친다(수·맵은 합, HDR은 merge, `last_done_ms`는 워커별 최대). `run_phase_metrics`와 같은 방식이다. 수신 때 읽고-고쳐-쓰기를 하지 않는다.
- 행 수: 준비는 VU 수만큼만 일어나므로 준비가 끝나면 더 늘지 않는다.
- 시나리오 삭제의 run 연쇄 삭제 목록(`store/scenarios.rs`)에 두 표를 더한다. run만 지우는 경로는 지금 없다.
- 번호는 `/new-migration`으로 확정한다(지금 마지막은 Rust 가드 방식의 0026).

### D10. 리포트 JSON — `setup` 블록

```json
"setup": {
  "ok": 98, "failed": 2, "interrupted": 0,
  "steps": [
    { "step_id": "01J…", "count": 100, "errors": 2,
      "p50_ms": 41, "p95_ms": 120, "max_ms": 310,
      "status_counts": { "200": 98, "401": 2 },
      "failure_kinds": { "status_assert": 2 } }
  ]
}
```

- 시나리오에 준비 스텝이 없으면 **키 자체가 없다**(기존 run의 리포트 JSON 불변).
- 준비 스텝이 있으면 통계 행이 없어도 블록을 낸다(`ok: 0, failed: 0, interrupted: 0`, `steps`는 스텝마다 0행).
- `steps` 순서는 시나리오의 준비 스텝 순서다. 컨트롤러가 `scenario_yaml`을 읽어 정한다. 읽기에 실패하면 블록을 내지 않는다(인사이트의 기존 fail-soft 방식). 스텝 이름은 UI가 붙인다.
- `ok + failed + interrupted`는 VU 수(슬롯 수)보다 작을 수 있다(시작하지 못한 VU, 쓰이지 않은 슬롯).
- `?basis=steady|whole` 두 리포트 모두 같은 `setup` 블록을 싣는다.
- 요약·판정·인사이트는 준비 통계를 쓰지 않는다. `failed > 0`이면 유효성(`validity`)에 「준비 실패로 부하가 설정보다 적었음」 항목을 더한다(항목 형식은 기존 것을 따른다).

## 6. test-run과 운영 모니터

### D11. trace

- `trace_scenario`·`trace_scenario_with_seed`: 준비 스텝을 먼저 한 번 실행하고 본 스텝으로 간다. 준비 행은 `steps` 앞쪽에 `section: "setup"` 표지(`StepTrace`의 선택 필드, 엔진 안에서는 열거형, 본 스텝이면 없음)를 달고 들어간다.
- `trace_scenario_rows`: 준비는 **첫 행 앞에 한 번**. 준비 행은 `RowsTrace`의 새 선택 필드 `setup_steps`에 싣는다(행별 trace에 넣지 않는다).
- 변수 순서는 부하 실행(D5)과 같게 한다: 준비는 「시나리오 변수 + 시드」로 돌고(시드 = 단일 실행이면 주어진 시드, 행 모드면 **첫 행**), 준비 추출을 보관했다가 본 패스(행)마다 「시나리오 변수 → 준비 추출 → 그 패스의 시드」로 시작한다. 첫 패스는 D5의 첫 반복 규칙대로 준비가 쓴 시나리오 변수 값을 다시 쓴다(다시 시드하지 않는다). 둘째 패스부터는 지금처럼 패스마다 새로 시드한다.
- trace의 준비 실패 = 준비 행에 오류가 있거나, 그 행의 `unbound_vars`가 비어 있지 않음(trace는 너그러운 렌더라 `UnknownVar`가 오류로 나오지 않는다), 또는 선언한 추출을 못 뽑았거나 빈 값을 뽑음(D6과 같은 규칙, 기본값 안 씀). 실패하면 본 스텝을 실행하지 않고 `ScenarioTrace`의 새 선택 필드 `setup_failed: true`를 단다(`RowsTrace`도 같은 필드, 이때 `ok`는 false). 오류 없이 실패로 판정한 준비 행(미해결 변수·빈 추출)에는 trace가 고정 문구의 오류를 채운다 — `setup_failed`인 trace에는 오류를 가진 준비 행이 반드시 있다. `ScenarioTrace.error`는 쓰지 않는다. 모니터는 지금처럼 「오류가 있는 첫 http 행」에서 사유를 얻는다.
- `ScenarioTrace.setup_ms`(선택): 준비에 걸린 시간. `total_ms`는 준비를 포함한다(D7).
- 요청 상한(`max_requests`)과 시간 상한은 준비 요청도 센다. 준비 도중 상한에 닿으면 `truncated: true`로 끝내고 본 스텝을 실행하지 않는다(`setup_failed`는 달지 않는다 — 실패가 아니라 잘림이다).
- 운영 모니터는 `trace_scenario`를 쓰므로 점검 한 번이 준비 → 본 스텝 한 바퀴다. `setup_failed`인 점검은 실패로 판정한다(사유 = 그 준비 행의 사유). 모니터 칸 설정에서 준비 스텝을 고를 수 있게 하는 것(`PanelEditor`)은 「모니터 가림 문구」 슬라이스(D15·§10-0).

**D13. 에디터**

- 아웃라인 맨 위에 「준비 스텝 — VU마다 한 번만 실행」 구획(준비 스텝이 있을 때만). 행은 본 스텝과 같은 모양이고, **끄는 대상도 놓는 대상도 아니다**(끌기 목록에 등록하지 않는다 — 본 스텝이나 loop·if를 준비 구획에 떨어뜨릴 길이 없어야 한다. 준비 구간은 http만 받는다). 구획이 있으면 본 스텝 목록 위에도 「본 스텝 — 반복 실행」 머리 줄을 둔다. A1의 읽기 전용 한 줄(「준비 스텝 n개 — YAML 보기에서…」)은 없앤다.
- 고르면 Inspector에서 고칠 수 있다. Inspector와 그 주변이 `model.steps`만 찾는 자리(`findStepById`·`findStepSiblings`·`isInsideParallelBranch`·`topLevel` 판정)와 쓰기 경로(`findStepPath`)가 준비 스텝도 찾게 한다. 스텝 id를 골라 주는 다른 자리도 준비 스텝에서 동작한다: 변수 사용처 팝오버의 「이동」, test-run 결과의 「+추출」, 신뢰도 점검 목록(`TrustBoard`)의 스텝 연결, 검증 배너의 준비 스텝 항목(A1은 연결 없는 글이었다 — 스텝으로 가는 연결로 바꾼다), 넓게 보기의 흐름 칩.
- **구획 사이 옮기기**: 최상위 http 스텝의 Inspector에 「준비 스텝으로 옮기기」, 준비 스텝의 Inspector에 「본 스텝으로 옮기기」. 옮기면 대상 구획의 끝에 붙는다. QA가 YAML 없이 준비 스텝을 만드는 길이다(본 스텝으로 만든 뒤 옮긴다). loop·if·parallel 안의 스텝과 컨테이너에는 버튼이 없다. 본 스텝이 하나뿐이어도 옮길 수 있다(사용자 결정 2026-11-22) — 본 스텝이 없는 시나리오는 준비 스텝만 실행한다(D16).
  - YAML: 첫 준비 스텝이 생길 때 `setup:` 키를 `steps:` 키 **바로 앞**에 만든다(§3 D1의 예시와 같은 순서). 손으로 쓴 `setup:`이 이미 있으면(빈 `steps: []`·flow 표기 포함) 그 키를 다시 쓰고 block 표기로 돌린다. 마지막 준비 스텝이 나가거나 지워지면 `setup:` 키를 통째로 지운다.
  - 옮긴 스텝의 추출 기본값(`default:`)은 지우지 않는다. 준비 스텝의 Inspector는 기본값 칸 옆에 「준비 스텝에서는 쓰이지 않습니다」를 보인다(D1).
- 준비 스텝 삭제는 된다. 준비 구획 안의 순서 바꾸기(Inspector의 ↑↓ 포함)·추가 버튼·끌어 옮기기는 슬라이스 B — 준비 스텝의 Inspector에는 ↑↓를 내지 않는다.
- 템플릿 삽입: 준비 스텝을 고른 상태에서 삽입하면 본 스텝의 끝에 들어간다(지금 「고른 스텝 없음」과 같은 동작).
- 페이싱 현황판과 think 일괄 편집에 준비 스텝이 든다(준비 스텝에도 think time이 적용된다 — D3). 행의 경로 칸은 「준비」. 「think 있음」 판정(`scenarioHasThink`)도 준비 스텝을 본다.
- test-run 결과와 흐름 칩(`TestFlowChips`)은 준비 스텝을 앞에 구분해 보이고 「준비」 표지를 단다. 준비 실패면 「준비 스텝이 실패해 본 스텝을 실행하지 않았습니다」. 행 모드(데이터셋 순차)는 준비 행(`setup_steps`)을 행 목록 위에 한 번 보인다. 결과 머리의 스텝 수는 본 스텝 행만 세고 준비 행 수를 따로 적는다.
- UI trace 스키마에 `section`·`setup_failed`·`setup_ms`·`setup_steps`를 선택 키로 더한다(서버는 없으면 키를 생략한다). `section`은 글자로 읽고 `"setup"`과 비교한다(나중에 다른 구간 이름이 와도 응답 파싱이 깨지지 않게).
- 사이징 도우미는 `total_ms − setup_ms`를 쓰고 요청 수에서 준비 행을 뺀다(D7). 준비가 실패한 test-run은 잘린 test-run처럼 「측정 아님」으로 다룬다(본 스텝이 실행되지 않았다).
- 그 밖에 준비 스텝을 보게 하는 자리: 파일 가져오기의 「내용 있음」 판정, run 상세·리포트의 스텝 이름표와 타임아웃 재정의 안내, 인쇄 보고서의 「대상 시스템」(준비 스텝의 사실은 본 스텝 목록과 **따로** 담는다 — 스텝 표·비교의 스텝 수는 본 스텝만 그대로), 비교 보고서의 「같은 시나리오」 판정(준비 스텝의 이름·메모만 다른 두 run은 같은 시나리오다 — 지금은 다르다고 나온다. 준비 스텝의 내용이 다르면 지금도 다르다고 나온다). 실행 중 화면(`RunDetailPage`)의 준비 진행은 슬라이스 B라 손대지 않는다.

**D16. 본 스텝이 없는 시나리오 — 시작 전에 경고하고, 진행하면 준비 스텝만 한 번 하고 끝낸다 (사용자 결정 2026-11-22)**

- 지금 동작(이 기능 전부터): `steps`가 빈 시나리오는, run 단위 think time이 없으면 VU 고정·VU 곡선의 VU 반복 루프가 기다림 없이 돈다(요청 없이 CPU만 쓴다). open-loop는 도착 간격이 있어 쉬지 않고 돌지는 않지만 실행 시간 끝까지 빈 도착을 센다.
- **시작 전 경고**(막지 않는다): run 생성 창과 스케줄 폼은 본 스텝이 없는 시나리오에 경고 상자(노란색)를 보인다 — 준비 스텝이 있으면 「본 스텝이 없습니다. 준비 스텝만 한 번 실행하고 run이 끝납니다.」, 준비 스텝도 없으면 「본 스텝이 없습니다. 보낼 요청이 없어 run이 바로 끝납니다.」 미리 실행(test-run)에는 경고를 두지 않는다(한 바퀴만 도는 확인용이다).
- **진행하면** — 세 부하 모델 모두 준비만 하고 **정상 종료**한다. 실패로 세지 않고 run은 `completed`로 끝난다.
  - VU 고정: VU는 준비 스텝을 마친 뒤(준비 스텝도 없으면 곧바로) 반복 없이 끝난다. 모든 VU가 끝나면 run이 끝난다(상승 시간이 있으면 마지막 VU가 시작해 준비를 마친 뒤).
  - VU 곡선: VU는 같은 식으로 끝난다(끝난 VU의 자리는 다시 채워지지 않는다 — 지금 동작). 곡선 감독 루프는 지금 실행 시간 끝까지 돌므로 종료 조건을 더한다 — 본 스텝이 없고, **지금까지 시작한 VU 수가 곡선의 최고점에 닿았고, 시작한 VU가 모두 끝났으면** 끝낸다. 곡선이 뒤에서 더 올라가면 그때 시작하는 VU도 준비를 한 번 해야 하므로 최고점에 닿기 전에는 끝내지 않는다.
  - open-loop: 슬롯마다 한 번 준비를 한다. 본 스텝이 없으면 도착은 **준비 안 된 슬롯을 받았을 때만** 준비를 띄우고, 빈 슬롯이 없거나 이미 준비된 슬롯을 받은 도착은 아무것도 세지 않는다(시작·완료·보내지 않음 모두 0 — 보낼 요청이 없는 run에 「보내지 못한 요청」이 찍히지 않게). 모든 슬롯이 준비를 마쳤거나 준비 실패로 빠지면 스케줄러가 끝낸다(준비 스텝도 없으면 첫 도착 전에). 판정은 스케줄러 루프 머리라 다음 도착 시각에 일어난다. 모든 슬롯이 준비에 실패하면 지금처럼 `AllVusFailed`다.
  - 준비 실패·준비 중 종료의 규칙(D6)은 그대로다.
  - 곡선의 최고점이 감독 tick(250ms)보다 짧아 시작한 VU 수가 최고점에 못 닿으면 지금처럼 실행 시간에 끝난다.
  - 「일찍 끝난다」 = VU 고정은 모든 VU의 준비 뒤, VU 곡선은 최고점 도달과 준비 뒤, open-loop는 모든 슬롯의 준비 뒤. 설정한 실행 시간이 그보다 짧으면 지금처럼 실행 시간에 끝난다.
- test-run·모니터: 바꾸지 않는다(준비 행만 나온다).
- 리포트: 본 요청이 0건이고 `setup` 블록에 준비 통계가 있다. 새 필드 없음. 유효성은 지금 규칙 그대로 「요청 0건」(`zero_requests`) 사유로 「의심」이 된다 — 측정된 본 요청이 없으므로 맞는 표시이고, 실행 창 경고가 미리 알린 결과다.
- 본 요청 경로(`execute_steps`의 http 가지)에는 분기를 더하지 않는다. 검사는 VU 반복 머리·스케줄러 루프 머리에서 한다(D7·§8과 같은 제약). 본 스텝이 있는 시나리오의 동작·숫자는 바뀌지 않는다.

**D15. 운영 모니터 — A2는 표시만, 칸 대상 선택은 다음 슬라이스 (사용자 결정 2026-11-22)**

- 모니터 점검은 준비 → 본 스텝 한 바퀴라(D11) 준비 스텝이 있는 시나리오의 미리 실행 결과와 점검 기록 창에는 지금도 준비 행이 나온다. A2는 그 행의 **이름을 찾고 「준비」 표지를 단다**(`PanelEditor`의 이름표·`CheckRecordDialog`·`PreviewResult`). `PanelEditor`는 한 목록을 이름표와 「응답 시간 기준 스텝」 선택지에 함께 쓴다 — 이름표와 조건·표시 항목의 「스텝 없음」 판정만 준비 스텝을 보고, **선택지는 본 스텝만** 그대로 둔다. TUI로 준비 스텝을 기준으로 걸어 둔 칸은 선택지에 없는 값이므로 지금처럼 따로 한 줄로 보이되 id 대신 이름을 쓴다. 묶음의 스텝 칸이 준비 스텝을 가리킬 때 뜨는 「스텝 없음」(스텝 선택지 기준)은 다음 슬라이스가 선택지를 열 때 함께 풀린다.
- A2는 GUI 칸 설정에서 준비 스텝을 **고르는 길을 열지 않는다**: 스텝 선택지(`stepOptionsFor`)는 본 스텝만 그대로이고, 미리 실행 결과의 준비 행에는(칸 하나 보기·묶음 보기 모두) 「조건으로 추가」·「화면에 추가」를 내지 않고 「준비 스텝의 값은 아직 칸에 쓸 수 없습니다」를 보인다. (§7-2 초안의 「스텝 선택지에 준비 스텝을 포함한다」를 다음 슬라이스로 옮겼다.)
- 이유(보안 리뷰 N3): 준비 구간이 로그인의 표준 자리가 되면 「로그인 응답의 토큰을 전시 화면에 표시」가 한 번의 설정이 된다. 사용자 결정 — 서버가 준비 스텝 값을 무조건 가리지 않는다(준비 스텝이 꼭 로그인은 아니고, 「(인증 값)」이라고 부르면 거짓이다). 대신 **조건·화면 표시 항목마다 선택 칸 「가림 문구」**를 둔다: 값이 있으면 전시 화면 값·실패 사유에 받은 값 대신 그 문구를 내고, 비면 그대로 낸다. 모든 스텝에 적용한다. 설정 화면은 준비 스텝의 값이거나 이름이 비밀 같으면(기존 `isSecretName` 규칙) 「(가린 값)」을 미리 채운다(지우거나 바꿀 수 있다).
- 「가림 문구」는 칸 설정 형식(서버 검증·보드 파일·TUI 거울)을 바꾸는 모니터 기능이라 **자기 spec을 가진 별도 슬라이스**로 한다(§10-0). 모니터 칸의 준비 스텝 선택은 그 슬라이스가 함께 연다.
- 남는 것(A1부터 있던 상태, roadmap에 적는다): TUI·API·보드 파일로는 지금도 준비 스텝을 칸 대상으로 걸 수 있고, 그 값은 가려지지 않는다. 다음 슬라이스의 「가림 문구」가 사용자가 막는 수단이다.

**D14. run 생성 창·스케줄 폼 안내** (막지 않는다. 문구에 「로그인」을 쓰지 않는다 — 사용자 승인 2026-11-22)

같은 안내를 run 생성 창(`RunDialog`, 간단·상세 두 모드)과 스케줄 폼(`ScheduleForm`)에 낸다. 판정은 순수 함수 하나, 표시는 공용 컴포넌트 하나다.

- 준비 스텝이 있고 VU 고정이고 상승 시간이 0: 「준비 스텝이 VU 수만큼 한꺼번에 나갑니다. 상승 시간을 두면 나눠서 나갑니다.」(사용자 결정 「가」)
- 준비 스텝이 쓰는 `per_vu`(바인딩 방식 선택지 「per_vu — VU마다 한 행 (고정)」) 데이터셋의 행 수가 VU 수(VU 곡선은 최고점, open-loop는 슬롯 수)보다 적음: 「데이터 N행을 VU M개가 나눠 씁니다. 같은 행으로 준비 스텝이 여러 번 실행됩니다. 값 하나가 틀리면 그 행을 받은 VU가 모두 준비에 실패합니다.」(open-loop에서는 「VU」 자리에 「슬롯」)
- 준비 스텝이 있고 open-loop: 「준비 스텝은 슬롯마다 한 번 실행됩니다. 슬롯이 N개면 준비 스텝이 최대 N번 나갑니다.」
- 준비 스텝이 `per_vu`가 아닌 바인딩의 변수를 참조: 「준비 스텝은 VU마다 첫 반복의 값으로 한 번만 실행됩니다. `user` 값이 VU마다 고정돼야 한다면 데이터셋 방식을 'per_vu — VU마다 한 행 (고정)'으로 두세요.」(변수가 여럿이면 이름을 쉼표로 잇는다. 승인 문구에서 두 군데를 바꿨다 — ① 방식 이름: 'VU별 고정'은 화면에 없는 이름이라 바인딩 방식 선택지의 글자 그대로, 선택지와 안내가 한 `ko` 키를 쓴다 ② 「`user`가 … 값이라면」 → 「`user` 값이 … 한다면」: 변수 이름이 영문이면 조사를 고를 수 없어서)
- 「준비 스텝이 쓰는 데이터셋」 = 그 바인딩이 대는 변수 가운데 하나라도 준비 스텝의 주소·헤더·본문이 `{{이름}}`으로 참조하는 바인딩.

## 8. 호환성과 성능

- 준비 스텝이 없는 시나리오: YAML·proto 배치 바이트·리포트 JSON·DB 행이 변경 전과 같다.
- 워커와 컨트롤러는 함께 올려야 한다. 옛 워커는 `setup` 키를 모르는 필드로 거절해(`deny_unknown_fields`) run이 즉시 `failed`가 된다. 릴리즈 노트에 적는다.
- 본 스텝의 요청 경로에는 분기를 더하지 않는다(D7). 반복 머리에 준비 추출 변수 덮기가 생기지만 준비가 없으면 빈 맵 검사 한 번이다.
- 성능 확인: 준비 없는 시나리오로 master 바이너리와 같은 조건에서 RPS를 비교한다(라이브 검증 표).

## 12. 검증

### 자동

- 엔진: 세 진입점을 각각 직접 타는 테스트(`Mode::{Closed,Curve,Open}` 선례) — 준비 요청 수 = VU(슬롯) 수, 본 스텝이 준비 추출 값을 매 반복 받음, 쿠키 이어받기, 준비 실패 VU(슬롯)는 본 요청 0건이고 다시 시도하지 않음, 전부 실패하면 run 오류, 본 집계 창에 준비 스텝 id 없음, 준비 없는 시나리오의 flush에 준비 통계 없음, 준비 통계만 든 주기 flush가 전달됨, 곡선의 park 뒤 재개에서 준비를 다시 하지 않음, open-loop 준비 실패 도착이 시작·완료·버림 어디에도 없고 준비 실패로만 세어짐, 빈 값·`null` 추출과 기본값 선언이 있는 추출 실패가 준비 실패가 됨.
- 엔진: `to_yaml` 왕복 — 준비 없는 시나리오 출력 글자 불변, 준비 있는 시나리오 왕복 일치. 준비 구간의 http 아닌 스텝 거절.
- trace: 준비 → 본 순서, 표지, 준비 실패 시 멈춤과 `setup_failed`, 행 모드의 `setup_steps`, `setup_ms`.
- 컨트롤러: 수신·읽을 때 합산·리포트 `setup` 블록·순서, 준비 없는 run 리포트에 키 없음, 유지 구간 창 시작 보정(VU 고정), http 아닌 준비 스텝 거절(생성·수정 400, test-run 422, 보드 파일), 시나리오 삭제 연쇄, 모니터 인증 변수 가림이 준비 스텝을 봄.
- UI(A1): Zod·`normalizeForModel` 왕복(빈 `setup` 키 없음), 변수 탐색, 리포트 구획(접힘·경고).
- 엔진(A2): 본 스텝이 없는 시나리오 — 세 부하 모델에서 준비 요청 수 = VU(슬롯) 수이고 run이 실행 시간 전에 정상 종료, 준비도 없으면 곧바로 종료, 준비가 전부 실패하면 여전히 실패, 본 스텝이 있는 시나리오는 불변.
- UI(A2): Inspector로 준비 스텝 수정 → YAML 반영, 구획 사이 옮기기(첫 준비 스텝이면 `setup:` 키가 `steps:` 앞에 생기고, 마지막 준비 스텝을 옮기면 `setup:` 키가 사라짐), test-run 표지와 준비 실패 문구, 사이징 보정, 안내 네 종류(두 폼), 모니터 미리 실행의 준비 행에 추가 버튼이 없음.
- 회귀 테스트는 되돌려 확인한다(고친 코드를 옛 상태로 되돌려 RED를 본다).

### 전수 명령 (plan이 분류표를 만들고 구현 뒤 다시 돌린다)

```bash
grep -rn '\.steps\b' crates/engine/src crates/controller/src crates/worker/src crates/tui/src --include='*.rs'
grep -rnE '\.steps\b|"steps"' ui/src --include='*.ts' --include='*.tsx'
```

각 매치를 「모든 스텝」·「반복 본문만」·「시나리오와 무관(리포트 스텝·계단 등)」 셋 중 하나로 분류한다.

## 13. 보안

- 준비 스텝은 요청 실행·템플릿·데이터셋 바인딩 경로를 새 순서로 쓴다 → `security-reviewer` 대상. 살필 곳: 모니터의 인증 변수 가림이 준비 스텝을 보는지(D2), `SetupFailed` 문구와 `failure_kinds`에 값이 없는지, 준비 실패 로그 줄.
- 새 저장 값은 고정 분류·스텝 id·변수 이름뿐이다. 토큰·계정·URL은 run 레코드·리포트·새 로그 줄에 싣지 않는다.
- VU 변수로 보관하는 토큰은 메모리에만 있고 VU와 함께 사라진다. trace의 `final_vars`·`extracted`에는 지금도 추출 값이 실린다(변화 없음).
