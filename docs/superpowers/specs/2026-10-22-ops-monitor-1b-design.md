## 사용자 스토리 (US)

- **US1**: QA가 칸 설정 화면에서 미리 실행 결과를 보며 "200인데 실제로는 실패인 응답"을 잡는 조건을 만든다 — 성공하면 응답 본문 값·상태코드·헤더 값을 클릭해 규칙과 비교값을 고른 조건이 칸에 저장되고, 다음 점검부터 조건이 깨지면 그 칸이 `✖ 실패`가 되며, 시나리오는 그대로라 같은 시나리오의 부하 테스트 판정은 바뀌지 않는다.
- **US2**: 운영자가 조건 때문에 실패한 칸을 멀리서 볼 때 무슨 값이 왔는지 알아본다 — 성공하면 큰 줄에 실제 값(값 없음/비어 있음/`"OK" 포함 안 됨`)이, 작은 줄에 경로·규칙·스텝이 보이고, 값이 아주 길어도 `…`로 잘려 제목·그래프 자리와 글자 크기가 그대로다.
- **US3**: QA가 보드마다 화면 방식을 A(신호등)·B·C로 골라 전시한다 — 성공하면 A는 칸 배경 전체가 상태 색이고 그래프는 어두운 상자 안에서 B와 같은 색 규칙으로 보이며, 바꾼 방식이 켜진 전시 화면에 수 초 안에 반영된다.
- **US4**: 운영자가 C 방식 보드에서 평소엔 차분한 화면을 보다가 장애 시 어느 칸이 실패인지 즉시 안다 — 성공하면 실패 칸만 화면 대부분을 차지하고(여럿이면 나눠 씀) 정상·느림 칸은 옆/아래 띠로 작게(제목·상태·ms) 줄며, 복구되면 원래 배치로 돌아간다.

## 1. 배경과 목표

①a는 칸 성공 판정을 **시나리오 자체 판정**(상태코드 assert·값 추출 실패)으로만 했다. 그래서 "HTTP 200 + 본문 `resultCode: E1023`" 같은 응답은 정상으로 보인다. ①b는 시나리오를 건드리지 않고 **모니터 칸 설정**에 성공 조건을 둔다. 조건은 미리 실행 결과에서 값을 클릭해 만든다. 또 결정 원천의 화면 방식 A(신호등)·C(실패만 크게)를 B(①a) 옆에 추가한다.

**범용 API 모니터**(①a와 동일 `[사용자]`): 로그인 특화 판정·문구·비밀번호 식별 로직을 넣지 않는다.

### 비목표
- 조건 OR/그룹, 정규식, 쿠키 대상, 미리 실행 없이 조건을 처음부터 손으로 만드는 화면(만든 조건의 규칙·값·경로 편집은 가능 — §5.2).
- 칸별 화면 방식(보드 단위 — 결정 원천 추가 결정).
- C 배치 전환 애니메이션.
- ② ③, 결과 영속, 외부 알림, 삭제 가드의 보드 참조(①a §B37 연기 그대로).

### 안티골
- 긴 응답 값이 제목·그래프를 밀어내거나 글자를 줄임(D2·①a §7.3).
- 조건 실패 값이 `reason` 고정 문구 분할 규칙(`splitReason`, 첫 ` · `)에 걸려 엉뚱하게 쪼개짐(값에 ` · `가 들어 있을 수 있다).
- 같은 시나리오의 부하 테스트 판정이 조건 때문에 바뀜(조건은 run 경로에 절대 닿지 않는다).
- A 방식에서 사용자 기준선 색(예: 노랑) 배경 위 흰 글씨처럼 **읽히지 않는 조합**.
- 목업에 없는 화면·배치를 새로 만듦(D9).

## 3. 저장 — `PanelConfig.conditions`, `BoardConfig.display_style`

migration 없음(F1). 두 필드 모두 serde default라 ①a 행은 `conditions: []`, `display_style: "border"`로 읽히고 ①a와 같게 동작한다.

```jsonc
// BoardConfig 추가
"display_style": "fill" | "border" | "focus"   // A=fill(신호등) · B=border(①a, 기본) · C=focus(실패만 크게)

// PanelConfig 추가
"conditions": [ Condition, ... ]                // 0..=10개, 위에서부터 평가
// Condition
{
  "step_id": "<ULID>",                          // 시나리오 http 스텝
  "source": "body" | "header" | "status" | "body_text",
  "path": "$.resultCode",                       // body: JSONPath / header: 헤더 이름 / status·body_text: ""
  "op": "exists" | "not_empty" | "eq" | "ne" | "contains" | "gt" | "lt",
  "value": "0000",                              // eq/ne/contains/gt/lt만 의미, 나머지는 저장 시 ""로 정규화
  "ignore_case": false,                         // eq/ne/contains만 의미 — 대소문자 무시 (D10)
  "trim": false                                 // eq/ne/contains만 의미 — 앞뒤 공백 무시 (D10)
}
```

**source별 허용 op**(`[Claude]`): `body`·`header` = 7종 전부 / `status` = `eq`·`ne`·`gt`·`lt`(있음·비어 있지 않음은 항상 참이라 무의미) / `body_text` = `contains`·`not_empty`.

`Condition`도 ①a 방식 그대로 컨테이너 `#[serde(default)]` + 손 `Default`(`ignore_case`·`trim` 기본 `false`, F1).

**저장 검증 → 400**(①a 규칙과 같은 위치·한국어 메시지, F2라 `preview-check`에도 적용): 개수 ≤10 · `step_id` 유효 ULID · source별 허용 op · `body`면 `path` 1..=500자이고 JSONPath로 파싱됨 — 컨트롤러는 `serde_json_path`에 직접 의존하지 않으므로(F18) **엔진이 공개 헬퍼를 연다**(JSONPath 파싱 검증 / 첫 매치를 `serde_json::Value`로 반환 — 숫자 여부를 판정에 써야 하므로 문자열만 돌려주지 않는다 / 엔진과 같은 문자열화; §4 4단계와 같은 헬퍼) · `header`면 `path` trim 후 1..=200자 · `contains`면 `value` 비어 있지 않음(빈 문자열 포함은 항상 참) · `status`/`body_text`면 `path`를 `""`로 정규화 · `gt`/`lt`면 `value`가 유한한 숫자 · `value` ≤200자 · eq/ne/contains가 아니면 `ignore_case`·`trim`을 `false`로 정규화. **스텝 존재 여부는 저장 시 검사하지 않는다**(①a 원칙 — 실행 시 `config_error`, §4).

## 4. 판정 (`judge` 확장 — controller `monitor/`)

`judge`의 기존 §6.2 단계는 **그대로**, 시나리오 판정이 통과해 `Ok`가 될 자리에서만 조건을 평가한다. 시나리오 판정 실패(HTTP 503·시간 초과·추출 실패 등)는 지금처럼 그 사유가 우선이다.

1. **요청 전 확인**(`run_check`, ①a의 기준 스텝 확인 바로 뒤): 조건의 `step_id`가 시나리오 http 스텝이 아니면 → `config_error` "조건 기준 스텝 없음"(설정 문제에 부하를 쓰지 않는다). `judge`도 같은 검사를 **맨 앞**, `latency_step_exists` 검사 바로 뒤(trace truncated/error 검사보다 먼저)에 한다 — `run_check`와 `judge`가 같은 입력에 같은 결과를 내도록 순서 고정(①a의 이중 구조와 같음).
2. 시나리오 판정 통과 후 조건을 위에서부터 평가, **처음 깨진 조건 하나**가 사유. 모두 통과 → `ok`.
3. 조건 대상 응답 = 그 스텝의 **마지막 실행**(F5와 같은 규칙). 그 스텝이 한 번도 실행되지 않았으면(분기로 안 탐) → `fail` "조건 스텝 미실행".
4. 실제 값 구하기:
   - `body`: 본문이 잘렸으면(`body_truncated`, F7) → `fail` "응답 본문이 너무 큼". JSON이 아니면 → `fail` "본문이 JSON 아님". JSONPath 첫 매치가 없으면 → **값 없음**. 매치 값 문자열화는 **엔진과 같은 규칙**(F6: `null`→`""`) — 엔진 `extract.rs`의 두 비공개 fn을 `pub`으로 열어 재사용하는 방향(`[Claude]`, 규칙이 갈라지지 않게. 구현 방식은 plan 결정).
   - `header`: 이름 대소문자 무시 조회(F8), 없으면 → 값 없음. 값이 비ASCII라 trace에서 빠진 헤더도 값 없음(F8 — 수용, §7).
   - `status`: 상태코드 10진 문자열.
   - `body_text`: 본문 전체(잘렸으면 위와 같이 "응답 본문이 너무 큼").
5. op 평가(값 없음은 **모든 op에서 실패**, `[Claude]`):

| op | 통과 조건 | 실패 시 큰 줄(`reason`) |
|---|---|---|
| exists | 매치 있음(`null`도 있음) | `값 없음` |
| not_empty | 문자열화 값 ≠ `""` | `비어 있음`(값 없으면 `값 없음`) |
| eq / ne | 문자열 일치 / 불일치 — 기본 완전 일치, `trim`이면 양쪽 앞뒤 공백 제거 후, `ignore_case`면 양쪽 소문자화 후(D10). **단 `body` 매치 값이 JSON 숫자이고 비교값이 유한 숫자로 파싱되면 숫자(f64)로 비교**(`[Claude]` — 화면 트리는 `1.0`을 `1`로 보이지만 엔진 문자열화는 `"1.0"`이라 문자열 비교면 기본 조건이 영영 실패. JSON 문자열 `"0000"`은 문자열 비교 유지) | 실제 값(원문 그대로 — 정규화 전 값) |
| contains | 실제 값이 비교값을 포함 — `trim`·`ignore_case`는 eq와 같은 방식으로 양쪽에 적용(D10) | `body_text`: `"{비교값}" 포함 안 됨`(D5) · 그 외: 실제 값 |
| gt / lt | 실제 값(trim)이 **유한한** 숫자로 파싱되고 비교값보다 큼/작음(`inf`·`NaN` 문자열은 실패) | 실제 값(숫자 아님도 그대로 보여 줌) |

실제 값이 빈 문자열이면 큰 줄은 `비어 있음`(빈 줄 방지).

### 4.1 와이어 — `CheckResult.detail` 추가

```jsonc
{ "at_ms": ..., "verdict": "fail", "latency_ms": null,
  "reason": "E1023",                                   // 큰 줄
  "detail": "resultCode · 같음 0000 · 로그인" }         // 작은 줄 — 조건 관련 결과에서만, 그 외 null
```

- `detail`은 `Option<String>`, **항상 직렬화**(null 포함 — UI Zod `.nullable()`). ①a의 모든 기존 결과는 `detail: null`이고 `reason` 규칙도 그대로(byte-identical 의미).
- **`detail`이 있으면 UI는 `reason`을 `splitReason`으로 쪼개지 않는다**(안티골 — 값에 ` · `가 있을 수 있음). `detail`은 조건 판정 결과(§4의 2·3·4·5 단계, "조건 기준 스텝 없음" 포함)에 **항상** 붙고, 그 밖에선 절대 안 붙는다. 조건 판정 결과의 `reason`에는 ①a식 ` · {스텝 이름}` 접미를 **붙이지 않는다**(스텝 이름은 `detail`이 가진다) — 고정 문구(`본문이 JSON 아님` 등)여도 같다. 즉 `splitReason`은 `detail == null`인 ①a 경로에서만 돈다.
- 실제 값이 우연히 고정 문구(`값 없음` 등)와 같은 글자일 수 있다 — 수용(`[Claude]`). 작은 줄의 규칙·경로가 맥락을 주고, 큰 줄에 따옴표·접두를 붙이면 D3(값이 가장 잘 보이게)에 반한다.
- `detail` 형식: `{대상} · {규칙} {비교값} · {스텝 이름}` — 비교값이 없는 op(exists·not_empty)는 `{규칙}`만, 스텝 이름은 ①a처럼 **시나리오에 정의된 http 스텝이 2개 이상일 때만**(F3, `[Claude]`). "조건 기준 스텝 없음"은 스텝이 시나리오에 없어 이름을 모르므로 스텝 부분 없이 `{대상} · {규칙} {비교값}`. 대상 표시: `body` = JSONPath에서 선두 `$.` 제거(`resultCode`, `data.items[0].code`, 괄호 표기는 그대로), 루트 `$` 자체면 `본문` · `header` = `헤더 {이름}` · `status` = `상태코드` · `body_text` = `본문 전체`. 규칙 문구: 값이 있음 / 비어 있지 않음 / 같음 / 같지 않음 / 포함 / 보다 큼 / 보다 작음. 문구 정본은 plan이 `check.rs` 상수로 확정.
- **서버 상한**(D4): `reason`·`detail` 각각 **200자**(문자 경계)로 자른다. 줄바꿈·제어 문자(`char::is_control`, Cc)와 서식 문자(Cf — 양방향 재정렬 U+202A–202E·U+2066–2069, 폭 없는 문자 U+200B–200F·U+2060–2064, U+FEFF, U+00AD 등, 벽 글자 위장 방지)는 공백 하나로 바꾼다. Rust std엔 일반 범주 API가 없으므로 **`check.rs`에 Cf 코드포인트 범위 목록을 하드코딩**(새 의존성 없음, `[Claude]`) + U+202E·U+200B·U+FEFF 단위 테스트. `"{비교값}" 포함 안 됨`은 **따옴표 안 비교값을 먼저 줄여**(`"…"` 안에서 `…`) 꼬리 `포함 안 됨`이 항상 남게 한다.
- **프론트의 `포함 안 됨` 사유 렌더**: `FitLine`은 끝 생략뿐이라 꼬리를 자른다. 그래서 UI는 이 사유를 **세 조건이 모두 맞을 때만** 식별한다: `detail`이 `본문 전체 · 포함 `으로 시작 **그리고** `reason`이 `"`로 시작 **그리고** `" 포함 안 됨`으로 끝남(대상 표시가 `본문 전체`인 source는 `body_text`뿐 — body 루트는 `본문`, 헤더는 `헤더 `라 충돌 없음; 서버의 따옴표 안 축약 규칙이 이 모양을 보장하므로 정확. `body_text`의 다른 결과 — `비어 있지 않음` 실패·본문 잘림·조건 스텝 미실행·조건 기준 스텝 없음 — 은 접두가 같아도 이 모양이 아니므로 일반 `FitLine`). 식별되면 `reason`에서 앞 `"`와 뒤 `" 포함 안 됨`을 떼어 **가로 flex 한 줄**로 그린다: `"` + 줄어드는 `min-w-0 truncate` 값 span + 줄지 않는(`shrink-0`) `" 포함 안 됨` span. JS 측정 없이 꼬리가 항상 보이고, 라이브에서 rect로 확인한다.
- **`/status` 크기**(F17): `/status`는 칸마다 **최신 결과에만** `reason`·`detail`을 싣고 그 이전 결과는 `null`로 보낸다(UI는 최신 사유만 읽는다 — F17). 링버퍼(메모리)는 결과 전체를 그대로 둔다. 9칸×300개×(사유 400자) 매초 폴링을 피한다(①a 대비 크기 증가 없음).
- 조건 실패의 `latency_ms`는 `null`(①a의 모든 `fail`과 같음 — 막대는 풀높이 빨강 빗금).
- `config_error` "조건 기준 스텝 없음"은 깜빡이지 않는다(①a §7.5 그대로).

### 4.2 시나리오·run 경로 무변경
조건은 `monitor` 모듈 안에서만 평가한다. 시나리오 YAML·엔진 실행 경로·run/리포트는 바뀌지 않는다(US1 마지막 절 — 검증 §8).

## 5. 설정 화면

### 5.1 보드: 화면 방식
보드 설정(이름·글자 크기·깜빡임 옆)에 **화면 방식** 선택: `신호등 (칸 전체 색)` / `테두리 (기본)` / `실패만 크게`. 형태는 기존 보드 설정 컨트롤과 같은 계열(`[Claude]` — 새 그림 카드·썸네일 없음, D9). 저장 시 켜진 전시 화면은 ①a의 `board_updated_at` 경로로 수 초 내 반영(US3).

### 5.2 칸: 성공 조건 (목업 `01`)
- 칸 편집기에 **"성공 조건"** 섹션: 기본 접힘 disclosure, 조건이 있으면 자동 펼침·접힌 채면 "N개 설정됨"(①a 고급 섹션과 같은 이디엄, 사용자 선호). 안내 한 줄: "모두 만족해야 정상 · 시나리오 자체 판정에 더해서".
- 조건 목록 행 = **목업 `01`처럼 요약 한 줄**: `{스텝 이름} · {대상 표시} {규칙} {비교값}`(+ 체크박스가 켜졌으면 `· 대소문자 무시`/`· 앞뒤 공백 무시` 꼬리) + `✎`(편집) + `🗑`(삭제). `✎`는 그 행 자리에 **조건 확인 줄과 같은 편집 줄**을 연다(규칙 select — 그 source의 허용 op만 · 비교값 입력 — 필요한 op일 때만 · 체크박스 `대소문자 무시`·`앞뒤 공백 무시` — 같음·같지 않음·포함일 때만, D10 · 대상 경로 입력 — body·header만 · `저장`/`취소`). 저장 전까지는 로컬 편집(①a 보드 저장 흐름 그대로).
- **만들기는 미리 실행 결과에서만**(비목표 참조). `PreviewResult`를 확장:
  - 응답 본문이 JSON이고 잘리지 않았으면 **트리**로 보여 주고 스칼라 값마다 `+ 조건`. 에디터 `ResponseBodyTree`(F9)를 **조건용으로도 쓸 수 있게 일반화**(값 클릭 → 콜백)하되 에디터의 `+추출` 동작·문구·테스트는 그대로(F9 체인 일반화 — ①a §10). 긴 본문의 모달 보기 방식도 에디터와 같은 패턴. 이건 **실제 리팩터**다(F20 — 트리·본문 블록·헤더 표가 `Extract`에 결합돼 있고 일부는 `TestRunPanel.tsx` 비공개): plan은 "공용 컴포넌트로 추출 + 에디터 소비처를 무동작 변경으로 이전" task를 **조건 UI task보다 먼저** 독립 green 커밋으로 두고, 기존 에디터 test-run/추출 테스트 무수정 green을 회귀 가드로 삼는다.
  - 응답 헤더 표의 행마다 `+ 조건`, 상태코드 옆 `+ 조건`.
  - 본문이 JSON이 아니거나 잘렸으면 `+ 본문 전체 포함 조건` 버튼.
  - 클릭 → 그 자리에 **조건 확인 줄**(목업 `01`의 보라 띠): 대상 표시 · 규칙 · 비교값 · 체크박스 두 개(기본 꺼짐) · `추가`/`취소`. 에디터 `ExtractConfirmRow`처럼 **인라인 JSX**(모달 안 중첩 모달 금지 — scenario CLAUDE.md ESC 함정). 입력이 저장 검증(§3)을 통과하지 않으면 `추가` 비활성(예: 크다·작다에 숫자 아님, 포함에 빈 값).
  - **기본값**(`[Claude]` — "만들자마자 실패하거나 저장이 안 되는 조건"과 "매번 바뀌는 비밀 값을 벽에 띄우는 조건"을 기본으로 만들지 않게):

    | 클릭한 것 | 기본 규칙 | 기본 비교값 |
    |---|---|---|
    | 짧은 문자열 값(40자 이하) · 숫자 · `true`/`false` | 같음 | 지금 값(숫자는 §4 숫자 비교라 표기 차이 무관) |
    | 긴 문자열 값(40자 초과 — 토큰·세션 id 같은 매번 바뀌는 값일 가능성) | 비어 있지 않음 | — (확인 줄에 "매번 바뀌는 값이면 '같음'은 매 점검 실패하고 그 값이 벽에 표시됩니다" 안내 한 줄) |
    | `null` | 값이 있음 | — |
    | 헤더 | 값 길이에 따라 위 두 행과 같은 규칙 | 같음이면 지금 값 |
    | 상태코드 | 같음 | 지금 상태코드 |
    | 본문 전체 | 포함 | 빈 칸(사용자가 입력 — 비어 있으면 `추가` 비활성) |
- **PreviewResult 판정 줄**: `reason` 옆에 `detail`이 있으면 함께 보여 준다(설정 화면이라 전체 문자열, 줄바꿈 허용).
- 진행 중인 조건 편집 줄의 미완성 값은 `preview-check`에 보내지 않는다(편집 줄 `추가`/`저장` 전엔 칸 설정에 안 들어감). 저장된 조건이 서버 검증에 걸리면 기존 미리 실행 오류 표시(①a)로 400 문구가 보인다.
- 미리 실행은 지금 편집 중인 칸 설정(조건 포함)으로 `preview-check`를 부르므로, 조건을 추가하고 다시 미리 실행하면 판정 줄에 조건 결과(`✖ 실패 · E1023` 등)가 바로 보인다.
- 시나리오에서 스텝이 사라진 조건 행은 `⚠ 스텝 없음` 표시(①a의 기준 스텝 `stepGone` 표시와 같은 방식) — 저장은 막지 않는다.

## 6. 전시 화면

### 6.1 공통 — 조건 실패 사유 (목업 `02`)
- `detail`이 있으면: 큰 줄 = `reason`(①a 사유 줄과 같은 크기·`--reason-fit` 배율·`FitLine`, 넘치면 `…`), 작은 줄 = `detail`(①a 스텝 이름 줄과 같은 크기·스타일, 넘치면 `…`). 줄 수는 ①a와 같은 2줄 — 연속 실패 줄·그래프 공간 규칙(§7.3) 그대로.
- **배율 고정 규칙 유지**(①a §7.3): 조건 값은 결과라 배율 계산에 들어가지 않는다. 새 **고정** 사유(`조건 기준 스텝 없음`·`조건 스텝 미실행`·`본문이 JSON 아님`·`응답 본문이 너무 큼`·`값 없음`·`비어 있음`)는 `WIDEST_REASON_CANDIDATES`(F12)에 추가해 사유 줄 배율이 이들을 한 줄에 담게 한다. 가변 값(실제 응답 값·`… 포함 안 됨`)은 `…`로 처리(D2).
- 세 방식 모두 같은 사유 규칙.

### 6.2 A — 신호등 (`fill`, 목업 `03`)
- 칸 배경 = 상태 색: 정상 `#15803d` · 느림 = 넘은 기준선 색 · 실패 `#b91c1c` · 설정 오류·확인 불가(`stale`·`stale_off`) `#475569` · 확인 중 = B와 같은 어두운 칸(`[Claude]` — 목업 03 정상/실패 색과 같은 값). 느림 배경이 사용자가 고른 기준선 색 그대로라, 빨강 계열 기준선(기본 2번째 `#ef4444`, F19)이면 실패 칸과 배경이 비슷해진다 — 상태 글자(`▲ 느림`/`✖ 실패`)가 항상 구분해 주므로 수용(B에서도 같은 색 겹침이 있다, `[Claude]`).
- 글자(제목·상태·큰 값·사유·연속 실패) = 배경 대비색 하나: 배경 상대휘도로 **흰색 또는 거의 검정**을 고른다(`[Claude]`, 안티골 — 기준선 색은 사용자가 고르므로 고정 흰색이면 노랑 위 흰 글씨가 생긴다). A에선 상태 색 글자를 쓰지 않는다(배경이 이미 상태).
- 테두리 자리는 유지하되 배경과 같은 색 — **칸 기하·배율 계산은 B와 동일**(probe·§7.3 규칙 무변경).
- 그래프 = 칸 안 **어두운 상자**(배경 `COLOR.bg` 계열) 안에 B와 똑같은 막대·기준선·기준값 열·시간축(D8). 상자 여백은 `display.ts`의 `GRAPH_CHROME`에 **이름 붙은 상수**로 두고, 스타일과 `barsAreaHeight`/`graphFits` 계산이 같은 상수를 쓰게 한다(방식이 A일 때만 더함 — 계산 함수가 방식을 인자로 받는다). 그래야 그래프 숨김 판정(15%·8%)이 실제 막대 높이와 어긋나지 않는다.
- 깜빡임 = ①a 오버레이 그대로(F14, 배경과 무관하게 동작).

### 6.3 C — 실패만 크게 (`focus`, 목업 `04`)
- **실패(`fail`) 칸이 0개이거나 전부면** = B와 똑같은 화면(같은 그리드·같은 칸·**같은 글자 배율** — 아래 '평소 배율'). D6 장면 ①·D7·`[Claude]`(전부 실패면 키울 대상이 따로 없다).
- 그 외(실패 f개, 1 ≤ f < n):
  - **큰 영역**: 실패 칸들을 `gridFor(f)` 배치로, 칸 내용·스타일은 B와 같다(제목·상태·사유·연속 실패·그래프). 깜빡임 설정 적용.
  - **작은 띠**: 나머지 n−f개 칸(정상·느림·설정 오류·확인 불가·확인 중)을 **한 줄(또는 한 열)에 같은 크기 카드**로 — 줄바꿈·스크롤 없음. 카드 내용: 1줄 제목(넘치면 `…`), 2줄 상태(아이콘+글자, 상태 색) + 현재 ms(없으면 `—`). 그래프·사유 없음. 카드 스타일 = B 방식 칸(어두운 칸 + 상태 색 테두리)의 축소판(목업 장면 ②③).
  - 위치: **f = 1이면 띠가 오른쪽 세로 열**(목업 장면 ②), **f ≥ 2면 띠가 아래 가로 줄**(목업 장면 ③). 띠 두께는 화면(그리드 영역)의 약 1/4(`[Claude]` — 목업 비율 3:1, 실측 조정 가능). 최악 크기 예: n=9·f=1 → 8장이 1/4 폭 열에(1920×1080에서 약 460×120px), n=9·f=2 → 7장이 1/4 높이 줄에(약 260×250px).
  - 순서는 큰 영역·띠 각각 **칸 추가 순서** 유지.
- 확대는 실패만(D7) — 느림·설정 오류·확인 불가는 띠에서 색으로만. 조건 실패도 `fail`이므로 항상 큰 영역에 있고, 작은 카드엔 사유·`detail`이 나올 일이 없다(설정 오류 카드는 상태 글자만). 깜빡임은 크기와 무관하게 상태로 정한다(①a §7.5 그대로 — `느림+실패` 설정이면 띠의 느림 카드도 깜빡임).
- 배치는 **매 상태 갱신마다 즉시** 바뀐다(애니메이션·히스테리시스 없음, `[Claude]` — 성공/실패를 오가는 칸이면 배치도 오간다. 그것이 실제 상태이고, 목업 세 장면이 사용자 승인 동작이다). 복구되면 다음 폴링에 원래 배치(US4).
- **글자 크기 — 설정만으로 고정되는 배율 유지**(①a §7.3 원칙을 C에 확장): C에선 칸 크기가 결과에 따라 바뀌지만(그게 목적), **배율 자체는 결과로 바뀌지 않는다**. C 배치는 f(1..n−1)에만 달린 유한한 기하이고 f는 설정이 아니지만 **가능한 모든 f를 설정 시점에 미리 잰다**:
  - **평소 배율**(f=0 또는 n): ①a와 똑같이 B 그리드 probe로 정한 배율 — 차분한 평소 화면은 B 보드와 글자 크기까지 같다(사용자가 승인한 장면 ①).
  - **장애 배율**(1 ≤ f < n의 큰 칸): ①a 크기 probe(F12)를 **f=1..n−1 각각의 큰 영역 칸 기하**에 배치해 재고, 그 전부를 만족하는 가장 큰 값(최소값) 하나. 그래서 큰 칸이 넓적해져도(예 n=3·f=2) 글자가 칸을 넘치지 않고, 장애 중 f가 바뀌어도 이 배율은 그대로다. 평소↔장애 전환 때 글자 비율이 바뀌는 것은 C의 목적(칸 크기가 바뀜)에 포함된다(`[Claude]` 트레이드오프 — §10). 사유 줄 배율(`reasonFit`)도 같은 방식으로 평소/장애 각각. C가 아닌 보드는 probe가 지금과 같아 byte-identical.
  - probe 개수: 각 C 기하마다 **모든 칸**의 probe가 필요하다(어느 칸이든 실패할 수 있다) — 최대 약 n×n(n=9면 81) + 띠 카드 probe. 같은 기하(예: f=7과 f=8은 둘 다 3×3 `gridFor`·같은 영역)는 한 번만 잰다. 측정은 설정·뷰포트·방식이 바뀔 때만 돈다.
  - **띠 카드 배율**: 카드 글자는 카드 크기 기준 단위(cq)에 고정 비율, 그리고 **f=1..n−1 각각의 띠 카드 기하**에서 카드 제목 1줄(넘침은 `…` 허용)·가장 긴 띠 상태 문구(`⚠ 설정 오류`)+그 칸 제한 시간의 ms 값이 들어가는 배율을 별도 probe로 재서 최소값 하나를 모든 카드에 쓴다(카드끼리 글자 크기 같음).
  - 측정 방식(같은 probe 컴포넌트 재사용/별도 컴포넌트, 탐색 방식)은 plan 결정. 조건: 설정·뷰포트·방식으로만 키를 잡고 결과는 절대 키/probe에 안 들어감(ui CLAUDE.md 운영 모니터 함정).
  - 큰 칸·카드 각각 안에서 ①a 극단값 규칙(겹침·잘림 없음, `…`, 제목 줄 내림, 실패 줄은 그래프 공간 사용)을 지킨다 — 라이브 극단값 매트릭스로 확인(§8).

## 7. 오류·엣지
- 조건 평가 중 패닉 금지: JSONPath는 저장 시 검증되지만 실행 시 파싱 실패해도(이론상) "값 없음"으로 처리.
- 응답 본문이 거대해도 조건 평가는 이미 trace에 담긴 1 MiB 이내만 본다(F7) — 추가 메모리 없음. 링버퍼 결과당 사유 최대 400자 정도(D4).
- 벽 화면 노출 범위(보안): 조건 판정 결과일 때만 다음이 벽·`/status`(최신 결과만, §4.1)에 실린다 — ① `reason`: 사용자가 고른 경로의 **실제 값**(경로가 객체·배열을 가리키면 그 JSON 문자열 일부, 최대 200자), ② `detail`: 경로·규칙과 **사용자가 입력한 비교값**. 그 밖의 응답 조각·URL·다른 헤더는 여전히 안 나간다. 제어·서식 문자는 공백으로 바뀌고(§4.1) React 텍스트 렌더라 마크업 주입 없음.
- 위험 한 가지 — **매번 바뀌는 비밀 값**(토큰·세션 id)에 `같음` 조건을 걸면 매 점검 실패하면서 그 값이 벽에 뜬다. 막는 장치: 긴 값의 기본 규칙은 `비어 있지 않음` + 확인 줄 안내(§5.2). 사용자가 일부러 `같음`을 고르는 것은 막지 않는다(범용 도구 — 무엇이 비밀인지 판단하지 않는다, 결정 원천 ②와 같은 원칙).
- 비ASCII 값을 가진 헤더는 trace에 없어서(F8) 그 헤더 조건은 `값 없음`으로 실패한다 — 수용(드묾, 엔진 trace 변경은 범위 밖). 확인 줄은 trace에 있는 헤더만 보여 주므로 그런 헤더로는 조건을 만들 수도 없다.
- → `security-reviewer` 필수(§8).

- **보안 표면 게이트**: 응답 값이 새 sink(벽·`/status`)로 나가므로 `security-reviewer` **필수**(grep 결과와 무관 — 메모리 security-gate-judgment-override).
- 보드 이전 행 호환: ①a로 저장된 보드가 ①b에서 그대로 열리고 B로 보임(라이브 1회).

## 9. ADR-0053 보완 (이 슬라이스에서 작성)
"①b: 칸별 성공 조건(모니터 칸 설정, 시나리오 무변경) — 조건 판정 결과일 때 사용자가 고른 경로의 실제 값(객체면 JSON 일부, 200자 상한)과 사용자가 입력한 비교값을 벽·`/status`(최신 결과만)에 표시한다. ①a의 '벽엔 고정 문구만' 원칙의 의도된 예외이며, 그 외 응답 조각·URL은 여전히 미노출. 화면 방식 A(fill)·C(focus) 추가 — C는 칸 크기가 결과에 따라 바뀌지만 글자 배율은 가능한 모든 C 배치를 설정 시점에 미리 재어 고정한다(①a '배율은 설정으로 고정' 유지)."
