# 터미널 모니터 — 응답에서 값을 골라 성공 조건·표시 값 추가 (tui-2b) — 설계

- 날짜: 2026-11-11 · 유형: `user-path` · 상위 설계: [tui-monitor 설계](2026-11-07-tui-monitor-design.md)의 슬라이스 **2b**(US9)를 이 문서가 구체화한다 · 결정 기록: [ADR-0053](../../adr/0053-ops-monitor-mode.md)·[ADR-0055](../../adr/0055-tui-monitor.md)(새 ADR 없음 — §11)
- 범위: `crates/tui`(새 화면 하나 + 키·저장 연결) + 문서. **컨트롤러·엔진·proto·DB·GUI(`ui/`) 0-diff** — 저장은 2a의 보드 PUT, 점검은 tui-check-now의 `check-now`를 그대로 쓴다.
- 상태: 설계 초안(리뷰 중)

## 사용자 스토리 (US)

사용자 결정(2026-11-11, 질문 4개의 답): ① 값은 **값 목록 화면**에서 고른다(요청·응답 화면 안 커서 아님) ② `a`는 요청·응답 화면을 **어느 길로 열었든**(오류 보기·칸 설정 `r`) 된다 ③ 칸 설정 11·12 하위 목록의 `a` = **지금 점검 → 값 목록까지** 지름길 ④ 저장 뒤 **값 목록에 머문다**(자동 재점검 없음). 아래 US1~US4는 같은 날 사용자 승인.

- **US1 (성공 조건 추가)**: 운영자가 칸의 성공 조건을 응답 값으로 달아야 한다(예: 본문 `status`가 `"OK"`여야 정상) — 요청·응답 화면(오류 보기 경로든 칸 설정 `r` 경로든)에서 `a`를 누르면 그 스텝 응답의 응답 코드·응답 헤더·본문 값이 "대상 + 받은 값" 한 줄씩 목록으로 보이고, 값을 골라 `조건으로 추가`를 택하면 받은 값이 미리 채워진 조건 칸(규칙·값·체크)이 뜬다. Enter로 저장하면 다음 점검부터 그 조건으로 판정되고(값이 달라지면 칸이 실패로 바뀐다), 칸 설정 11번에 그 조건이 보이며, TUI를 재시작해도 남는다. GUI에서 같은 값을 클릭해 만든 조건과 같은 설정(대상 경로·기본 규칙·값)으로 저장된다.
- **US2 (화면 표시 값 추가)**: 운영자가 판정과 무관한 값(예: 대기열 길이)을 칸에 보이게 하려 한다 — 같은 값 목록에서 값을 골라 `화면에 추가`를 택하면 저장되고, 다음 점검부터 모니터 화면의 그 칸에 그 값이 보이며, 칸 설정 12번에 보이고 재시작해도 남는다. 이미 2개가 찼거나, 같은 대상이 이미 있거나, 인증 헤더면 저장되지 않고 이유가 보인다.
- **US3 (칸 설정에서 바로)**: 운영자가 칸 설정의 `11 성공 조건`·`12 화면에 표시`에서 바로 추가하려 한다 — 하위 목록에서 `a`를 누르면 지금 점검이 돌고, 스텝이 하나로 정해지는 칸(스텝 칸·HTTP 스텝 1개짜리 흐름)은 그 스텝의 값 목록이 곧바로 열린다. 스텝이 여럿인 흐름 전체 칸은 자세히(스텝 표)가 열려 스텝을 고른 뒤 Enter → `a`로 이어간다. "조건 추가는 GUI에서" 안내는 사라진다.
- **US4 (고를 수 없을 때)**: 운영자가 고를 수 없는 상황을 만난다 — 스텝 칸에서 그 칸의 스텝이 아닌 스텝, 응답이 없는 스텝(전송 실패), 조건 10개가 찬 칸, 본문이 JSON이 아니거나 너무 크거나 잘린 응답 — 잘못된 조건이 저장되지 않고, 왜 안 되는지와 대신 고를 수 있는 것(응답 코드·헤더·`본문 전체` 포함 조건)이 화면에 보인다. 서버가 가린 인증 값(`••••`)은 비교값으로 채워지지 않는다(기본 규칙이 `값 있음`).

## 1. 목표 / 비목표

**목표**: US1~US4. GUI ①b의 "응답 트리 클릭 → 조건·화면 표시 추가"(`PreviewResult.tsx`)와 같은 결과를 TUI 키보드로.

**비목표**
- **대상(경로·헤더 이름)을 손으로 입력해 추가** — 응답에서 고른 값만. 와일드카드·`..` 경로는 GUI에서.
- **객체·배열 자체를 대상으로 고르기** — GUI 트리와 같이 스칼라 값(문자열·숫자·참거짓·null)만.
- **요청 쪽 값**(요청 헤더·요청 본문) — 조건·표시 값은 응답만 본다(서버 모델).
- **저장 뒤 자동 지금 점검·판정 미리 보기** — 사용자 결정 ④. 새 조건의 판정은 다음 주기 또는 `Esc` → 칸 설정 `r`.
- 값 목록에서 이미 있는 조건·표시 값을 고치거나 지우기 — 2a의 11·12 하위 목록에서.
- 값 목록의 마우스 클릭, 값 목록 안 검색.

## 2. 동작 규칙 (정본)

### 2.1 값 목록에 나오는 것

요청·응답 화면에서 보던 **그 스텝 실행의 응답**(`trace.steps[trace_idx].response`)으로 만든다. 줄 순서 = ① 응답 코드 ② 응답 헤더(기록의 순서 = 이름 순) ③ 본문.

| 줄 | 대상 글자(왼쪽) | 받은 값(오른쪽) | 조건의 `source`·`path` | 표시 값 |
|---|---|---|---|---|
| 응답 코드 | `상태코드` | `200` | `status` · `""` | `status` · `""` |
| 응답 헤더 | `헤더 {이름}` | 값(서버가 가린 값은 가린 그대로) | `header` · 이름 | `header` · 이름 |
| 본문 값(JSON 스칼라) | 경로에서 앞 `$.`·`$`를 뗀 글자(`data.order.id`·`items[0].sku`), 뿌리 스칼라는 `본문` | 문자열은 `"…"`, 그 밖은 그대로(`7`·`true`·`null`) | `body` · 경로 | `body` · 경로 |
| 본문 전체(본문 값 줄이 없을 때만) | `본문 전체` | `글자 포함 조건으로` | `body_text` · `""` | 없음(조건만) |

- 대상 글자는 2a 칸 설정 11·12번과 **같은 함수**(`panel_settings::condition_target`·`display_target`)로 만든다 — 값 목록에서 본 글자가 저장 뒤 칸 설정에 그대로 보인다.
- **본문 줄은 아래 표의 첫 번째로 맞는 행**을 따른다("본문 있음" = 기록의 본문이 비지 않았거나 기록 상한에 잘렸다 — 상한이 다 차면 뒤 스텝의 본문은 빈 글자로 잘린다):

  | 순서 | 본문 상태 | 본문 줄 | 이유 줄 |
  |---|---|---|---|
  | 1 | 본문 없음(비었고 잘리지도 않음) | 없음 | 없음 |
  | 2 | 엔진이 자름(`body_truncated`, 1 MiB) | **없음** | `1 MiB에서 잘린 응답은 본문 조건을 달 수 없습니다` |
  | 3 | 기록 상한에 잘림(`clipped` 응답 쪽) | `본문 전체` | `기록 상한 NKB에서 잘림`(요청·응답 화면과 같은 문구) |
  | 4 | 64KB 초과(`PRETTY_MAX_BYTES`) | `본문 전체` | `64KB를 넘는 본문은 값을 고를 수 없습니다` |
  | 5 | JSON으로 안 읽힘 | `본문 전체` | 없음 |
  | 6 | 풀기까지 마친 값의 중첩이 64단 초과(`PRETTY_MAX_DEPTH`) | `본문 전체` | `너무 깊게 중첩된 본문은 값을 고를 수 없습니다` |
  | 7 | 그 밖 | 본문 값 줄들 | (풀었으면 풀기 안내) |

  - 2행은 **GUI와 일부러 다르다**: 서버는 엔진이 자른 본문에 대해 본문 값·본문 전체 조건을 모두 "본문이 너무 큼"으로 실패시킨다(늘 실패하는 조건) — GUI는 이때도 `+ 본문 전체 포함 조건` 버튼을 낸다(선재 갭, roadmap에 기록). US4 "잘못된 조건이 저장되지 않고"를 따른다.
  - 3행은 괜찮다 — 기록만 잘렸고 서버는 온전한 본문으로 판정한다.
  - 5~7행은 GUI의 "트리가 없을 때만 `+ 본문 전체 포함 조건`"과 같은 갈래.
- **감싼 JSON 풀기**(서버 `parse_body_json`·`BodyJson::path_first`, GUI `parseBodyJson`과 같은 규칙): 본문 전체가 JSON을 담은 문자열이면 최대 3겹 풀어 객체·배열을 뿌리로 삼고, 문자열 필드가 객체·배열을 담은 JSON 문자열이면 그 필드를 최대 3겹 풀어 안쪽 값을 줄로 낸다(시도 대상은 JSON 공백 뒤 첫 글자가 `{`·`[`·`"`인 문자열만). 한 겹이라도 풀었으면 안내 줄 `문자열로 감싼 JSON을 풀어서 표시 중`.
- **키 순서는 응답에 적힌 순서**(요청·응답 화면의 들여쓴 JSON과 같은 순서). 같은 키가 두 번이면 서버와 같이 뒤 값이 이기고 자리는 처음 것.
- **경로 글자**는 GUI `segmentsToPath`와 같다: 키가 `[A-Za-z_][A-Za-z0-9_]*`면 `.키`, 아니면 `['키']`(`\`→`\\`, `'`→`\'`, U+0020 미만 → `\uXXXX` 소문자 16진 4자리 — GUI와 글자까지 같게), 배열 번호는 `[n]`. 이렇게 만든 경로는 모두 서버 허용 문법(`jsonpath_is_simple`·`jsonpath_is_valid`) 안이다.
- 빈 객체·빈 배열은 줄이 없다(GUI 트리도 누를 데가 없다).

### 2.2 값 목록을 열 수 있는가 (US4)

요청·응답 화면의 `a`는 **언제나 값 목록 화면을 연다**. 고를 수 없으면 줄 없이 이유 한 줄을 보인다(고를 줄이 없으니 `Enter`는 무동작).

| 상황 | 화면 |
|---|---|
| 스텝 칸(칸에 `step_id`가 있다 — 묶음 칸 포함)인데 보던 스텝이 그 칸의 스텝이 아님 | `이 칸은 "{그 칸 스텝 이름}" 스텝만 봅니다 — 그 스텝의 요청·응답에서 추가하세요` |
| 그 스텝에 응답이 없음(전송 실패·시간 초과) | `응답이 없어 고를 값이 없습니다` |
| 그 밖 | §2.1의 줄 |

- 판단은 **지금의 칸 설정**으로 한다(기록을 찍은 뒤 볼 스텝이 바뀌었으면 바뀐 스텝 기준). GUI `onlyStepId`와 같은 뜻이되 범위는 서버 기준이다: GUI는 묶음 칸만 제한하지만(`ownStep = group ? panel.step_id : undefined`) 서버는 `step_id`가 있는 칸이면 묶음이 아니어도 조건·표시 값의 스텝을 칸의 스텝으로 덮어쓴다(`normalize_step_panel`) — TUI는 `step_id`가 있는 모든 칸을 제한한다(다른 스텝에서 고른 값이 조용히 칸 스텝의 조건으로 바뀌지 않게).
- 흐름 전체 칸은 응답이 있는 어느 HTTP 스텝에서나 된다. 조건·표시 값의 `step_id` = 그 스텝의 id.
- **같은 스텝이 그 기록에서 뒤에 다시 실행됐으면**(반복) 줄 위에 안내 `같은 스텝이 뒤에 다시 실행됐습니다 — 판정은 마지막 실행의 응답을 봅니다`(서버는 조건·표시 값을 그 스텝의 마지막 HTTP 실행에서 읽는다). 고르기는 막지 않는다.

### 2.3 고른 뒤 — 조건인가 표시인가

`Enter` → 목록 창(2a의 목록 창과 같은 자리·모양) 두 줄: `조건으로 추가` · `화면에 추가`. 창 머리에 고른 대상과 받은 값. 못 하는 쪽은 이유를 붙여 흐리게 하고 `Enter`를 받지 않는다:

| 줄 | 막히는 때 → 붙는 이유(GUI 문구 그대로) |
|---|---|
| `조건으로 추가` | 칸의 조건이 이미 10개 → `조건은 최대 10개까지 추가할 수 있습니다` |
| `화면에 추가` | **이 순서로 첫 번째 것**(GUI와 같은 순서): ① 표시 값이 이미 2개 → `화면 표시는 최대 2개까지` ② 같은 스텝·같은 대상이 이미 표시 중 → `이미 화면에 표시 중` ③ 인증 헤더(`set-cookie`·`cookie`·`authorization`·`proxy-authorization`, 앞뒤 공백·대소문자 무시) → `인증 헤더는 화면에 표시할 수 없음` |

- `본문 전체` 줄은 표시 값이 없으므로 목록 창을 건너뛰어 바로 조건 칸(조건이 10개면 이유 안내만).
- 커서는 처음에 고를 수 있는 첫 줄. 둘 다 막혔으면 창 대신 두 이유를 안내 한 번으로.

### 2.4 조건 칸 (US1)

2a의 조건 수정 칸(`CondForm` — 규칙 `←→`, 값 입력줄, 체크 둘, `Tab` 이동, `Enter` 저장, `Esc` 취소)을 **추가용으로도** 쓴다. 다른 점: 맨 위에 `대상` 줄(대상 글자 · 스텝 이름)과 `받은 값` 줄이 있고, 저장하면 새 조건이 목록 **끝에** 붙는다.

처음 채워지는 값 — GUI `defaultCondition`과 같다(US1 "같은 설정"). **★ 두 행만 일부러 다르다**: GUI 미리 실행은 가리지 않은 응답을 보여 주지만 TUI가 보는 기록은 서버가 인증 값을 가린 것이고, TUI 입력줄은 받지 않는 글자가 있다.

| 고른 값 | 규칙 | 값 칸 | 붙는 안내 |
|---|---|---|---|
| 응답 코드 | `=` | 코드(`200`) | |
| 본문 `null` | `키 있음`(`exists`) | — | |
| 본문 숫자·참거짓 | `=` | 그 글자(`7`·`true`) | |
| 문자열(본문·헤더) 40자 이하 | `=` | 그 문자열 | |
| 문자열 40자 초과 | `값 있음`(`not_empty`) | — | `매번 바뀌는 값이면 '='은 매 점검 실패하고 그 값이 화면에 표시됩니다` |
| ★ 인증 헤더(§2.3의 4종) — GUI는 40자 이하면 `=` + 값 | `값 있음` | — | `가려진 값이라 비교값을 채우지 않았습니다` |
| ★ 값이 입력줄 규칙에 안 맞음(제어 문자·U+0085·U+2028/2029·bidi 제어 포함) — GUI는 40자 이하면 `=` + 값 | `값 있음` | — | 위 40자 초과와 같은 안내 |
| `본문 전체` | `글자 포함`(`contains`) | 빈 칸(커서가 값 칸에서 시작) | |

- 규칙 목록·값 칸·체크의 나타남은 2a와 같다(`ConditionSource::allows`·`needs_value`·`has_flags`).
- 숫자 글자는 정수면 그대로, 소수면 가장 짧은 십진 표기(`1.5`). GUI(`String(v)`)와 **글자**가 다를 수 있는 값: GUI가 지수 표기로 바꾸는 범위(절댓값 1e21 이상·1e-6 미만), 2^53을 넘는 정수(GUI는 정밀도를 잃는다), `-0`. 어느 쪽이든 판정은 같다(서버가 숫자끼리 f64로 비교).
- 검증의 권위는 서버(2a §6.1과 같다) — 거절이면 서버 문구가 조건 칸 아래에 뜨고 칸은 열린 채. 서버 한도(본문 경로 500자·헤더 이름 200자·비교값 200자)를 넘는 대상·값도 TUI가 미리 막지 않고 서버 문구로 알린다.

### 2.5 표시 값 (US2)

`화면에 추가`는 묻지 않고 바로 저장한다(입력할 것이 없다). 표시 값 목록 **끝에** 붙는다(하나 있었으면 새 것이 ② 작은 줄 — 자리 바꾸기는 12번의 `s`). 서버가 거절하면 서버 문구 안내.

### 2.6 저장

2a §6.2 그대로: 보드 PUT(그 칸만 바꾼 전체 설정) → 캐시 갱신 → 내보내기 → 파일 쓰기(백업 규칙 포함) → 머리 줄 `저장됨 HH:MM:SS`. 저장 중엔 `저장 중…`, 다른 저장이 진행 중이면 `저장 중…` 안내(2a와 같은 한 번에 하나). 스텝 칸이면 서버가 조건·표시 값의 `step_id`를 칸의 스텝으로 맞춘다(`normalize_step_panel`) — TUI도 같은 값을 보낸다.

저장이 끝나면 **값 목록에 그대로**(사용자 결정 ④). 저장된 대상의 줄 오른쪽 끝에 표지가 붙는다: 그 스텝·그 대상의 조건이 있으면 `조건`(둘 이상이면 `조건 N`), 표시 값이 있으면 `표시`. 표지는 지금의 칸 설정에서 매번 계산한다(값 목록을 열기 전부터 있던 것도 보인다).

### 2.7 칸 설정 11·12의 `a` (US3)

- `11 성공 조건`·`12 화면에 표시`는 값이 없어도 `Enter`로 하위 목록이 열린다(빈 목록 + 안내 줄 `없음 — a로 추가(지금 점검 뒤 응답에서 값 고르기)`). 2a의 `조건 추가는 GUI에서(다음 버전에서 TUI 지원)`·`표시 값 추가는 GUI에서(…)` 문구는 없앤다.
- 하위 목록의 `a`: 조건이 이미 10개(11번)·표시 값이 이미 2개(12번)면 §2.3의 이유 안내만(점검 안 함). 아니면 **지금 점검**(메뉴 `r`과 같은 요청·같은 대기 창 — 꺼진 보드면 같은 꺼짐 안내) → 새 회차의 자세히를 열고 기록이 도착하면:
  - **대상 스텝이 하나로 정해지면** 그 스텝의 값 목록을 곧바로 연다 — 스텝 칸 = `◀ 이 칸` 줄(그 스텝의 마지막 실행), 흐름 전체 칸 = **이번 실행 기록의 HTTP 줄이 정확히 1개**일 때 그 줄(US3의 "HTTP 스텝 1개짜리 흐름"은 이 뜻 — 스텝이 하나여도 반복으로 줄이 여럿이면 자세히에 머문다).
  - 정해지지 않으면(HTTP 스텝이 여럿인 흐름 전체 칸, 스텝 칸인데 그 스텝이 이번 실행에 없음, 기록이 없거나 trace가 없음) 자세히 화면에 머문다 — 스텝을 골라 `Enter` → `a`.
- 12번에서 눌렀어도 값 목록은 같다(조건도 추가할 수 있다).
- 열리는 것은 화면이 **정확히 자세히**일 때만이다 — 기록을 기다리는 사이 종료 확인창을 띄웠으면 닫지 않고 기다렸다가, 취소해 자세히로 돌아온 다음 갱신에서 연다(tui-check-now의 대기 창과 같은 규칙). 그 사이 `Esc`로 자세히를 떠나면 열지 않는다.
- `Esc`는 값 목록 → 요청·응답 → 자세히 → 칸 설정 **메뉴**(하위 목록이 아니라 — 메뉴 줄에 방금 더한 조건·표시 값이 보인다).

## 3. 화면

화면 전체 전환·모니터와 같은 머리 줄·무입력 5분 자동 복귀(안내 줄 포함)는 1b 확정 블록(상위 설계 §5.3)과 같다. 빈 줄 없음도 같다.

### 3.1 값 목록 (새 화면)

```
운영 보드 A                            14:02:11 · 점검 중
주문 조회 · 14:01:58 · 2 주문 상세 — 값 고르기        4/8
문자열로 감싼 JSON을 풀어서 표시 중
  대상                    받은 값
  상태코드                200
  헤더 content-type       application/json
  헤더 x-request-id       7f3a91c2…
▶ status                  "OK"                       조건
  data.order.id           7
  data.order.state        "PAID"                     표시
  data.items[0].sku       "A-100"
  data.queue              12
5분 동안 입력이 없으면 모니터로 돌아갑니다
↑↓ 고르기 · Enter 추가 · Esc 요청·응답으로
```

- 제목 줄 = 요청·응답 화면 제목(`{칸 제목} · {시각} · {순번} {스텝 이름}`) + ` — 값 고르기`, 오른쪽 `{커서}/{전체}`(폭이 모자라면 통째 생략).
- 고른 줄은 흰 바탕 `▶`(2a 메뉴와 같은 표시). `PgUp`/`PgDn`/`Home`/`End`도 된다. 목록은 창에 맞춰 민다(고른 줄이 늘 보인다).
- **폭**: 대상 칸 폭 = min(가장 긴 대상 폭, 본문 폭의 절반). 넘치는 대상은 **앞을 `…`로** 줄인다(끝의 키 이름이 보이게), 받은 값은 뒤를 `…`로. 표지는 폭이 모자라면 통째로 뺀다. 줄여서 안 보이는 대상·값의 전체는 §3.2 창 머리에서(줄바꿈).
- 원격 글자(헤더 이름·값·본문 키·값)는 폭 계산 **전에** `inspect::sanitize`.
- 안내 줄(§2.1 풀기·§2.2 반복·본문 값 줄이 안 나오는 이유)은 표 머리 위, 높이가 모자라면(줄이 1줄도 안 남으면) 안내 줄부터 뺀다. 본문 값 줄이 안 나오는 이유 문구는 §2.1 표(요청·응답 화면의 `…원문으로 표시합니다` 문구는 값 목록에 맞지 않아 새 문구를 쓴다 — 기록 상한 문구만 같다).

### 3.2 고른 뒤의 창 (화면 맨 아래 — 2a 조건 수정 칸과 같은 자리)

```
  status  =  "OK"
▶ 조건으로 추가
  화면에 추가 — 화면 표시는 최대 2개까지
↑↓ 고르기 · Enter 선택 · Esc 취소
```

```
  대상      status · 주문 상세
  받은 값   "OK"
  규칙      ◀ = ▶
  값        OK▏
  [ ] 대소문자 무시   [ ] 앞뒤 공백 무시
Tab 다음 칸 · Space 켜기·끄기 · Enter 저장 · Esc 취소
```

조건 칸의 키·좁은 화면 규칙은 2a 그대로(`fit_keys` — `Enter 저장`이 끝까지 남는다). `받은 값` 줄과 안내 줄(§2.4)은 높이가 모자라면 먼저 뺀다.

### 3.3 키

| 화면 | 키 | 동작 |
|---|---|---|
| 요청·응답 | `a`(`ㅁ`) | 값 목록 열기. 키 줄에 `a 조건·표시 추가`를 `Esc 자세히로` 바로 앞에 더한다(앞 조각부터 빠지므로 `Esc` 다음으로 오래 남는다) |
| 값 목록 | `↑↓`(`j`/`k`)·`PgUp`·`PgDn`·`Home`·`End` | 고르기 |
| 값 목록 | `Enter` | 고른 뒤의 창(§2.3) |
| 값 목록 | `Esc` | 요청·응답으로(스크롤·가림 상태 그대로) |
| 값 목록 | `q`/`Ctrl+C` | 종료 확인. 그 밖의 `Ctrl+글자`는 무동작 |
| 하위 목록 11·12 | `a`(`ㅁ`) | §2.7. 키 줄 `a 추가`가 기준선(8번)뿐 아니라 11·12에도 나온다 |

도움말(`?`)에 한 줄: `a` — 요청·응답 화면에서 성공 조건·표시 값 추가(50칸 상자에 통째로 들어가는 문구로).

## 4. TUI 구조

### 4.1 값 목록 만들기 (새 순수 모듈 `crates/tui/src/pick.rs`)

- `value_list(resp: &TracedResponse, clipped_resp: bool, limit_kb: u32) -> ValueList { rows, notes }` — §2.1(응답 하나만 본다). 값 목록을 **열 때 한 번** 만들어 화면 상태에 둔다(그릴 때마다 파싱하지 않는다 — `crates/tui/CLAUDE.md` "목록을 그릴 때 항목마다 전체 파싱 금지").
- `open_values(panel: &PanelConfig, trace: &ScenarioTrace, trace_idx: usize, clipped_resp: bool, limit_kb: u32, names: &Names) -> ValuesState` — §2.2를 얹는다: 스텝 칸 제한·응답 없음이면 이유 한 줄짜리 상태, 아니면 `value_list` + 반복 안내(같은 `step_id`의 HTTP 실행이 `trace_idx` 뒤에 또 있는가). 조건·표시 값에 쓸 `step_id`(스텝 칸 = 칸의 스텝)도 여기서 정해 상태에 싣는다.
- 키 순서를 지키려고 `serde_json::Value`(이 워크스페이스에선 키가 정렬된다) 대신 **순서를 지키는 작은 트리**로 읽는다(객체 = `Vec<(String, Node)>`, `serde::Deserialize` 손 구현). 워크스페이스 `serde_json`에 `preserve_order`를 켜지 않는다(기능 통합으로 컨트롤러·엔진의 직렬화 순서가 바뀐다).
- 깊이는 직접 센다(풀기 포함, 64 초과면 그 자리에서 멈추고 "너무 깊음"). 한 번의 파싱은 `serde_json` 재귀 상한(128)이 스택을 지킨다.
- `segments → 경로`(§2.1), `default_condition`(§2.4 표), `display_block`(§2.3 표), 표지 계산(§2.6)도 이 모듈의 순수 함수.
- 값을 품는 타입(`ValueRow`·`ValueList`·`ValuesState`)은 **손 `Debug`**(종류·길이만) — 응답 값이 로그·패닉 문구로 새지 않게(`crates/tui/CLAUDE.md` "값을 품는 타입은 derive `Debug` 금지").

### 4.2 화면 상태·전환 (`app.rs`)

**화면**: `Screen::Values` 추가. `is_sub`(5분 복귀·`Ctrl+글자` 무동작)·`SubViews::back`(→ `Screen::Body`)·`on_edit_screen`·`edit_key`의 화면 규칙(지금은 메뉴·하위 목록·변수 화면이 아니면 무동작)에 넣는다.

**값 목록 상태는 `EditUi` 안에** — `EditUi.values: Option<ValuesState>`(줄·안내·이유·`step_id`·**자기 커서**). 이유:
- 값 목록의 창(선택 창·조건 칸·`저장 중…`·안내)은 2a의 `EditUi.overlay`를 쓴다 — 저장 길(`commit` → `EditReq::SaveBoard` → `apply_done`)을 그대로 타기 위해서다. 키 처리(`edit_apply`)는 `EditUi`만 보므로 줄 목록도 거기 있어야 `Enter`를 처리할 수 있다.
- 커서는 `list_cursor`를 **쓰지 않는다** — `apply_done`이 저장 성공 뒤 `list_cursor`를 하위 목록 길이로 자른다(칸 설정 경로에선 메뉴 커서가 11·12에 있어 그 가지가 돈다). 같이 쓰면 저장할 때마다 값 목록 커서가 튄다.
- 버리는 곳: 값 목록에서 `Esc`(→ 요청·응답) · `idle_drop`(5분 복귀 — 진행 중 저장 때문에 `EditUi`가 남는 경우에도 값은 버린다) · `SubViews::clear`(`EditUi`째로). `EditUi`의 손 `Debug`는 `values`를 있는지만 찍는다.

**`EditUi`가 누구 것인가**(오류 보기 경로에는 `EditUi`가 없다 — `OpenSettings`만 만든다):
- 요청·응답에서 `a`를 누를 때 `views.edit`가 **없거나 그 기록의 보드·칸 것이 아니면** 그 기록의 보드·칸으로 새로 만든다(있던 것은 버린다). "아니면"이 필요한 까닭: 5분 복귀는 저장 중인 `EditUi`를 남긴 채 모니터로 가고(`idle_return`), 그 저장이 끝나도 `EditUi`는 남는다 — 그 뒤 다른 칸의 오류 보기로 들어와 `a`를 누르면 남은 `EditUi`(칸 A)로 칸 B의 값을 저장하게 된다.
- 새로 만들 때 진행 중 저장이 있으면 `OpenSettings`와 같은 규칙: 그 칸의 저장이면 `저장 중…` 창(결과가 오면 닫힌다), 다른 칸의 저장이면 `저장 중…` 안내 한 번.
- 값 목록에서 `Esc`로 나갈 때: 그 기록을 **오류 보기에서 열었으면**(`RecordOrigin::Errors`) `EditUi`를 없앤다. 칸 설정에서 열었으면 `values`만 비우고 `EditUi`(메뉴 커서)는 둔다. 저장 중(`Saving`)에는 `Esc`가 무시되므로 진행 중 저장이 버려지지 않는다.

**고른 뒤의 창**(§2.3 — 2a의 `Overlay::Pick`은 환경·스텝·응답 시간 전용이라 못 쓴다: 흐린 줄·이유·머리 줄이 없고 고르면 그 종류의 저장을 만든다):
- 새 `Overlay::AddChoice { cursor, cond_block: Option<&'static str>, display_block: Option<&'static str> }`(`kind()` = `"AddChoice"`). 고른 줄은 `values`의 커서가 가리킨다(창이 값을 따로 품지 않는다). 키는 목록 창과 같은 동작(`PickMove`·`PickChoose`·`PickCancel`)을 쓰되 `edit_apply`가 창 종류로 갈라 처리한다 — 막힌 줄의 `PickChoose`는 무동작.
- `Overlay::CondForm`의 `index: usize`를 `target: CondTarget`으로 바꾼다 — `Existing(usize)`(2a) / `New { step_id, source, path, shown: String, hint: Option<&'static str> }`(§2.4의 `받은 값`·안내). `Enter`는 앞이면 `Change::Condition`, 뒤면 `Change::AddCondition`. `with_error`와 저장의 `restore`는 `target`을 그대로 옮긴다(거절 뒤에도 `대상`·`받은 값` 줄이 남는다). 5분 복귀는 2a와 같이 창과 `restore`를 버린다.

**새 편집 두 가지**: `Change::AddCondition(Condition)` · `Change::AddDisplay(DisplayItem)` → `edit.rs`의 새 변환 `add_condition`·`add_display`(끝에 붙임, 스텝 칸이면 `step_id` = 칸의 스텝). 확인 줄은 없다(`confirm_for` → None). `Change`의 손 `Debug`는 종류만.

**서버 거절**: 조건 칸은 오류 줄을 채워 되살린다(2a `with_error`), 표시 값 추가는 안내(`Notice`).

**그리기**: `draw_sub`의 편집 화면 갈래에 `Screen::Values`. 값 목록은 `values`의 줄 + 지금 칸 설정으로 계산한 표지, 창은 화면 맨 아래(§3.2).

### 4.3 11·12의 `a` (`app.rs`)

- `edit_kind`의 11·12는 값이 없어도 `List`. 빈 목록의 안내 줄은 §2.7 문구.
- 대기 창 `Overlay::Checking`에 "끝나면 무엇을 여나"(자세히 / 값 목록)를 더한다. `check_open_allowed`는 그 의도가 값 목록이면 `Screen::EditList`에서 연다(메뉴 `r`은 지금처럼 `Screen::Settings`에서만).
- 자세히를 열 때 `RecordState`에 "기록이 오면 값 목록으로" 표지를 싣는다. **매 갱신**(`pump` — `pump_check_ready`와 같은 자리)마다: 표지가 서 있고 · 기록이 도착했고(`Loaded`) · `self.screen`이 **정확히** `Screen::Record`이면 §2.7의 대상 줄을 정해, 정해지면 요청·응답 상태(`BodyState`)와 `values`를 만들어 `Screen::Values`로 가고, 어느 쪽이든 표지를 내린다. 기록이 실패·없음으로 끝났으면 표지만 내린다. 화면이 종료 확인창이면 그대로 둔다(다음 갱신에 다시 본다). 표지는 `RecordState`와 함께 사라지므로 `Esc`로 자세히를 떠나면 없어진다.

### 4.4 `Names`

조건·표시 값 추가는 시나리오·환경 이름과 변수 키를 바꾸지 않는다 → `Names`는 다시 읽지 않는다. roadmap §B49 (2)는 "2b가 조건/표시를 추가하거나 키를 건드리면 재계산이 필요하다"고 적었지만 앞 절반은 틀린 전제다 — `Names`는 조건·표시 값을 들지 않는다(시나리오·스텝·환경 이름과 변수 키뿐). 마무리 때 그 메모를 바로잡는다(§6).

## 9. 보안 표면

- 값 목록·조건 칸은 **서버가 가린 기록 그대로**를 보인다(1b와 같은 출처 — 새로 받는 데이터 없음). 응답 본문은 가려지지 않으므로 값 목록에 토큰이 보일 수 있다 — 요청·응답 화면과 같은 수준(전용 단일 사용자 모니터 PC 전제, 상위 설계 §9).
- 인증 헤더의 가린 값(`sid=••••`)을 비교값으로 저장하지 않는다(§2.4) — 잘못된 조건이자, 가림 문자열이 설정 파일에 남는 일을 막는다. 사용자가 규칙을 `=`로 바꿔 직접 입력하는 것은 막지 않는다.
- 응답 값은 조건의 `value`로 **보드 파일에 저장된다**(GUI와 같다). 운영자가 고른 값만, 조건 칸에서 보고 고친 뒤 저장.
- 원격 글자는 `sanitize` 뒤에 그린다. 값을 품는 타입은 손 `Debug`. 로그에 값·경로·헤더 이름을 남기지 않는다.
- 경로는 TUI가 만든 것만 보낸다(사용자 입력 경로 없음) — 서버 `validate_and_normalize`가 다시 검사한다.
- 새 요청 길 없음(보드 PUT·`check-now`·기록 조회는 이미 있는 것). `finish-slice` §0 보안 grep으로 `security-reviewer` 필요 여부 확정.

## 10. 알려진 한계 / 연기

- 꺼진 보드는 기록이 없고 지금 점검도 안 되므로 TUI에서 추가할 길이 없다(GUI의 미리 실행으로).
- 값 목록은 고른 **그 실행**의 응답이다 — 반복 스텝의 앞 실행에서 고르면 판정(마지막 실행)과 다른 값을 보고 고르는 셈(안내 줄만, §2.2).
- 조건 칸이 판정 결과를 미리 보여 주지 않는다(비목표). 틀린 조건을 달면 다음 점검에 칸이 실패로 바뀐다 — 11번에서 고치거나 지운다.
- 숫자 표기가 GUI와 다를 수 있는 극단값(§2.4). 판정은 같다.
- 본문이 64KB를 넘으면 본문 값을 못 고른다(GUI는 큰 본문도 트리를 연다) — 요청·응답 화면의 들여쓰기 한도와 같은 값.
- 11·12 `a`의 `Esc` 사슬은 하위 목록이 아니라 메뉴로 돌아온다(§2.7).
- 12번에서 `a`로 들어가도 조건을 달 수 있고 그 반대도 된다(값 목록은 하나). 반대로 표시 값이 2개 찬 칸은 12번의 `a`가 막혀(이유 안내) 그 길로는 조건도 못 단다 — 11번의 `a`나 요청·응답의 `a`로.
- 엔진이 자른(1 MiB 초과) 응답에는 본문 조건을 못 단다(§2.1 표 2행 — 서버가 어차피 실패시킨다).
- 기록의 스텝이 시나리오에서 사라진 경우는 다루지 않는다 — TUI 세션 안에서는 시나리오의 스텝이 바뀌지 않는다(고칠 수 있는 것은 `variables:` 값 한 줄뿐, 새 파일은 재시작해야 읽고 재시작하면 기록이 빈다).

## 11. 판단 기록 (설계자 몫)

- **한 슬라이스로**: 리뷰가 US3(11·12 `a`)을 따로 떼는 안을 냈다 — 상태 기계에서 가장 위험한 부분이고 나머지와 독립이다. 사용자 결정 ③이 이번 범위라 떼지 않되, 계획에서 **마지막 task 묶음**으로 두어 US1·2·4가 먼저 독립 green이 되게 한다.
- **새 ADR 없음**: 서버 계약·파일 형식·판정 규칙 불변, TUI 화면 하나 추가 — ADR-0053(조건·표시 값 모델)·ADR-0055(TUI) 범위 안.
- **값 목록은 `EditUi.overlay`를 재사용**: 저장 길(한 번에 하나·`저장 중…`·거절 시 되살리기·5분 복귀 때 입력 버림·작업자 죽음 처리)을 새로 만들면 2a에서 리뷰로 잡은 경계 사례를 다시 밟는다.
- **이유를 요청·응답 화면의 안내 창이 아니라 값 목록 화면에**: 요청·응답 화면에는 창(overlay)이 없다 — 새 창 종류를 만드는 대신 "언제나 열리고, 못 고르면 이유 한 줄".
- **`preserve_order`를 켜지 않음**: §4.1.
- **표지(`조건`·`표시`)**: 사용자 결정 ④(값 목록에 머묾)의 짝 — 머리 줄 `저장됨`은 5초 뒤 사라져 이어서 추가할 때 무엇을 이미 달았는지 알 수 없다.
- **64KB 한도**: 요청·응답 화면이 들여쓰기를 포기하는 본문에서 값 목록만 수천 줄을 내는 것보다, 두 화면이 같은 한도를 쓰는 편이 설명하기 쉽다.
