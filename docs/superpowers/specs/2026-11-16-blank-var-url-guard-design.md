# 비워진 값의 주소 전송 차단 (blank-var-url-guard) — 설계

- 날짜: 2026-11-16
- 상태: 구현 완료(코드 `264eea37`..`ecb40102`). 구현 중 더해진 규칙(JSON `null`은 못 뽑은 값·스스로 잠긴 반복은 그 실행을 끝낸다)과 판단·연기는 roadmap §B62.
- 유형: correctness-bug
- 출처: roadmap §B58 (0) 사용자 결정의 "해소 경로(다음 후보)", 보안 리뷰 S2
- 관련: ADR-0056(조건 반복 — 이 작업이 "Negative" 절의 주소 항목을 해소), ADR-0050(에러 분류), ADR-0053(운영 모니터)

## 사용자 스토리 (US)

- **US1**: 운영자가 실서버 변경 API가 든 시나리오를 운영 모니터에 걸어 둔 상황에서 조건 반복이 값을 못 뽑고 끝난다 — 성공하면 그 값을 주소에 쓰는 뒤 요청이 서버에 도달하지 않고(서버 접수 0건), 막힌 칸이 빨강 「앞 단계 실패」로 뜨고 그 칸의 상세에서 값을 못 준 스텝 이름을 본다(스텝 칸 보드·흐름 칸 보드 모두).
- **US2**: QA가 에디터 시험 실행에서 같은 상황을 만난다 — 성공하면 그 스텝 행에서 "앞 스텝 `<이름>`이(가) `<변수>` 값을 주지 않아 요청을 보내지 않음"을 보고, 서버 접수는 0건이다.
- **US3**: QA가 부하 run에서 같은 상황을 만난다 — 성공하면 대상 서버에 빈 값이 든 주소(`/orders/` 꼴)의 요청이 0건이고, 리포트에서 그 스텝의 에러 수가 차단 건수만큼 잡히며, run 전체 실패 분류 표에 「보내지 않음 (앞 스텝 값 없음)」이 그 건수로 뜨고, 그 스텝의 응답 시간 통계와 상태 코드 분포에는 보내지 않은 건이 섞이지 않으며, run은 끝까지 돈다.

### 재현 / 기대 / 실측

- **재현**: `loop(while: {{code}} == WAIT) { GET /poll → extract orderId, code }` 뒤에 `DELETE /orders/{{orderId}}`. `/poll`이 `orderId`도 `code`도 없는 200 응답을 주어 반복이 끝난다.
- **실측(지금)**: `DELETE /orders/`가 전송된다(1차 라이브: 연결 끊김 뒤 `/next?c=&o=`).
- **기대**: `DELETE` 요청은 전송되지 않고 그 스텝의 에러로 센다.

## 1. 배경 — 지금 동작

- 조건 반복 본문의 http 스텝은 너그러운 추출을 쓴다. 못 뽑은 선언 이름은 `extract.rs::blank_missing_extracts`가 반복 변수 표(`iter_vars`)에 `""`로 써넣는다. 호출부는 `runner.rs::execute_steps`와 `trace.rs::trace_steps` 두 곳이다.
- 한번 `""`가 되면 "응답이 정말 빈 문자열을 줬다"와 구별할 표시가 없고, 반복이 끝난 뒤에도 남는다. 엄격 렌더는 이름이 **있으므로** 실패하지 않고 빈 문자열을 주소에 넣는다(`template.rs`의 `ctx.vars.get(name)`이 `Some("")`).
- 부하 run, 에디터 시험 실행, 운영 모니터(trace 재사용) 세 경로 모두 해당한다.

## 2. 접근

| 안 | 내용 | 판단 |
|---|---|---|
| **A (채택)** | 비워진 이름과 그 값을 비운 스텝을 반복 단위로 기억한다. 요청 주소가 그 이름을 쓰고 값이 아직 `""`이면 그 요청만 보내지 않고 스텝 에러로 센다. | 뒤 스텝·VU가 계속 돈다. 원인 스텝을 화면에 짚을 수 있다. |
| B | 조건 반복을 나올 때 비워진 이름을 지워, 뒤 스텝이 예전처럼 `UnknownVar`로 실패하게 한다. | 부하 run에서 엄격 렌더 실패는 그 VU를 영구 종료시킨다. 반복 안의 뒤 본문 스텝은 못 막는다. 기각. |
| C | 빈 값이 주소·헤더·본문 어디에도 못 나가게 한다. | 조건 반복 뒤에 빈 값을 본문에 넣어 보내는 기존 시나리오가 새로 실패한다. 사용자 결정(2026-11-16)으로 주소만. 헤더·본문은 §8 연기. |

## 3. 요구사항

### R0 — 지킬 조건

비워진 이름을 **주소에** 쓰지 않는 시나리오와 조건 반복이 없는 시나리오는 전 계층에서 지금과 같다: 전송되는 요청, 메트릭, 리포트 JSON, trace JSON(새 필드는 없을 때 직렬화 생략), 모니터 판정. proto 필드 추가·migration은 없다(§5).

### R1 — 비워진 이름 기억 (엔진)

- 반복 변수 표와 **같은 수명**의 "비워진 이름 → 그 값을 비운 스텝 id" 표를 둔다(이하 *비움 표*). 반복 변수 표를 만드는 네 곳 — 부하 진입점 `run_vu`·`run_vu_curve`·`run_arrival`(`runner.rs`)과 trace 패스(`trace.rs`, 데이터셋 행 패스마다) — 에서 빈 표로 함께 시작하고 `execute_steps`/`trace_steps`에 `iter_vars`와 나란히 넘긴다.
- `blank_missing_extracts`가 이름을 `""`로 써넣을 때 비움 표에 `(이름 → 그 http 스텝 id)`를 적는다. 같은 이름을 다시 비우면 나중 스텝으로 덮는다.
- 어떤 http 스텝이 그 이름을 **실제로 뽑으면**(값이 빈 문자열이어도) 비움 표에서 지운다. 응답이 정말 빈 문자열을 준 경우는 차단 대상이 아니다.
- parallel 분기: 분기는 진입 시점 비움 표의 복제본으로 돌고, 병합 때 변수와 **같은 이름 규칙**(`{분기명}.{이름}`, `Branch::output_var_names()` 대상)으로 분기의 비움 표 항목을 부모로 옮긴다. 분기에서 비워지지 않은 이름을 병합하면 부모 표의 `{분기명}.{이름}` 항목은 지운다. runner와 trace가 같은 규칙이어야 한다.

### R2 — 차단 판정 (엔진, runner·trace 공통)

http 스텝을 실행하기 직전(요청 단위 생성 변수의 `refresh` 뒤, **요청 렌더 앞**), 다음이 모두 참인 이름이 하나라도 있으면 **차단**한다.

1. 그 스텝의 주소 템플릿(`request.url`)을 렌더할 때 flow 변수 표에서 **실제로 읽히는** 이름이다. 판정은 별도 정규식이 아니라 `template.rs`의 토크나이저(`render_inner`)를 공유하는 수집 렌더로 한다 — 같은 trim 규칙(`{{ 이름 }}`), 같은 스캔 순서, `${…}` 안의 `{{…}}`는 토큰이 아니라는 규칙이 그대로 적용돼야 한다(우회·거짓 차단 방지).
2. 이름이 비움 표에 있다.
3. `iter_vars[이름]`이 지금도 빈 문자열이다(생성 변수 `refresh` 등이 값을 다시 써넣었으면 차단하지 않는다).

- `${ENV}`·시스템 토큰은 대상이 아니다. 헤더·본문에만 쓰인 이름은 차단하지 않는다(§8).
- 조건 반복 **안과 밖 모두**에 적용한다(같은 회차의 뒤 본문 스텝, 뒤 회차, 반복이 끝난 뒤 스텝).
- 차단이 렌더보다 먼저다: 주소에 비워진 이름과 **아예 없는 이름**이 함께 있으면 차단이 이긴다(부하 run에서 `UnknownVar`로 VU가 종료되던 것이 그 스텝의 에러로 바뀐다. trace에서는 「변수 미설정」이 아니라 차단으로 보인다).
- 차단된 이름 목록은 주소에 나온 순서(중복 제거), 원인 스텝은 **첫 이름**의 것이다.

### R3 — 차단된 스텝의 처리 (엔진)

- 요청을 만들지도 보내지도 않는다. think time은 평소 규칙대로 적용한다(차단이 재시도 간격을 없애 부하를 왜곡하지 않게).
- 그 스텝의 추출은 "추출 전에 이미 에러가 있는 경우"와 같게 다룬다: 조건 반복 안이면 선언한 추출 이름을 전부 비우고(비움 표의 원인은 **이 차단된 스텝**), 밖이면 아무것도 쓰지 않는다.
- 흐름은 `Continue` — 뒤 스텝은 계속 돈다.
- **부하 run 기록**(사용자 결정 2026-11-16 — 보내지 않은 요청이 응답 시간 분포를 낮추지 않게): 집계기에 "보내지 않음" 기록 길을 더한다. 이 길은 그 스텝의 **요청 수 +1, 에러 수 +1, loop_index별 건수(`loop_counts`) +1**만 하고, **HDR 히스토그램·status 분포(`status_counts`)·단계별 시간(`record_phase`)·조건 반복 회차 응답 표본(`PassSamples`)에는 넣지 않는다**. 같은 `agg.lock()` 안에서 에러 분류 새 종류 `blank_var`를 1건 기록한다.
  - 기존 등식은 "status `0` 건수 = `blank_var`를 **뺀** 분류 건수 합"으로 바뀐다(차단 건은 status `0`에 없다).
  - 리포트 계산 중 "요청 수 = 히스토그램 표본 수" 또는 "요청 수 = status 분포 합"을 전제하는 곳이 없는지 plan에서 전수 확인하고, 있으면 그 자리의 처리도 plan에 적는다.
- **trace 기록**: http 행 하나를 남긴다.
  - `request`: `url`은 수집 렌더 결과(빈 값이 든, 보내려던 주소), `headers`는 빈 맵, `body`는 `None`(헤더·본문은 렌더하지 않는다).
  - `response: None`, `extracted`는 위 추출 규칙대로, `unbound_vars`는 **비운다**(「변수 미설정」·「미바인딩」으로 분류되지 않게), `timed_out: false`.
  - `error`: 고정 문자열 `not sent: blank value in url`(값·이름 없음 — 기존 "에러 있는 행" 로직이 그대로 동작하게).
  - 새 선택 필드 `blocked`(§5)에 이름 목록과 원인 스텝 id.
  - 요청 수 상한(`max_requests`)에는 **센다**(`state.requests += 1`). while 없는 loop이 차단된 행을 상한 없이 쌓는 것을 막고(§B59에서 막은 구멍과 같은 모양), 모니터 `truncated_reason`의 "http 행 수 ≥ 상한" 판정과도 어긋나지 않는다.

### R4 — 운영 모니터 판정 (컨트롤러)

`blocked`가 있는 http 행은 새 가지로 받는다. 판정은 빨강 `Fail`, 사유는 기존 `REASON_UPSTREAM`(「앞 단계 실패」) — **새 사유 문구 없음**(`WIDEST_REASON_CANDIDATES` 무변경). 원인 스텝 이름은 `blocked`의 스텝 id로 시나리오에서 찾고, 못 찾으면 id를 쓴다. 아래에서 `<원인>` = 원인 스텝 이름, `<막힌>` = 차단된 스텝 이름.

| 칸 | 판정 | 사유 | 상세 |
|---|---|---|---|
| 스텝 칸 — 막힌 스텝 자신의 칸(`own_result`, `error_verdict` 앞 가지) | `Fail` | 「앞 단계 실패」 | 「`<원인>` · 값 없음」 |
| 스텝 칸 — 막힌 스텝의 칸이 없어 뒤 칸이 대리 원인 칸이 될 때 | `Fail` | 「앞 단계 실패」 | 「`<막힌>` · `<원인>` · 값 없음」 |
| 스텝 칸 — 그 밖의 뒤 칸 | 기존 규칙 그대로 `UpstreamFailed` | 「앞 단계 실패」 | 기존 「`<막힌>`에서 멈춤」 |
| 흐름 칸(`check.rs::judge`, 첫 에러 http 행이 막힌 행) | `Fail` | 「앞 단계 실패」(스텝 이름 접미 **없음**) | 「`<막힌>` · `<원인>` · 값 없음」 |

- 원인 스텝의 칸은 판정을 바꾸지 않는다(§7 판단 2).
- 사유·상세에 변수 값은 싣지 않는다(이름과 스텝 이름만).
- 흐름 칸 사유에 접미를 붙이지 않는 이유: 상세가 있으면 화면은 사유 전체를 큰 글자 줄로 그린다(`ui/src/monitor/display.ts`, TUI `judge.rs`). 접미가 붙으면 큰 줄에 스텝 이름이 들어가 「가장 넓은 고정 사유가 한 줄에 들어간다」는 글자 크기 전제가 깨진다. 상세 줄은 흐름 칸·스텝 칸 모두 GUI 벽 화면·TUI·기록 창·미리보기에서 이미 그려진다 — 대리 원인 칸과 같은 모양이라 새 그리기 코드는 없다.
- `blocked` 가지는 `unbound_vars`·`timed_out`·`classify`보다 먼저 본다.

### R5 — 화면 문구 (UI·TUI)

- trace 행의 `error`를 보여 주는 화면은 `blocked`가 있으면 원문 대신 한국어 문구를 보여 준다: `TestRunPanel`(에디터 시험 실행), 모니터 `CheckRecordDialog`·`PreviewResult`, TUI `inspect.rs`의 두 곳(스텝 목록 줄 `StepLine::Http { error }`와 본문 보기 — 지금 둘 다 `step.error`를 그대로 쓴다). 문구 = "앞 스텝 `<이름>`이(가) `<변수>` 값을 주지 않아 요청을 보내지 않음"(이름 여러 개면 쉼표로, 스텝 이름을 못 찾으면 id). GUI는 `ko.ts` 경유 순수 함수 한 곳을 세 화면이 같이 쓰고, TUI는 자기 문구 모듈에 같은 문장을 둔다.
- 리포트의 실패 분류 표시에 `blank_var` 라벨 「보내지 않음 (앞 스텝 값 없음)」을 더한다(사용자 결정 2026-11-16 — 리포트의 요청 수에는 차단 건이 들어가므로, 이 건수만큼은 서버에 가지 않았다는 것이 라벨에서 읽혀야 한다). 라벨 표는 `ko.ts`의 분류 라벨 한 곳이고 웹 리포트 실패 분류 표와 인쇄 보고서가 같이 쓴다(export에는 분류 라벨이 없다). 웹 리포트의 표 제목 「Transport 실패 분류」는 그대로 둔다(§7 판단 5).
- **인쇄 보고서**: 지킬 것은 세 가지다 — ① 인쇄물이 차단 건을 「응답 받은 뒤 실패」로 서술하지 않는다 ② 차단 건은 「보내지 않음」으로 따로 보인다 ③ 차단이 없는 run의 인쇄물은 지금과 같다. 이를 위해 리포트 JSON 스텝 행에 선택 필드 `not_sent`(그 스텝의 `blank_var` 건수, 0이면 직렬화 생략 — R0)를 더하고(§5), 인쇄 코드의 다음 네 곳을 고친다.
  - **잔여**(`ui/src/print/stepTable.ts`): `max(0, 에러 수 − 에러로 세는 status 칸 합 − not_sent)`.
  - **열**: 표의 묶음 머리는 「응답 코드별 건수」 하나이고 「응답 없음」은 그 아래 한 열(`kind: "none"`)이다. 「보내지 않음」 열을 그 머리 아래 `none` 열 바로 뒤·`residual` 앞에 두되, 차단 건이 있는 run에서만 만든다. `buildColumns`의 고정 열 수에 포함한다. 개별 4xx/5xx 코드 열 수는 지금 `Math.max(MAX_COLS - fixedCount, 3)`이라 고정 열이 5개가 되면 8열이 되므로, 하한을 2로 낮춘다(`Math.max(MAX_COLS - fixedCount, 2)`) — 차단이 없는 run은 고정 열이 최대 4개라 결과가 지금과 같고(③), 차단이 있고 고정 열 5개가 다 있는 run에서만 개별 코드 열이 3개에서 2개로 줄어 전체가 `MAX_COLS`(7열)에 머문다. 이 칸은 에러로 세는 칸(`counted`)이고 가장 큰 칸 표시 대상이다. 묶음 머리 문구는 그대로 둔다(§7 판단 5).
  - **요약 문장**(`ui/src/print/sentences.ts::identityLine`): 지금은 에러가 가장 많은 스텝에 에러로 세는 status 칸이 없으면 무조건 `identityResidual`(「응답은 받았지만 값을 꺼내거나 본문을 읽지 못했습니다.」)을 찍는다. 그 스텝에서 `not_sent`가 가장 큰 에러 칸이면 새 문장 「앞 스텝이 값을 주지 않아 요청을 보내지 않았습니다.」(`ko.ts`)를 찍는 가지를 더한다.
  - **용어 설명·분류 내역 줄**(`ui/src/print/stepStatus.ts`): 「보내지 않음」 열이 있으면 용어 설명에 한 줄("앞 스텝이 값을 주지 않아 요청을 보내지 않음")을 더한다. 「응답 없음」 설명은 그대로 둔다. 분류 내역 줄은 지금 status `0`이 있을 때만 나오는데(`hasNone`), 차단 건이 있을 때도 나오게 넓힌다 — 이때 줄 머리 「응답 없음 내역」은 그대로 둔다(§7 판단 5).
- 에디터 도움말 `loopLenientExtractHelp`를 새 동작으로 고친다: 빈 값이 된 값을 **주소에** 쓰는 뒤 요청은 보내지 않고 에러로 센다는 것, 헤더·본문에는 빈 값이 그대로 들어간다는 것.

### R6 — 인사이트·유효성 (컨트롤러)

차단 건은 status 분포에 들어가지 않으므로(R3) status `0`을 읽는 규칙은 손대지 않아도 차단 건을 세지 않는다. 규칙별 결정:

| 규칙 | 읽는 것 | 결정 |
|---|---|---|
| `validity.rs` `transport_heavy` | status 분포의 `0` | 그대로(차단 건이 `0`에 없다) |
| `insights.rs` `midrun_error_onset` | 초별 status `0`+5xx, 분모는 초별 요청 수 | 그대로. 분모에 차단 건이 들어가 실패 비율이 약간 낮게 계산된다(§7 판단 6) |
| `insights.rs` `dominant_error_kind` | 분류 건수 합 | `blank_var`를 합과 후보 양쪽에서 **뺀다** |
| 분류 한 종류를 직접 읽는 규칙(`loadgen_port_exhaustion` 등) | 그 종류의 건수 | 그대로 |
| 에러 수(`error_count`) 기반 규칙·SLO 에러율 | 에러 수 | 그대로 — 차단 건도 에러다 |
| `validity.rs` `silent_http_errors` | `errors == 0`일 때만 발행 | 그대로 — 차단 건이 에러 수를 올리면 이 경고는 나오지 않는다(전송 실패가 있을 때와 같은 성질) |
| `report.rs` 연결 재사용률(`reuse_ratio = 1 − 새 연결 수 / 요청 수`) | 요청 수 | 분모에서 차단 건수를 **뺀다**(연결이 필요 없던 요청이 재사용률을 올리지 않게) |

새 인사이트는 만들지 않는다. plan에서 `error_kinds`·status `0`을 읽는 곳을 전수 grep해 위 표에 없는 소비처가 있으면 같은 원칙(차단 건은 전송 실패 근거가 아니다)으로 정하고 표를 고친다.

## 4. 범위 밖 (하지 않는 것)

- 헤더·본문에 실리는 빈 값 차단(§8).
- 조건 반복 **밖**에서 생긴 빈 값(응답이 준 빈 문자열, 사용자가 `variables`에 넣은 빈 값).
- 원인 스텝의 판정 변경(조건 반복 안 "성공 응답인데 값 없음"을 에러로 세기).
- 에디터의 정적 경고("이 주소는 조건 반복이 비울 수 있는 값을 쓴다").

## 5. 와이어

- **trace**: `StepTrace`에 선택 필드 `blocked: Option<{ vars: Vec<String>, by_step: String }>`를 더한다(`#[serde(default, skip_serializing_if = "Option::is_none")]` — 없으면 trace JSON이 지금과 같다, R0).
  - 받는 쪽: UI `StepTraceSchema`는 `.strict()`가 아닌 `z.object`라 `.optional()` 필드를 더하면 된다. TUI는 엔진 `ScenarioTrace` 타입을 그대로 쓰고(`crates/tui/src/wire.rs`의 `CheckRecord.trace`) 컨트롤러를 in-process로 띄우므로 항상 같은 빌드다. `deny_unknown_fields`는 `CheckRecord` 층에만 있고 trace 안쪽 구조체에는 없다.
  - 비용: `StepTrace { … }` 리터럴을 쓰는 곳(엔진 trace push, TUI `inspect.rs` 테스트, 컨트롤러 테스트)을 모두 고쳐야 한다 — 컴파일러가 강제한다.
  - 모니터 기록 본문(`build_record_body`)은 행을 제자리에서 고치며 `final_vars`·`extracted`·`branch_eval`만 비우므로 `blocked`는 남는다. 차단 행의 `request.url`도 다른 행처럼 `mask_url_userinfo`를 거친다.
- **리포트**: `ReportStep`에 선택 필드 `not_sent: Option<u64>`(`skip_serializing_if`, 0건이면 없음). 원천은 이미 스텝별로 저장되는 `run_error_kind_metrics`의 `kind = blank_var` 행이다. UI `ReportStepSchema`는 `.strict()`이므로 `.optional()` 필드를 **반드시** 더해야 한다(빠지면 차단이 있는 run의 리포트 화면 전체가 파싱 실패) — 이 Zod 한 줄은 컨트롤러가 `not_sent`를 내보내기 시작하는 task와 같은 커밋에 넣는다. `ReportStep { … }` 리터럴(`report.rs`·`export.rs`·`insights.rs`, 골든 `testdata/compare_golden.json`은 선택 필드라 무변경)을 고친다.
- **부하 메트릭**: 에러 분류 문자열 `blank_var`(`ErrorKind`의 9번째 종류). proto `ErrorKindStat.kind`는 문자열이라 필드 추가가 없고(종류를 나열한 proto 주석만 고친다), `run_error_kind_metrics`에 `kind` 제약이 없어 migration도 없다. 컨트롤러·워커는 함께 배포한다.

## 6. 검증

- **엔진 단위·통합**: (a) 비움 표 기록·해제(재추출 성공, 빈 문자열 추출 성공, refresh가 값 채움) (b) 차단 시 요청 0건 — 수신 서버의 접수 건수로 단언 (c) 주소 아닌 곳(헤더·본문)만 쓰면 전송됨 (d) runner·trace가 같은 시나리오에서 같은 스텝을 차단 (e) 조건 반복 안 뒤 본문 스텝 차단 (f) parallel 병합 (g) R0: 조건 반복 없는 시나리오·비워진 이름을 주소에 안 쓰는 시나리오의 메트릭·trace JSON이 그대로 (h) 바뀐 등식(status `0` = `blank_var` 뺀 분류 합)과 차단 건이 히스토그램·status 분포에 없음 (i) 토큰 모양(`{{ 이름 }}`, `${X:-{{a}}}`, 분기 접두 이름) (j) 부하 진입점 세 곳 각각(진입점을 모드로 갈라 직접 spawn — `run_scenario`만 타면 곡선·open-loop 배선 누락을 못 잡는다) (k) while 없는 loop 안에서 차단이 반복될 때 trace가 요청 수 상한에서 끊김.
- **리포트·인쇄**: `not_sent` 집계(스텝별, 0건이면 키 없음), 재사용률 분모, `dominant_error_kind` 제외, 인쇄 표의 잔여 식·「보내지 않음」 칸·분류 내역 줄 조건. 인쇄 레이아웃은 jsdom이 못 보므로 라이브에서 쪽별 rect와 PDF 쪽 수를 확인한다(차단 칸이 생긴 run과 없는 run 둘 다).
- 회귀 가드를 표방하는 테스트는 차단 판정을 꺼서 RED를 확인한 뒤 되돌린다.
- **모니터**: R4 표의 네 줄을 판정 표 테스트로(원인 칸 불변 포함).
- **UI·TUI**: 문구 변환(이름 여러 개·스텝 이름 없음), 네 화면 렌더, 분류 라벨, `blocked` 없는 응답 파싱(기존 픽스처)과 있는 응답 파싱.
- **라이브(US 척추)**: 접수 기록을 남기는 응답기로 US1–US3 각각 "서버 접수 0건"을 와이어에서 확인. 모니터는 스텝 칸 보드와 흐름 칸 보드 둘 다, 벽 화면에서 사유·상세가 잘리지 않는지(가장 긴 스텝 이름 포함) 실측. US3은 리포트 JSON의 그 스텝 요청 수·에러 수·분류 건수와 status 분포 합을 대조. TUI에서도 같은 보드의 판정·기록 화면 문구 확인(칸 그리기는 바꾸지 않으므로 칸 개수별 검증은 생략하고 근거를 build-log에).
- **보안 게이트**: 요청 실행 경로를 건드리므로 `security-reviewer` 필수. 초점 = 차단 우회 경로(토큰 모양, 분기 이름 접두, 중첩 loop, 생성 변수와 이름 겹침), `blocked`·상세·문구에 값이 새지 않는지, 차단된 행이 trace를 상한 없이 키우지 않는지.

## 7. 판단 (틀렸을 때 비용 · 해소 경로) — 마무리 때 roadmap §B에 옮긴다

1. **차단 건을 요청 수·에러 수에 센다(응답 시간 표본과 status 분포에서는 뺀다).** 비용: 리포트의 요청 수·RPS가 서버 접수 건수보다 많고, status 분포 합이 요청 수보다 적다 — 차이는 분류 라벨 「보내지 않음 (앞 스텝 값 없음)」의 건수다. 조건 반복 응답 시간 두 줄(끝낸 응답/재시도 응답)의 건수 합도 차단 건만큼 스텝 요청 수보다 적다. 해소: 차단 전용 카운터를 새 드레인 벡터로 분리해 요청 수에서 빼기(proto·migration 필요).
2. **원인 스텝 칸은 초록으로 둔다.** 비용: 스텝 칸 보드에서 빨강이 원인보다 한 칸 뒤에 뜬다(상세 줄이 원인을 짚는다). 해소: 조건 반복이 끝났을 때 비워진 채 남은 이름을 선언한 본문 스텝을 실패로 판정하는 규칙 추가.
3. **차단된 스텝이 조건 반복 밖에 있고 뒤 스텝이 그 추출 값을 쓰면, 뒤 스텝은 기존대로 엄격 렌더 실패(부하 run에서 VU 종료)다.** 지금도 전송 실패한 스텝의 추출 값을 뒤에서 쓰면 같은 일이 일어난다. 비용: US3의 "run은 끝까지 돈다"가 이 모양의 시나리오에서는 VU가 줄어든 채로 성립한다. 해소: 엄격 렌더 실패를 VU 종료가 아니라 반복 종료로 바꾸는 별도 작업.
4. **조건 반복 본문 안에서 한 회차라도 차단되면 그 점검은 실패다**(뒤 회차가 성공해도). 흐름 칸은 빨강, 스텝 칸은 그 행 뒤가 「앞 단계 실패」가 된다 — 본문 안 에러 행을 다루는 기존 규칙과 같다. 비용: "재시도해서 결국 됐다"를 모니터가 실패로 본다. 해소: 조건 반복 본문의 에러 행을 마지막 회차 기준으로 판정하는 규칙(기존 에러 행에도 같이 적용해야 한다).
5. **`blank_var`를 전송 실패용 표·머리 아래 같이 보여 준다.** 웹 리포트의 「Transport 실패 분류」 표, 인쇄 보고서의 「응답 코드별 건수」 묶음 머리, 인쇄 분류 내역 줄 머리 「응답 없음 내역」 세 곳의 제목은 그대로 두고 그 아래에 「보내지 않음」을 넣는다. 비용: 전송 실패도 응답 코드도 아닌 종류가 그 제목 아래 있다(칸·라벨·용어 설명 줄이 무엇인지는 말해 준다). 해소: 세 제목을 "응답을 받지 못한 요청" 뜻으로 넓힌다.
6. **모든 요청이 차단된 스텝은 응답 시간이 `0ms`로 보이고 그 스텝의 p95 SLO가 표본 없이 통과한다**(히스토그램이 빈다). `midrun_error_onset`의 분모에 차단 건이 들어가 실패 비율이 약간 낮게 계산된다. 비용: 에러 수 100%와 `0ms`가 한 줄에 같이 보인다. 해소: 표본 0인 스텝의 응답 시간을 「—」로 표시하고 SLO를 건너뛰는 규칙.

## 8. 연기 (조건과 함께)

- **헤더·본문의 빈 값**(사용자 결정 2026-11-16: 주소만). 연기 조건: 빈 토큰은 대상 서버가 401로 거절하고, 빈 본문 필드는 의도일 수 있다. 재개 신호: 빈 값이 든 본문·헤더 요청이 실서버에서 의도와 다른 변경을 일으켰다는 보고, 또는 모니터를 "본문의 id로 대상을 고르는" 변경 API에 걸 때. 해소 경로: 같은 비움 표로 헤더·본문 렌더도 판정하되 스텝별 "빈 값 허용" 표시를 둔다.
- **에디터 정적 경고**: 재개 신호 = 차단이 실행 뒤에야 보여 불편하다는 보고.

## 9. 구현 순서 (plan에 대한 요구)

엔진(비움 표·차단·집계 길·`ErrorKind`·trace 필드) → 컨트롤러(모니터 판정·인사이트·리포트 `not_sent`·재사용률) → UI·TUI(문구·라벨·도움말·인쇄 표) → 문서. 각 task는 독립 green 커밋이다. `StepTrace` 필드 추가는 리터럴을 쓰는 다른 크레이트까지 같은 커밋에서 고쳐야 컴파일된다.

## 10. 문서

- `crates/engine/CLAUDE.md`: 비움 표의 runner·trace lockstep, 바뀐 등식, "`ScenarioTrace`에 필드를 더하지 말 것(TUI 거울)" 서술을 사실에 맞게 고친다(막는 것은 `CheckRecord` 층뿐이다). `crates/controller/CLAUDE.md`: `blocked` 가지의 우선순위 한 줄.
- 릴리즈 노트 줄(§B58 (3)의 둘째 문장 교체): "조건 반복 안에서 응답에 없는 값을 뒤 요청 **주소**에 쓰면 그 요청은 보내지 않고 에러로 셉니다. 헤더·본문에는 빈 값이 그대로 들어갑니다."
