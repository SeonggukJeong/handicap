## 사용자 스토리 (US)

사용자 원문(앵커, 2026-11-10): "tui가 충분히 여유가 있는데도 불구하고, 양 끝 시간 가운데 측정 시간이 표시되지 않는거 같아. 그리고 정확히 중간 시간이 x축에 표시된다고 해도 어느 부분을 가리키는건지 인지하기 어려울거 같아." → 진단 후 "1, 2번 제안대로 적용", `▲` 배치는 A안(중간 눈금에만) 승인.

**재현 / 기대 / 실측**
- 재현: tmux 120×30, 6칸 보드(칸 안쪽 막대 30칸), 1초 간격, 기준선 2개 → 시각 줄이 `19:49:41              19:50:14  (ms)` — 양 끝 사이 14칸이 비었는데 중간 눈금 없음.
- 기대: 양 끝 사이에 시각 하나가 들어갈 자리가 있으면 중간 눈금이 보인다.
- 실측 원인: `crates/tui/src/view/axis.rs:65` `let lo = prev_end + tl.max(MIN_GAP);` — 앞 눈금 뒤에는 **글자 길이(8칸)** 를, 오른쪽 끝 눈금 앞에는 `MIN_GAP`(2칸, `axis.rs:50`)만 띄운다. 8글자 중간 눈금 하나에 8+8+2 = 18칸이 필요해 막대 폭 33칸 이하에선 안 나온다.

- **US1**: 운영자가 6칸·9칸 보드 모니터에서 지나간 실패 막대가 몇 시쯤이었는지 읽으려 한다 — 성공하면 양 끝 시각 사이에 자리가 있을 때 중간 시각이 보이고, 모든 이웃 눈금 사이가 같은 최소 간격(2칸) 이상이다. (관찰: 위 재현 조건에서 시각 줄에 눈금 3개.)
- **US2**: 운영자가 멀리서 화면을 보며 중간 시각이 어느 막대의 시각인지 짚으려 한다 — 성공하면 중간 눈금 앞의 `▲` 바로 위 막대가 정확히 그 시각에 점검한 막대다. (관찰: 응답 시간을 막대마다 다르게 낸 라이브에서 `▲` 열의 막대 높이 ↔ 응답기 로그의 그 시각 지연이 일치.)
- **US3**: 막대가 아직 덜 찬 시작 직후에도 같다 — 첫 결과와 최신 결과 사이에 자리가 있으면 중간 시각이 보인다.

## 1. 목표 / 비목표

**목표**: US1~US3.

**비목표**
- 세로 눈금(맨 위 `graph_max_ms` 값 상시 표시)·상한 초과 막대 표시 — 진단에서 제안했으나 사용자와 합의로 제외(실패/타임아웃은 이미 빨강 전체 높이, 상한을 넘는 *성공*은 막대 색·평균·최대 줄이 알린다, 숫자 열을 늘 두면 막대 폭이 줄어 이 슬라이스와 충돌).
- 중간 눈금을 딱 떨어지는 시각(:00·:30)의 막대에 맞추기 — 1·2번 범위 밖.
- 양 끝 눈금에 `▲` — A안 결정: 양 끝은 늘 첫 결과 막대에서 시작/최신 막대에서 끝나 위치가 이미 분명하고, `▲` 2글자를 더하면 6칸 배치(30칸)에서 중간 눈금이 다시 안 들어간다(9+2+9+2+9 = 31 > 30).
- 막대 영역에 세로 안내선(`┊`) — 막대 6줄에서 기준선 점선과 겹쳐 지저분(진단 때 비추천, 사용자 이견 없음).
- 형식 전환(10분 경계)·양 끝 눈금 위치·빈 슬롯·결과 0개 규칙 변경.

## 2. 새 규칙 (정본)

입력·양 끝은 1a §5.1과 같다: `times` = 보이는 막대 슬롯의 시각(왼→오), `f` = 첫 결과 슬롯, 왼쪽 눈금 = `f`의 시각을 `min(f, w − 글자 길이)`에서 시작, 오른쪽 눈금 = 마지막 슬롯 시각을 폭 끝에 맞춰(앞 눈금과 2칸 이상 떨어지고 글자가 다를 때만). 간격 상수 `G = 2`(`MIN_GAP` 그대로).

**중간 눈금** (바뀌는 부분):
1. 오른쪽 눈금이 없으면 중간 눈금도 없다. 오른쪽이 빠지는 두 경우: ① 자리 부족이면 중간도 들어갈 수 없다. ② 글자가 왼쪽과 같으면, 시각이 단조이고 구간이 24시간 미만일 때 그 사이 막대도 같은 글자다. (24시간을 넘어 `HH:MM`이 한 바퀴 돈 구간은 현행 코드가 `limit = w`로 중간 눈금을 놓았지만 새 규칙은 놓지 않는다 — §6.)
2. 중간 눈금 하나 = `▲` + 그 막대의 시각 글자. 폭 `m = 1 + 시각 글자 길이`(초 형식 9, 분 형식 6). **`▲`는 그 막대의 열에 놓인다** — 눈금 시작 열 = 막대 열. 중간 눈금이 놓이는 열은 모두 시각이 있는 막대다: 왼쪽 눈금이 폭 끝으로 밀린 경우(`f > w − 글자 길이`)엔 오른쪽 눈금이 없어 1로 빠지고, 아니면 왼쪽 눈금 끝 이후 열은 모두 `f` 이후다(`bar_slots`는 빈 슬롯을 왼쪽에만 둔다).
3. 빈 구간 `free = 오른쪽 눈금 시작 − 왼쪽 눈금 끝`(오른쪽 눈금이 있으면 `free ≥ G`). 자리로 들어가는 최대 개수 `n_max = (free − G) / (m + G)`(정수 나눗셈) — 곧 `n·m + (n+1)·G ≤ free`인 최대 `n`.
4. 개수 `n`에 대한 배치: 남는 칸 `free − n·m`을 `n+1`개 간격에 고르게 나눈다(몫 + 나머지는 **왼쪽 간격부터 1칸씩**). k번째 눈금 시작 = 왼쪽 눈금 끝 + 앞 간격들 + 앞 눈금 폭들. 3의 정의로 모든 간격 ≥ `G`이고, 눈금과 간격의 합이 정확히 `free`라 마지막 눈금은 늘 오른쪽 눈금 앞에 들어간다.
5. **이웃 글자가 같으면 개수를 줄여 다시 고르게 놓는다**: `n = n_max`부터 시작해, 4로 놓은 눈금 줄에서 이웃끼리(왼쪽 끝 → 중간들 → 오른쪽 끝) 시각 글자(`▲`를 뺀 글자)가 같은 곳이 하나라도 있으면 `n`을 1 줄여 4를 다시 한다. 모두 다르거나 `n = 0`이면 멈춘다. 빈칸을 남기는 개별 제외는 없다 — 분 형식에서 눈금을 촘촘히 놓으면 같은 분이 겹치는 경우(예: 5초 간격, 넓은 칸)에 눈금 수만 줄고 간격은 고르게 남는다. (1a의 "이웃과 글자가 같으면 생략"을 개수 축소로 바꾼 것.)

예(초 형식 `HH:MM:SS`, 정확히 1초 간격, 빈 슬롯 없음 — 막대 k열의 시각 = 첫 시각 + k초):
```
30칸: 19:49:41   ▲19:49:52  19:50:10            free 14 → n 1, 간격 3·2
60칸: 19:53:20     ▲19:53:33    ▲19:53:46    ▲19:53:59    19:54:19   free 44 → n 3, 간격 5·4·4·4
```
(위 예의 공백 수는 규칙 4의 산술 그대로 — 구현 테스트가 정본이다.)

- 글자색: `▲`와 시각 모두 기존 시각 줄 색(`C_AXIS`). 굵기·색 강조 없음(설계자 판단 — 시각 줄을 막대보다 눈에 띄게 하지 않는다).
- `▲`(U+25B2)는 이미 상태 문구 `▲ 느림`(`text.rs:18`)과 막대 블록 문자처럼 1칸 폭으로 그려진다는 전제를 공유한다(동아시아 모호 폭을 2칸으로 그리는 터미널 설정은 기존 화면도 이미 깨진다 — 새 위험 아님).

## 5. 라이브 검증 (머지 전 필수)

tmux, 막대마다 다른 지연을 순환하는 응답기(100·200·400·800·1200·1600·2000·300·50·1000 ms) + 응답기 로그(도착 시각·지연, 순서대로), 보드 `graph_max_ms` = 기본 2000(가장 긴 지연이 잘리지 않게 — 잘리면 한 칸 어긋남을 못 본다):
- **US1**: 120×30 6칸(막대 30칸)·160×45 9칸에서 시각 줄 캡처 — 중간 눈금 존재, 겹침·잘림 없음, `(ms)` 열과 안 겹침. 80×24 9칸(막대 ≤ 25칸)은 1초 간격 초 형식에서 중간 눈금이 들어갈 자리(29칸)가 없으므로 **겹침·잘림 없음만** 확인.
- **US2**: 1칸 120×30에서 `▲` 열의 막대 높이를 캡처에서 ms로 환산(진단 때 쓴 방식: 블록 8단계 합 / (막대 줄 × 8) × `graph_max_ms`) ↔ 응답기 로그의 같은 막대. 대응은 **순서로** 잡는다(오른쪽 끝 막대 = 로그 마지막 줄에서 열 차이만큼 거슬러) — `at_ms`는 점검 시작 시각이고 로그는 도착 시각이라 `HH:MM:SS` 문자열만으론 같은 초에 두 줄이 걸릴 수 있다. 그 막대 지연이 1/8칸 오차 안에서 일치하고, `▲` 뒤 시각과 로그 시각이 1초 안에서 맞으면 통과.
- **US3**: 시작 직후(막대가 폭의 절반쯤 찬 시점) 1칸 캡처에서 중간 눈금 존재.
- 극단값: 칸 폭 최소(24열 칸)에서 눈금 겹침 없음. 규칙 5 발동은 실제 화면에서 분 형식이어야 하므로 **보이는 막대 ≥ 121개가 다 찬 뒤**에 본다 — 1칸 보드(기준선 없음 — 숫자 열이 막대 폭을 줄이지 않게), `bar_count` 300, 5초 간격, 터미널 폭 ≥ 205(막대 ≥ 200칸), 결과가 200개 쌓일 때까지 약 17분(백그라운드로 띄워 두고 다른 확인을 먼저). 통과 = 시각 줄이 `HH:MM` 형식, 눈금 겹침 없음, 이웃 글자 다름, 중간 눈금 간격이 고름.

## 6. 알려진 한계 (수용)

- 점검이 밀리거나 끊긴 구간은 눈금 열이 고르게 놓여도 시각 간격은 고르지 않다 — 1a와 같다(시각을 지어내지 않는다).
- 분 형식에서 촘촘한 간격이면 규칙 5가 눈금 수를 자리로 들어가는 최대보다 줄인다(간격은 고르게 유지). 줄어드는 정도(스펙 리뷰 시뮬레이션): 5초·폭 120 → 13 중 8, 5초·폭 200 → 23 중 15, 3초·폭 300 → 36 중 13, 10초·폭 300 → 36 중 36(축소 없음). 눈금이 대략 분마다 하나씩 남는 셈이라 수용.
- 보이는 구간이 24시간을 넘어 양 끝 `HH:MM`이 같은 글자가 되면 중간 눈금도 없다(1a spec §7 "날짜 없음" 한계의 연장 — 모니터 PC 용도상 드묾).

## 7. 연기

없음 — 비목표 둘(세로 눈금·딱 떨어지는 시각)은 사용자가 이번에 뺀 것이고, 재개 신호가 생기면 새 요청으로 받는다. `grep -rn "axis_marks\|시각 줄" crates/tui docs/dev` 외 형제 경로 없음(GUI 축은 "N분 전 … 지금" + hover라 이 규칙과 무관 — 1a spec §5.1).

## 8. 판단 기록 (설계자 몫)

- 남는 칸은 왼쪽 간격부터 1칸씩 — 오른쪽 끝 눈금(최신)이 가장 자주 보는 곳이라 그 앞 간격을 넓히는 것보다 왼쪽에 몰아도 무방.
- 이웃 글자가 같으면 개별 제외 대신 개수 축소 + 재배치(규칙 5) — 스펙 리뷰 지적(옛 탐욕 배치는 분 바뀜마다 눈금을 놓아 빈칸이 없었는데, 고른 배치 + 개별 제외는 5초 간격 분 형식에서 눈금 ⅓쯤을 빼 불규칙한 빈칸을 남긴다). 개수는 최대 `n_max`라 계산량은 무시할 만하다.
- `▲` 색 강조 없음. `▲`는 상태 문구 `▲ 느림`에서도 쓰이지만, 시각 줄은 회색(`C_AXIS`)이고 상태 문구는 느림 색이며 놓이는 줄이 달라 혼동 위험은 낮다고 판단(사용자가 `▲` 승인).
