## 배경 (사용자 원문 요지)

- 로그인이 필요한 API를 시나리오별 칸으로 만들면 시나리오 수만큼 계정이 필요하다. **계정 하나로** 감시하려면 한 시나리오에서 원하는 스텝을 골라 칸을 만들 수 있어야 한다. **[사용자]**
- 지금 가장 급한 흐름: 더비온 1.0 로그인 → 더비온 2.0 로그인 → 경주 기초 정보 조회 → 경주 헤더 정보 조회 → 구매가능여부 체크. 최근 Redis 데이터 소실 장애가 있어 로그인 후 그 값이 있는지 확인하는 목적. 중요 API는 계속 추가된다. **[사용자]**
- 경마일 여부는 **모니터링 중인 API 응답의 참/거짓 값**으로 판단한다. 경마일 특화가 아니라 응답 값으로 갈리는 분기 일반. **[사용자]**

## 코드 확인 결과 (2026-11-04)

- 칸마다 `spawn_panel`이 독립 루프 → 같은 시나리오 칸 N개 = 주기마다 로그인 N회 동시 발생.
- IF는 trace에서 정상 실행된다. 그러나 판정 함정 2개: ① 안 탄 분기 스텝에 성공 조건 → `REASON_COND_STEP_NOT_RUN` 빨강 실패 ② 안 탄 분기 스텝을 응답속도 기준으로 → 초록 + 값 없음(거짓 안심).
- 성공 조건 "비어 있지 않음"이 `[]`·`{}`를 통과시킨다(`stringify`가 `"[]"` 두 글자) → Redis 소실로 빈 배열이 와도 초록.

## 결정

### 구조
- **점검 묶음**: 시나리오 1개를 주기마다 **한 번만** 실행(로그인 1회), 묶음 안 칸들이 그 결과를 스텝별로 나눠 본다. **[사용자 동의]**
- 묶음은 **명시적**으로 만든다 — 같은 시나리오라고 자동으로 묶지 않음(주기·제한이 다르면 따로 실행돼 로그인이 다시 갈라지므로). **[Claude]**
- 시나리오·환경·점검 주기 = 묶음 단위. 칸 = 볼 스텝 + 그 스텝의 느림 기준·성공 조건·표시 값·**제한 시간**. **[사용자: 제한 시간 칸별]**
- 단독 실행하는 칸(시나리오 전체) = 지금 동작 그대로. 기존 보드·보드 파일 호환 필수. **[사용자 동의]**
- 칸 최대 9개 유지(멀리서 안 보임, 필요하면 나중에). **[사용자]**

### 판정
- 앞 단계 실패 → 원인 칸만 빨강, 뒤 칸 = **"확인 못 함"**(앞 단계 실패 · X에서 멈춤), 깜빡임·연속 실패 카운트 제외. **[사용자 동의]**
- 안 탄 분기의 칸 = **"분기 제외"**, 큰 줄 `조건 대상 = 실제 값`(예 `isRaceDay = false`), 작은 줄 `조건 <기대> · <IF 이름>`. "분기 조건 불충족"·"오늘 해당 없음" 문구 기각. **[사용자: 조건명 = false처럼 어떤 값이 안 맞았는지]**
- 조건이 AND/OR 복합이면 분기를 실제로 가른 첫 조건 하나만 표시. **[Claude]**
- 분기 값을 못 꺼냄(값 없음)·그 응답 실패 → **실패**. **[사용자: "너 판단이 맞아"]**
- 칸별 제한 시간 = 그 스텝의 요청 제한 시간(엔진 `HttpStep.timeout_seconds` 경로 재사용). 칸이 없는 스텝은 기본 5초, 흐름 전체 상한 = 스텝 제한의 합. **[Claude]**
- "비어 있지 않음"이 `[]`·`{}`를 비어 있음으로 판정 — 이번 슬라이스에 포함. **[사용자]**
- 배열 길이 추출은 **이번 범위 밖**(사용자가 추후 요청 예정 — 엔진 추출 변경이라 분리). **[사용자]**
