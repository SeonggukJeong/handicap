## 사용자 스토리 (US)

- **US1 (②a — 처음 옮기기)**: QA가 내 자리 PC에서 시험을 마친 보드 2개를 목록에서 골라 파일 하나로 내보내고, 시나리오도 환경도 없는 모니터링 PC에서 그 파일을 가져온다 — 성공하면 아무 질문 없이 보드 2개와 그 보드들이 쓰는 시나리오·환경(테스트 계정 값 포함)이 생기고 "보드 2개 가져옴(새로 2)"이 보이며, 두 보드가 공유하는 시나리오는 하나만 생기고, 보드를 켜면 내 자리와 같은 칸·성공 조건·표시 값으로 점검이 돈다.
- **US2 (②b — 보드만 고쳐 다시 가져가기)**: QA가 내 자리에서 보드 성공 조건만 고친 파일을, 그 보드가 점검 중인 모니터링 PC에서 가져온다 — 성공하면 겹침 질문이 뜨고 [덮어쓰기] 아래에 "점검 중인 보드 '야간 결제 점검'은 새 설정으로 바로 다시 시작됩니다"가, 시나리오·환경은 "변경 없음"이 보이며, 덮어쓰면 보드가 새 조건으로 다시 시작되고 시나리오·환경 개수는 그대로다.
- **US3 (②b — 시나리오도 바뀐 파일)**: QA가 시나리오까지 고친 파일을 가져온다 — 성공하면 겹침 질문에 [보드만 덮어쓰기]가 나타나고 시나리오 내용이 다르다는 것과 그 시나리오를 쓰는 모니터링 PC의 다른 보드 이름이 보이며, 보드가 가리키는 스텝이 모니터링 PC 시나리오에 없으면 [보드만 덮어쓰기]는 꺼진 채 이유가 보이고, [새 보드로 추가]를 고르면 기존 보드는 점검을 계속하고 새 보드는 꺼진 채 "결제 흐름 (2)" 같은 복사본과 함께 추가되며, 내용이 같은 시나리오·환경은 새로 만들지 않는다.
- **US4 (②b — 여러 보드가 겹칠 때)**: QA가 모니터링 PC에 이미 있는 보드 3개가 든 파일을 가져온다 — 성공하면 "겹치는 보드 1/3"부터 하나씩 묻고, [모두 덮어쓰기]나 [모두 새 보드로 추가]를 누르면 남은 질문을 건너뛰며, 도중에 [취소]하면 모니터링 PC에는 아무것도 바뀌지 않는다.
- **US5 (②a — 잘못된 파일·저장 안 한 수정)**: QA가 화면에서도 막히는 설정(허용되지 않는 조건 경로 등)이 든 파일·깨진 파일·이 프로그램보다 새 버전의 파일을 가져온다 — 성공하면 아무것도 들어가지 않고 어느 보드의 어느 칸이 왜 문제인지 보인다. 보드 설정 화면에서 저장 안 한 수정이 있는 채 내보내기를 누르면 "저장되지 않은 내용이 있습니다. 저장 후 내보내시겠습니까?" [취소] [저장 후 내보내기]가 뜨고, 저장이 실패하면 파일은 만들어지지 않는다.

## 1. 배경·목표·비목표

모니터링 PC는 운영실에 있고 QA 자리에 있지 않다. QA는 자기 PC에서 보드를 만들고 미리 실행으로 조건을 맞춘 뒤, **파일 하나만 들고 가서 그대로 넣는다**(사용자 원문: "내 자리에 있는 PC에서 설정과 테스트를 마친 후에 파일만 가져가서 그대로 넣어야 함"). 모니터링 PC엔 그 시나리오·환경이 없을 수 있으므로 파일은 **자기완결**이어야 한다.

**목표**
- 보드 목록에서 여러 보드를 골라 파일 하나로 내보내기(보드 + 칸이 쓰는 시나리오 + 칸이 쓰는 환경, 환경 값 평문 포함 — 사용자 결정).
- 보드 설정 화면에서 그 보드 내보내기(저장 안 한 수정이 있으면 저장 후 내보내기 대화창).
- 가져오기: 파일 전체 검증 → 겹침 판정 → 겹치는 보드만 하나씩 질문(모두 덮어쓰기/모두 새 보드로) → **전부 아니면 전무**로 한 트랜잭션 적용.
- 파일 형식을 "보드 묶음 / 시나리오 묶음 / 환경 묶음" 세 칸 + 형식 버전으로 잡아, 후속 "시나리오 선택 내보내기"가 같은 형식을 재사용할 수 있게 한다(사용자 계획 — 이번 범위 아님).

**비목표**
- 시나리오만 내보내기/가져오기(후속 슬라이스 — 형식만 대비). 이번 가져오기는 보드가 1개 이상이고 시나리오·환경이 모두 어떤 보드에 쓰이는 파일만 받는다(§4.2 R6).
- 데이터셋·스텝 템플릿·프리셋·스케줄 옮기기(모니터 칸은 데이터셋을 쓰지 않는다 — `PanelConfig`에 데이터셋 필드 없음).
- 파일 암호화·비밀 값 마스킹(사용자 결정: 평문으로 옮긴다 — 내보내기 옆 안내 한 줄만).
- 이름이 같고 ID가 다른 시나리오·환경을 "같은 것"으로 묶기(§3.2 — 우연히 이름이 같은 다른 리소스 공유 위험).
- 겹침 질문에서 덮어쓸 시나리오의 예약 실행·프리셋 영향 표시(모니터링 PC 용도 = 모니터 — 다른 **보드**만 표시, §7 판단 J3).
- 보드의 `enabled`(켜짐) 상태 옮기기 — 새로 생긴 보드는 꺼진 채, 덮어쓴 보드는 모니터링 PC의 켜짐 상태 유지.


## 2. 파일 형식 (`format_version` 1)

```json
{
  "format": "handicap-bundle",
  "format_version": 1,
  "exported_at": 1761700000000,
  "app_version": "0.9.0",
  "boards":       [{ "id": "<ULID>", "name": "야간 결제 점검", "config": { /* BoardConfig 그대로 */ } }],
  "scenarios":    [{ "id": "<ULID>", "yaml": "<시나리오 YAML 원문>" }],
  "environments": [{ "id": "<ULID>", "name": "운영", "vars": { "PASSWORD": "..." } }]
}
```

- `config`는 `BoardConfig` serde 그대로(`font_scale`·`blink`·`display_style`·`panels`·`show_latency_stats`·`record_limit_kb`, 칸의 `latency_source`·`conditions`·`display_items` 포함). 와이어 1:1 원천 = `crates/controller/src/monitor/config.rs` ↔ `ui/src/api/monitors.ts`.
- 시나리오 이름은 YAML 안 `name`이 원천(`store/scenarios.rs` `insert`가 `scenario.name`을 쓴다)이라 별도 `name` 필드를 두지 않는다.
- `exported_at`·`app_version`은 정보용(가져오기 판정에 안 쓴다). `app_version`은 `GET /api/version`과 같은 값.
- 파일 이름: 보드 1개면 `<보드 이름>.handicap-board.json`, 여러 개면 `monitor-boards-<N>.handicap-board.json`. 보드 이름은 기존 `sanitizeFilename`(`ui/src/api/sanitizeFilename.ts`) 경유, 결과가 빈 문자열이면 `monitor-board`. 저장은 기존 `downloadText`(`ui/src/api/downloadJson.ts`) 재사용.
- 같은 시나리오·환경을 여러 보드가 쓰면 한 번만 담는다(ID 기준 중복 제거). 순서: `boards`는 요청한 `board_ids` 순서, `scenarios`·`environments`는 처음 등장 순서.

### 2.1 형식 버전 규칙 (ADR-0054에 기록)

- 읽는 쪽이 모르는 키가 있으면 **거부**한다(§4.2 R2'). 두 층:
  - **파일 구조체**(최상위·`boards[]` 항목 `{id,name,config}`·`scenarios[]` 항목·`environments[]` 항목)는 새로 만드는 타입이므로 `#[serde(deny_unknown_fields)]`. 환경 `vars`는 열린 맵 그대로.
  - **보드 `config`**: `BoardConfig`·`PanelConfig`는 `#[serde(default)]`이고 모르는 키를 조용히 버린다(`config.rs:180,216` — DB 행 호환 때문에 `deny_unknown_fields`를 걸 수 없다). 그래서 가져오기는 **각 보드 `config` 원본 JSON과, 그것을 `BoardConfig`로 읽어 다시 직렬화한 JSON의 키 집합을 재귀 비교**해 원본에만 있는 키를 찾는다(정규화 전 값으로 비교 — R7이 칸 ID를 채우기 전). 있으면 "이 파일에는 이 버전의 핸디캡이 모르는 보드 설정(`panels[0].새키`)이 있습니다. 핸디캡을 업데이트하세요." `config.rs`의 serde 속성(무필드 enum `rename_all`·컨테이너 `default`·`LatencySource` 내부 태그)엔 `alias`·`flatten`·`skip` 등이 없어 거짓 양성이 없다 — 이 성질이 유지되도록 그 비교에 표 테스트를 둔다.
  - 시나리오 YAML: 엔진 타입 대부분이 `deny_unknown_fields`라 R5에서 거의 같은 효과가 나지만 예외가 있다(`ThinkTime` — `crates/engine/src/pacing.rs:14-15`). YAML은 원문 그대로 저장되므로 모르는 키가 사라지지 않고 남는다 — 영향 작음, 수용.
- 따라서 `BoardConfig`/`PanelConfig`에 **필드를 추가하는 것만으로는** `format_version`을 올리지 않아도 된다(옛 핸디캡이 새 파일을 받으면 위 규칙으로 막힌다). `format_version`은 **파일 최상위 구조나 기존 필드의 의미가 바뀔 때만** 올린다.
- 귀결(ADR-0054에 기록): `BoardConfig`에 필드가 하나라도 추가된 뒤의 핸디캡이 내보낸 파일은, 그 필드가 기본값이어도(직렬화가 항상 모든 필드를 쓰므로) **옛 핸디캡에서 거부된다** — 모니터링 PC도 같이 업데이트해야 한다. 조용히 설정이 사라지는 것보다 낫다고 판단(J12).

## 3. 가져오기 의미론

### 3.1 용어

- **PC**: 가져오는 쪽(모니터링 PC) DB.
- 시나리오 상태(가져오기 전 PC 기준): `absent`(같은 ID 없음) · `same`(같은 ID + YAML 문자열 완전 일치) · `different`(같은 ID + YAML 다름).
- 환경 상태: `absent` · `same`(같은 ID + `vars` 완전 일치) · `different`. **이름은 비교하지 않는다** — 가져오기가 이름 충돌로 `운영 (2)`처럼 바꿔 저장한 환경이 다음 가져오기에서 영원히 `different`가 되는 것을 막기 위해(§3.3). 이름은 저장 전 `trim`한다(환경 생성 API와 같게 — `api/environments.rs:97`).
- 보드가 **겹침** = **(보드 ID가 PC에 있음) ∨ (그 보드가 쓰는 시나리오·환경 중 `different`가 하나라도 있음)**. 겹침이 아닌 보드는 묻지 않고 추가한다.
  - 쓰는 시나리오·환경이 `same`이기만 하고 보드는 PC에 없으면 어떤 결정이든 결과가 같으므로 묻지 않는다(기존 것을 그대로 쓴다). brainstorming 중 "시나리오·환경이 이미 있으면 겹침"이라 했던 정의를 이렇게 좁혔다(§7 J10).
- **보드가 참조하는 스텝** = 칸마다 `conditions[].step_id` ∪ `display_items[].step_id` ∪ `latency_source`가 `Step { step_id }`면 그 `step_id`. 스텝 존재 판정은 점검이 쓰는 것과 같은 기준 — `monitor/check.rs` `collect_http_steps`(HTTP 스텝만; 조건·응답 시간 기준이 loop/if/parallel ID를 가리키면 점검은 설정 오류다)를 `pub(crate)`로 열어 재사용한다.

### 3.2 결정 3종과 리소스 처리표

겹치는 보드마다 사용자가 하나를 고른다: `overwrite`(덮어쓰기 — 시나리오·환경까지) · `board_only`(보드만 덮어쓰기) · `new`(새 보드로 추가). 겹치지 않는 보드는 결정 없이 "추가".

| | 보드 | 시나리오/환경 `absent` | `same` | `different` |
|---|---|---|---|---|
| 겹침 아님 | 원래 ID로 추가(꺼짐) | 원래 ID로 추가 | 그대로 사용 | (발생 안 함 — 정의상 겹침) |
| `overwrite` | PC에 있으면 파일 내용으로 갱신, 없으면 원래 ID로 추가 | 원래 ID로 추가 | 그대로 | **PC 것을 파일 내용으로 갱신** |
| `board_only` | 위와 같음 | 원래 ID로 추가 | 그대로 | **PC 것 유지** |
| `new` | PC에 같은 ID가 **있을 때만 새 ID**, 없으면 원래 ID로 추가(꺼짐) | 원래 ID로 추가 | 그대로 사용 | **복사본을 새 ID로 추가** |

- `new`에서 보드 ID를 보존하는 경우(보드는 PC에 없고 리소스만 다른 경우)를 둔 이유: 새 ID를 주면 같은 파일을 다시 가져올 때마다 같은 겹침이 나와 복사본이 쌓인다(J1 ID 보존 취지).
- `new` 보드의 칸들은 복사본(또는 그대로 쓰는 기존) 시나리오·환경 ID를 가리키도록 `scenario_id`·`environment_id`를 바꿔 저장한다. 칸 `id`·`step_id`는 그대로(스텝 ID는 시나리오 YAML 안에 있어 복사본에도 같다).
- **한 파일 안 결정이 갈릴 때(공유 리소스)** — 적용 순서: ① `overwrite`가 건드리는 `different` 리소스를 파일 내용으로 갱신 → ② 나머지 보드의 리소스 처리(① 이후 상태로 `same` 재판정 — ①에서 갱신된 리소스는 `new` 보드도 그대로 쓴다) → ③ 복사본은 리소스당 **하나만** 만들고 그 리소스를 쓰는 `new` 보드들이 공유. `board_only` 보드 C가 같은 리소스를 쓰는데 다른 보드 A가 `overwrite`면 그 리소스는 갱신된다(덮어쓰기가 이긴다 — J4). 질문 화면은 이 상황을 **미리** 보여 준다(§5.3 — 앞에서 고른 결정을 클라가 알고 있으므로).
- **`board_only` 허용 조건**: 그 보드가 쓰는 `different` 시나리오마다, 보드가 참조하는 스텝(§3.1) 중 **파일 쪽 시나리오에 있는 것**이 PC 쪽 시나리오에도 모두 있어야 한다(파일 쪽에도 없는 스텝 = 내 자리에서 이미 끊긴 참조는 판정에서 뺀다). 없으면 `board_only` 불가 + 사유 "모니터링 PC의 시나리오 '결제 흐름'에 '토큰 받기' 스텝이 없어 보드만 덮어쓸 수 없습니다"(스텝 이름 = 파일 쪽 HTTP 스텝의 `name`, 여럿이면 첫 하나 + " 외 N개"). `different`가 환경뿐이면 항상 허용.
- `board_only` 버튼은 그 보드가 쓰는 시나리오·환경 중 `different`가 하나 이상일 때만 보인다(없으면 `overwrite`와 결과가 같다).
- **덮어쓰기가 파일 밖 보드를 깨는 경우**: `different` 시나리오를 파일 내용으로 바꾸면, 그 시나리오를 쓰는 PC의 다른 보드(파일에 같은 ID로 없는 보드)가 참조하던 스텝이 사라질 수 있다. 분석은 그런 보드를 `breaks_other_boards`로 따로 알린다(§4.3) — 질문 화면 문구 "이 보드는 덮어쓰면 설정 오류가 됩니다: '주간 점검'".

### 3.3 이름

`monitor_boards.name`·`environments.name`은 UNIQUE(migration 0022·0007). 시나리오 이름은 유일하지 않다.

- **새로 추가하는 행**(원래 ID 추가·`new` 새 ID·복사본)의 이름이 PC의 다른 행과 겹치면 `이름 (2)`, `(3)`…로 처음 비는 것을 쓴다. 보드 이름은 40자 상한(`config.rs` `NAME_MAX_CHARS`)을 지키도록 원래 이름을 잘라 접미사를 붙인다. 같은 파일 안 보드끼리 이름이 같아도 같은 규칙(이번 가져오기에서 이미 정한 이름도 "쓰는 중"으로 친다).
- **갱신하는 행**(보드가 PC에 **있을 때**의 `overwrite`·`board_only` 보드, `overwrite`로 갱신되는 `different` 환경): 파일 이름이 다른 행과 겹치지 않으면 파일 이름으로, 겹치면 **PC의 현재 이름을 유지**한다(접미사를 붙였다 뗐다 하지 않는다 — 반복 가져오기에서 이름이 흔들리지 않게). 보드가 PC에 없을 때의 `overwrite`·`board_only`는 "새로 추가하는 행" 규칙.
- **이름 결정 순서**(트랜잭션 안, 종류별 — 보드·환경·시나리오 복사본 각각): ① 갱신하는 행을 파일 순서대로 ② 새로 추가하는 행을 파일 순서대로. 어떤 행 X의 "쓰는 중인 이름" 집합 = **X 자신을 뺀** PC의 모든 행의 현재 이름(갱신될 행의 현재 이름도 포함) + 이번 가져오기에서 이미 정한 이름들. 그래서 갱신 행의 대체값인 "자기 PC 이름"은 다른 누구에게도 배정되지 않아 항상 비어 있고, 맞바꾸기(A→"B", B→"A")는 둘 다 PC 이름 유지로 끝난다. SQLite UNIQUE는 문장마다 검사되므로(지연 불가) 이 규칙은 어떤 UPDATE 순서에서도 중간 충돌이 없다는 것을 보장해야 한다 — 표 테스트에 맞바꾸기·3자 순환을 넣는다.
- 결과 요약 `renamed`에는 **최종 이름이 파일 이름과 다른 행**을 싣는다 — 새 행은 `reason: "name_taken"`(`이름 (2)` 등 접미사), 갱신 행은 `reason: "kept_pc_name"`(파일 이름이 다른 행과 겹쳐 이 PC 이름을 유지 — 파일의 새 이름이 적용되지 않았음을 알린다. 겹침이 남아 있는 한 매번 나오는 것이 사실이므로 반복은 수용).
- 시나리오 **복사본**은 구별을 위해 `이름 (2)` 규칙(PC의 시나리오 이름 + 이번 가져오기에서 정한 이름 집합 기준). 이름이 YAML 안에 있으므로 복사본 YAML은 `serde_yaml::Value`로 읽어 최상위 `name`만 바꿔 다시 쓴다 — 키 순서는 유지되고 기본값 필드가 새로 붙지 않는다(`Scenario::to_yaml` 왕복은 `body: null`·`assert: []` 등 기본값을 펼친다). 주석은 사라진다(수용 — J5). 바꾼 YAML은 저장 전 `Scenario::from_yaml`로 다시 읽어 확인한다(가드). 원래 ID로 추가·갱신하는 시나리오는 YAML 원문을 그대로 저장한다.

### 3.4 점검 재시작

- 덮어쓴 보드(`overwrite`·`board_only`)는 커밋 후 `state.monitor.reconcile(&db, id)` — 켜져 있던 보드는 새 설정으로 즉시 다시 시작한다(화면 저장과 같은 동작, `api/monitor_boards.rs` `update`).
- 덮어쓴 시나리오·환경은 감독자 재시작 없이 다음 점검부터 반영된다(점검이 매번 `store::scenarios::get`·`environments::get`을 읽는다 — `monitor/check.rs:634,642`).
- 새로 추가된 보드는 꺼진 채(`store/monitor_boards.rs` `insert`의 `enabled=0`).
- 커밋 후 reconcile이 실패하면 가져오기는 성공(200)으로 두고 그 보드의 결과에 `restarted: false` + 경고 로그(DB는 이미 새 설정 — 사용자가 끄고 켜면 적용).

### 3.5 전부 아니면 전무

- 적용은 SQLite 트랜잭션 하나(읽고-쓰는 트랜잭션이므로 `BEGIN IMMEDIATE`로 시작해 도중 쓰기 승격 실패를 피한다 — 구체 API는 plan). 실패하면 롤백되어 PC는 그대로다. reconcile은 커밋 **후**에만.
- **지문(fingerprint)**: `analyze` 응답에 분석 결과 전체(§4.3 본문에서 `fingerprint` 자신 제외)를 JSON 직렬화한 바이트의 해시(`std::hash::DefaultHasher` — 같은 바이너리 안 비교용이고 보안 토큰이 아니라 새 의존성 불필요, 16진 문자열)를 싣는다. 클라는 `import` 요청에 그 값을 그대로 보낸다. 서버는 트랜잭션 안에서 다시 분석해 **결정 검사보다 먼저** 지문을 비교하고, 다르면 409 "가져오는 사이 이 PC의 보드·시나리오가 바뀌었습니다. 파일을 다시 가져오세요."(그래야 사용자가 고르는 동안 새로 겹친 보드가 400 "클라 버그"가 아니라 409가 된다). 지문이 같은데 결정이 없는 겹침 보드·겹치지 않는 보드에 대한 결정·허용 안 되는 `board_only`가 있으면 400(클라 버그 방어).
- **지문 결정성 규칙**: 분석 DTO에 `HashMap`/`HashSet` 금지(직렬화 순서가 호출마다 다를 수 있다 — 순서 있는 `Vec`/`BTreeMap`만). 배열 순서 고정 — `boards`: 파일 순서 · 보드별 `scenarios`·`environments`: 칸 순서대로 처음 쓰인 순서 · `used_by_other_boards`·`breaks_other_boards`: 이름순(보드 이름 UNIQUE라 전순서) · `warnings`: 칸 순서, 칸 안에서는 응답 시간 기준 → 성공 조건(순서대로) → 화면 표시 항목(순서대로). R7이 빈 칸 ID에 새로 만드는 ULID(`config.rs:265-266`)처럼 호출마다 달라지는 값은 분석 결과에 넣지 않는다.
- **`import` 요청 본문은 파일 텍스트를 그대로 끼워** 만든다(`'{"bundle":' + 파일텍스트 + ',"decisions":' + JSON.stringify(…) + ',"fingerprint":' + JSON.stringify(…) + '}'`). 클라가 `JSON.parse` 후 다시 `stringify`하면 큰 숫자 정밀도·중복 키 처리 차이로 서버가 다른 파일을 보게 될 수 있어서. `analyze`가 같은 텍스트를 이미 통과시켰으므로 끼운 결과도 유효한 JSON이다.

## 4. 서버 (`crates/controller`)

### 4.1 엔드포인트

| 메서드·경로 | 입력 | 출력 |
|---|---|---|
| `POST /api/monitor-boards/export` | `{ "board_ids": [..] }` (1~50개, 중복 없음) | 200 파일 JSON(§2) · 400 빈 목록/50개 초과/중복 ID · 404 없는 보드 · 400 자기 검증 실패(§4.6) |
| `POST /api/monitor-boards/import/analyze` | 파일 JSON(본문 그대로) | 200 분석(§4.3) · 400 검증 실패(§4.2) · 413 본문 상한 초과 |
| `POST /api/monitor-boards/import` | `{ "bundle": <파일 JSON>, "decisions": { "<board_id>": "overwrite"\|"board_only"\|"new" }, "fingerprint": "<analyze 값>" }` | 200 결과(§4.4) · 400 검증 실패/결정 오류 · 409 지문 불일치 · 413 |

- 라우트 등록 순서는 상관없다 — axum 0.8(matchit)은 정적 세그먼트를 매개변수보다 먼저 맞춘다. 선례: POST `/monitor-boards/preview-check`가 이미 `/monitor-boards/{id}` 옆에 있다(`app.rs:118-125`). 통합 테스트로 세 경로가 각 핸들러에 닿는지 확인.
- 두 가져오기 엔드포인트는 `axum::Json` 추출기 대신 본문 바이트를 직접 파싱해(§4.2 R0) 타입 오류도 **400 + 한국어 사유**로 낸다(axum `Json`은 422 — 컨트롤러 CLAUDE.md 422 노트).
- 본문 상한: 두 가져오기 라우트에만 `DefaultBodyLimit::max(32 MiB)`(전역 변경 금지). 초과 시 axum은 **413 + 평문 본문**(JSON `{error}` 아님)을 낸다 → UI가 413을 따로 처리(§5.3). UI는 업로드 전 `file.size > 32 MiB`면 서버 호출 없이 같은 문구를 낸다.

### 4.2 파일 검증 (`analyze`·`import` 공통, 순서대로, 첫 실패에서 400)

- R0 본문 → `serde_json::Value`. 실패면 "파일을 읽을 수 없습니다(JSON 형식 오류, N번째 줄)"(`serde_json::Error::line()`). **오류 문구에 값을 넣지 않는다** — serde 오류 `Display`는 값(`invalid type: integer \`12345\``)을 인용하므로 위치(줄 또는 경로)만 쓴다.
- R1 `format == "handicap-bundle"` 아니면 "핸디캡 보드 파일이 아닙니다".
- R2 `format_version`: 정수가 아니거나 1 미만이면 R1 문구 · 1 초과면 "더 새 버전의 핸디캡에서 만든 파일입니다(파일 형식 N, 이 프로그램은 1까지 읽습니다). 핸디캡을 업데이트하세요." — **머리(`format`·`format_version`)를 먼저 읽은 뒤** 전체를 타입 구조로 읽는다(그래야 모양이 바뀐 새 버전 파일에서도 R2가 먼저 뜬다).
- R2' 전체를 타입 구조로 읽기 — `serde_path_to_error`(이미 axum 경유로 `Cargo.lock`에 0.1.20이 있다 → 컨트롤러 직접 의존성으로 추가, 새 다운로드 없음)로 감싸 **경로만** 쓰고 안쪽 메시지는 버린다: "파일 형식이 올바르지 않습니다: boards[0].config.panels[1].bar_count". 단 `deny_unknown_fields` 구조체의 `unknown field` 오류는 §2.1 문구("이 파일에는 이 버전의 핸디캡이 모르는 항목(`boards[0].enabled`)이 있습니다. 핸디캡을 업데이트하세요.")로 바꾼다(필드 이름은 파일 구조 키라 값이 아니다). 이어서 §2.1 보드 `config` 모르는 키 검사.
- R3 개수: 보드 1~50개(0개면 "가져올 보드가 없습니다").
- R4 ID: 모든 보드·시나리오·환경 ID가 **정규형 ULID**(`Ulid::from_string(s)`이 성공하고 `to_string() == s` — 소문자 ULID를 받아들이면 문자열 비교에서 `absent`가 돼 같은 리소스가 두 행이 된다), 각 묶음 안에서 중복 없음.
- R5 시나리오마다 `Scenario::from_yaml` + `validate_parallel_branch_names` + `validate_scenario_think_times`(시나리오 생성 API와 같은 검사 — `api/scenarios.rs` `create`; `validate_parallel_branch_names`는 지금 private이라 `pub(crate)`로 연다). 사유 앞에 `시나리오 '<이름 또는 ID>': `.
- R5' 환경마다 `validate_env`(`api/environments.rs`, private + `ApiError` 반환 → `pub(crate)`로 열고 사유 문자열을 꺼내 쓴다). 사유 앞에 `환경 '<이름>': `.
- R6 참조 정합: 모든 칸의 `scenario_id`가 파일 `scenarios`에, `environment_id`(있으면)가 파일 `environments`에 있다. 어느 보드도 쓰지 않는 시나리오·환경이 있으면 "파일 내용이 서로 맞지 않습니다(쓰이지 않는 시나리오 '…')"(J8).
- R7 보드마다 `validate_and_normalize(name, &mut config)`(§B38 (3) 필수 전달). 사유 앞에 `보드 '<이름>' `(함수가 이미 `칸 N: `을 붙인다 → "보드 '야간 결제 점검' 칸 2: 본문 경로(JSONPath)가 올바르지 않습니다"). 정규화된 `config`를 이후 단계에서 쓴다.
- 파일 쪽 시나리오에 없는 스텝을 참조하는 칸(§3.1)은 **거부하지 않는다** — 내 자리에서도 같은 상태로 저장될 수 있는 보드(roadmap §B38 M1)를 그대로 옮기는 것이 목표라서(J6). 보드별 `warnings`로 알린다: "칸 N: 성공 조건이 가리키는 스텝이 시나리오에 없습니다" / "…화면 표시 항목이…" / "…응답 시간 기준 스텝이…"(마지막은 점검이 매번 설정 오류가 된다는 뜻이므로 문구에 "점검이 설정 오류로 표시됩니다"를 붙인다).

### 4.3 분석 응답

```json
{
  "fingerprint": "<hex>",
  "boards": [{
    "id": "...", "name": "야간 결제 점검", "pc_name": "야간 결제 점검",
    "conflict": true, "exists": true, "enabled": true,
    "board_only_allowed": false,
    "board_only_reason": "모니터링 PC의 시나리오 '결제 흐름'에 '토큰 받기' 스텝이 없어 보드만 덮어쓸 수 없습니다",
    "scenarios":    [{ "id": "...", "name": "결제 흐름", "state": "different",
                       "used_by_other_boards": ["주간 점검"], "breaks_other_boards": ["주간 점검"] }],
    "environments": [{ "id": "...", "name": "운영", "state": "same",
                       "used_by_other_boards": [], "breaks_other_boards": [] }],
    "warnings": ["칸 3: 성공 조건이 가리키는 스텝이 시나리오에 없습니다"]
  }],
  "summary": { "boards": 3, "conflicts": 1, "scenarios": 2, "environments": 1 }
}
```

- `name` = 파일 쪽 이름, `pc_name` = PC에 있는 같은 ID 보드의 이름(`exists=false`면 null). "점검 중인 보드 '<이름>'" 문구는 `pc_name`(화면에 떠 있는 이름)을 쓴다.
- `used_by_other_boards` = PC 보드 중 **이 파일에 같은 ID로 들어 있지 않은** 보드들 가운데 칸이 그 리소스 ID를 쓰는 보드 이름(이름순). `breaks_other_boards` = 그중 시나리오를 파일 내용으로 바꾸면 참조 스텝(§3.1)이 사라지는 보드. 둘 다 `different`일 때만 채운다. 환경의 `breaks_other_boards`는 항상 빈 배열(환경은 스텝이 없다).
- `board_only_allowed`·`board_only_reason`은 `different`가 하나 이상일 때만 의미(아니면 `false`·null — UI는 버튼을 숨긴다).
- `enabled` = PC 보드의 켜짐 상태(`exists=false`면 false).
- 응답에 환경 `vars` 값은 싣지 않는다.
- `warnings`는 겹치지 않는 보드에도 채운다(US1 경로에서도 결과 화면에 보이도록 — §5.3 5단계).

### 4.4 결과 응답

```json
{
  "boards": [{ "id": "<PC에 저장된 ID>", "name": "<최종 이름>", "action": "added"|"overwritten"|"board_only"|"copied",
               "restarted": true, "warnings": [] }],
  "scenarios":    { "added": 1, "updated": 1, "copied": 0, "unchanged": 1 },
  "environments": { "added": 0, "updated": 0, "copied": 0, "unchanged": 1 },
  "renamed": [{ "kind": "board"|"scenario"|"environment", "from": "운영", "to": "운영 (2)", "reason": "name_taken"|"kept_pc_name" }],
  "overridden_board_only": ["<J4로 board_only인데 공유 시나리오가 갱신된 보드 이름>"]
}
```

- `action`: 겹침 아님 → `added`, `overwrite` → `overwritten`, `board_only` → `board_only`, `new` → `copied`(보드 ID 보존 여부와 무관하게 "새 보드로 추가"한 것).
- `restarted` = 덮어쓴 보드가 켜져 있었고 reconcile이 성공했을 때 true.

### 4.5 저장소

- 원래 ID로 넣기 위해 `store::scenarios`·`store::environments`·`store::monitor_boards`에 **ID를 받는 insert**와, 같은 트랜잭션 안에서 쓸 수 있는 변형(지금 함수들은 모두 `&Db`=풀을 받고, `scenarios::update`는 자기 트랜잭션을 연다 — 구체 시그니처는 plan)이 필요하다. 기존 함수는 그대로 둔다.
- 시나리오 갱신은 `version + 1`, `updated_at` 갱신(기대 버전 검사 없이 — 가져오기가 권위). 모니터링 PC에서 그 시나리오 편집기를 열어 둔 채였다면 저장 시 기존 버전 충돌 경로가 알린다.
- 분석·결정 적용 계획은 **DB를 읽지 않는 순수 함수**(입력 = 검증된 파일 + PC 쪽 관련 행 스냅샷 + 결정)로 두고 표 테스트로 잠근다. DB 읽기·쓰기는 그 바깥 얇은 층.
- migration 없음.

### 4.6 내보내기

- `board_ids` 순서대로 보드를 읽고, 칸의 `scenario_id`·`environment_id`를 모아 PC에서 읽는다. 칸이 PC에 없는 시나리오·환경을 가리키면 400 "보드 '<이름>' 칸 N: 시나리오가 없습니다".
- **자기 검증**: 만든 파일에 §4.2 R1~R7을 그대로 돌려, 실패하면 파일을 내주지 않고 400 + 같은 사유(예: 1b 이전에 저장돼 허용 문법 밖 경로를 가진 보드, `config_json`이 깨져 칸 0개로 읽힌 보드 — `store/monitor_boards.rs:23-27`). 모니터링 PC에서 처음 알게 되는 일을 내 자리에서 막는다.
- 응답은 JSON(파일 이름은 UI가 정한다, §2).

## 5. UI (`ui/src`)

모든 문구는 `ko.ts`(`ko.monitor` 아래 새 하위 묶음) 경유(ADR-0035). 새 컴포넌트는 `ui/src/components/monitor/`. 파일 읽기는 기존 `api/readTextFile`(jsdom에 `File.text()` 없음).

### 5.1 보드 목록 (`pages/MonitorListPage.tsx`)

- 표 맨 앞에 선택 체크박스 열(머리에 전체 선택, 접근명 "모든 보드 선택" / 행마다 "'<이름>' 선택").
- 머리 줄 [새 보드] 옆에 [선택한 보드 내보내기 (N)](선택 0개거나 50개 초과면 비활성 — 50개 초과면 버튼 옆에 "한 번에 50개까지 내보낼 수 있습니다")와 [파일에서 가져오기].
- 안내 한 줄(내보내기 버튼 근처): "환경 값(비밀번호·토큰 포함)이 그대로 파일에 담깁니다. 파일 보관에 주의하세요."
- 목록이 비어 있어도 [파일에서 가져오기]는 보인다(모니터링 PC의 첫 화면이 빈 목록 — US1).

### 5.2 보드 설정 화면 (`pages/MonitorEditPage.tsx`)

- 하단 동작 영역(`#monitor-actions`)에 [파일로 내보내기] + 같은 안내 문구.
- 저장 안 한 수정(`dirty`, 또는 아직 저장 안 한 새 보드)이 있으면 대화창: 제목 "저장되지 않은 내용"(`Modal`은 `title` 필수 — `components/Modal.tsx:18`), 본문 "저장되지 않은 내용이 있습니다. 저장 후 내보내시겠습니까?", [취소] [저장 후 내보내기].
  - [저장 후 내보내기] = 기존 저장 경로(`valid()`·`persist`·`adopt`·`markFromServer`)를 성공/실패를 돌려주는 형태로 정리해 재사용(지금 `onSave`는 값을 돌려주지 않고 오류를 삼킨다 — plan에서 리팩터) → 성공하면 그 보드 하나를 내보내기. 실패하면 대화창을 닫고 기존 저장 오류 표시(칸 자동 펼침 포함)만 남기며 **파일은 만들지 않는다**. 새 보드를 처음 저장하는 경우 기존처럼 `/monitors/{id}`로 주소가 바뀌어도 내보내기는 저장 결과의 ID로 계속한다.
  - 수정이 없으면 대화창 없이 바로 내보낸다.

### 5.3 가져오기 흐름 (`ImportBoardsDialog` — 이름은 plan 재량)

1. [파일에서 가져오기] → 숨은 `<input type=file accept=".json,application/json">`(`YamlFileActions`의 숨김 트리플가드 패턴) → `file.size > 32 MiB`면 "파일이 너무 큽니다(최대 32MB)." → `readTextFile`.
2. `analyze` 호출(본문 = 파일 텍스트 그대로). 400이면 오류 대화창에 서버 사유 + [닫기], 413이면 1단계의 크기 문구. PC 변경 없음(US5).
3. 겹치는 보드가 0개면 바로 `import`(결정 없음, 지문 포함) → 결과(5단계).
4. 겹치는 보드가 있으면 목록 순서대로 하나씩 질문 대화창(`Modal` — ESC·바깥 클릭 = [취소]):
   - 제목: 보드가 PC에 있으면 "이미 있는 보드: '<pc_name>'", 없으면 "내용이 다른 시나리오·환경을 쓰는 보드: '<name>'". 겹침 2개 이상이면 앞에 "겹치는 보드 i/N · ".
   - 본문: 시나리오·환경 목록 — 각 줄 `시나리오 '결제 흐름': 변경 없음 | 내용 다름 | 이 PC에 없음(새로 추가)`. `내용 다름`이면 아래에 "이 시나리오를 쓰는 다른 보드: '주간 점검'", `breaks_other_boards`가 있으면 "덮어쓰면 설정 오류가 되는 보드: '주간 점검'"(경고색). **앞 질문에서 [덮어쓰기]로 이미 바뀌기로 한 리소스**는 "앞에서 고른 [덮어쓰기]로 파일 내용으로 바뀝니다"로 표시하고, 그 리소스 때문에만 겹침이던 보드는 사실상 질문할 것이 없어도 그대로 묻는다(단순성 — 결과는 J4대로). `warnings`가 있으면 맨 아래 작은 글씨.
   - 버튼과 그 바로 아래 결과 문구:
     - [덮어쓰기] — 보드가 PC에 있고 `enabled`면 "점검 중인 보드 '<pc_name>'은 새 설정으로 바로 다시 시작됩니다.", 있고 꺼져 있으면 "기존 보드 설정을 바꿉니다(지금 점검 중 아님).", 없으면 "보드를 추가하고, 내용이 다른 시나리오·환경은 파일 내용으로 바꿉니다."
     - [보드만 덮어쓰기] — `different`가 있을 때만. "이 PC의 시나리오·환경은 그대로 두고 보드 설정만 바꿉니다."(보드가 PC에 없으면 "보드만 추가하고 …"). 허용 안 되면 비활성 + `board_only_reason`(`aria-describedby` 연결).
     - [새 보드로 추가] — 보드가 PC에 있으면 "기존 보드는 그대로 두고 점검도 계속됩니다. 새 보드는 꺼진 상태로 추가되고, 내용이 다른 시나리오·환경은 복사본으로 만듭니다.", 없으면 "보드를 꺼진 상태로 추가하고, 내용이 다른 시나리오·환경은 복사본으로 만듭니다."
     - N ≥ 2이면 [모두 덮어쓰기] [모두 새 보드로 추가] — 현재 포함 남은 겹침 보드 전부에 그 결정을 주고 질문을 끝낸다. [모두 덮어쓰기]는 `overwrite`. 건너뛰는 질문의 경고가 묻히지 않도록 [모두 덮어쓰기] 아래 문구에 남은 보드들의 합산 정보를 싣는다: "남은 보드 k개를 모두 덮어씁니다. 바로 다시 시작되는 보드: '…'. 덮어쓰면 설정 오류가 되는 보드: '…'."(해당 없는 문장은 생략).
     - [취소] — 아무것도 보내지 않는다(PC 변경 없음 — US4).
   - 마지막 결정 후 `import` 호출. 409면 사유 + [닫기], 400이면 사유.
5. 결과: 목록 화면 위 성공 Callout — "보드 N개 가져옴(새로 a · 덮어씀 b · 보드만 c · 복사 d)"에서 **0인 항목은 생략**(US1 = "보드 2개 가져옴(새로 2)"), 시나리오·환경 요약 한 줄(0 생략), `renamed` 항목(문구는 `reason`별 — `name_taken` "이름이 겹쳐 '운영 (2)'로 추가" / `kept_pc_name` "파일의 이름 '…'이 다른 항목과 겹쳐 이 PC 이름 '…' 유지"), 다시 시작된 보드, `overridden_board_only`, 보드별 `warnings`. 목록 쿼리 무효화. 보드 이름은 각 보드 설정 화면 링크.

### 5.4 다운로드 시점 (수용한 위험)

목록·설정 화면 내보내기는 클릭 → POST → `downloadText` 순서다. `showSaveFilePicker`는 클릭의 사용자 활성화(약 5초)가 필요한데, 로컬 컨트롤러 POST는 그보다 훨씬 빨라 정상 경로에선 문제없다. 설정 화면의 "저장 후 내보내기"는 저장 + POST 두 번이라 더 길지만 여전히 로컬 왕복이다. 활성화를 잃으면 `downloadText`가 blob 링크로 내려가며, 오프라인 PC의 Chrome은 이를 막을 수 있다(`downloadJson.ts:11-14`). 내보내기는 보통 온라인인 QA 자리 PC에서 하므로 **수용**하고, 라이브 검증에서 실제로 파일이 생기는지 확인한다.

## 6. 보안

- 파일에 환경 값이 평문으로 담긴다(사용자 결정). 기존 환경 API가 이미 같은 값을 UI에 주므로 새 노출 경로는 아니지만, 파일은 PC 밖으로 나가는 **새 sink** → 내보내기 근처 안내 문구로 알린다. 분석 응답에는 `vars` 값을 싣지 않는다(§4.3).
- 가져온 보드 설정은 반드시 `validate_and_normalize` 통과(R7) — `judge`는 실행 시 경로를 재검사하지 않으므로 이 검사가 유일한 방어(§B38 (3)). 모르는 키 거부(§2.1)로 새 필드가 검사를 우회해 들어오는 일도 없다.
- 가져온 시나리오는 시나리오 생성 API와 같은 검사(R5). 요청 대상 URL은 기존 시나리오 생성과 같은 신뢰 수준(사내 QA 도구) — 단 security-reviewer 게이트는 finish-slice §0 grep대로 실행.
- 32 MiB 본문 상한·보드 50개·칸 9개·조건 10개 상한으로 분석 비용이 묶인다.
- 서버 오류 사유에 파일 속 값(특히 환경 값)이 섞이지 않게 한다 — serde 오류는 위치만(R0·R2'), `validate_env` 사유는 키 이름까지만(현재 문구가 이미 그렇다).

## 7. 판단 (사용자 결정 / 내 판단 구분)

사용자 결정: 환경 값 평문 이전 · 덮어쓰기/새 보드 선택 · 덮어쓰기는 묻지 않고 즉시 재시작하되 미리 알림 · 버튼 아래 결과 문구로 오해 방지 · 저장 후 내보내기 대화창 · 여러 보드 선택 내보내기 · 겹침 없으면 자동 추가·겹침은 하나씩 + [모두 덮어쓰기]·[모두 새 보드로 추가] · [보드만 덮어쓰기] 명시 버튼 · 같은 내용 시나리오·환경 재사용.

내 판단:
- **J1 ID 보존** — 처음 가져올 때 원래 ID를 써서 두 번째부터 "같은 것"을 ID로 찾는다. `new`도 보드 ID가 PC에 없으면 보존.
- **J2 같음 판정 = ID + 내용**(시나리오 YAML 문자열 / 환경 `vars`, 환경 이름은 비교 안 함). 이름 기반 매칭 기각.
- **J3 덮어쓸 시나리오의 영향 표시는 다른 보드만**(사용 중·깨짐) — 예약 실행·프리셋은 표시 안 함.
- **J4 공유 리소스는 덮어쓰기가 이긴다**(§3.2) — 질문 화면에서 미리, 결과에서 다시 알림.
- **J5 시나리오 복사본은 `serde_yaml::Value`로 `name`만 교체** — 주석은 사라짐(수용; YAML 탭은 주석을 보존하므로 주석을 쓴 시나리오의 *복사본*만 해당).
- **J6 끊긴 스텝 참조는 거부하지 않고 경고** — 사용자에게 "스텝이 있는지 확인한다"고 말한 부분을 "경고로 알린다"로 조정(그대로 옮기기 목표와 충돌). `board_only` 판정에는 그대로 쓴다.
- **J7 행마다 내보내기 버튼 대신 체크박스 선택**.
- **J8 보드에 안 쓰이는 시나리오·환경이 든 파일은 거부**(후속 시나리오 내보내기 슬라이스가 완화).
- **J9 결과 후 화면은 목록 유지 + 결과 Callout**.
- **J10 겹침 = 보드 ID 존재 ∨ 내용 다른 리소스**(§3.1).
- **J11 갱신 행의 이름은 충돌 시 PC 이름 유지**(§3.3) — 반복 가져오기에서 이름이 흔들리지 않게.
- **J12 모르는 키는 거부, `format_version`은 구조·의미 변경 때만**(§2.1) — 귀결: 보드 설정 필드가 추가된 버전의 파일은 옛 모니터링 PC에서 거부(업데이트 필요).
- **J13 `import` 본문은 파일 텍스트를 그대로 끼워 만든다**(§3.5) — 재직렬화 차이로 지문·내용이 어긋나는 것을 막는다.

- **라이브(필수 — 새 API 응답 파싱 경로, S-D)**: 컨트롤러 2개를 **서로 다른 DB·포트**로 띄워 "내 자리 PC"·"모니터링 PC"를 흉내 낸다. US1~US5를 그대로 수행:
  - US1: A에서 보드 2개(시나리오 공유) 내보내기 → 빈 B에 가져오기 → 질문 0 · "보드 2개 가져옴(새로 2)" · B의 시나리오 1개 · 보드 켜고 점검 판정이 A의 미리 실행과 같음.
  - US2: A에서 조건만 수정 → 재내보내기 → B(보드 켜짐)에 가져오기 → "점검 중인 보드 … 바로 다시 시작" · 시나리오 "변경 없음" · 덮어쓴 뒤 새 조건 판정.
  - US3: A에서 시나리오에 스텝 추가 + 그 스텝 조건 → B에 가져오기 → [보드만 덮어쓰기] 비활성+사유 · [새 보드로 추가] → B의 기존 보드 계속 점검 · "결제 흐름 (2)" 생성 · 같은 환경은 새로 안 생김.
  - US4: 겹침 3개 → 1/3 → [모두 새 보드로 추가] / 별도 시도에서 [취소] 후 B 행 수 불변.
  - US5: 허용 안 되는 경로를 손으로 넣은 파일·`format_version: 2` 파일·모르는 키 파일·깨진 JSON → 각각 사유, B 행 수 불변 · 설정 화면 dirty 상태 내보내기 대화창 · 저장 실패 시 파일 없음.
  - 극단값(사용자 지시): 보드 이름 40자 + 접미사 · 질문 화면에 다른 보드 이름 여러 개·긴 시나리오 이름·경고 여러 줄 — 대화창 안 겹침·잘림 없음을 rect로 실측. 목록·설정 화면 두 진입점 모두.
