# if 판정 줄 상한 — 요청 없이 판정만 도는 시나리오가 컨트롤러를 잡아먹지 않게 (if-judge-row-cap)

- 상태: 설계
- 날짜: 2026-11-14 · 유형: `correctness-bug`(선재, 보안 리뷰 P1) · 출처: roadmap §B58 (0)·(2) "if 판정 행 무제한"
- 범위: 엔진 `crates/engine/src/trace.rs`(시험 실행·모니터가 쓰는 단일 패스 trace) + 컨트롤러 모니터 사유 2곳 + UI 문구·사유 표. 부하 run 경로(`runner.rs`)·proto·마이그레이션·trace 와이어 모양 무변경.

## 사용자 스토리 (US)

사용자 승인 2026-11-14(start-slice 브레인스토밍). 승인 뒤 바뀐 문장은 §8에 모아 사용자 확인을 받는다(US1의 상한 숫자, US3 문장, US4의 범위 한정).

- **US1**: QA가 요청 없이 조건 분기만 도는 시나리오(예: 100만 번 반복 안에 항상 거짓인 if)를 시험 실행할 때 — 성공하면 곧 끝나고, if 판정 줄은 상한까지만 나오며(요청 상한 50이면 1,000줄) "잘림" 안내가 뜬다. 컨트롤러 메모리 증가는 요청 상한에 비례하는 예산에 묶인다(요청 상한 50에서 수 MB).
- **US2**: 운영자가 판정 줄 상한에 닿는 시나리오가 걸린 모니터 패널을 볼 때(보드·TUI) — 성공하면 그 점검이 `판정 줄 상한 초과` 사유로 실패한 것을 본다. 조건 반복 판정 줄 상한(200)에 닿은 경우도 같은 사유다(지금은 `시간 초과(N초)`).
- **US3**: QA가 본문이 아무것도 하지 않는 반복(빈 `do`, 큰 `repeat`)을 시험 실행할 때 — 성공하면 곧 끝나고(잘림 아님), 그런 시험 실행이 여러 개 돌아도 다른 화면의 API가 밀리지 않는다. 모니터에 걸린 경우도 시간 제한까지 붙잡지 않고 곧 끝난다.
- **US4**: QA·운영자가 어느 판정 줄 상한에도 닿지 않고 무진행 회차도 없는 기존 시나리오를 시험 실행하거나 모니터에 걸어 둘 때 — 성공하면 결과가 이전과 같다(잘림·새 사유 없음). 요청 상한을 크게 잡은 데이터 순차 실행(행마다 if 몇 개)도 여기에 든다.

## 1. 재현 / 실측 (2026-11-14, 이 브랜치 baseline = master `5cea1bac`, debug 빌드, 12코어 맥)

격리 컨트롤러(`./target/debug/controller --db <scratch>/repro.db --rest 127.0.0.1:8197 --grpc 127.0.0.1:8196`)에 `POST /api/test-runs`(`max_requests: 50`).

### 1.1 if 판정 줄 무제한

```yaml
version: 1
name: ifspin
steps:
  - id: "01HX0000000000000000000001"
    name: spin
    type: loop
    repeat: 1000000
    do:
      - id: "01HX0000000000000000000009"
        name: never
        type: if
        cond: { left: "1", op: eq, right: "2" }
        then: []
```

| 항목 | 실측 |
|---|---|
| 응답 | 200, **312,888,974바이트**, 11.5초 |
| `steps` 길이 | **1,000,000** · `truncated: false` |
| 컨트롤러 RSS | 24,624 KB → **798,624 KB** |

요청이 0건이라 `max_requests`가 안 걸리고, trace 1.39초라 시간 제한(120초)도 안 걸린다. `repeat`를 키우면 그만큼 는다.

### 1.2 본문이 빈 반복

```yaml
version: 1
name: emptyspin
steps:
  - id: "01HX0000000000000000000001"
    name: spin
    type: loop
    repeat: 4000000000
    do: []
```

| 항목 | 실측 |
|---|---|
| 평소 `GET /api/scenarios` | 0.001초 |
| 위 시험 실행 12개(코어 수)를 띄운 2초 뒤 같은 GET | **15초 제한에 걸려 응답 없음**(http 000) |
| 시험 실행 클라이언트가 전부 끊긴 뒤(20초 제한) 컨트롤러 CPU | **약 1,040%** — 계속 돈다 |

원인: `trace_steps`의 while 없는 loop 가지에는 본문에 요청이 없으면 `.await` 지점이 없다. 실행기 스레드를 시간 제한(시험 실행 120초, 모니터는 패널 제한 시간)까지 쥐고, 클라이언트가 끊겨도 future가 버려질 틈이 없다.

### 1.3 모니터 사유가 틀림 (코드 읽기)

`check.rs`·`step_judge.rs`의 잘림 사유는 "요청 줄 ≥ 50이면 `요청 수 상한(50) 초과`, 아니면 `시간 초과(N초)`" 두 갈래뿐이다. 조건 반복 판정 줄 상한(200, `MAX_LOOP_JUDGE_ROWS`)으로 잘린 trace는 지금도 `시간 초과`로 찍힌다.

### 1.4 줄 수만 묶어서는 메모리가 안 묶인다 (코드 읽기 — 리뷰 적발)

if 판정 줄은 조건 원문을 줄마다 복사한다(`condition.rs` `LeafEval.left`/`right`는 원문 그대로, 200자 상한은 `left_value`/`right_value`만). 분기(elif) 수만큼 `BranchEval`이 붙고 `unbound_vars`도 상한이 없다. `/test-runs` 본문 상한은 axum 기본 2 MB라, 2 MB 가까운 조건 하나를 1,000번 판정하면 줄 수 상한 안에서도 GB 단위가 된다. 조건 반복 판정 줄(`while` 조건)도 같은 구조다.

## 2. 엔진 — `trace.rs`

### 2.1 if 판정 줄 수 상한 (US1·US4)

- 상한은 요청 상한에 비례한다: `pub fn if_judge_row_cap(max_requests: u32) -> u32 { max(1000, max_requests × 10) }`(포화 곱).
  - 시험 실행 기본·모니터(요청 상한 50) → 1,000줄. 시험 실행 최대 입력(10,000) → 100,000줄.
  - 고정 1,000이 아닌 이유: 시험 실행 요청 상한은 화면에서 10,000까지(설정 `max_test_run_requests`로 100,000까지) 올릴 수 있고, 순차 데이터 실행은 예산을 행 사이에 공유한다. 고정이면 "1,001행 × 행마다 if 1개" 같은 정상 실행이 새로 잘린다(US4 위반, 에디터 검증 표시 `markVerified`도 `!truncated`를 요구).
  - 배수 10의 근거: 요청 1건당 if 10개까지는 정상으로 본다. 이미 trace 메모리는 요청 상한에 비례하도록 설계돼 있다(요청마다 본문 1 MiB까지). 틀렸을 때 비용: 요청 1건당 if가 10개를 넘는 큰 실행이 잘린다 → 배수 상수 한 곳.
- `TraceState.if_rows: u32`. `Step::If` 가지의 **맨 앞**(조건 평가 3종보다 먼저)에서 `if_rows >= cap`이면 `state.truncated = true; return;`. 아니면 지금처럼 평가·줄 추가 후 `if_rows += 1`.
- 경계: 정확히 상한 번째 줄까지 넣고 시나리오가 끝나면 `truncated`가 아니다(조건 반복 상한의 경계 규칙과 같음).
- 예산 범위: `judge_rows`·`max_requests`처럼 **한 시험 실행 전체**(순차 데이터 행 사이에 초기화하지 않음).
- 조건 반복 예산(200, `MAX_LOOP_JUDGE_ROWS`)과 **합치지 않는다**. 조건 반복 상한 자체는 이번에 안 바꾼다(요청 상한에 비례하지 않는 것은 선재 — §7).

### 2.2 판정 줄 바이트 예산 (US1 — §1.4)

- 판정 줄(if 줄 + 조건 반복 판정 줄)을 넣을 때마다 그 줄의 **어림 바이트**를 `TraceState.judge_bytes: u64`에 더한다. 어림 = 줄의 가변 글자 UTF-8 바이트(`str::len`) 합(`step_id`·`branch`·`unbound_vars` 각 이름·`branch_eval`의 `branch`와 잎의 `left`·`right`·`left_value`·`right_value`) + 줄당 고정 64 + `BranchEval`당 고정 32.
- 예산: `pub fn judge_byte_budget(max_requests: u32) -> u64 { (if_judge_row_cap(max_requests) + MAX_LOOP_JUDGE_ROWS) × 4096 }`. 요청 상한 50 → 약 4.7 MiB. 줄당 평균 4 KiB까지는 줄 수 상한이 먼저 닿는다(§1.1의 줄은 약 313바이트). 요청 상한에 비례해 커진다: 요청 상한 10,000 → 약 410 MB, 설정 최대 100,000 → 약 4.1 GB(요청마다 응답 본문 1 MiB까지 담는 기존 설계와 같은 규모). 와이어 크기는 JSON 이스케이프 때문에 어림보다 클 수 있다(제어 문자 하나가 6바이트).
- 검사 위치: 줄을 넣은 **뒤** `judge_bytes > budget`이면 `state.truncated = true; return;`(넘긴 그 줄은 남는다). 넣은 뒤에 보는 이유: 합이 예산을 넘은 것이 trace에 남아야 §3이 줄만 보고 "바이트로 잘렸다"를 알 수 있다. 초과분은 줄 하나이고, 줄 하나의 크기는 시나리오 YAML 크기로 묶인다 — 시험 실행·시나리오 저장은 본문 상한 2 MB, 보드 파일 가져오기는 32 MB(시나리오별 크기 검사 없음 — §7).
- 줄 내용은 건드리지 않는다(원문을 자르면 정상 시나리오의 시험 실행 표시가 달라진다). 예산 안의 trace는 이전과 글자까지 같다.
- 어림 함수는 엔진에 하나만 둔다(`pub fn judge_row_bytes(&StepTrace) -> u64`). §3이 같은 함수를 쓴다.

### 2.3 진행 없는 반복 끊기 + 양보 지점 (US3)

- **끊기**: while 없는 loop 가지에서 회차 본문 재귀 앞뒤로 `(state.steps.len(), state.requests)`를 비교해 둘 다 그대로면 남은 회차를 돌지 않고 loop을 빠져나온다. `truncated`는 세우지 않는다.
  - 근거: 줄도 요청도 안 생긴 회차는 http를 하나도 안 돌았다. 그 회차가 한 일은 parallel 병합(같은 이름에 같은 값을 다시 넣기)뿐이라 다음 회차도 같은 무진행이다. `${loop_index}`는 렌더되지 않았다.
  - 한계(수용): 손 YAML로만 만들 수 있는 두 경우에서 건너뛴 결과가 다를 수 있다 — ① parallel 분기의 추출 이름에 점이 든 경우(`A.x`를 다른 분기가 다시 내보내 회차마다 `B.A.x`류 이름이 하나씩 는다), ② parallel 분기마다 요청 단위 생성기가 씨앗을 한 번씩 뽑는 것(관찰 불가 — 씨앗이 엔트로피). UI는 parallel 분기에 http만 두므로 UI로 만든 시나리오는 해당 없음. 엔진 CLAUDE.md에 한 줄.
  - 이 규칙으로 while 없는 loop의 모든 회차는 요청 또는 판정 줄을 하나 이상 만든다 → 회차 수가 상한들로 묶인다. 중첩(`4e9 × 4e9 × []`)도 안쪽·바깥 모두 1회차에서 끊긴다.
- **양보**: `tokio::task::yield_now().await`를 ① `Step::If` 가지 맨 앞(상한 검사 직후), ② while 없는 loop의 회차마다(진행이 있었던 회차 뒤), ③ while 있는 loop의 회차마다(판정 줄을 넣은 뒤) 넣는다.
  - ②가 필요한 경우: 보내기 전에 실패하는 http(값이 빈 `{{base}}`로 상대 주소가 된 요청, 잘못된 헤더 값)는 `send().await`가 멈추지 않고 바로 에러를 돌려준다. 그런 요청만 든 loop은 회차마다 줄을 만들지만(진행 있음) 양보가 없다. 회차 수는 요청 상한으로 묶인다.
  - 이유: 끊기는 회차 **수**를 묶지만 회차 하나의 **값**은 못 묶는다. if 줄 하나가 조건을 3–4번 렌더하고 `matches`는 평가마다 정규식을 다시 컴파일한다(선재, §B58 (2)). 큰 조건·비싼 정규식이면 줄 1,000개가 실행기 스레드를 초 단위로 쥘 수 있다.
  - 양보 지점이 있으면 클라이언트가 끊겼을 때 future가 버려지고, 모니터의 바깥 `tokio::time::timeout`도 동작한다. trace는 hot path가 아니다(부하 run의 조건 반복 가지에 같은 선례 — `runner.rs` `yield_now`).
- while 있는 loop은 회차 수가 이미 상한 200에 묶여 있어 끊기 규칙은 넣지 않고 ③의 양보만 더한다(빈 본문 + 비싼 `while` 조건이 200회차 동안 `.await` 없이 도는 것을 막는다 — 회차마다 조건을 두 번 평가).

### 2.4 순차 데이터 행 시작 검사

- `trace_scenario_rows`의 "행 시작 전 예산 소진 → 이 행부터 미실행" 검사에 판정 줄 수 예산 2종(if 줄 수, 조건 반복 줄 수)을 더한다. 바이트 예산은 더하지 않는다 — 바이트는 넘기는 순간 그 행이 잘려 지금의 `mid_cut → break`로 이미 멈춘다.
- 이유: 안 더하면 판정 줄 예산이 **정확히 바닥난 채 끝난 행**(잘리지 않음) 다음 행들이 if 앞의 요청을 보내고 잘린 행으로 남는다. `max_requests`와 같은 규칙으로 맞춘다. (예산을 **넘겨서** 잘린 행은 지금도 그 행에서 멈춘다 — `mid_cut → break`.)
- 조건 반복 줄 수 쪽은 기존 동작 변경이다(지금은 200줄째가 `done`으로 끝난 행 다음 행들이 조건 반복 앞까지 돌고 잘림). 같은 개념이라 같이 맞춘다. 비용: 그 경우 뒤 행들이 "잘린 행" 대신 "미실행"으로 보인다.

### 2.5 그대로인 것 (R0)

- **어느 판정 줄 상한(if 줄 수·조건 반복 200·바이트)에도 닿지 않고 무진행 회차가 없는** 시나리오의 `ScenarioTrace`/`RowsTrace`는 이전과 같다(필드·순서·값).
- 달라지는 것(전부 의도): ① if 줄 수·바이트 상한에 닿는 시나리오는 `truncated` ② 조건 반복 상한에 닿은 trace의 모니터 사유(§3)와 순차 실행의 뒤 행(§2.4) ③ 무진행 반복만 있는 시나리오는 곧 끝나고 `truncated` 아님 — 모니터에서는 예전에 `시간 초과`로 실패하던 것이 trace의 나머지 내용대로 판정된다. 요청이 0건인 시나리오라면: 전체 시간 기준 패널은 **정상**(잘림·에러 없음, 응답 시간 = 전체 시간)으로 보이고, 조건이나 스텝 기준 시간을 쓰는 패널은 `조건 스텝 미실행`·설정 오류로 보인다. 빈 반복은 원래 아무 요청도 안 보내는 시나리오라 "아무것도 안 하고 정상 종료"가 사실에 맞다.
- `ScenarioTrace`에 필드를 더하지 않는다. TUI 와이어 거울이 `deny_unknown_fields`라 필드 추가는 TUI 파싱을 깬다. 어느 상한인지는 줄에서 다시 계산한다(§3).
- `execute_steps`(부하 run)는 판정 줄을 쌓지 않으므로 상한 대상이 아니다. 빈 반복의 스레드 점유는 부하 run에도 있을 수 있다 — §7 연기.
- 고칠 문서 주석: `TraceOptions.max_requests`·`max_wall`과 `ScenarioTrace.truncated`의 주석("max_requests 또는 시간")에 판정 줄 상한을 더한다.

## 3. 모니터 사유 (US2)

- 새 상수 `pub const REASON_JUDGE_ROW_CAP: &str = "판정 줄 상한 초과";`(`check.rs`).
- 엔진에 판정 도우미 하나: `pub fn judge_rows_exhausted(steps: &[StepTrace], max_requests: u32) -> bool` — if 줄 수 ≥ `if_judge_row_cap` **또는** 조건 반복 줄 수 ≥ `MAX_LOOP_JUDGE_ROWS` **또는** 판정 줄 어림 바이트 합 > `judge_byte_budget`. 상수·함수는 `handicap_engine::trace::…` 경로로 쓴다(`lib.rs`에 다시 내보내거나 경로로 직접).
- 잘림 사유를 고르는 두 곳(`check.rs` 흐름 판정, `step_judge.rs` 규칙 5)이 컨트롤러 도우미 하나를 쓴다. 순서:
  1. 요청 줄 수 ≥ `MONITOR_MAX_REQUESTS` → `요청 수 상한(50) 초과` (지금과 같음)
  2. `judge_rows_exhausted(&trace.steps, MONITOR_MAX_REQUESTS)` → `판정 줄 상한 초과`
  3. 그 외 → `시간 초과(N초)` (지금과 같음)
- 판정은 가공 전 trace로 한다(보관 기록은 `build_record_body`가 `branch_eval`을 비우므로 바이트가 달라진다 — 판정 뒤에 가공하는 지금 순서 그대로).
- 알려진 어긋남(수용): 판정 줄이 정확히 상한 개수인 채로 시간 제한에 잘리면 2번으로 찍힌다. 판정 줄이 상한까지 찼다는 것 자체가 같은 고장이라 사유로서 틀리지 않다.
- 폭: `판정 줄 상한 초과`(한글 7 + 공백 3)는 기존 최장 `응답 시간 기준 스텝 없음`(한글 10 + 공백 4)보다 짧다 → 보드 사유 글자 크기 불변. `ui/src/monitor/reasons.ts` `WIDEST_REASON_CANDIDATES`에 한 줄 추가(동기 유지 규칙).
- TUI는 사유를 와이어 글자 그대로 그린다(사유 표 없음) → TUI 코드 변경 없음.
- 사유 우선순위는 지금과 같다: `truncated`가 `ended_by_loop`·스텝 에러보다 앞.

## 4. 시험 실행 화면 문구

- `TestRunPanel.tsx`의 잘림 안내 `상한 도달 — 일부만 실행됨 (max_requests 또는 시간 천장)`은 원인을 둘만 적는다. 판정 줄 상한(기존 200 포함)으로 잘려도 이 문구가 뜨므로 사실과 다르다 → `상한 도달 — 일부만 실행됨 (요청 수·판정 줄 수 또는 시간 상한)`으로 바꾸고 `ko.ts` 경유로 옮긴다(ADR-0035).
- 순차 실행 패널(`seqTruncated`·`seqRowTruncated`)과 모니터 기록(`recordTraceCut`, TUI `RECORD_TRACE_CUT`)은 원인을 적지 않는 문구라 그대로.
- `docs/dev/ui-area-c-manual-check.md`의 옛 문구 인용 1곳을 같이 고친다.

## 5. 테스트 (이빨 실증 포함)

엔진(`trace.rs` 인라인, 요청 상한 50 → if 상한 1,000):
- if 줄 수 상한: §1.1 시나리오 → if 줄 정확히 1,000 · `truncated` · 5초 안. **이빨**: 상한 검사를 지우면 RED.
- 경계: `repeat: 1000` + 항상 거짓 if → 1,000줄 · `truncated` 아님. `repeat: 1001` → 1,000줄 · `truncated`.
- 비례: `if_judge_row_cap(50) == 1000`, `(10_000) == 100_000`, `(u32::MAX)` 포화. 요청 상한 200으로 if 1,500줄 시나리오 → `truncated` 아님.
- 바이트 예산: 조건 원문이 큰(수십 KB) if를 반복 → 줄 수 상한 전에 `truncated`, 줄 어림 합이 예산 + 줄 하나 이하. 조건 반복 `while` 조건이 큰 경우도 같다. **이빨**: 바이트 검사를 지우면 RED.
- 무진행 끊기: §1.2 시나리오 → `max_wall`보다 훨씬 빨리 끝남 · `steps` 0 · `truncated` 아님 · `ok`. **이빨**: 끊기를 지우면 RED(테스트 `max_wall`은 짧게).
- 끊기가 발동하면서 병합 결과가 남음: `loop repeat: 4000000000 → parallel{ A: [loop repeat: 0 [http extract x]] }` + 변수 `x`, 짧은 `max_wall` → `truncated` 아님 · `max_wall`보다 훨씬 빨리 끝남 · `final_vars["A.x"] == x`. **이빨**: 끊기를 지우면 RED(시간 제한에서 잘림).
- while 양보: 빈 본문 + 항상 참 `while` → 판정 줄 200 · `truncated`(기존 동작) — 양보를 넣어도 결과가 같다.
- 양보 지점 자체: `crates/engine/tests/loop_while.rs`의 `cond_loop_no_request_body_yields_to_other_tasks` 방식(단일 스레드 런타임 + 카운터를 올리는 옆 task + 카운터가 올랐다는 단언)으로 If 가지 양보·while 없는 loop 회차 양보(보내기 전에 실패하는 http 본문)·while 회차 양보를 각각. **이빨**: 해당 양보를 지우면 RED.
- 진행 있는 loop은 안 끊김: http가 든 loop·if가 든 loop의 회차 수가 `repeat`과 같다.
- 순차(정확한 경계 픽스처): 1행이 if 줄 정확히 상한 개수로 **잘리지 않고** 끝나고, 2행은 http로 시작 → 2행이 `rows`에 없고 2행의 요청이 나가지 않았다. 조건 반복 쪽: 1행이 판정 줄 정확히 200개(마지막 `done`)로 끝남 → 2행 미실행. **이빨**: §2.4를 되돌리면 RED(2행이 요청을 보내고 잘린 행으로 남음).
- R0: 기존 판정 줄 테스트(`trace_judge_rows_capped*`·`…boundary_done_is_not_truncated`) 그대로 통과.

컨트롤러(`check.rs`·`step_judge.rs` 인라인):
- if 줄 1,000 + `truncated` → `판정 줄 상한 초과`(흐름 판정·스텝 판정 양쪽).
- 조건 반복 줄 200 + `truncated` → 같은 사유.
- 바이트 예산 초과 + `truncated` → 같은 사유.
- 요청 줄 50 + if 줄 1,000 → `요청 수 상한(50) 초과`(순서).
- 판정 줄이 상한 미만 + `truncated` → `시간 초과(N초)`(기존 테스트 유지).

UI: `reasons.test.ts`의 최장 사유 불변 단언 유지. 잘림 안내 테스트는 글자 조각 `판정 줄`을 리터럴로 단언한다(기존 `/상한 도달/` 정규식은 새 문구도 통과해 변화를 못 잡고, `getByText(ko.x)`는 자기 참조).

## 7. 비목표 · 연기

- **부하 run(`runner.rs`)의 빈 반복**: while 없는 loop 가지에 양보 지점이 없다(조건 반복 가지에는 `yield_now`가 있음). 워커 프로세스 안이라 컨트롤러는 안 죽지만 그 워커의 실행기 스레드를 run 끝까지 쥘 수 있다(코드 읽기, 미실행). 부하 경로는 hot path라 A/B 측정이 필요해 이번에 안 한다 → roadmap §B 연기 항목으로 기록(해소: plain loop 회차에 `yield_now` + 처리량 A/B).
- **조건 반복 판정 줄 상한(200)이 요청 상한에 비례하지 않는 것**(선재): 요청 상한을 크게 잡은 순차 실행에서 조건 반복이 합계 200회를 넘으면 잘린다. 이번에 안 바꾼다 → §B 기록(해소: `if_judge_row_cap`처럼 비례).
- **`matches` 정규식의 평가마다 재컴파일**(선재, §B58 (2)) — 양보 지점으로 다른 요청은 안 밀리지만 CPU는 쓴다.
- **http 줄 하나의 크기는 묶여 있지 않다**(선재): 렌더된 요청 본문은 템플릿보다 훨씬 클 수 있다(`{{big}}` 반복). 줄 수는 요청 상한으로 묶인다. 이번 범위 밖 → §B 기록.
- **보드 파일 가져오기의 시나리오 크기**(선재): 본문 상한 32 MB 안에서 시나리오별 크기 검사가 없어, 모니터에서는 판정 줄 하나가 그만큼 클 수 있다(바이트 예산 초과분 = 줄 하나). 이번 범위 밖 → §B 기록(해소: 가져오기에 시나리오별 2 MB 검사).
- 시험 실행 응답에 "어느 상한에 걸렸는지" 필드 추가 — 안 함(TUI 거울·UI Zod 변경).
- 상한값을 설정으로 노출 — 안 함.
- 시험 실행 취소 버튼 — 없음, 이번 범위 밖.
- 컨트롤러의 시나리오 구조 검증(`repeat` 상한 등) — 안 함. 손 YAML·API 직통도 엔진 상한으로 막는다.

## 8. 사용자 확인 대상 (spec 승인 때)

1. **상한이 고정 1,000이 아니라 `max(1,000, 요청 상한 × 10)`**(§2.1). 기본·모니터에서는 1,000 그대로. 요청 상한을 크게 잡은 순차 데이터 실행이 새로 잘리지 않게 하려는 것.
2. **판정 줄 바이트 예산 추가**(§2.2). 줄 수만으로는 큰 조건 원문 때문에 메모리가 안 묶인다. 예산은 요청 상한에 비례한다(요청 상한 50 → 약 4.7 MiB, 10,000 → 약 410 MB).
3. US3 문장 변경("취소가 곧 먹는다" → "곧 끝나고 다른 API가 안 밀린다"). 시험 실행 화면에 취소 버튼이 없다.
4. 양보 지점에 더해 "진행 없는 반복 끊기"(§2.3).
5. 시험 실행 잘림 안내 문구 변경(§4).
6. 부하 run 쪽 빈 반복은 연기(§7).
7. 순차 실행에서 판정 줄 예산이 정확히 바닥난 뒤의 행을 "미실행"으로(§2.4 — 조건 반복 쪽은 기존 동작 변경).
