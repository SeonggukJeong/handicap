## 사용자 스토리 (US)

사용자 승인 2026-11-12(US 초안 단독 제시 → "진행"). US4의 판정 변화(`포함` 조건)는 승인 전에 알렸다.

- **US1 (재현 / 기대 — 폭 재기)**
  - 재현: `❤️`(U+2764 U+FE0F)처럼 글자 하나씩 잰 폭과 화면에 그려지는 폭이 다른 글자가 든 값·경로를 여러 줄로 보는 화면(도움말 경로 줄, 값 고르기 선택 창 머리, 오류 자세히, 요청·응답, 값 목록의 대상 칸)에서 그 줄이 1칸 넘쳐 오른쪽 끝이 잘리거나 값 목록의 열이 밀린다.
  - 기대: 모든 줄이 주어진 폭 안에 그려지고, 줄바꿈한 줄들을 이어 붙이면 원래 글자와 같다.
- **US2 (낮은 화면)**: 운영자가 터미널 높이 5–6줄에서 값을 골라 `조건으로 추가`/`화면에 추가` 선택 창을 열 때 — 성공하면 무엇을 골랐는지(`대상 = 받은 값`)를 한 줄로 본다(넘치면 `…`). 높이 4줄 이하는 선택 줄만 남는다(한계). 비밀 안내가 붙는 선택 창은 안내가 보이는 높이(터미널 7줄)부터만 그 한 줄이 나온다 — 안내가 머리보다 오래 남는다는 tui-2b-secrets 규칙을 지킨다(§2.2-2).
- **US3 (재현 / 기대 — 대체 화면)**
  - 재현: 칸·상태를 못 찾은 하위 화면을 안내가 다 들어가지 않는 크기(예: 20열 × 본문 1–2줄 — 안내는 43칸이라 42열 이하에서 줄바꿈된다)에서 보면 안내 뒤쪽(`Esc로 돌아가세요`)이 `…` 없이 끊긴다.
  - 기대: 마지막으로 보이는 줄이 `…`로 끝난다. 확인은 단위 테스트로만(TUI 안에서 칸을 지울 길이 없다 — roadmap §B53 사용자 결정).
- **US4 (서버 숫자 표기)**: 운영자가 소수 값(`1.0`·`1e16`·`0.000001`)을 조건·표시 값으로 쓰는 칸을 볼 때 — 성공하면 화면 표시 값·실패 사유·TUI와 GUI가 채우는 비교값이 모두 같은 글자(`1`·`10000000000000000`·`0.000001`)다.
- **US5 (반올림 동률)**: 운영자가 본문 `1658206780088562.3` 같은 값을 TUI와 GUI에서 각각 조건으로 추가할 때 — 성공하면 두 보드 파일의 비교값 글자가 같다(`1658206780088562.2`).
- **조건 칸 그리기 비용**: `US: N/A` — 화면에 보이는 변화가 없는 내부 개선(§2.4).

목표

## 2. 동작 규칙 (정본)

### 2.1 폭 재기 (US1)

1. **기준**: 문자열의 폭 = ratatui `Buffer::set_stringn`이 그 문자열에 쓰는 칸 수. 곧 `UnicodeSegmentation::graphemes(s, true)`의 글자 묶음마다, 제어 문자(`char::is_control`)가 든 묶음은 0칸, 그 밖은 `ratatui::buffer::CellWidth::cell_width`의 합이다. TUI가 글자를 그리는 길(`put` → `Paragraph`)도 묶음마다 `cell_width`로 배치한다. 예외: `Block` 제목은 ratatui가 문자열 전체 폭(`Span::width`)으로 자리를 잡는다 — 지금 제목은 모두 한 조각이고 고정 문구·`fit`한 글자라 보이는 차이는 없다(§9).
2. `view/mod.rs`에 묶음과 그 폭을 내는 도우미 하나(`cells`)를 두고, `text_width`·`fit`·`wrap_width`·`view::values::fit_head` 넷이 그것만 쓴다. 글자 하나씩 폭을 재는 코드는 이 넷에서 없앤다. (구현 뒤 정정: `cells`는 앞에서부터만 돈다 — 뒤에서부터 보는 `fit_head`는 같은 칸 수 규칙(`cell_of`)을 쓰는 `cells_rev`를 쓴다.)
3. `fit(s, w)`: 폭이 `w` 이하면 그대로. `w == 0`이면 빈 글자. 아니면 앞에서부터 묶음을 넣되 넣은 폭이 `w − 1`을 넘지 않게 하고 끝에 `…`.
4. `wrap_width(s, w)`: 묶음 단위로 줄을 채운다. 다음 묶음을 넣으면 `w`를 넘고 현재 줄이 비어 있지 않으면 줄을 바꾼다. 폭 0 묶음은 줄을 바꾸지 않고 현재 줄에 붙인다. 묶음 하나가 `w`보다 넓으면 그 묶음만으로 한 줄이다. 빈 글자는 빈 줄 하나.
5. `fit_head(s, w)`: 폭이 `w` 이하면 그대로. `w == 0`이면 빈 글자. 아니면 뒤에서부터 묶음을 넣되 넣은 폭이 `w − 1`을 넘지 않게 하고 앞에 `…`. 결합 글자는 앞 글자와 한 묶음이라 `…` 바로 뒤에 결합 글자만 남는 일이 없다(옛 "경계의 폭 0 글자 버리기" 보정 삭제). (구현 뒤 정정: 틀렸다 — soft hyphen(U+00AD)·ZWSP 같은 제어 갈래 글자 뒤의 결합 글자는 홀로 서고 soft hyphen 자체도 0칸 묶음이다. `fit_head`는 잘린 자리의 **폭 0 묶음**을 버린다 — 옛 보정을 묶음 단위로 되살렸다, roadmap §B56 (1).)
6. 글자 묶음 나누기는 `unicode-segmentation`을 `crates/tui`의 직접 의존으로 선언해 쓴다(`unicode-segmentation = "1"`). ratatui가 같은 crate로 나누므로 결과가 같고, `Cargo.lock`에 이미 있는 버전이라 새로 받는 crate는 없다.
7. `view::edit::wrap_measured`와 `target_rows`의 두 보정(조기 반환 조건 중 `text_width(&s) <= fw` 쪽, 줄 폭 재검사)을 지운다. 같은 재기라 `wrap_width` 하나로 충분하다. 값 칸이 좁으면 한 줄(`fw < TARGET_WRAP_MIN_W`)은 그대로 둔다.
8. **불변식**(테스트 오라클 — §6): 임의의 문자열 `s`와 폭 `w`에 대해
   - `text_width(s)` == `Buffer::set_stringn(0, 0, s, usize::MAX, …)`이 돌려준 x.
   - `fit(s, w)`·`fit_head(s, w)`를 그린 폭 ≤ `w`.
   - `wrap_width(s, w)`의 각 줄을 그린 폭 ≤ `w`(묶음 하나가 `w`보다 넓은 줄은 예외), 줄들을 이어 붙이면 `s`.
9. 입력줄(`input.rs` `view`·`view/settings.rs` `col_w`)은 글자 하나를 `text_width`에 넣어 폭을 잰다. 그 코드는 그대로지만 `text_width`가 바뀌므로 글자 하나의 폭이 달라지는 경우가 있다 — 탁점·반탁점 단독(`ﾞ`·`ﾟ`)은 1 → 2칸(ratatui가 그리는 폭). 입력줄은 제어 문자를 받지 않는다. 그리는 폭 쪽으로 가까워지는 변화이고, 묶음 단위 커서는 여전히 범위 밖이다(§9).
10. 속도: 새 `text_width`는 문자열을 복제하지 않는다(지금은 호출마다 `to_string`). 1 MiB 본문의 요청·응답 화면 줄 만들기와 3만 줄 값 목록 열기를 release 빌드로 전후 1회 재서, 새 쪽이 옛 쪽의 1.5배를 넘으면 STOP(§6). (구현 뒤 정정: 묶음 나누기는 옛 문자열 전체 폭 재기보다 느리다 — 비-ASCII 구간이 1 MiB에 약 18ms. 그래서 `cells`에 ASCII 빠른 길(`Cells` — 앞뒤 바이트도 ASCII인 인쇄 글자는 묶음 나누기 없이 낸다, `graphemes(true)`와 같은 묶음)을 넣었고, 기준은 이 문장의 두 동작을 직접 재는 `#[ignore]` 측정으로 판정했다: 본문 줄 만들기 1.04·1.07배, 값 목록 열기 1.27배. `text_width` 미세 측정은 약 5배다 — roadmap §B56 (1).)

### 2.2 낮은 화면의 선택 창 머리 (US2)

지금: 선택 창(`OverlayView::Choice`)의 머리(`대상 = 받은 값`, 줄바꿈)는 본문 높이 5 이상(안내 줄이 있으면 6 이상)에서만 나온다. 안내 줄은 본문 높이 5 이상에서만 나온다.

안내 줄이 없는 선택 창

| 본문 높이 | 지금 | 바뀐 뒤 |
|---|---|---|
| 5 이상 | 제목 · 목록 · 머리(1줄 이상) · 선택 2줄 | 그대로 |
| 4 | 제목 · 고른 목록 줄 · 선택 2줄 | **머리 1줄** · 고른 목록 줄 · 선택 2줄 |
| 3 | 제목 · 선택 2줄 | **머리 1줄** · 선택 2줄 |
| 2 | 선택 2줄 | 그대로(한계) |
| 1 | 고른 선택 줄 | 그대로(한계) |

안내 줄(`이름이 비밀 값처럼 보입니다 — 화면에 늘 보입니다`)이 있는 선택 창

| 본문 높이 | 지금 | 바뀐 뒤 |
|---|---|---|
| 6 이상 | 제목 · 목록 · 머리(1줄 이상) · 선택 2줄 · 안내 | 그대로 |
| 5 | 제목 · 고른 목록 줄 · 선택 2줄 · 안내 | **머리 1줄** · 고른 목록 줄 · 선택 2줄 · 안내 |
| 4 | 제목 · 고른 목록 줄 · 선택 2줄 (안내 없음) | 그대로 |
| 3 | 제목 · 선택 2줄 | 그대로 |
| 2 · 1 | 위 표와 같음 | 그대로 |

본문 높이 = 터미널 높이 − 2(맨 위 줄·키 줄)이다. 터미널 높이 10 이상이고 폭이 넉넉하면 무입력 안내 줄이 하나 더 빠지고, 터미널 높이 2 이하는 맨 위 줄이 없다 — 표의 행에는 영향이 없다.

1. 규칙: 값 목록 화면에서 선택 창이 열려 있고, 선택 창 줄들에 머리가 없으며(본문 높이가 머리 최소 높이 미만), 제목 줄 자리가 있고(목록 영역 1줄 이상), **선택 창에 안내가 없거나(`note` 없음) 안내 줄이 그려지는 높이이면**, 제목 줄 대신 머리 한 줄을 그린다.
2. 안내 줄이 있는 선택 창은 안내가 보이는 높이(본문 5 이상)에서만 머리 한 줄이 나온다. tui-2b-secrets §2.4의 "안내는 머리보다 오래 남는다"(머리가 보이면 안내도 보인다)를 그대로 지킨다. 본문 3·4에서는 지금처럼 제목이 남는다. (구현 뒤 추가: 비밀 이름 줄이라도 `화면에 추가`가 막힌 줄 — 이미 화면에 표시 중·인증 헤더 — 은 안내가 없으므로 안내 없는 선택 창 규칙을 따른다. 보이는 글자는 방금 고른 목록 줄과 같다 — 보안 리뷰 Nit-2.)
3. 머리 한 줄의 모양은 선택 창 머리의 첫 줄과 같다: 앞 공백 2칸 + `sanitize`한 머리, 화면 폭으로 `fit`(넘치면 끝 `…`), 글자색은 머리 줄과 같다. 머리는 64KB일 수 있으므로 `sanitize` 전에 `(w + 1) × 4`글자까지만 자른다(잘렸으면 끝에 `…`을 붙인 뒤 `fit`).
4. 선택 창이 닫히면 제목 줄이 돌아온다. 선택 창이 아닌 창(입력·확인·저장 중·조건 칸)은 그대로다.
5. 머리 최소 높이(안내 없음 5 · 있음 6)와 안내 최소 높이(5)는 `view/settings.rs`의 순수 도우미로 빼서 선택 창 줄 만들기(`overlay_rows`)와 값 목록 화면이 같이 쓴다. `overlay_rows`의 반환 모양은 바꾸지 않는다(호출 5곳).

### 2.3 대체 화면 안내 (US3)

`render_missing`: 안내를 줄바꿈한 줄 수가 본문 높이보다 많으면, 마지막으로 보이는 줄에 남은 글자 전체를 이어 붙여 본문 폭(왼쪽 공백 1칸 제외)으로 `fit`한다 — `…`로 끝난다. 다 보이면 지금과 같다.

### 2.4 조건 칸 그리기 비용 (US: N/A)

지금: 조건 칸은 프레임마다 `target_rows`를 두 번(높이 계산 `cond_form_height` + 그리기 `render_cond_form`) 부르고, 그때마다 대상 전체를 `sanitize`하고 줄바꿈한다.

1. `target_rows`가 **필요한 줄 수 상한**을 받는다. 상한 `n`줄을 채우는 데 넉넉한 만큼(`(n + 1) × max(fw, 1) × 4`글자)만 대상의 앞에서 잘라 `sanitize`·줄바꿈하고, 잘랐는지를 함께 돌려준다.
2. 상한은 높이 계산(`cond_form_height`)에서는 본문 높이, 그리기(`render_cond_form`)에서는 조건 칸 영역의 높이(`area.height`)다 — 조건 칸은 그보다 많은 줄을 그릴 수 없다. 높이 계산은 "이어지는 줄 수"만, 그리기는 "보이는 줄 + 잘림 여부"만 쓴다.
3. 화면 결과는 지금과 같다. 줄바꿈은 앞에서부터 채우므로, 앞부분만 잘라 줄바꿈한 줄들은 **자른 자리가 든 마지막 줄을 빼면** 전체를 줄바꿈한 줄들의 앞부분과 같다(자른 자리가 묶음 가운데면 — 예 `❤` | `\u{FE0F}` — 그 묶음의 폭이 달라져 마지막 한두 줄이 달라질 수 있다). 예산의 `+1`줄이 그 줄을 화면 밖에 둔다: 보이는 대상 줄은 상한보다 적고(조건 칸에는 대상 말고도 필수 줄이 있다), 다 못 보이는 마지막 줄은 남은 글자 전체를 이어 `fit`하므로 줄이 어떻게 나뉘었든 같은 글자다. 자른 경우도 `…`로 맺는다. (구현 뒤 정정: 1칸에 글자 4개 이하인 대상에서는 `+1` 없이도 앞 `상한`줄이 같다 — 줄 하나는 `4 × fw`글자 이하이고 덜 찬 줄은 더 적은 글자를 쓴다. `+1`줄은 여유다, roadmap §B56 (1).)
4. 예외: 1칸에 글자가 평균 4개보다 많이 드는 대상은 예산이 먼저 떨어져 줄이 덜 채워진 채 `…`로 끝날 수 있다 — 결합 글자가 길게 이어진 글자, 긴 ZWJ 이모지(`👨🏻‍❤️‍💋‍👨🏼`는 글자 10개에 2칸)만 이어진 글자. `received_head`·선택 창 머리 예산과 같은 한계(§9).

### 2.5 숫자 글자 (US4·US5)

1. 컨트롤러 `monitor::number`에 두 함수를 둔다.
   - `float_text(v: f64) -> String`: 유한한 수에 대해 JavaScript `String(number)`와 같은 글자. 0과 −0은 `0`. `NaN`·무한대는 Rust 표기 그대로(`NaN`·`inf`·`-inf`) — JSON 본문에서는 나오지 않는 값이라 GUI와 맞추지 않는다. 자릿수는 가장 짧은 왕복 자릿수(동률이면 짝수 쪽)이고, 십진 지수 −6..=20 범위는 지수 없는 십진, 그 밖은 `{가수}e{+|-}{지수}`.
   - `number_text(n: &serde_json::Number) -> String`: 정수로 읽힌 값(`n.is_i64() || n.is_u64()` — 소수점·지수 없이 적혔고 그 범위에 드는 본문 글자)은 본문 글자 그대로(`n.to_string()`), 그 밖은 `float_text`.
2. 자릿수는 `serde_json::Number::from_f64(v)`의 글자에서 얻는다(가장 짧은 왕복 자릿수). 그 글자의 모양(`1e300`/`1e+300`, `1.0`)은 `serde_json` 버전에 따라 달라질 수 있으므로 부호·정수부·소수부·지수를 따로 읽어 자릿수 열과 십진 지수로 바꾼 뒤 위 규칙으로 다시 적는다. 읽지 못하는 모양이면 그 글자를 그대로 돌려준다(패닉 없음). `from_f64`가 `None`인 값(`NaN`·무한대)은 위 1번대로 Rust 표기다.
3. 쓰는 곳
   - 서버 판정(`monitor/check.rs`): 본문 조건의 받은 값 글자와 화면 표시 값의 글자. 값이 숫자면 `number_text`, 그 밖은 지금처럼 엔진 `stringify`.
   - TUI(`pick.rs`): `number_text(v: f64)`가 컨트롤러 `float_text`를 부른다. TUI 안의 숫자 표기 구현은 지운다.
4. **바뀌는 글자**(서버 — 지금 → 뒤): `1.0` → `1` · `100000.0` → `100000` · `1e+16` → `10000000000000000` · `1.2345678901234568e+20` → `123456789012345680000` · `1e-6` → `0.000001` · `-0.0` → `0`. `1e+21` 이상·`1e-7` 이하·`100.25` 같은 값은 그대로다. 정수는 그대로다.
5. **바뀌는 글자**(TUI): 가장 짧은 자릿수가 둘이고 값이 정확히 그 가운데인 소수(크기 2^50~2^51, 약 1.1e15~2.3e15)의 끝자리 — 예 본문 `1658206780088562.3` → 지금 `…562.3`, 뒤 `…562.2`(GUI와 같다).
6. **판정 영향**: `포함` 조건만 바뀐다 — 받은 값 글자에 대고 부분 문자열을 찾기 때문이다(예: 값 `1.0`에 `포함 ".0"`은 지금 통과, 뒤에는 실패).
   - `=`·`≠`·`∈`: 값이 숫자이고 비교값이 수로 읽히면 수로 비교한다. 비교값이 수로 읽히지 않으면 글자로 비교하는데, 숫자 글자와 같은 글자는 언제나 수로 읽히므로 그 갈래에서 결과가 달라지지 않는다.
   - `>`·`<`·`≥`·`≤`: 받은 값 글자를 수로 다시 읽는다. 새 글자도 같은 수로 읽힌다(왕복).
   - `값 있음`·`키 있음`: 글자가 비었는지만 본다.
7. 저장된 조건·보드 파일·와이어 모양은 그대로다. 화면 표시 값은 다음 점검부터 새 글자로 보인다.

## 4. 영향 범위

- `text_width`·`fit`은 TUI 전체가 쓴다(§11). ASCII·한글·보통 이모지에서는 새 재기와 옛 재기가 같아 화면이 그대로다. 달라지는 것은 묶음 폭이 글자 폭 합과 다른 글자뿐이다(§11의 표).

- GUI: 코드 0-diff. 서버가 주는 표시 값·사유 글자가 달라져 화면에 그대로 보인다.

## 6. 테스트

폭 재기(§2.1)
- 글자 묶음 풀: ASCII · 한글 · `❤️` · `❤` · ZWJ 가족 이모지 · 피부색 이모지 · `e`+결합 악센트 · 아랍 람-알레프(`\u{644}\u{627}`) · 국기 · 반각 가타카나+탁점(`\u{FF76}\u{FF9E}`) · 키캡(`1\u{FE0F}\u{20E3}`) · `\u{FFFD}` · 한글 자모 묶음.
- 풀에서 1–3개를 이어 만든 모든 문자열 × `w` 1..=12에 §2.1-8의 불변식 셋을 단언한다(그린 폭은 `Buffer::set_stringn`의 x). 실제 그리기 길(`Paragraph`)은 아래 소비처 렌더 테스트가 본다.
- 회귀 실증: `text_width`를 옛 구현(문자열 전체 폭)으로 되돌리면 람-알레프·반각 탁점에서, `wrap_width`를 글자 단위로 되돌리면 `❤️`에서 RED가 되는지 확인하고 원복.
- 소비처 렌더: 값 목록에서 대상에 `❤️`가 든 줄과 ASCII 줄의 받은 값 열이 같은 x에서 시작 · 선택 창 머리(`❤️`가 줄 끝에 걸리는 폭)가 화면 폭 안 · 요청·응답 본문 줄이 폭 안.
- 기존 `target_rows` 테스트(U+FE0F·ZWJ·피부색)는 그대로 통과해야 한다.

선택 창 머리(§2.2)
- 본문 높이 1..=8 × 안내 있음/없음 스윕: 표의 줄 구성(머리 글자가 보이는 줄, 제목 접미 `— 값 고르기`가 보이는지, 고른 목록 줄, 선택 2줄)을 높이마다 단언. 선택 창이 없으면 모든 높이에서 제목이 보인다.
- 긴 머리(1,000자)·`sanitize` 대상 글자가 든 머리에서 한 줄이 `…`로 끝나고 폭 안.
- **고쳐야 하는 기존 테스트 2개**(`tests/values_view_test.rs`): `choice_note_outlives_head_sweep`의 "안내만 보이는 높이가 폭마다 하나"(`note_only >= 4 * 91`) 단언 — 본문 5에서 이제 머리 한 줄도 보이므로 "본문 5에서 머리 한 줄과 안내가 같이 보인다"로 바꾼다(`머리가 보이면 안내도 보인다` 단언은 그대로 둔다 — 이 슬라이스의 회귀 가드). `choice_note_only_at_body_height_five`의 `first_head == first_note + 1` — `first_head == first_note`로 바꾸고 이름도 맞춘다.
- 회귀 실증: §2.2-1의 "안내 줄이 그려지는 높이이면" 조건을 빼면 `머리가 보이면 안내도 보인다` 단언이 RED가 되는지 확인하고 원복.

대체 화면(§2.3)
- 본문 1줄·2줄·다 보이는 높이 × 폭 20·40·80: 잘리면 마지막 줄이 `…`로 끝나고, 다 보이면 `…`가 없다(80열은 안내가 한 줄이라 본문 1줄에서도 `…` 없음).

조건 칸(§2.4)
- 같음(`view/edit.rs` 안의 `#[cfg(test)]` — `target_rows`가 비공개다): 대상 길이(짧음·500자·10만 자) × 폭·상한 몇 조합에서, 상한을 건 `target_rows`의 앞 `상한`줄이 전체를 `sanitize`·`wrap_width`한 참조 결과의 앞 `상한`줄과 같다. 자른 자리가 `❤`와 `\u{FE0F}` 사이에 오는 대상 1건 포함. 1 MiB 대상에서 돌려준 줄들의 글자 수 합이 예산 이하(전체를 훑지 않았다는 증거).
- 화면: 기존 조건 칸 테스트(`cond_form_target_*`·`values_form_long_target`)가 그대로 통과한다.
- 비용: 1 MiB 대상으로 조건 칸 한 프레임(높이 계산 + 그리기)을 release로 전후 1회 측정해 build-log에 적는다(단위 테스트에는 시간 단언을 넣지 않는다).

숫자 글자(§2.5)
- 골든 픽스처 `testdata/number_text_golden.json`: `[비트(16진), 기대 글자]` 줄. `node testdata/number_text_golden.mjs`가 고정 난수로 만든다 — 경계값(1e21·1e20·1e-6·1e-7·최대·최소 비정규·2^53 근처) + 임의 비트 500 + 동률 구간(2^50~2^51, 0.25 단위) 500 + 짧은 소수 300. 기대 글자는 `String(v)`(V8 — GUI가 쓰는 것과 같은 함수). **유한한 수만 싣는다**(스크립트가 `NaN`·무한대 비트를 건너뛴다). 시안 실측: 1,339줄·58KB, 두 번 만들어 `cmp` 일치.
- 컨트롤러 테스트: 픽스처 전 줄에서 `float_text(비트) == 기대 글자`, 그리고 기대 글자를 `f64`로 다시 읽으면 같은 비트(0 제외).
- `number_text`: 정수 `12345678901234567890`·`9007199254740993`은 그대로, `1.0`·`1E5`·`-0.0`은 §2.5-4의 글자. `float_text(f64::NAN)`·무한대는 패닉 없이 Rust 표기.

- 사전 대조(설계 시점 실측): 이 규칙의 시제품을 node `String(v)`와 499,853개 값(임의 비트 30만·동률 구간 10만·짧은 소수 10만·경계값)으로 대조해 전부 일치.

- 새 sink 없음: 같은 값이 같은 자리(사유·표시 값·보드 파일의 `value`)에 다른 표기로 들어간다. 로그·파일 쓰기·`Debug` 추가 없음.
- 원격 문자열은 지금처럼 `sanitize` 뒤에 폭을 잰다. 폭 0으로 세는 제어 문자 묶음은 ratatui도 그리지 않는다.
- 숫자 글자 함수는 `f64`·`serde_json::Number`만 받는다(원격 글자를 직접 받지 않는다). 읽지 못하면 원래 글자를 돌려주고 패닉하지 않는다.
- `finish-slice` §0 grep은 구현 뒤 직접 돌린다 — 판정 경로(`monitor/check.rs`)를 건드리므로 매치 여부와 무관하게 `security-reviewer`에 "판정 글자 변경이 가림(인증 값·비밀 이름) 경로를 건너뛰지 않는가"를 묻는다.

## 9. 알려진 한계 / 연기

- **입력줄은 글자 하나 단위로 폭을 잰다**(`input.rs` `view`·`view/settings.rs` `col_w`·`window`) — 사용자 결정 2026-11-12 제외. `❤️`를 붙여넣으면 커서가 1칸 어긋날 수 있다. 해소: 커서 이동·지우기 단위를 묶음으로 바꾸는 별도 설계.
- **엔진 `extract::stringify`는 그대로**(공용 개념 sweep — "숫자를 글자로 바꾸는 규칙"): 부하 시나리오의 추출 변수·test-run trace·모니터 묶음의 흐름 변수 글자는 `1.0`·`1e+16` 꼴로 남는다. 사용자 결정 2026-11-12(범위 질문). 해소: 엔진 `stringify`를 같은 규칙으로 — 부하 시나리오의 추출 값이 바뀌므로 별도 슬라이스.
- **배열·객체 값의 글자는 그대로**(`[1.0,2]` — `serde_json` 표기): 조건 대상이 숫자 하나일 때만 새 글자다.
- **2^53을 넘는 정수는 GUI와 다르다**: 서버·TUI는 본문 글자 그대로, GUI는 정밀도를 잃은 글자를 채운다(판정은 같다). 사용자 결정 2026-11-12.
- **터미널 높이 4줄 이하**에서는 선택 창에 고른 값이 안 보인다(§2.2 표). **비밀 안내가 붙는 선택 창**은 터미널 높이 5–6줄에서도 고른 값 한 줄이 없다(안내가 안 보이는 높이라 머리도 내지 않는다 — §2.2-2).
- **조건 칸 대상 예산**(§2.4-4): 1칸에 글자가 평균 4개보다 많은 대상(결합 글자 연속·긴 ZWJ 이모지 연속)은 덜 채운 줄에서 `…`.
- **`Block` 제목은 ratatui가 문자열 전체 폭으로 잰다**(§2.1-1): 제목에 묶음 폭 합과 전체 폭이 다른 글자(람-알레프·반각 탁점)가 들어가면 1칸 어긋날 수 있다. 지금 제목은 고정 문구와 `fit`한 칸 이름뿐이다.
- **`cell_width`의 반각 탁점 규칙**(`ｶﾞ` = 3칸)은 ratatui의 것이다 — 실제 터미널이 2칸으로 그리면 그 줄은 1칸 짧게 보인다. 기준을 "ratatui가 배치하는 칸"으로 정한 결과다.
- **업그레이드**: 소수 값에 `포함` 조건을 단 칸은 판정이 바뀔 수 있다. 릴리즈 노트 한 줄(roadmap §B 블록).

## 10. 판단 기록 (설계자 몫)

- **사용자 결정(2026-11-12, 다시 묻지 않는다)**: 묶음 B = 폭 재기 공용화·낮은 화면 선택 창 머리·대체 화면 안내 잘림·조건 칸 그리기 비용 / 묶음 C = 서버 사유·표시 값 표기·반올림 동률 끝자리(2^53 넘는 정수는 제외) / 입력줄은 이번에 제외 / US4는 `포함` 판정 변화를 알고 포함.
- **roadmap §B53의 "판정 무영향"은 틀렸다**: `포함`은 받은 값 글자에 대고 비교한다(§2.5-6). 범위 질문에서 그 서술을 옮겨 적었다가 US 제시 때 정정했다.
- **폭 기준을 "줄 전체 폭"이 아니라 "묶음 폭의 합"으로**: roadmap이 적은 해소 방향(`wrap_width`를 줄 전체 폭 기준으로)과 다르다. 실측에서 줄 전체 폭(`UnicodeWidthStr::width`)도 그린 폭과 다른 글자가 있었다(람-알레프 1 vs 2, 반각 탁점 2 vs 3 — §11). 그린 폭과 늘 같은 것은 묶음 폭의 합뿐이다.
- **`unicode-segmentation` 직접 의존**: `Span::styled_graphemes`로도 묶음을 얻을 수 있지만 제어 문자가 든 묶음을 버려 "이어 붙이면 원래 글자"가 깨진다. 새로 받는 crate가 없어 직접 선언을 골랐다. cost-if-wrong: 의존 선언 1줄 되돌리기.
- **자릿수를 `serde_json` 글자에서 얻는다**(새 의존 `ryu-js` 대신): 이미 쓰는 crate이고 50만 값 대조가 일치했다. cost-if-wrong: `serde_json`이 자릿수 생성기를 바꿔 동률 처리나 모양이 달라지면 골든 픽스처 테스트가 RED로 알린다 → 그때 `ryu-js`로.
- **비밀 안내가 붙는 선택 창은 US2에서 뺐다**(spec 리뷰 F1): 머리 한 줄을 본문 3·4에도 내면 안내 없이 머리(받은 값)만 보여 tui-2b-secrets의 "안내는 머리보다 오래 남는다"를 뒤집는다. 안내를 제목 자리에 올리는 길도 있지만 그 규칙의 높이표를 다시 여는 일이라 하지 않았다. cost-if-wrong: 비밀 이름 값을 터미널 5–6줄에서 고르면 무엇을 골랐는지 고른 목록 줄(높이 6)로만 보인다.
- **§2.2에서 제목 줄을 머리에 내준다**: 선택 창이 열린 동안에는 "어느 칸의 값 목록인가"보다 "무엇을 골랐나"가 필요하다. 본문 높이 4에서는 고른 목록 줄에도 대상·받은 값이 있지만 열로 나뉘어 각각 잘리므로 규칙을 3·4에 똑같이 적용했다.
