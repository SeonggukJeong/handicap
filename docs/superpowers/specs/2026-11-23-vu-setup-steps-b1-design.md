## 사용자 스토리 (US)

- **US1**: QA가 준비 스텝이 둘 이상인 시나리오에서 준비 스텝의 순서를 바꾼다 — 성공하면 Inspector의 ↑↓나 끌기로 준비 구획 안 순서가 바뀌고, test-run이 바뀐 순서대로 준비 스텝을 실행한다.
- **US2**: QA가 준비 스텝이 없는 시나리오에서 첫 준비 스텝을 만든다 — 성공하면 `[+ 준비 스텝]`을 누르거나 http 스텝을 목록 맨 위로 끌어 거기 나타난 자리에 놓았을 때 준비 상자가 생기고 그 안에 스텝이 들어 있다. 끌지 않는 동안에는 화면이 지금과 같다(버튼 하나만 늘어난다).
- **US3**: QA가 스텝을 준비 구획과 본 스텝 사이로 끌어 옮긴다 — 성공하면 본 스텝의 http(반복·조건 안의 것 포함)를 준비 구획의 원하는 위치에, 준비 스텝을 본 스텝의 원하는 위치에 놓을 수 있다. 반복·조건·병렬을 준비 구획에 놓으려 하면 놓이지 않는다.
- **US4**: QA가 새 시나리오 갤러리에서 「로그인 흐름」을 고른다 — 성공하면 「로그인」이 준비 스텝, 「내 정보 조회」가 본 스텝인 시나리오로 시작하고, test-run이 준비 → 본 스텝 순서로 돈다.
- **US5**: 개발자가 같은 시나리오를 YAML로 연다 — 성공하면 추가·순서 바꾸기·끌기의 결과가 `setup.steps`와 `steps`에 그대로 보이고, 마지막 준비 스텝이 나가면 `setup:` 키가 사라진다. 준비 구획을 건드리지 않은 시나리오의 YAML은 바뀌지 않는다.

## 1. 배경

A2(2026-11-23)는 준비 구획을 「보이고 고를 수만 있는」 자리로 만들었다. 준비 스텝을 만드는 길은 본 스텝으로 만든 뒤 Inspector의 「준비 스텝으로 옮기기」뿐이고, 옮기면 구획 끝에 붙는다. 준비 스텝끼리 순서를 바꾸려면 본 스텝으로 뺐다가 다시 넣거나 YAML을 고쳐야 한다(사용자가 A2 확인 중 지적).

지금 코드(2026-11-23, `7d9bca3f` 기준):

- `FlowOutline.tsx`의 `SetupRow`는 `OutlineRow`의 줄인 사본이다 — `useSortable`·손잡이가 없고 컨테이너를 그리지 못한다.
- 끌기 규칙(`scenario/dropRules.ts`)·해석(`scenario/reorder.ts`)은 `model.steps`만 받는다. 준비 구획은 좌표계에 없다.
- YAML 편집(`scenario/yamlDoc.ts`): `findStepPath`는 `setup.steps`를 먼저 찾는다. `moveStep`은 스텝이 든 seq 안에서 움직이므로 준비 스텝에도 동작한다. `reparentStep`은 출발지가 준비여도 되지만(`dropEmptySetup` 호출) 목적지 `bandSeqPath`에 준비 가지가 없다.
- Inspector(`Inspector.tsx`)는 `{!inSetup && <MoveButtons/>}`로 준비 스텝의 ↑↓를 숨긴다. `MoveButtons`는 `findStepSiblings(model.steps, …)`를 쓰는데, 이 함수는 못 찾으면 최상위 본 스텝을 돌려준다(준비 스텝에 그대로 쓰면 틀린 형제).
- 추가 버튼은 `addStep`(본 스텝 끝)뿐이다.
- 갤러리 「로그인 흐름」(`scenario/templates.ts` `LOGIN_FLOW_YAML`)은 본 스텝 2개이고 `setup:`이 없다.

### 목표가 아닌 것

- 준비 구획에 loop·if·parallel 허용(엔진·YAML 검증이 http만 받는다 — 상위 설계 §11). B1은 **나중에 열기 쉽게** 짓기만 한다(§6).
- 키보드로 구획 사이 옮기기. 키보드 끌기는 지금처럼 같은 구획 안 순서만 바꾼다. 구획 사이의 키보드 경로는 Inspector의 「옮기기」 버튼(A2)이다.
- 스텝 템플릿 삽입을 준비 구획에 넣기. 준비 스텝을 고른 채 삽입하면 지금처럼 본 스텝 끝에 들어간다.
- B2의 것(인쇄·내보내기·비교·실행 중 진행).

### 하면 안 되는 것

- 준비 구획을 건드리지 않는 시나리오의 화면·YAML이 달라지는 것. 끌지 않는 동안 준비 스텝 없는 시나리오에서 달라지는 것은 아래 버튼 줄의 `[+ 준비 스텝]` 하나뿐이다.
- 본 스텝끼리의 끌기 동작(같은 구획 순서·컨테이너 사이 옮기기)이 달라지는 것.
- http가 아닌 스텝이 준비 구획에 들어가는 길이 생기는 것(끌기·추가·옮기기 어느 쪽으로도).
- 화면 문구에 「로그인」을 박는 것(갤러리 템플릿의 이름·내용은 예외 — 그 템플릿이 로그인 예시다).

## 2. 방법 비교

| | 방법 | 장단 |
|---|---|---|
| **가 (채택)** | 준비 구획을 기존 밴드 좌표계의 한 밴드(`setup`)로 넣는다. 규칙은 `bandAccepts`의 한 줄, 행은 `OutlineRow` 재사용 | 규칙·해석·YAML 편집이 한 벌. 나중에 컨테이너를 열 때 규칙 한 줄 + 모델 타입만 바꾼다. 대신 `dropRules`·`reorder`의 함수들이 준비 목록도 받도록 시그니처가 넓어진다 |
| 나 | 준비 구획 전용 끌기 처리(별도 `DndContext` 또는 `handleDragEnd`의 특수 가지 + `moveStepSection` 재사용) | 기존 규칙 코드를 안 건드린다. 대신 「http만」·「마지막 자식은 못 나감」 규칙이 두 벌이 되고, 위치 지정 삽입을 따로 만들어야 하며, 컨테이너를 열 때 두 벌을 고친다 |
| 다 | 끌기 없이 ↑↓와 추가 버튼만 | 가장 작다. US2의 끌기·US3를 못 한다(사용자가 요청한 범위 밖) |

사용자는 결과(끌기·추가·확장 가능성)를 정했고 짓는 방법은 맡겼다 — 「가」는 내 판단이다.

## 3. 규칙 — 준비 밴드

**D1. 밴드 키.** 준비 구획은 밴드 `SETUP_BAND = { parentId: null, band: "setup" }`, 키 `"setup"`이다. 최상위 본 스텝은 지금처럼 `TOP_BAND`·키 `"top"`. `bandKey`는 `parentId === null`일 때 `band === "setup"`이면 `"setup"`, 아니면 `"top"`을 돌려준다.

밴드 키 계약은 지금 여러 곳이 같아야 한다: `dropRules.bandKey`, 놓을 자리 id를 읽는 정규식 `/^band:([^:]+):(.+)$/`의 사본 셋(`dropRules.filterDropCandidates`·`reorder.resolveDrop`·`FlowOutline`의 `overBandKey`), `yamlDoc.bandSeqPath`, `EmptyBandDrop`의 id. 준비 밴드를 모두에 더한다:

- 놓을 자리 id 읽기를 `dropRules.ts`의 함수 하나로 모은다(정규식 사본 셋을 그 함수로 바꾼다 — 넷째 사본을 만들지 않는다). 부모 없는 놓을 자리 id는 글자 그대로 둘: 빈 준비 구획 `"band:setup"`, 빈 본 스텝 목록 `"band:top"`(D11-2). 기존 `band:{parentId}:{band}` 꼴과 겹치지 않는다(콜론이 하나).
- `yamlDoc.bandSeqPath(doc, null, band)`: 지금은 `parentId === null`이면 밴드를 보지 않고 `["steps"]`를 돌려준다(`yamlDoc.ts`의 첫 줄). 준비 밴드 판정이 그 줄보다 앞에 와야 한다.
- `resolveDrop`이 돌려주는 `target`은 준비 밴드면 `{ parentId: null, band: "setup", index }`. 지금 코드는 `parentId === null`인 밴드를 모두 `"top"`으로 고쳐 쓴다(`reorder.ts`의 `band: overBand.parentId === null ? "top" : overBand.band`) — 그대로 두면 준비 목적지가 조용히 최상위 본 스텝이 된다.

**D2. 규칙 함수가 준비 목록을 받는다.** `enumerateBands`와 그 위의 함수들(`findParentBand`·`bandChildren`·`bandIndex`·`legalTargetBands`·`keyboardCandidateIds`·`resolveDrop`)이 준비 스텝 목록을 함께 받는다. 꼴은 **끝에 붙는 선택 인자 `setup`(기본 빈 배열)** 로 한다 — 기존 호출과 기존 테스트(`dropRules.test.ts`·`reorder.test.ts`·`reparent.test.ts`)가 한 글자도 안 바뀌고 통과해야 하고, 그것이 「본 스텝끼리의 끌기 불변」의 회귀 가드다.

- `enumerateBands`는 준비 밴드를 **항상** 등록한다(비어 있어도 — if의 `else`와 같은 이유: 빈 준비 구획이 놓을 자리다). 준비 목록 안도 본 스텝과 같은 재귀로 훑는다(지금은 http뿐이라 하위 밴드가 없다 — §6).
- 준비 스텝을 `findStepById`·`findStepSiblings`로 찾는 자리는 준비 목록도 본다. 특히 `keyboardCandidateIds`: 준비 스텝의 키보드 후보는 **준비 형제**여야 한다(`findStepSiblings(steps, …)`의 「못 찾으면 최상위」 폴백을 그대로 타면 본 스텝이 후보가 된다). `legalTargetBands`는 끄는 스텝을 못 찾으면 빈 집합을 돌려준다 — 준비 스텝을 찾게 해야 한다.
- `FlowOutline.tsx` 안에서 본 스텝만 보는 자리도 준비 목록을 봐야 한다(끌기를 여는 순간 모두 틀려진다): 끄는 스텝 찾기 `activeStep = findStepById(steps, activeId)`(못 찾으면 끄는 미리보기가 안 뜬다 — 출발 행은 숨겨지므로 아무것도 안 움직이는 것처럼 보인다. jsdom은 못 잡는다), 충돌 판정의 컨테이너 여부 찾기, `overBandKey` 계산의 `findParentBand`, `keyboardCandidateIds` 호출 두 곳, `handleDragStart`의 `legalTargetBands`·`bandIndex`, `handleDragEnd`의 `resolveDrop`, `collisionDetection`의 의존 목록 `[steps]`.

**D3. 받는 규칙 (`bandAccepts`).** 준비 밴드는 `dragged.type === "http"`만 받는다 — 한 줄. 이 줄은 지금의 첫 줄 `if (ref.parentId === null) return true`(최상위 = 모든 유형)보다 **앞**에 와야 한다(뒤에 두면 준비가 loop·if·parallel을 받는다 — 기존 `dropRules.test.ts`의 parallel 합법 집합 단언이 이것을 잡는다). loop·if·parallel은 준비 밴드가 합법 목적지에 들지 않아 충돌 후보에서 빠지고, 놓아도 아무 일도 일어나지 않는다(기존 「놓을 수 없는 자리」와 같은 방식).

**D4. 나가는 규칙.** 준비 밴드는 최소 1개 밴드가 아니다 — 마지막 준비 스텝도 나갈 수 있다(나가면 `setup:` 키가 지워진다). 최상위 본 스텝도 지금처럼 마지막 하나가 나갈 수 있다(본 스텝이 없는 시나리오는 준비만 실행한다 — 상위 설계 D16, 실행 창이 경고한다). 최소 1개 밴드(`do`·`then`·`elif_j`·`branch_i`)의 마지막 자식은 지금 규칙대로 준비 구획으로도 못 나간다. if의 `else`는 최소 1개 밴드가 아니라서 마지막 자식도 나갈 수 있다(지금 규칙 그대로). 아래에서 「마지막 자식」은 최소 1개 밴드의 마지막 자식을 뜻한다.

**D5. 준비 스텝의 목적지.** 준비 스텝(http)은 http를 받는 모든 밴드로 갈 수 있다: 최상위, loop `do`, if의 분기, parallel 레인. 기존 `bandAccepts`의 http 규칙 그대로다.

**D6. 같은 밴드 안.** 준비 밴드 안의 끌기는 기존 같은-밴드 규칙 그대로다(`computeReorder` 결과 그대로, 위/아래 절반 무시 → `moveStep`). 준비 밴드와 다른 밴드 사이는 교차 밴드 규칙(가리킨 행의 위/아래 절반 → 앞/뒤 인덱스 → `reparentStep`).

규칙 표(끄는 것 × 놓는 곳, B1이 더하는 칸만):

| 끄는 것 | 놓는 곳 | 결과 |
|---|---|---|
| 준비 스텝 | 준비 구획의 다른 위치 | 순서 바뀜 |
| 최상위 본 http | 준비 구획(위치 지정) | 준비 스텝이 됨 |
| 컨테이너 안 http(마지막 자식 아님) | 준비 구획 | 준비 스텝이 됨 |
| 컨테이너 안 http(마지막 자식) | 준비 구획 | 놓이지 않음 |
| loop·if·parallel | 준비 구획 | 놓이지 않음 |
| 준비 스텝 | 최상위·loop·if 분기·parallel 레인 | 그 자리의 본 스텝이 됨 |
| 준비 스텝(마지막 하나) | 위와 같음 | 옮겨지고 `setup:` 키가 지워짐 |
| http 스텝 | 빈 준비 구획의 놓을 자리(§5 D11) | 준비 상자가 생기고 그 스텝 하나가 듦 |
| 준비 스텝 | 본 스텝이 하나도 없을 때의 놓을 자리(§5 D11-2) | 첫 본 스텝이 됨 |

## 4. YAML 편집

**D7. `reparentStep`의 준비 목적지.** 목적지가 준비 밴드면 **항상** `ensureSetupSeq`를 거친다(옮길 노드를 빼내기 전에 부른다 — 기존 코드가 목적지 seq 노드를 빼내기 전에 잡는 것과 같은 이유). `bandSeqPath`가 돌려준 경로로 `doc.getIn`만 하면 손으로 쓴 flow 표기 `setup: {steps: []}`가 flow인 채 남는다. `ensureSetupSeq`(A2 — 없으면 `setup:` 키를 `steps:` 키 **바로 앞**에 만들고, 손으로 쓴 `setup:`이 있으면[빈 `steps: []`·flow 표기 포함] 그 키를 block 표기로 다시 쓴다)로 seq를 얻는다. 기존 「빈 else」 가지(`doc.setIn(경로, createNode([]))`)를 준비에 쓰지 않는다 — 키 위치와 flow 표기 처리가 다르다. 출발지가 준비이고 비게 되면 `dropEmptySetup`(지금 동작).

- 옮긴 스텝 노드는 그대로 옮긴다(스텝 안의 주석이 따라간다 — A2 `moveStepSection`과 같은 성질).
- 옮긴 스텝의 추출 기본값(`default:`)은 지우지 않는다(상위 설계 D13).
- 본 스텝이 모두 나가면 `steps: []`가 남는다(A2의 「옮기기」와 같은 결과).
- store의 `reparentStep`은 지금처럼 사본에 적용 → 다시 읽기에 성공할 때만 반영한다. http가 아닌 스텝이 준비에 들어가면 Zod(`setup.steps: HttpStepModel[]`)가 거절해 아무 일도 일어나지 않는다(규칙이 뚫렸을 때의 둘째 방어).

**D8. 준비 스텝 추가.** 새 편집 `addSetupStep { id, name }` — `ensureSetupSeq` 뒤 끝에 http 스텝을 더한다. 스텝의 초기 내용은 `addStep`과 같다(`GET` `/`, `assert: [{ status: 200 }]`). store 액션 `addSetupStep(name)`은 `addStep`과 같은 꼴이다(YAML 오류 상태면 `null`, 아니면 새 id). 이름은 `Setup ${준비 스텝 수 + 1}`(본 스텝의 `Step N`과 같은 방식 — 내 판단).

**D9. 순서 바꾸기.** 기존 `moveStep` 그대로(새 편집 없음).

**D10. YAML이 안 바뀌는 경우.** 준비 구획을 건드리지 않는 편집은 `setup:` 키를 만들지도 다시 쓰지도 않는다. 놓을 수 없는 자리에 놓거나 끌기를 취소하면 YAML은 한 글자도 안 바뀐다.

## 5. 화면

시각 기준은 목업이다. 아래는 목업이 말하지 않는 동작과, 목업의 어느 부분이 무엇인지다.

**D11. 준비 스텝이 없을 때 (목업 장면 1 「다」).**

- 평소: 준비 상자도 「본 스텝 — 반복 실행」 머리 줄도 없다(지금과 같다). 아래 버튼 줄 끝에 `[+ 준비 스텝]`(목업 `.setup-add`)이 하나 더 있다. 놓을 자리가 열려 있는 동안에도 「본 스텝」 머리 줄은 내지 않는다(목업 「다」 그대로).
- 끄는 동안 — **맨 위로 가져갈 때만 열린다**(사용자 결정 2026-11-23, 목업의 「끌자마자 나타남」에서 바뀐 것은 나타나는 시점뿐이고 모양은 그대로다): 끄는 스텝의 합법 목적지에 준비 밴드가 있고(= http이고 마지막 자식이 아니고) 포인터가 **목록 맨 위 영역**에 들어와 있는 동안만 목록 맨 위에 놓을 자리(목업 `.dropzone`, 열려 있는 동안은 곧 포인터가 그 위라 `.dropzone.over`)가 열린다. 글: 「여기에 놓으면 준비 스텝이 됩니다」. 포인터가 영역을 벗어나면 닫힌다. 끌기가 끝나거나 취소되면 사라진다. loop·if·parallel을 끌 때는 열리지 않는다.
- 왜 끌자마자 열지 않는가: 놓을 자리가 열리면 목록이 그 높이만큼 밀리는데 포인터는 그대로다. 끌자마자 열면 ① 첫 스텝을 집어 조금 움직였다 제자리에 놓았을 때 포인터가 놓을 자리 위에 있어 그 스텝이 준비 스텝이 되고 ② 본 스텝끼리 순서만 바꾸려 해도 놓을 대상이 그만큼 달아난다(「본 스텝끼리의 끌기 불변」을 깬다). 포인터 센서에 활성화 조건이 없어 손잡이를 누르는 순간 끌기가 시작된다는 점도 같은 사고를 만든다(「손잡이를 움직이지 않고 누르기」는 지금 테스트가 있는 경로다). 센서의 활성화 조건은 바꾸지 않는다.
- 지켜야 하는 성질(숫자보다 이것이 기준이다):
  1. 어느 행이든 집었다가 **집은 자리로 돌아와 놓으면** 놓을 자리는 닫혀 있고 YAML이 바뀌지 않는다(첫 행 포함).
  2. 포인터가 맨 위 영역에 들어오지 않는 끌기에서는 놓을 자리가 한 번도 열리지 않고, 형제 행의 밀림·놓이는 자리가 이 슬라이스 전과 같다.
  3. 열고 닫는 판정은 **목록 내용의 맨 위 가장자리에 고정된 선**으로 한다(행의 위치로 하지 않는다 — 열리면 행이 밀리므로 행 기준이면 열림·닫힘이 진동한다). 놓을 자리는 그 가장자리에 끼워지므로 열려도 선은 움직이지 않는다.
  4. 열려 있는 동안 놓으면 그 스텝이 준비 스텝이 된다(인덱스 0). 거리 계산에 맡기지 않는다 — 놓을 자리가 열려 있으면 충돌 판정이 그 자리를 곧바로 돌려준다.
- 영역(크기는 내 판단 — plan의 첫 작업에서 실제 브라우저로 위 네 성질을 확인해 굳힌다): 포인터가 **선 + 24px보다 위**에 있고(위쪽 한계 없음 — 목록 맨 위를 지나쳐 패널 여백·흐름 칩 줄까지 올라가도 열린 채다. 「맨 위로 끌기」는 지나치는 것이 자연스럽다) **그리고** 집은 자리보다 8px 넘게 위에 있을 것. 둘째 조건은 첫 행을 위한 것이다 — 첫 행의 손잡이는 이미 그 24px 근처에 있어서, 첫 조건만이면 누르자마자 열린다.
- 두 조건 모두 **목록 내용 좌표**로 잰다(화면 좌표가 아니다). 화면 좌표로 재면 끄는 동안 목록이 스크롤될 때 「집은 자리보다 8px 위」가 틀어진다 — 스크롤된 목록에서 패널 위쪽 가까이의 행을 집어 올리면 자동 스크롤이 내용을 내려 보내는데, 화면에서 집은 자리는 그대로라 열릴 틈이 2px쯤만 남는다. 한 가지 방법: 끌기 시작 때 `집은 내용 Y = 누른 화면 Y − 내용 맨 위`를 적어 두고, 움직일 때마다 `포인터 내용 Y = 집은 내용 Y + delta.y`(dnd-kit `onDragMove`의 `delta`는 스크롤만큼 이미 보정돼 있고 스크롤만 돼도 불린다). 충돌 판정이 받는 화면 좌표(`pointerCoordinates`)를 끌기 시작 때 적어 둔 선과 섞어 쓰지 않는다.
- 목록을 **실제로** 스크롤하는 요소에 `overflow-anchor: none`을 건다(적어도 끄는 동안). 그 요소는 마운트마다 다르다 — 「변수 넓게」는 격자에 높이 상한이 없어 문서 자체(`document.documentElement`)가 스크롤할 수 있다. plan의 첫 작업에서 세 마운트 각각의 실제 스크롤 요소를 브라우저로 찾아 그 요소에 건다(`outline-blank`에만 걸면 깜빡임이 남을 수 있다). 같은 작업에서 문서가 스크롤하는 마운트에서도 `delta`가 스크롤을 반영하는지 확인한다. 브라우저의 스크롤 고정(지금 `ui/src` 어디에도 꺼져 있지 않다)이 켜져 있으면, 목록이 조금 스크롤된 채(0 < scrollTop ≤ 24px쯤) 놓을 자리가 열릴 때 브라우저가 끼워진 높이만큼 scrollTop을 올리고 → 그 스크롤이 `delta`에 들어가 포인터가 영역 밖이 되어 닫히고 → 닫히면 스크롤이 돌아와 다시 열리는 깜빡임이 날 수 있다.
- 목록이 스크롤돼 맨 위가 화면 밖이면 영역도 화면 밖이다. 위쪽 가장자리로 끌면 기존 자동 스크롤이 목록을 올려 영역이 들어온다.
- 끄는 중인 행의 미리보기는 놓을 자리가 열리고 닫혀도 포인터 아래에 있어야 한다. dnd-kit의 「배치 변화 스크롤 보정」은 끌기 시작 직후 한 번만 돌므로(그때는 놓을 자리가 없다) 이 밀림을 보정하지 않는다 — 보정 설정을 건드릴 일은 없다.
- 키보드로 집었을 때는 놓을 자리를 내지 않는다(키보드 끌기는 같은 구획 안만 — §1). 판정: 끌기 시작 이벤트의 `activatorEvent`가 키보드 이벤트.

**D11-2. 본 스텝이 하나도 없을 때.** 본 스텝이 0개이고 준비 스텝을 끄는 중이면 본 스텝 자리에 놓을 자리를 낸다(기존 빈 밴드 놓을 자리 `EmptyBandDrop`의 모양·글 「여기로 드롭」 그대로, id `"band:top"`). 놓으면 그 준비 스텝이 첫 본 스텝이 된다. 없으면 마지막 본 스텝을 준비로 끌어 넣은 뒤 끌어서 되돌릴 길이 없다(D4가 그 상태를 허용한다). 목업에 없는 화면이다 — 기존 컴포넌트의 모양을 그대로 쓰므로 새 시각 결정은 없다(내 판단). `EmptyBandDrop`은 지금 `parentId: string`을 받아 id를 만든다 — 부모 없는 두 id(`"band:top"`·`"band:setup"`)를 낼 수 있게 컴포넌트가 바뀐다(꼴은 구현에 맡긴다). D11의 「맨 위 영역」 조건은 여기에 걸지 않는다 — 끌기가 시작되면 바로 낸다(준비 행 아래에 생겨 집은 행을 밀지 않는다).

**D12. 준비 스텝이 있을 때 (목업 장면 2).**

- 준비 행은 본 스텝 행과 **같은 컴포넌트**(`OutlineRow`)로 그린다 — 손잡이(⠿)·선택·키보드·넓게 보기 동작이 본 스텝과 같다. `SetupRow`는 없앤다. A2에서 준비 행이 하던 것(선택, 넓게 보기의 활성화, 다른 화면이 스텝으로 찾아오는 표시 `data-step-id`)은 그대로 동작해야 한다.
- 준비 상자 안 맨 아래에 `[+ 준비 스텝]`(목업 `.box-add`). 누르면 준비 구획 끝에 새 http 스텝이 생기고 선택된다. 준비 스텝이 있으면 아래 버튼 줄의 `[+ 준비 스텝]`은 내지 않는다(버튼은 한 곳에만).
- 끄는 동안의 표시:
  - 놓일 자리의 파란 줄 — 기존 교차 밴드 표시(가리킨 행의 위/아래 테두리)를 그대로 쓴다.
  - 준비 밴드가 가리킨 밴드이고 출발 밴드가 아니면 상자에 강조 테두리(목업 `.setup-box.target`).
  - 끄는 스텝의 합법 목적지에 준비 밴드가 없으면 상자를 흐리게(목업 `.setup-box.refuse`). 출발 밴드가 준비인 경우(준비 스텝을 끄는 중)는 흐리게 하지 않는다.
- 준비 구획 안에서의 순서 바꾸기는 본 스텝의 같은-밴드 끌기와 같은 모습이다(행이 밀리는 애니메이션, 파란 줄 없음).

**D13. 추가 버튼의 잠금.** `[+ 준비 스텝]` 두 자리 모두 YAML 오류 상태에서는 기존 추가 버튼들과 같은 방식으로 아무 일도 하지 않는다(store가 `null`을 돌려주고 선택이 바뀌지 않는다).

**D14. Inspector (목업 장면 3).** 준비 스텝에도 ↑↓를 낸다. 형제는 준비 스텝 목록이다 — 맨 위에서 ↑, 맨 아래에서 ↓가 꺼진다. 「본 스텝으로 옮기기」 줄과 「준비 스텝으로 옮기기」 버튼은 A2 그대로다.

**D15. 갤러리 「로그인 흐름」 (목업 장면 4).** `LOGIN_FLOW_YAML`을 준비 스텝 형태로 바꾼다: 「로그인」 스텝이 `setup: { steps: [...] }`에(`steps:` 키 앞), 「내 정보 조회」가 `steps:`에. 스텝 id·요청·추출·검증은 그대로다. 템플릿 안의 주석은 새 구조에 맞게 고친다(「준비 스텝」이 무엇인지 한 줄 — VU마다 한 번만 실행). 갤러리 카드의 이름(`ko.templates.loginName`)·설명(`loginDesc`: 「로그인(POST) → 토큰 값 추출 → 인증 GET. …」)은 바꾸지 않는다 — 바뀐 뒤에도 맞는 말이다.

**D16. 문구.** 새 문구는 `ko.ts` 경유(ADR-0035): `[+ 준비 스텝]`의 글(「+ 준비 스텝」), 놓을 자리의 글(「여기에 놓으면 준비 스텝이 됩니다」), 필요한 접근성 이름. 기존 `ko.editor.setupSectionName`·`setupSectionNote`·`mainSectionTitle`은 그대로 쓴다.

## 6. 나중에 loop·if·parallel을 열 때 (사용자 요청 2026-11-23: 확장 가능성)

B1은 준비 구획에 컨테이너를 **허용하지 않는다**. 대신 나중에 여는 슬라이스가 화면 쪽에서 고칠 곳이 아래로 끝나게 짓는다.

B1이 미리 해 두는 것:

- 준비 행을 `OutlineRow`로 그린다(컨테이너와 그 밴드를 이미 그릴 줄 안다).
- `enumerateBands`가 준비 목록 안도 재귀로 훑는다(준비 안 컨테이너의 하위 밴드가 생기면 자동으로 좌표계에 든다).
- 받는 규칙이 `bandAccepts`의 준비 가지 한 곳이다.
- `yamlDoc.findStepPath`(→ `searchSeq`)는 이미 `setup.steps` 아래를 재귀로 찾는다.
- 준비 상자 안의 추가 버튼 자리는 버튼이 옆으로 늘어날 수 있는 줄이다.

그 슬라이스가 고칠 것(여기 적어 두기만 한다):

- 엔진: 준비 구간의 스텝 타입과 실행(상위 설계 §11).
- UI 모델: `ScenarioModel.setup.steps`의 타입(`HttpStepModel[]` → 허용할 스텝 타입), `setupSteps()`의 반환 타입과 그것을 http 목록으로 쓰는 자리.
- `bandAccepts`의 준비 가지(허용 타입·깊이 규칙), 준비 밴드 안 컨테이너의 「최상위 여부」 판정(`parentIsTop`은 지금 본 스텝 최상위만 본다).
- store `moveStepToSection`의 http 검사, Inspector의 「준비 스텝으로 옮기기」 표시 조건.
- 준비 상자 안에 `[+ 반복]`·`[+ 조건]` 버튼.

## 7. 구현하는 사람에게 맡기는 것

- D2의 함수들에 `setup`을 넘기는 구체적 꼴(선택 인자의 위치, `FlowOutline`이 `setup`을 메모해 넘기는 방식). 조건은 「기존 테스트 파일 무수정 통과」.
- `FlowOutline` 안의 준비 놓을 자리 컴포넌트 이름과, 준비 상자의 `SortableContext` 배치.
- `OutlineRow`가 준비 행에서 `data-step-id`를 내는 방식(A2의 `SetupRow`는 항상 냈고 `OutlineRow`는 `view`에 따라 낸다 — 준비 행에서 A2의 동작이 유지되면 된다).
- 놓을 자리가 열려 있는 동안 충돌 판정이 그 자리를 곧바로 돌려주게 하는 코드 꼴(D11 성질 4 — `nearestByHeader`의 거리 비교에 놓을 자리를 행처럼 넣지 않는다). 조건은 §8 라이브 표.
- 템플릿 주석의 정확한 글(「값 추출」·「환경」 낱말은 남긴다 — `templates.test.ts`의 주석 round-trip 테스트가 그 둘을 찾는다).

### 자동

- `dropRules`: 준비 밴드 등록(빈 준비 포함)·`bandKey`·규칙 표(§3)의 각 칸·준비 스텝의 키보드 후보가 준비 형제뿐. **기존 `dropRules.test.ts`·`reorder.test.ts`·`reparent.test.ts`는 고치지 않고 통과.**
- `resolveDrop`: 준비 ↔ 다른 밴드의 인덱스(위/아래 절반), `"band:setup"` 놓을 자리 → 인덱스 0, 준비 안 같은 밴드 → `move`.
- `yamlDoc`: 준비 목적지 `reparentStep` — `setup:` 키가 `steps:` 앞에 생김 / 손으로 쓴 flow `setup: {steps: []}`가 block으로 / 위치 지정 삽입 / 스텝 안 주석이 따라감(옮겨졌는지도 함께 단언) / 마지막 준비 스텝이 나가면 키 삭제. `addSetupStep` — 키 생성 위치·끝에 붙음.
- store: `addSetupStep`의 YAML 오류 상태 `null`, `reparentStep`으로 loop를 준비에 넣으려 하면 상태 불변.
- `FlowOutline`: 준비 행에 손잡이 / 상자 안 버튼 / 준비 없을 때 아래 버튼 줄의 버튼과 평소 놓을 자리 없음 / 준비 있을 때 아래 버튼 없음 / A2 준비 행 동작(선택·`data-step-id`·넓게 보기) 유지.
- Inspector: 준비 스텝의 ↑↓와 끝에서의 꺼짐, ↑↓ 뒤 `setup.steps` 순서.
- 템플릿: 네 템플릿 모두 읽힘 / 「로그인 흐름」이 준비 1 + 본 1 / 주석 round-trip / 갤러리 선택 뒤 아웃라인에 준비 상자.
- 본 스텝끼리만 옮긴 뒤(준비 없는 시나리오에서 최상위 http → loop 안) YAML에 `setup:` 키가 없다.
- 준비 놓을 자리의 열림 판정(순수 함수로 떼어 단위 테스트, 입력은 내용 좌표): 선 + 24px 아래면 닫힘 / 그 위여도 집은 자리보다 8px 넘게 위가 아니면 닫힘 / 둘 다면 열림 / 선보다 한참 위(음수)여도 열림 / 영역을 벗어나면 다시 닫힘.
- `resolveDrop`: `"band:top"` → 최상위 인덱스 0.
- A2 테스트 가운데 이 슬라이스가 **뒤집는 것**(회귀로 착각하지 않게 적어 둔다): `FlowOutline.setup.test.tsx`의 「준비 행에는 끌기 손잡이가 없다」(→ 있다), 「끌기 계산은 준비 스텝 id를 모른다」(선택 인자를 안 넘겨 통과는 하지만 설계와 반대말이 된다 → 준비 목록을 넘긴 단언으로 다시 쓴다), `Inspector.setup.test.tsx`의 「준비 스텝에는 ↑↓가 없고…」(→ 있다), 같은 파일 「본 스텝으로 옮기기를 누르면…」의 끝 두 줄(↑↓가 옮기기 전에도 있어 이빨이 없어진다 → 지우거나 다른 단언으로). **지켜야 하는 것**: 「준비 행은 data-step-id를 항상 단다」(기본 마운트 `<FlowOutline />`는 `wide`도 `onActivateStep`도 안 넘기고, `EditorShell`의 스텝으로 가기가 이 속성에 기댄다), 「준비 행을 누르면 선택된다」, 「넓게 보기에서 준비 행을 누르면 onActivateStep이 불린다」, 「본 스텝이 없고 준비 스텝만 있어도 그려진다」.
- 회귀 가드라고 내세우는 테스트는 고의로 되돌려 RED를 본 뒤 원복한다(특히 「http만」 한 줄, 키보드 후보, 주석 따라가기).

### 라이브 (US 척추) — 끌기는 jsdom으로 볼 수 없다

포인터로 누른 채 관측하는 방식(`page.mouse.down → move → 관측 → up`)으로, 컴포넌트가 뜨는 모든 진입 화면에서 본다: 새 시나리오 `/scenarios/new`, 저장된 시나리오 `/scenarios/{id}`, 그리고 `EditorShell`의 세 마운트(기본 `<FlowOutline />`, 「스텝 넓게 보기」 `wide`, 「변수 넓게」 `varsWide`).

| US | 절차 | 통과 신호 |
|---|---|---|
| US1 | 준비 스텝 3개 시나리오에서 ① Inspector ↓ ② 준비 행을 끌어 순서 바꿈 → test-run | 아웃라인 순서 = 저장 뒤 `GET /api/scenarios/{id}`의 `yaml` 속 `setup.steps` 순서 = test-run 결과의 준비 행 순서 |

극단값(같은 화면에서):

- 긴 스텝 이름·긴 URL의 준비 행: 손잡이가 생긴 뒤에도 이름이 말줄임되고 행이 상자 밖으로 넘치지 않음(rect 실측).
- 본 스텝이 많아 목록이 스크롤된 상태에서 http 스텝을 집어 맨 위까지 끎: 자동 스크롤로 맨 위 영역에 닿아 놓을 자리가 열리고 놓임. 집는 행을 둘로 — 화면 아래쪽 행, 패널 위쪽 가장자리 바로 아래 행.
- 목록이 조금만 스크롤된 상태(scrollTop ≈ 10px)에서 놓을 자리를 엶: 깜빡이지 않고 열린 채 유지. 세 마운트 각각(스크롤하는 요소가 다르다).
- 목록 맨 위를 지나쳐 위(패널 여백, 넓게 보기의 흐름 칩 줄)까지 끌어 놓음: 열린 채이고 준비 스텝이 됨. 세 마운트 각각.
- 준비 스텝 20개: 상자 안 순서 바꾸기·상자 안 버튼이 동작.
- 창 폭 1024.
- 끄는 동안 형제 행의 밀림을 rect로 실측(놓은 뒤의 순서만 보지 않는다 — `ui/src/components/scenario/CLAUDE.md`의 끌기 검증 함정).

성능: 본 요청 경로를 건드리지 않는다(UI만) — 워커 성능 비교는 하지 않는다.
