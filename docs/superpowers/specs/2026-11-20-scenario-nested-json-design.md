# 시나리오 쪽 감싼 JSON 풀기 (설계)

- 날짜: 2026-11-20 · 유형: user-path · roadmap §B47 (2)(사용자 지적 2026-11-09)
- 슬러그: `scenario-nested-json` · 선행: monitor-nested-json(`98772573`, roadmap §B47), ops-monitor-polish 1차(모니터 경로만 풀기)
- 범위 결정(사용자 2026-11-20): US 4개와 §4 판단 1–6 승인. 성능 질문 → §7 측정 행으로 답한다.
- 상태: 구현됨(코드 `079b4c76`..`05bfab5a`, master 미합류) — §6 깊이 테스트가 멈춤 조건에 걸려 사용자 판단 대기. §8의 "미리 실행만 1 MiB"는 저장되는 trace 본문 얘기이고 추출은 원 본문 전체로 돈다(구현 중 적발). 판단·연기·수치 → roadmap §B72.

## 사용자 스토리 (US)

(사용자 승인 2026-11-20)

- **US1**: QA가 응답이 `{"data":"{\"id\":7}"}`처럼 JSON을 문자열로 감싸 주는 스텝을 에디터에서 미리 실행한다. 성공하면 응답 본문 트리에서 `data` 아래 `id`가 펼쳐져 보이고, 「문자열로 감싼 JSON을 풀어서 표시 중」 안내가 본문 머리에 뜬다.
- **US2**: QA가 그 `id` 잎에서 `+추출`을 눌러 확정한다. 성공하면 경로 `$.data.id` 추출이 스텝에 추가되고, 다시 미리 실행하면 그 변수에 `7`이 들어 있다.
- **US3**: QA가 그 시나리오로 부하 run을 돌린다. 성공하면 그 스텝의 추출 실패 에러가 0건이고, 뒤 스텝 요청에 추출한 값이 실려 나간다(로깅 응답기 와이어로 확인).
- **US4**: QA가 감싼 JSON이 없는 기존 시나리오를 돌린다. 성공하면 추출 값·에러 문구·리포트가 이전과 같다.

## 1. 왜

모니터는 감싼 JSON 안쪽 경로(`$.data.id`)를 찾는데(roadmap §B47), 시나리오 쪽은 바깥 1겹도 풀지 않는다. 에디터 미리 실행 트리는 `JSON.parse` 한 번이라 감싼 값이 문자열 잎 하나로 보이고, 엔진 본문 추출은 `serde_json::from_slice` 한 번이라 `$.data.id`가 `no match`다. 감싼 JSON을 주는 API에서 QA는 토큰·ID를 추출하지 못해 시나리오를 짤 수 없다 — 모니터에선 되는데 시나리오에선 안 되는 불일치다. 1차 spec이 비목표 한 줄로 뺀 뒤 연기 기록이 없어 유실됐던 항목이다.

## 2. 목표 / 비목표 / 반목표

**목표**
- 엔진 본문 추출(`from: body`)이 원래 본문에서 경로를 못 찾을 때만, 모니터와 같은 규칙으로 감싼 JSON을 풀어 다시 찾는다. 엄격·너그러운 추출, 부하 3진입점·미리 실행 모두.
- 에디터 미리 실행 응답 본문 트리가 같은 규칙으로 풀어 보여 주고 안내 문구를 띄운다. 트리 잎의 `+추출`이 만든 경로는 엔진에서 트리에 보인 값과 같은 값을 낸다.
- 풀기 규칙 구현은 Rust 한 곳(엔진)에 두고 모니터가 그것을 쓴다. Rust↔TS는 공유 fixture로 묶는다.

**비목표**
- 헤더·쿠키 추출, `decode`/`claim` 경로에 풀기 적용(`claim`은 이미 디코딩된 JSON을 본다).
- 트리의 객체·배열 칸에 `+추출` 붙이기(roadmap §B47 (1) 재개 조건 — 그대로 연기).
- `crates/tui/src/pick.rs`의 풀기 사본을 엔진 함수로 교체(자체 대조 테스트가 있다 — §B 연기 기록).
- 모니터의 **조건·표시 값 찾기**(`BodyJson`) 규칙 변경 — 함수의 소스 위치만 바뀌고 순서·결과는 같다. (모니터 칸이 돌리는 시나리오의 **본문 추출**은 엔진을 타므로 §4.5대로 바뀐다.)
- 본문이 JSON이 아닐 때의 동작·문구(`body not JSON: …`) 변경.

**반목표 (돌아가도 실패)**
- 지금 값을 찾던 추출 경로의 값이 달라진다(문자·숫자 표기 하나라도).
- 경로를 찾은 요청에 풀기 비용(훑기·복사·파싱)이 붙는다.
- 트리에 보인 잎 값과 그 잎에서 만든 추출이 부하 run에서 내는 값이 다르다.
- 에러 문구에 본문 조각이 새로 실린다.

## 4. 설계

### 4.1 찾는 순서 (엔진)

본문 추출 한 항목의 경로 찾기:

1. **원래 본문**(`from_slice` 결과)에서 찾는다. 찾으면 끝 — 지금과 같은 값, 추가 일 없음. 찾은 값이 JSON `null`인 것도 "찾음"이다(엄격은 `""`, 너그러운 쪽은 "못 뽑음" — 지금 규칙 그대로, 풀기로 넘어가지 않는다).
2. 못 찾았고 **본문 뿌리가 문자열**이면, 뿌리를 최대 3겹 풀어 객체·배열이 될 때 그 값에서 찾는다.
3. 그래도 못 찾으면 **안쪽 필드까지 푼 값**(2의 값, 뿌리가 문자열이 아니면 1의 값의 문자열 필드를 필드당 최대 3겹 푼 사본)에서 찾는다. 뿌리가 문자열인데 객체·배열로 풀리지 않으면(`"hello"`, 4겹 이상) 2·3은 찾을 것이 없다 — 바로 4.
4. 셋 다 없으면 지금과 같은 실패(`no match: {path}` / 너그러운 쪽은 못 뽑음).

2·3은 모니터 `BodyJson::path_first`(바깥만 푼 값 → 안쪽까지 푼 값)와 같은 순서다. 엔진은 그 앞에 1을 둔다 — 본문이 JSON 문자열일 때 `$`로 통째 뽑는 기존 시나리오의 값을 지키기 위해서다(모니터는 바깥을 항상 먼저 푼다). 뿌리가 문자열이 아니면 1과 2의 값이 같으므로 2는 건너뛴다(같은 경로를 두 번 찾지 않는다).

찾은 값의 글자화(`stringify`)·`decode`·`claim` 처리는 어느 단계에서 찾았든 같다. 경로 글자는 항목당 한 번만 파싱해 1–3단계가 나눠 쓴다(지금 `jsonpath_first`는 부를 때마다 파싱한다 — 못 찾는 경로에서 같은 글자를 세 번 파싱하지 않는다).

**규칙 세부(모니터와 동일, 바꾸지 않는다)**: 문자열은 JSON 공백 4종 뒤 첫 글자가 `{`·`[`·`"`일 때만 후보. 한 문자열을 최대 3번 파싱해 객체·배열이 되면 그 값, 아니면 원래 문자열 그대로. 푼 값 안의 문자열 필드도 다시 후보(필드당 3겹, 누적 한도 없음).

### 4.2 코드 배치

- 풀기 함수 묶음(`MAX_JSON_UNWRAP`·`unwrap_json_str`·`parse_body_json`·`unwrap_nested`)을 엔진으로 옮긴다(`crates/engine/src/extract.rs` 또는 새 모듈 — plan이 정한다). `check.rs`는 엔진 것을 가져다 쓴다. `BodyJson`(모니터의 "바깥 먼저" 순서)은 모니터에 남는다.
- 엔진 `BodyCache`가 2·3의 값을 응답당 한 번만 만들어 같은 응답의 다른 본문 항목과 나눠 쓴다.
- `unwrap_nested`는 **실제로 풀리는 문자열이 하나도 없으면 본문을 복사하지 않고** `None`을 낸다(지금은 항상 `root.clone()` 뒤 훑는다 — 결과는 같고 복사만 없앤다. 모니터도 같은 함수를 쓰므로 함께 빨라진다). 방법: 읽기 전용으로 훑어 "풀리는 문자열이 있는가"를 먼저 답하는 함수를 따로 두고, 있을 때만 복사해 푼다. 첫 글자가 `{`·`[`·`"`인 평범한 문자열(`[INFO] …`·`{name}`)은 후보지만 풀리지 않는다 — 파싱 시도 한 번만 들고 복사는 일으키지 않는다.
- 모니터 쪽 fixture 테스트는 `BodyJson`이 `pub(crate)`라 `check.rs` 안 `#[cfg(test)]`에 두고 `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../../testdata/…"))`로 읽는다(`export.rs` 선례).
- `crates/tui/src/pick.rs`·`crates/tui/tests/pick_test.rs`의 "서버 `check.rs` …와 같다" 주석은 옮긴 위치를 가리키게 고친다(주석만, 코드 무변경).
- 에러 문구는 새로 만들지 않는다. 풀기 중 파싱 실패는 "후보가 아니었다"로 조용히 넘어간다(`serde_json::Error`를 문구에 싣지 않는다).

### 4.3 에디터 트리

- `TestRunPanel`이 응답 본문을 `parseBodyJson`으로 읽어 그 값을 `ResponseBodyTree`에 넘긴다(`PreviewResult`와 같은 방식 — `BodyBlock`은 고치지 않는다). 읽기는 `useMemo([body, truncated])`로 응답당 한 번(`+추출` 확인 줄을 여닫을 때마다 최대 1 MiB를 다시 읽지 않는다). 본문이 잘렸거나 JSON이 아니면 지금의 안내(`본문 필드 추출 불가 …`) 그대로.
- `unwrapped >= 1`이면 **트리 바로 위**에 안내 문구 한 줄을 띄운다 — `tree.render`가 내는 조각 안에 넣는다. 그래서 트리가 서는 곳마다(짧은 본문의 인라인 트리, 긴 본문의 「전체 보기·추출」 창 트리 보기) 안내가 함께 선다. 풀 것이 없는 응답엔 줄이 추가되지 않는다(`BodyBlock`에 `heading`을 넘기지 않는다 — 넘기면 모든 응답에 머리 줄이 생긴다). 문구는 모니터와 같은 글자(「문자열로 감싼 JSON을 풀어서 표시 중」). (부재 중 판단 — roadmap §B에 기록.)
- `SequentialRunPanel`은 같은 `TraceStepList`를 그리므로 따로 고칠 곳이 없다 — 라이브에서 확인한다(§7).
- `parseBodyJson`은 모니터 전용 모듈(`ui/src/monitor/conditions.ts`)에서 공용 위치로 옮기고 모니터 두 곳(`PreviewResult`·`RecordBody`)은 그것을 가져다 쓴다(위치는 plan이 정한다). 함수 동작은 그대로.
- 「전체 보기」 창의 원본·「JSON 포맷」 보기는 원래 본문 글자를 그대로 보인다(풀지 않는다). 트리 보기만 푼 값.

### 4.4 트리 경로 = 엔진 값 (불변식)

트리의 스칼라 잎 경로는 `segmentsToPath`가 만든다(`$`·`.이름`·`[n]`·`['…']`만). 그 경로에 대해:

- 잎이 풀린 칸 밖이면: 원래 본문에 같은 경로·같은 값이 있다 → 1단계에서 찾는다.
- 잎이 풀린 칸 안이면: 원래 본문에서 그 경로는 문자열 값을 지나가므로 못 찾는다 → 2·3단계가 트리와 같은 값을 찾는다.
- 본문 뿌리가 감싼 JSON이 아닌 문자열(`"hello"`)이면 트리는 `$` 잎 하나이고 1단계가 찾는다.

이 불변식을 공유 fixture로 잠근다(§6).

**전제와 알려진 어긋남**: 불변식은 "감싼 글자가 두 파서(`JSON.parse`·`serde_json`)에서 똑같이 읽힐 때" 성립한다. `JSON.parse`만 받아들이는 입력에서는 트리에 잎이 보이는데 엔진은 `no match`다. 후보(구현 중 실측으로 확정 — 각각 fixture `known_divergence`에 한 건씩 고정):
- 짝 없는 서러게이트가 든 감싼 값(`\ud800`)
- 범위를 넘는 수가 든 감싼 값(`1e400`)
- 감싼 값 하나의 중첩이 `serde_json` 재귀 한도(128)를 넘음

이 셋은 모니터에 이미 있는 어긋남과 같은 종류다. 고치지 않고 fixture에 고정 + roadmap §B에 비용과 함께 기록한다(cost: 그런 응답에서 `+추출`한 경로를 run이 못 찾는다 — 드물다. 엄격 추출은 `no match` 에러로 드러나지만, 기본값 항목은 기본값이, 조건 반복 안 너그러운 추출은 빈 값이 **조용히** 들어간다). 별개로 선재하는 어긋남: 미리 실행 본문은 1 MiB에서 잘리고 UTF-8이 깨진 바이트는 대체 문자로 보이지만 엔진은 원 바이트에서 뽑는다(이번에 안 바뀜).

### 4.5 행동이 바뀌는 곳

지금 "못 찾음"이던 본문 추출이, 감싼 값 안에 그 경로가 있으면 성공한다. 그래서:

- 엄격 추출: 그 스텝의 `no match` 에러가 사라진다.
- 기본값 항목·조건 반복 안 너그러운 추출: 기본값·빈 값 대신 실제 값이 들어간다.
- `$..name`·`$.*` 같은 손으로 적은 경로도 같은 순서를 탄다(원래 본문에서 하나라도 찾으면 그 값).
- **운영 모니터 칸**: 칸이 돌리는 시나리오의 본문 추출도 같은 엔진 길이라, 감싼 값 안 경로를 추출하던 칸은 「값 추출 실패」에서 정상 진행으로 바뀌고 뒤 스텝이 실제 값을 받는다(터미널 모니터도 같은 컨트롤러를 쓴다).

릴리즈 노트에 한 줄 적는다(시나리오·모니터 칸 둘 다 언급).

## 5. 성능

- **찾은 경로**: 1단계에서 끝난다. 추가 일 없음 — 라이브 ⓐ 측정이 지킨다.
- **못 찾은 경로, 후보 문자열 없음**: 응답당 한 번, 파싱된 본문을 훑으며 문자열의 첫 글자만 본다. 복사·파싱 없음. 같은 응답의 다음 본문 항목은 캐시된 "없음"을 본다.
- **못 찾은 경로, 후보는 있으나 풀리는 것 없음**: 위 + 후보 문자열마다 파싱 시도 한 번. 복사 없음.
- **못 찾은 경로, 풀리는 문자열 있음**: 응답당 한 번, 본문 복사 + 후보 문자열 파싱(읽기 전용 훑기가 첫 성공에서 멈추며 그 문자열을 한 번, 풀기 순회가 다시 한 번 파싱한다 — 이 갈래에만 드는 작은 중복).
- 못 찾는 응답이 일상인 시나리오(조건 반복 폴링·기본값 항목)가 이 비용을 매 응답 낸다. working-rules §10대로 기준선(master)과 비교한다. 두 가지로 잰다:
  - **엔진 미세 측정**(`#[ignore]` 테스트, 고정 시간 상한 없이 비율로): 후보 문자열 없는 본문(≈100 KiB)에서 못 찾는 본문 항목 하나의 평가 전체(본문 파싱 포함)를, 같은 테스트 안에 사본으로 둔 옛 길(파싱 + `jsonpath_first` 한 번)과 비교. **멈춤 기준 = 1.25배 초과**.
  - **라이브**: 워커 프로세스 CPU 시간 ÷ 요청 수(`scripts/bench-throughput.sh` 방식 — 컨트롤러 PID의 자식 `ps -o time=` 차이)를 master와 이 브랜치에서. **멈춤 기준 = 찾는 경로만 있는 시나리오 ±3% 밖, 후보 없는 못 찾음 시나리오 +5% 초과**. 풀리는 문자열이 있는 못 찾음 시나리오는 새로 하는 일이라 기록만.
  - 라이브는 바이너리마다 3회 이상 돌려 중앙값으로 비교하고, **먼저 master 대 master 한 쌍**으로 회차 간 흔들림을 잰다. 흔들림이 기준(3%·5%)보다 크면 라이브 숫자는 기록만 하고 엔진 미세 측정이 판정한다.
  - 멈춤 기준을 넘으면 구현을 멈추고 설계로 돌아온다.

## 6. 테스트

- **공유 fixture** `testdata/nested_json_vectors.json`(기존 `testdata/pick_array_vectors.json` 방식): 사례마다 `body`(글자)와 `leaves`(트리 스칼라 잎의 `[경로, 값]` 전부 — **값은 JSON 값 그대로** 적고 글자화하지 않는다. 화면 `String(v)`와 엔진 `stringify`는 `1.0`·`1e2`·큰 정수에서 글자가 달라서다). 별도 `known_divergence` 묶음(§4.4)은 사례마다 "TS 잎 있음 / Rust 못 찾음"을 적는다 — fixture 파일 자체를 Rust가 `serde_json`으로 읽으므로, 어긋나는 글자(`\ud800`·`1e400`)는 `body` 글자 안(감싼 값 안쪽)에만 두고 사례가 가리키는 잎은 그 감싼 값 안의 **평범한 다른 잎**(`$.a.id` = `7`)으로 한다. 세 곳이 읽는다.
  - TS: `parseBodyJson(body)` 값의 스칼라 잎을 `segmentsToPath`로 나열한 **집합**이 `leaves`와 같다(JS는 정수 모양 키를 앞에 두므로 순서 비교 금지). 잎 나열은 테스트용 순수 함수로 — 트리 컴포넌트와 같은 "스칼라만 잎" 규칙.
  - 엔진: `leaves`의 경로마다 경로 찾기(1–3단계)가 그 JSON 값을 낸다. 추출 결과로는 — 엄격: `stringify(값)`(`null`은 `""`). 너그러운 쪽: `null`이 아닌 잎은 `stringify(값)`, `null` 잎은 못 뽑음(§4.1 — 1단계 규칙과 같게 2·3단계에서 찾은 `null`도 못 뽑음).
  - 모니터(`check.rs` 안 테스트): `leaves`의 경로마다 `BodyJson::path_first`가 그 JSON 값을 낸다.
  - 사례: 평범한 객체(풀 것 없음) · 필드 1겹·3겹·4겹(4겹은 안 풀림) · 뿌리 1겹·3겹 · 뿌리 평범한 문자열 · 푼 값 안의 감싼 필드 · 배열 원소가 감싼 JSON · 감싼 빈 객체·빈 배열(잎 없음) · `{`로 시작하지만 JSON 아닌 문자열 · 공백 뒤 `{` · 감싼 값 안 `null`·숫자·불리언 · 이름에 점·따옴표가 든 키.
- **엔진 순서 테스트**(fixture 밖, 엔진만의 1단계): 뿌리가 감싼 JSON일 때 `$`는 원래 문자열 · `$.data`가 원래 문자열이면 그 문자열(풀린 객체 아님) · 원래 본문에서 `null`을 찾으면 풀기로 안 넘어감(엄격 `""`, 너그러운 쪽 못 뽑음) · `$..id`가 원래 본문에 있으면 그 값.
- **불변 테스트**: 기존 `extract.rs` 단위·`tests/extract_*.rs` 전부 무수정 통과(US4). `no match: {path}`·`body not JSON: …` 문구 그대로.
- **`unwrap_nested` 동등성**: 옛 구현(항상 복사)을 테스트 안에 사본으로 두고 fixture 본문 전부 + 후보-있으나-안-풀림 본문에 대조해 결과가 같다. "풀리는 문자열이 있는가" 함수는 따로 단위 테스트(없음·후보만·풀림 각각). **복사가 없다는 것 자체는 `None` 단언으로 못 본다**(옛 구현도 `None`을 낸다) — §5 미세 측정이 지킨다: 되돌려 확인(teeth check)으로 복사를 되살리면 비율이 멈춤 기준을 넘는지 한 번 실증한다. 넘지 않으면(복사가 파싱에 묻히면) 그 측정은 복사를 못 지키는 것이니, "훑기만" 대 "훑기+복사" 비율을 따로 재는 측정을 더해 그쪽에 기준을 둔다.
- **깊이**: 풀기 사슬(푼 값 안의 감싼 필드…)로 한 번의 파싱 한도(128)보다 깊은 값이 만들어질 수 있다(겹마다 이스케이프가 배로 늘어 사슬 길이는 본문 크기의 로그 — 1 MiB에서 2천 단계 남짓). 순회는 반복문이지만 `Value` 복사·해제·`$..` 찾기는 재귀다. 2 MiB 스택 스레드에서 그런 본문(≈1 MiB, 그리고 ≈16 MiB)의 못 찾는 추출이 넘치지 않음을 테스트한다 — 경로는 평범한 `$.a.b`와 `$..x` 둘 다(재귀 찾기는 `$..`만 탄다). **넘치면 멈추고**: 풀기 사슬 길이 한도를 세 구현(엔진·TS·TUI)에 같이 넣는 쪽으로 설계를 고쳐 사용자에게 보고한다.
- **모니터**: 기존 `check.rs`·`monitor_*` 테스트 무수정 통과.
- **UI**: `TestRunPanel` — 감싼 본문에서 안쪽 잎이 보이고 안내가 뜬다 / 풀 것 없으면 안내 없음 / 안쪽 잎 `+추출`이 `$.data.id`를 만든다. 회귀 가드는 되돌려 확인(teeth check)한다.

## 8. 보안

본문 추출 경로를 건드리므로 최종 `security-reviewer` 대상이다. 짚을 곳:

- 부하 경로 응답 본문엔 크기 상한이 없다(미리 실행만 1 MiB). 못 찾는 경로 + 풀리는 문자열이 있으면 VU마다 본문 사본이 하나 더 생긴다. 한 겹 풀 때마다 이스케이프가 줄어 총 파싱량은 본문 크기의 작은 배수로 묶인다. `serde_json` 재귀 한도(128)는 파싱 한 번의 깊이만 막는다 — 풀기 사슬로 더 깊은 값이 만들어질 수 있어 §6 깊이 테스트로 확인한다(미리 실행·모니터는 컨트롤러 프로세스 안에서 돈다).
- 풀린 값에서 뽑은 문자열이 변수로 들어가 뒤 요청에 실린다 — 지금도 본문 문자열을 그대로 변수로 쓰므로 새 통로는 아니다.
- 에러·로그 문구에 본문 조각을 새로 싣지 않는다(§4.2).

## 9. 구현자에게 남긴 것

- 풀기 함수의 모듈 위치·이름, `BodyCache`의 모양.
- `parseBodyJson`의 공용 위치와 안내 문구 `ko` 키(모니터 키 재사용 또는 공용 키로 이동 — 글자는 같게).
- "풀리는 문자열이 있는가" 함수와 그 뒤 풀기 순회의 구체 구현(첫 성공에서 멈추는 읽기 전용 순회 뒤 복사).
- `BodyCache`에서 2·3단계 값을 늦게 만드는 방법(`parse_body`가 캐시 참조를 돌려주므로 `OnceCell` 같은 안쪽 가변성이 필요하다 — `BodyJson` 선례).
- 엔진 task를 UI task보다 먼저(UI만 먼저 들어가면 엔진이 못 찾는 `+추출` 경로가 생긴다).
