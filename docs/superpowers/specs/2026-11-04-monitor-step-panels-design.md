# 운영 모니터 — 점검 묶음(스텝별 칸) + 분기 판정 + 빈 컨테이너 수정 (설계)

- 날짜: 2026-11-04 · 유형: `user-path` (+ `correctness-bug` 1건) · 브랜치 `worktree-monitor-step-panels`
- 결정 원천(단일 소스): `docs/superpowers/specs/2026-11-04-monitor-step-panels-mockups/00-decisions.md` + 같은 폴더 목업 3장(`01-editor-grouping.html` A안, `02-nav-numbering.html` 1안, `03-wall-states.html`). **목업 밖 화면을 만들지 않는다**(사용자 지시) — 기능상 불가피한 예외는 §8.1에 명시하고 사용자에게 보고한다.
- 선행: ADR-0053(운영 모니터)·ADR-0054(보드 파일). 이 설계는 ADR-0053에 "보완" 절로 기록한다(새 ADR 아님 — 같은 결정의 확장, [Claude]). 보완 절에 §4의 시간 상한 변경(묶음 흐름 상한 > 30초 가능)을 명시한다.

## 사용자 스토리 (US)

- **US1**: 운영자가 로그인이 필요한 API 흐름(1.0 로그인 → 2.0 로그인 → 경주 기초 → 경주 헤더 → 구매가능)을 계정 하나로 감시하려고 시나리오 하나로 점검 묶음을 만들고 스텝마다 칸을 둔다 — 성공하면 주기마다 로그인 요청이 **한 번만** 나가고(대상 서버 도착 요청 수로 확인) 칸 5개가 각자 자기 스텝의 응답속도·성공 조건으로 판정된다.
- **US2**: 운영자가 흐름 중간 단계(예 2.0 로그인)가 실패한 순간 화면을 볼 때 — 성공하면 그 칸만 빨강으로 깜빡이며 사유를 보이고, 뒤 칸들은 회색 "앞 단계 실패 · 2.0 로그인에서 멈춤"으로 깜빡이지 않고 연속 실패로 세지 않는다. 실패한 스텝에 칸이 없으면 그 뒤 첫 칸이 빨강으로 원인을 대신 보인다(장애가 조용한 회색으로만 보이지 않게).
- **US3**: 운영자가 응답 속 참/거짓 값으로 갈리는 분기(경마일/비경마일)를 감시할 때 — 성공하면 안 탄 분기의 칸이 빨강이 아니라 "○ 분기 제외"와 실제 값(`isRaceDay = false`)·기대 조건·IF 이름을 보인다. 분기 값을 못 꺼냈으면 그 칸이 실패로 보이고, 분기 값을 주는 응답 자체가 실패했으면 US2 규칙대로 원인 칸이 빨강·뒤 칸이 "확인 못 함"으로 보인다.
- **US4**: 운영자가 칸마다 "이 API는 N초"로 제한 시간을 정할 때 — 성공하면 그 스텝이 N초를 넘을 때 그 칸만 `시간 초과(N초)` 실패가 되고 뒤 칸들은 "확인 못 함"이 된다.
- **결함(재현/기대/실측)**: 재현 — 성공 조건 "값 있음"(`not_empty`)을 건 본문 경로가 `[]` 또는 `{}`를 반환. 기대 — 실패 "비어 있음". 실측 — 초록(정상): `check.rs` `actual_value`가 `stringify` 결과(`"[]"`, 2글자)를 텍스트로 쓰고 `op_passes`의 NotEmpty가 빈 문자열만 실패로 본다.

**함께 지킬 조건**: 기존 보드(묶음 없음)와 이미 내보낸 보드 파일은 지금과 똑같이 동작한다(§7 결함 수정만 의도된 예외).

## 2. 범위

**한다**: 점검 묶음(설정·감독자·판정·기록) · 스텝 칸 판정과 새 상태 2종(확인 못 함·분기 제외) · 칸별 스텝 제한 시간 · 엔진 trace에 분기 판정 근거 + 시간 초과 식별 · "값 있음" 빈 컨테이너 수정(모든 칸) · 설정/전시/기록 화면(목업 3장) · 보드 파일 왕복.

**안 한다(비목표)**: 배열 길이 추출(사용자 추후 요청) · 칸 9개 상한 변경 · 같은 시나리오 자동 묶기 · 묶음 안 "흐름 전체" 칸 · 혼자 실행(흐름 전체) 칸의 분기 처리 변경(§9) · 세션 유지(매 주기 로그인 그대로) · 묶음 간 칸 이동 · 화면 방식/배율 규칙 변경 · 시험 실행 화면에 분기 근거 표시(엔진 필드는 생기지만 UI 스키마·표시 무변경 — Zod가 모르는 키를 버림).

**슬라이스 분할 안 함** [Claude]: 리뷰어가 3분할(빈 컨테이너 / 묶음 / 분기)을 제안했으나, 묶음만 먼저 나가면 사용자의 실제 흐름(비경마일)에서 분기 칸이 "조건 스텝 미실행" 빨강이 되는 중간 상태가 생기고 사용자 우선순위가 묶음+분기 동시다. 하나의 plan에 task별 독립 green 커밋으로 순서화(빈 컨테이너 → 엔진 → 설정 → 감독자·판정 → 화면)한다.

## 3. 설정 모델 (와이어 = `config_json`, 가산적)

```text
BoardConfig {
  …기존 필드 그대로,
  groups: Vec<CheckGroup>          // 새로, 기본 [] — 기본값이면 직렬화 생략
}
CheckGroup {
  id: ULID,                        // 화면이 만든다(기존 newStepId 계열 ULID 생성기)
  scenario_id: String,
  environment_id: Option<String>,
  interval_seconds: u32,           // 1–3600
}
PanelConfig {
  …기존 필드 그대로,
  group_id: Option<String>,        // 새로, 기본 None = 혼자 실행 — None이면 직렬화 생략
  step_id:  Option<String>,        // 새로, 기본 None = 흐름 전체 — None이면 직렬화 생략
}
```

- 칸 판정 종류는 `step_id`로 갈린다: `None` = 흐름 전체(기존 `run_check`/`judge`, 무변경), `Some` = 스텝 칸(§5).
- **묶음 칸 = 스텝 칸**: `group_id: Some` ⇒ `step_id: Some` 필수. 묶음 안 "흐름 전체" 칸은 없다([Claude] — 조합 축소).
- `group_id: None` + `step_id: Some`(혼자 실행하는 스텝 칸)은 서버가 허용하고 **칸 1개짜리 묶음과 똑같이 실행**한다(스텝 칸 실행 경로는 하나). 미리 실행(§8.3)이 이 모양을 쓴다. 설정 화면은 이 모양을 만드는 입력을 두지 않는다. [Claude]
- **거울 필드**: 묶음 칸의 `scenario_id`·`environment_id`·`interval_seconds`는 서버가 소속 묶음 값으로 **덮어쓴다**(묶음 값이 권위). 근거: 내보내기·가져오기·분석이 `panel.scenario_id`/`environment_id`를 순회한다(`api/monitor_transfer.rs`, `monitor/transfer.rs`, `board_file.rs` R6) — 거울이면 그 순회는 무변경으로 정확. 단 가져오기는 R6이 정규화 앞에 돌므로 **R6 직전에 거울 덮어쓰기를 먼저 적용**한다(손으로 고친 파일에서 칸 사본과 묶음 값이 어긋나도 묶음 값 기준으로 참조 검사).
- **스텝 칸 정규화**(서버, 400 아님): `latency_source := Step{step_id}`, 조건·표시 값의 `step_id := 칸 step_id`(덮어쓰기). 화면은 스텝을 칸 단위로 한 번만 고르고, 스텝을 바꾸면 기존 조건·표시 값은 유지된 채 새 스텝을 대상으로 한다.

### 3.1 검증 순서와 오류 문구 (`validate_and_normalize`, 400 한국어 사유)
1. 보드 이름·`record_limit_kb`(기존).
2. `groups` 배열을 `panels`에서의 **첫 등장 순서로 정렬**(정규화 — 화면 머리 번호와 오류 번호 일치; 칸이 없는 묶음은 원래 순서대로 맨 뒤 — 어차피 아래에서 거부되지만 오류 번호가 정의되게). 묶음 각각 — 접두 `점검 묶음 N:`(N = 그 순서 1부터 = 목업 01의 묶음 번호): `id` ULID·중복 금지, `scenario_id` 비어 있지 않음, `interval_seconds` 1–3600, 소속 칸 0개면 "칸이 없는 점검 묶음입니다".
3. 칸 배치: 칸의 `group_id`는 존재하는 묶음을 가리켜야 함 · 같은 묶음 칸은 `panels` 배열에서 **연속** · `group_id: Some`이면 `step_id: Some`. (접두 `칸 N:`)
4. 거울 덮어쓰기 + 스텝 칸 정규화.
5. 칸 각각 기존 `validate_panel`(접두 `칸 N:` 그대로) + `step_id` ULID 형식(존재 여부는 실행 시 판정 — 시나리오가 나중에 바뀔 수 있음). 칸 9개 상한 등 기존 규칙 그대로.
- 화면: 기존 `parsePanelError`(`칸 N:` → 그 칸 펼침) 옆에 `점검 묶음 N:` → 그 묶음 상자 펼침을 추가.
- `board_warnings`(가져오기 경고)는 칸 `step_id`도 파일 속 시나리오에서 찾는다(기존과 같은 급의 경고).

## 4. 실행 (감독자)

- 감독자는 **실행 단위**로 task를 띄운다: 묶음 하나(또는 혼자 실행 스텝 칸 하나) = task 하나(주기 = 묶음 `interval_seconds`), 흐름 전체 칸 = 지금처럼 task 하나. `reconcile`의 "전부 멈추고 다시 띄움 + 살아남은 칸 id의 버퍼 유지" 규칙 그대로. 세마포어(`MAX_CONCURRENT_CHECKS`)는 실행 단위당 1개.
- 묶음 task 1회: 시나리오·환경을 DB에서 다시 읽고(지금과 같음) → 스텝 제한을 덮어쓴 시나리오 사본으로 trace 1회 → 칸마다 판정 → 각 칸 버퍼에 결과 push(각 칸 `bar_count`대로 자름). 한 회차의 모든 칸 결과는 **같은 `at_ms`**(기록 조회 키). 진행 중 표시(`running`)도 소속 칸 모두.
- 설정 오류(시나리오·환경 없음·파싱 실패)는 모든 칸 `config_error`. 일부 칸의 `step_id`만 시나리오에 없으면 **trace는 돌리고** 그 칸만 `config_error`(나머지 칸은 정상 판정) [Claude].
- **스텝 제한 시간** [Claude]:
  - 칸이 있는 스텝: 그 칸의 `timeout_seconds`(1–30)로 `HttpStep.timeout_seconds`를 덮어쓴다.
  - 칸이 없는 http 스텝: 시나리오 값이 있으면 `min(시나리오 값, 30)`, 없으면 5초.
  - 흐름 상한 `max_wall` = 시나리오 정의의 http 스텝별 유효 제한의 합, 최대 **120초**. 반복 안 스텝이 여러 번 돌아 넘으면 기존 `truncated` 처리.
  - 바깥 `tokio::time::timeout` = `max_wall` + 30초(가장 긴 단일 요청 제한) + 2초 — 엔진은 마감을 스텝 사이에서만 보므로 마지막 요청이 끝까지 갈 여유. 그래도 발동해 trace가 없으면 모든 칸 = `fail` `시간 초과(N초)`(N = 흐름 상한).
- 흐름 전체(`step_id: None`) 칸은 지금 경로 그대로 — `timeout_seconds` = 흐름 상한(의미 무변경).
- **화면 stale 기준**: `/status`의 `PanelStatus`에 `check_budget_seconds: u32`(그 칸 실행 단위의 바깥 제한 = 흐름 전체 칸은 `timeout_seconds`, 스텝 칸은 위 바깥 제한 초)를 추가한다. 값의 출처: 감독자가 회차마다 계산해 칸 버퍼에 저장하고 스냅샷이 싣는다(`/status`는 시나리오를 읽지 않는다 — 1초 폴링). 첫 회차 전·reconcile 직후 = 스텝 칸 **152초**(120+30+2 상한), 흐름 전체 칸 `timeout_seconds` — reconcile이 살아남은 칸의 결과 버퍼를 유지하더라도 저장된 예산 값은 **이 값으로 재설정**한다(편집 전의 작은 예산이 첫 긴 회차에 "확인 불가"를 내지 않게). 시나리오가 편집되면 다음 회차에 갱신. [Claude — 리뷰 2회차 2] 그리고 화면 `staleAfterMs`는 칸 `timeout_seconds` 대신 이 값을 쓴다(US1 흐름 3+3+5+5+5=21초 · 주기 10초에서 정상 회차가 "확인 불가"로 뒤집히지 않게). 흐름 전체 칸은 값이 같아 동작 동일.

## 5. 스텝 칸 판정 (`step_id: Some`)

입력: 시나리오, 칸, 묶음 trace, 묶음의 칸 배치. 아래 순서로 **처음 맞는 것** 하나.

**용어**
- *스텝 행*: trace에서 `kind=Http`이고 `step_id`가 그 스텝인 행. 여러 번 실행됐으면 판정은 **마지막 행** 기준(기존 규칙과 같음).
- *제외 결정 행*: 이 스텝을 감싼 IF 조상들을 **바깥에서 안쪽으로** 차례로 보며, 각 IF의 **마지막** 결정 행을 찾는다. 고른 분기가 이 스텝을 포함하면 안쪽 IF로 계속, 포함하지 않으면 그 행이 제외 결정 행(멈춤). 결정 행이 없는 IF를 만나면(도달 못 함) 멈추고 제외 결정 행 없음.
- *앞 구간*(trace 행 순서): 스텝 행이 있으면 **첫** 스텝 행보다 앞 / 없고 제외 결정 행이 있으면 그 행보다 앞 / 둘 다 없으면 trace 전체. 공통 제외: 이 스텝과 같은 `parallel` 조상의 **다른 분기**에 속한 스텝의 행(trace는 분기를 순서대로 돌지만 분기끼리는 독립).
- *엔진 수준 실패*: http 행의 `error`(상태코드 기대 불일치·전송 실패·시간 초과·추출 실패·본문 읽기 실패). 앞 칸의 **성공 조건** 실패는 해당 없음 [사용자 2026-11-04].

**판정 순서**
1. **설정 오류**: `step_id`가 시나리오 http 스텝에 없음 → `config_error` `REASON_LATENCY_STEP_MISSING`("응답 시간 기준 스텝 없음") 재사용.
2. **앞 단계 실패**: 앞 구간에 엔진 수준 실패 행이 있으면, 그중 가장 앞의 행의 스텝을 이 칸의 *원인 스텝*으로:
   - 원인 스텝에 같은 실행 단위의 칸이 있고 **그 칸의 판정이 `fail`/`config_error`이면** → `upstream_failed`, 사유 "앞 단계 실패", 상세 "<원인 스텝 이름>에서 멈춤".
   - 그 밖(원인 스텝에 칸이 없거나, 반복 안에서 앞 회차만 실패하고 마지막 회차가 성공해 그 칸이 빨강이 아님 — US2 둘째 문장): **이 규칙 2가 같은 원인 스텝으로 적용되는 칸들**(원인별로 묶음) 중 칸 배열 순서가 가장 앞인 칸 하나만 *대리 원인 칸*. 대리 원인 칸의 판정 = 원인 행에 규칙 3을 적용한 결과(`fail` 또는 변수 미설정이면 `config_error`, 시간 초과면 `시간 초과(N초)`), 사유 = "앞 단계 실패", 상세 = "<원인 스텝 이름> · <규칙 3 사유>" — 빨강·연속 실패·깜빡임 대상. 같은 원인의 나머지 칸은 `upstream_failed`. 원인이 여럿(서로 다른 `parallel` 분기 등)이면 원인마다 대리 칸 하나. [Claude — 리뷰 R1·2회차 1/3/6]
   - 따라서 판정은 칸별 순수 함수가 아니라 **실행 단위 전체를 한 번에** 계산한다(입력: 시나리오·trace·칸 배치, 출력: 칸별 결과).
3. **실행됨**(스텝 행 있음, 마지막 행 기준):
   - `error` → 기존 `classify` 사유로 `fail`(변수 미설정이면 기존처럼 `config_error`). 엔진이 시간 초과로 식별한 에러(§6.2)면 `시간 초과(N초)`(N = 이 스텝 유효 제한).
   - 성공 조건 → 기존 `eval_conditions` 규칙으로 `fail`.
   - 통과 → `ok`, `latency_ms` = 그 행 응답 시간.
4. **분기 제외**(제외 결정 행 있음): truncated 여부와 무관하게 이 규칙이 우선.
   - 막은 조건 = 제외 결정 행의 판정 근거(§6.1)에서: 앞 분기가 참이라 선점했으면 그 선점 조건(참), 이 스텝 분기의 조건이 거짓이면 그 조건(거짓). 그 조건의 *결정 잎*(§6.1)이 대상 미바인딩(`left_unbound`)이고 연산이 `exists`/`empty`가 아니면 → `fail` "분기 값 없음", 상세 "<IF 이름>".
   - 아니면 → `branch_skipped`, 사유(큰 줄) = `<대상 표기> = <대상 값 표기>`, 상세(작은 줄) = `조건 <대상 표기> <연산 기호> <기대 표기> · <IF 이름>`(목업 03). 표기 규칙 §6.3.
5. **그 외 미실행**: trace가 `truncated`면 기존 truncated 사유(요청 수 상한이면 `REASON_REQUEST_CAP`, 아니면 `시간 초과(N초)`, N = **흐름 상한**), 아니면 `fail` `REASON_COND_STEP_NOT_RUN`.

- 표시 전용 값(`display_items`)은 이 스텝 응답에서(기존 `display_values`).
- 새 상태 2종은 `latency_ms = None`.

### 5.1 와이어·연속 실패
- `Verdict`에 `UpstreamFailed`(`"upstream_failed"`)·`BranchSkipped`(`"branch_skipped"`) 추가.
- `consecutive_fail`은 **`fail`·`config_error`만** 센다(새 상태에서 끊김). 기존 세 상태뿐인 보드에선 결과 동일.
- `/status`의 "최신 결과에만 reason/detail/display" 규칙 그대로.

## 6. 엔진 (trace 전용 변경 — 부하 경로 무변경)

### 6.1 분기 판정 근거
- IF 결정 행에 필드 `branch_eval: Vec<BranchEval>`(`#[serde(default, skip_serializing_if = "Vec::is_empty")]` — http 행·기존 소비자 바이트 동일). 평가한 분기 조건마다(`if`, 그다음 평가된 `elif`들 — 참이 나온 데서 멈춤, `select_branch`와 같은 순서) 하나:
  `BranchEval { branch: "then"|"elif_{j}", passed: bool, leaf: Option<LeafEval> }`,
  `LeafEval { left: 원문, op, right: Option<원문>, left_value: 렌더 값(200자 상한), right_value: Option<렌더 값>, left_unbound: bool }`.
- *결정 잎*: `Compare`면 그 잎. `all`: 거짓이면 처음 거짓인 잎, 참이면 첫 잎. `any`: 참이면 처음 참인 잎, 거짓이면 첫 잎. 하위가 그룹이면 같은 규칙으로 재귀. 빈 `all`/`any`면 `leaf: None`(표기 = `조건 = 참`/`조건 = 거짓`).
- 계산은 trace 전용 함수(같은 `eval_condition` 의미론 재사용). **`passed`와 고른 분기가 `select_branch`와 반드시 일치** — 표 테스트로 잠금(then/elif/else/none × all/any/중첩/빈 그룹).
- 기록 보관(`record.rs`)은 "흐름 변수 폐기" 원칙대로 이 필드를 지운다.

### 6.2 시간 초과 식별
- `execute_step_traced`의 두 에러 반환(send `:515`, body `:552`)에서 `reqwest::Error::is_timeout()`이면 trace 행에 `timed_out: true`를 싣는다(`HttpTrace`→`StepTrace`, `#[serde(default, skip_serializing_if = "is_false")]`). 부하 경로의 `classify_send_error`와 별개로 최소 표면만. [Claude — 리뷰 F1]

### 6.3 표기 규칙 (화면·`/status` 노출)
- 대상 표기: `left` 원문이 정확히 `{{이름}}`이면 `이름`, 아니면 원문 그대로. 기대 표기: `right` 원문 그대로(템플릿이면 원문).
- 대상 값 표기 — **보안 규칙**: `left` 원문에 `${`가 있으면(환경 값 참조) 값을 내보내지 않고 `(환경 값)`. 그 밖엔 렌더 값(흐름 변수 = 응답에서 꺼낸 값 — ①b "조건 실패 값 표시"와 같은 급). 연산이 `exists`/`empty`면 값 대신 `값 있음`/`비어 있음`. 비밀 식별 로직은 두지 않는다(사용자 원칙 — 범용 도구).
- 연산 기호(IF 조건 전용 표, 성공 조건 라벨과 별개): `eq` `=` · `ne` `≠` · `lt` `<` · `gt` `>` · `lte` `≤` · `gte` `≥` · `contains` `포함` · `matches` `~` · `exists` `값 있음` · `empty` `비어 있음`.
- 길이: 화면은 기존 `…` 규칙(줄 수·글자 크기 불변).

## 7. 빈 컨테이너 수정 (모든 칸)

- 성공 조건 `not_empty`: 본문 경로 값이 빈 배열 `[]`·빈 객체 `{}`면 **실패, 사유 `REASON_EMPTY`("비어 있음")**. 두 곳을 고친다 — `op_passes`의 판정과 실패 사유 분기(`check.rs` ~:431-445, 지금은 `text.is_empty()`일 때만 `REASON_EMPTY`라 `[]`가 사유로 찍힘). `exists`·그 밖 연산·헤더·상태코드·본문 전체는 무변경.
- UI 라벨 `값 있음 (null·빈값 아님)`(`ko.ts` ~:1921)을 `값 있음 (null·빈값·빈 목록 아님)`으로.
- 혼자 실행 칸에도 적용(결함 수정 — 기존 보드 동작이 바뀌는 유일한 지점).

## 8. 화면

### 8.1 설정 화면 (목업 01 A안 + 02 1안)
- 칸 목록 본문: 묶음 = **상자**. 머리 = `점검 묶음 N` · 시나리오 이름 · 환경 · `N초마다 한 번 실행` · `칸 N`(목업 01 그대로), 접기/펴기. 상자 안 시나리오·환경·점검 주기 입력 1벌, 그 아래 소속 칸(접힌 줄 = `칸 N` · 이름 · `스텝: <이름>` · `제한 N초` · `조건 N`).
- 스텝 칸 입력: 칸 이름 · **볼 스텝**(시나리오 http 스텝 목록, IF 분기 안 스텝엔 `(<IF 이름> 분기 안)` 보조 표기 — 목업의 보라 글씨) · 제한 시간 · 느림 기준·그래프 설정 · 성공 조건 · 화면 표시 값(조건·표시 값에 스텝 선택 없음). 점검 주기·시나리오·환경 입력은 칸에 없음.
- 버튼(목업 01): 상자 안 `+ 이 묶음에 칸 추가`, 목록 끝 `+ 칸 추가 (혼자 실행)` · `+ 점검 묶음 추가 (스텝 골라 칸 여러 개)`. 점검 묶음 추가 = 빈 묶음 상자 + 빈 스텝 칸 1개 생성(시나리오를 고른 뒤 칸을 늘림) — 한 번에 여러 칸을 만드는 별도 선택 화면은 만들지 않는다 [Claude].
- 혼자 실행 칸의 접힌 줄: 보드에 묶음이 하나라도 있으면 목업처럼 `혼자 실행 ·` 접두와 `· 시나리오 전체` 접미를 붙인다. 묶음이 없는 보드는 기존 요약 그대로(기존 보드 화면 무변경) [Claude].
- **목업 밖 예외(보고 대상)**: 묶음 머리의 `묶음 삭제`(기존 `칸 삭제`와 같은 모양, 소속 칸 함께 삭제). 삭제 후 칸이 0개가 되면 비활성(기존 `canRemove` 규칙과 같음). 묶음의 마지막 칸을 지우면 묶음도 사라짐.
- 칸 9개 상한은 묶음 칸 포함 전체(버튼 비활성 규칙 그대로).
- 오른쪽 칸 목록(목업 02 1안): 번호는 화면 자리대로 이어서, 묶음 칸들은 연한 상자, 상자 머리 = `시나리오 이름 · N초`. 혼자 실행 칸은 상자 없음. 저장 오류 칸 ⚠·자동 펼침 그대로, `점검 묶음 N:` 오류면 그 묶음 상자 펼침.
- 묶음 시나리오를 바꿔 칸의 스텝이 새 시나리오에 없으면 기존 "조건 스텝 사라짐" 경고 계열로 칸에 표시, 저장은 막지 않음(실행 시 설정 오류).
- 와이어/상태: UI Zod는 `groups`·`group_id`·`step_id`를 `.optional()`(서버가 기본값을 생략하므로 — 이 필드들만 기존 `.nullable()` 관례의 예외; `group_id`/`step_id`는 `.nullish()` 아님 — 서버는 생략만 하고 `null`을 보내지 않는다). 편집 상태는 없는 것을 없는 그대로 두고, 저장 직렬화와 dirty 비교(`JSON.stringify` 기준선) 양쪽에 같은 정규화(빈 `groups` 키 제거·`undefined` 필드 제거)를 적용해 열자마자 dirty가 되지 않게 한다.

### 8.2 전시 화면 (목업 03)
- `panelState`: `upstream_failed` → `blocked`(확인 못 함), `branch_skipped` → `skipped`(분기 제외). `stale` 검사 뒤, `slow` 계산 앞. stale 기준은 §4 `check_budget_seconds`.
- B(테두리): 확인 못 함 = 실선 회색 테두리·흐린 글자, 상태 `― 확인 못 함`, 큰 줄 `앞 단계 실패`, 작은 줄 `<스텝>에서 멈춤` / 분기 제외 = 점선 회색 테두리·값은 밝게, 상태 `○ 분기 제외`, 큰 줄·작은 줄 §5-4. A(배경색) = 회색 배경 계열, C(실패만 크게) = 작은 칸에 머묾(`focusLayout`은 `fail`만 확대 — 무변경).
- 깜빡임 없음(`blinks`는 fail/slow만 — 무변경), "N회 연속" 줄 없음. §5-2의 대리 원인 칸은 `fail`이라 기존 실패 표시 그대로.
- 막대: 확인 못 함 = 회색 낮은 막대, 분기 제외 = 막대 없이 바닥에 작은 ○. 평균·최대는 기존 필터(`ok`만)로 제외.
- 기존 "확인 불가"(점검 멈춤)와 다른 문구. 모든 새 문구는 `ko.ts` 경유.
- 배율: 새 상태 글줄 수(큰 줄 1 + 작은 줄 1)는 실패 상태 이하 — 기존 배율 탐색이 덮는지 구현 시 확인, 안 덮으면 탐침에 추가. 극단값(9칸·긴 IF 이름·긴 대상 값·긴 스텝 이름)에서 겹침·잘림 금지.

### 8.3 미리 실행 · 기록 창
- 스텝 칸 `미리 실행`: 화면이 거울 필드(묶음의 시나리오·환경·주기)를 채우고 `group_id`는 **생략**, `step_id` 포함한 `PanelConfig`를 기존 엔드포인트로 보낸다 → 서버는 `step_id: Some`을 칸 1개짜리 묶음 경로로 실행·판정해 기존 `PreviewResponse{trace, result}`로 응답. 다른 칸의 스텝 제한 덮어쓰기는 반영 안 됨 [Claude]. 결과 클릭으로 조건 만들기는 이 칸 스텝 응답만.
- 막대 클릭 기록: 회차의 trace·잘림 정보는 **1벌**(`Arc`로 소속 칸 버퍼가 공유), 칸별 판정 결과는 각 칸 버퍼. 조회는 기존 `GET …/panels/{panel_id}/records/{at_ms}` 그대로 — 핸들러가 참조만 담은 직렬화용 구조체(`#[derive(Serialize)]` over `&CheckResult`·`&ScenarioTrace` 등)로 기존 응답 모양을 만든다(serde `rc` feature 추가 안 함). 응답의 `result` = 그 칸의 판정. 기록 창은 **그 칸 스텝 행을 펼친 채** 연다(흐름 전체 칸은 기존대로). 보관 개수 = 소속 칸 `bar_count`의 최댓값, 본문 상한 `record_limit_kb`는 회차 단위 — 지금과 같은 뜻.

## 9. 호환·알려진 한계

- 묶음 없는 보드: 새 필드가 생략되어 `config_json`·내보낸 파일이 지금과 **바이트 동일** → 옛 앱도 그대로 가져올 수 있다. 묶음을 쓴 보드 파일은 옛 앱이 모르는 키로 거부(ADR-0054 그대로). 형식 버전 1 유지. [Claude]
- 가져오기의 모르는 키 검사(`first_unknown_key`)는 **정확히 이 세 경로**(`config.groups`의 `[]`, `config.panels[*].group_id`·`step_id`의 `null`)의 명시적 기본값만 허용하도록 좁게 고친다(일반 "null·[] 무시" 금지 — ADR-0054 거부 규칙 약화 방지).
- 흐름 전체 칸의 분기 처리는 **무변경**: 안 탄 분기 스텝에 조건을 걸면 지금처럼 실패, 응답속도 기준이면 값 없는 초록. 칸 설정의 기존 도움말(HelpTip)에 "분기에 따라 달라지는 스텝은 점검 묶음 칸으로" 한 줄([Claude]).

## 10. 검증

- **단위(엔진)**: `branch_eval`의 `passed`·분기 == `select_branch`(then/elif/else/none × all/any/중첩/빈 그룹) · 결정 잎 규칙 · `left_unbound` · `timed_out`(send 시간 초과·body 시간 초과·비시간초과 에러) · http 행 직렬화 바이트 동일.
- **단위(서버)**: 스텝 칸 판정 표(1–5 각 가지, 2의 칸 있음/없음 대리·원인별 대리 칸(parallel 두 원인)·반복 마지막 회차 성공 시 대리·대리 사유가 시간 초과/변수 미설정일 때·미실행 칸이 대리 후보가 되는 경우, `groups` 첫 등장 순 정렬, `check_budget_seconds` 첫 회차 전 152·회차 후 계산값, 앞 구간 3형태, parallel 형제 제외, IF-in-loop 마지막 결정 행, truncated vs 분기 제외 우선, `시간 초과(N초)` N 값) · 빈 컨테이너(`[]`·`{}`·`[0]`·`{"a":1}`, 사유 문자열) · 검증 순서·문구(`점검 묶음 N:`/`칸 N:`)·연속성·빈 묶음·거울·정규화 · 가져오기 R6 거울 선적용 · `first_unknown_key` 세 경로만 허용(다른 `null` 키는 여전히 거부) · 묶음 1회차 = trace 1회(가짜 점검 카운터)·같은 `at_ms` · 연속 실패가 새 상태에서 끊김 · `check_budget_seconds` · 보드 파일 왕복(묶음 포함 **비기본값 픽스처** — 지난 슬라이스 교훈)·묶음 없는 보드 내보내기 바이트 동일.
