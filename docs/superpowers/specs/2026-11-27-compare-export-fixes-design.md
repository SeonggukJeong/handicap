## 2. 요구사항

### R1 (B1) — XLSX 글자 칸은 Excel 한도로 자른다

- `export.rs`의 비-테스트 코드에서 글자 칸은 **자르는 쓰기 도우미 하나**(이름은 builder 몫, 예 `put_text(ws, row, col, &str)` — 안에서 `xlsx_text`로 자르고 `write_string(...).expect("w")`)로만 쓴다. 리터럴 머리 칸도 같은 도우미를 쓴다 — 「사용자 글자인가」를 호출마다 판단하지 않게 하려는 것이다.
- 도우미 밖에 남아도 되는 `write_string` 계열은 넷뿐이다: 도우미 본문 1줄과 `write_delta_cell`의 3줄(`write_string_with_format` 둘 + `write_string` 하나 — 글자는 서버가 만든 변화율 `format_pct`이고 서식 인자가 달라 도우미에 못 넣는다). 주석 속 낱말(지금 862줄)은 세지 않는다.
- 기계 확인(두 상태): `#[cfg(test)]` 앞까지에서 `write_string`이 든 코드 줄 수. baseline(`97a5cb2b`)에는 사용자 글자를 자르지 않는 호출이 있다(예: 450·937·1072·1121·1242·1281·1282줄, 인사이트 329줄). 변경 뒤에는 위 넷 + 주석만 남는다. 정확한 baseline 줄 수와 변경 뒤 줄 수는 plan이 명령과 함께 적는다.
- **비교 `Setup` 시트의 라벨은 접미사를 지킨다**: 지금 `format!("{sid} p95_ms")`·`format!("{sid} error_count")`를 통째로 자르면 32,768자 id에서 두 행이 같은 글자가 된다. id를 `32_767 − 접미사 글자 수`로 먼저 자른 뒤 접미사를 붙인다.
- 잘린 칸의 내용은 앞 32,767자(`char` 기준 — rust_xlsxwriter 한도 `chars().count() > 32_767`과 같은 셈). 한도 이하인 글자는 바이트 그대로다(기존 XLSX 테스트가 그대로 통과).
- 테스트: 32,768자 스텝 id를 가진 리포트로 (a) `report_to_xlsx` (b) `comparison_to_xlsx`를 통째로 불러 패닉 없이 바이트가 나오고, calamine으로 다시 읽어 그 칸이 32,767자다. 준비 스텝·if 분기·창(`windows`)·인사이트 `step_id`에 같은 긴 id가 든 경우를 함께 넣는다. 비교 `Setup` 시트는 두 행의 라벨이 서로 다르고 각각 ` p95_ms`·` error_count`로 끝나는지 본다.

### R2 (B2) — CSV 사용자 글자 칸의 수식 글자 막기

- 도우미 하나(이름은 builder 몫, 예 `csv_text`): 글자의 첫 글자가 `=`·`+`·`-`·`@`·탭(`\t`)·CR(`\r`) 중 하나면 앞에 `'`를 붙이고, 아니면 그대로 돌려준다. 빈 글자는 그대로.
- 적용 칸 — CSV에 **사용자 글자가 칸 맨 앞에 오는** 곳 전부:
  - 단일 CSV(`report_to_csv`)의 스텝 행 첫 칸 `step_id`
  - 같은 함수 준비 스텝 블록의 첫 칸 `setup_step_id`
  - 인사이트 CSV(`insight_csv_cells`)의 `step_id` 칸 — 단일·비교 인사이트 CSV 둘 다 이 함수를 쓴다
- 적용하지 않는 칸과 이유: 숫자 칸(음수의 `-`를 건드리면 안 된다), 서버가 만든 run id(ULID), 비교 CSV의 `step:{sid}:{metric}` 칸(늘 `step:`으로 시작), 고정 낱말 칸(`kind`·`severity`·`metric`·`status_class`·`cause`·`error_kind`), 계단 CSV(`report_to_stairs_csv` — 서버가 만든 머리말 줄·숫자·상태 이름·사유 글자뿐, 사용자 글자 칸 없음).
- XLSX는 대상이 아니다: `write_string`은 칸을 글자 형식으로 쓴다(수식은 `write_formula`만 만든다).
- 값이 바뀌는 범위: 위 글자로 시작하는 id만. 그 밖의 CSV 바이트는 그대로다(기존 CSV 테스트가 그대로 통과).
- 테스트: 여섯 시작 글자 각각 + 보통 id + 빈 글자의 도우미 단위 테스트, `=1+1` 스텝 id로 단일 CSV·준비 블록·인사이트 CSV 통째 테스트(첫 칸이 `'=1+1`).

### R3 (B3) — 비교의 준비 스텝 p95에 60초 칸 규칙

- 비교 XLSX `Setup` 시트의 `{sid} p95_ms` 행: 값은 `cap_ms(st.p95_ms)`의 앞 값(60,000 이상이면 60000), 변화율 칸은 `delta_of("p95_ms", …)`에 잘림 여부를 실어 계산한다 — Δ 칸의 식·모양이 본 스텝 Steps 시트의 Δ 칸과 같다. (본 스텝 Steps 시트의 값 칸은 µs에서 온 값을 자르지 않고 쓴다 — 그것은 이번에 바꾸지 않는다.) 둘 다 안 잘렸으면 지금과 같은 바이트다.
- 비교 화면 `compareReports.ts`의 `setupRows` p95 행: 값이 60,000 이상이면 `value` 60000, 변화율은 `computeDeltaCapped`(잘림 실어서). **잘린 칸에만** `time: { us: CAP_US }`를 실어 `CellContent`가 「≥ 60,000」을 그리게 한다. 안 잘린 칸은 `time` 없이 지금처럼 정수 글자(`200`)다 — µs가 없는 값에 `.000`이나 「0 µs」를 만들지 않는다.
- 비교 CSV에는 준비 스텝별 행이 없다(`setup_ok`·`setup_failed`만) — 바뀌지 않는다.
- `setup_errors`·`setup_ok`·`setup_failed` 행은 그대로다.
- 식의 동등성: `delta_of`와 `computeDeltaCapped`는 이미 골든 fixture `testdata/compare_golden.json`의 `expected.capped` 표를 양쪽이 읽어 맞춘다. fixture에 `setup`이 든 리포트는 없다. 새로 생기는 것은 「`cap_ms`를 먼저 적용한다」이므로 양쪽 단위 테스트에 같은 입력 셋(60030 vs 200, 200 vs 60030, 60030 vs 60100)과 같은 기대(값 60000·`capped`·방향)를 넣는다.

### R4 (B4) — 비교 인쇄의 99%·95%·평균은 `stats`에서 읽는다

- `ui/src/print/compare/change.ts`의 `p99_ms`·`p95_ms`·`mean_ms` 행: `stats`가 있으면 값 = `stats.p99_us / 1000`·`stats.p95_us / 1000`·`stats.mean_us / 1000`, 잘림 = `p99_us ≥ CAP_US`·`p95_us ≥ CAP_US`·`stats.capped`. `stats`가 없으면 지금 식(정수 칸, `≥ 60000`).
- `ui/src/print/compare/dumbbell.ts`의 95% 덤벨: 그 단계 행에 `stats`가 있으면 `{ ms: stats.p95_us / 1000, cut: stats.p95_us >= CAP_US }`, 없으면 지금 식.
- R4는 글자 형식을 바꾸지 않는다 — 입력 값만 바뀐다. 달라지는 것은 변화율·「비슷/좋아짐/나빠짐」 판정, 반올림 경계의 값 글자, 그리고 같은 행을 받는 첫 쪽 종합 문장·요약 문장(`buildHeadline`·`cmpSummaryLines`가 이 행들을 읽는다).
- 한쪽 run만 `stats`가 있으면 각 쪽이 제 출처를 쓴다(옛 run과 새 run의 비교 — spec 결정: 옛 run은 신경 쓰지 않는다, verdict-stats-b 결정 1).
- 테스트: B4 재현 값(`p95_us` 100000 vs 105400, 정수 칸 100·105)으로 95% 행의 분류가 `similar`가 아니라 나빠짐이고 변화율 값이 0.054(허용 오차 1e-9)다. 덤벨도 같은 입력으로 분류를 본다. 고의로 정수 칸 식으로 되돌리면 RED가 되는 것을 확인한다.

### R5 (B5) — 비교 화면 오류율은 퍼센트 글자

- `CompareMatrix`의 `CellContent`: `metric === "error_rate"`이고 값이 있으면 `floorPct(value * 100)`(`ui/src/components/report/format.ts`). 0 → 「0.0%」, 0.0123… → 「1.2%」, 0보다 크고 0.05% 미만 → 「<0.1%」.
- 변화율 칩·`compareReports.ts`의 값(비율)·내보내기는 그대로다(CSV·XLSX의 `error_rate`는 비율 숫자 그대로 — 기계가 읽는 값).

### R6 (B6) — 인쇄 응답 시간 글자는 60초 미만에서 「60.0초」가 되지 않는다

- 고치는 곳은 `ui/src/print/format.ts`의 **`fmtMs`**(응답 시간 글자)다. `fmtDurMs`는 그대로 둔다 — think time 같은 길이에도 쓰이고(`ui/src/print/conditions.ts` 107줄) 거기서 59,950ms → 「60.0초」는 맞는 반올림이다. (§B100은 「`fmtDurMs`가」라고 적었지만 헷갈림이 생기는 자리는 60초 칸이 있는 응답 시간뿐이다.)
- 규칙: `ms < 60000`인데 `fmtDurMs(ms)`가 `fmtDurMs(60000)`과 같은 글자면 `fmtDurMs(59900)`의 글자(「59.9초」)를 돌려준다. `ms >= 60000`은 지금처럼 「60초 이상」.
- 그 밖의 모든 값은 글자가 그대로다.
- 테스트: 59,950 → 「59.9초」, 59,999 → 「59.9초」(이 둘이 고치기 전에 실패하는 값이다 — 되돌려 확인에 쓴다), 59,949 → 「59.9초」, 59,900 → 「59.9초」, 60,000 → 「60초 이상」(이 셋은 지금도 통과), `fmtDurMs(59950)`은 여전히 「60.0초」.

### R7 (B7) — 비교 화면은 좁은 창에서 페이지를 밀지 않는다

원인은 B7 실측대로 둘이다(표, 겹쳐 보기 그래프).

- **시각 기준 = 목업 `docs/superpowers/mockups/2026-11-27-compare-narrow.html`의 「안 C」**(사용자 선택 2026-11-27, 세 안 중 추천안): 이름 칸 폭 7rem + 왼쪽 고정(`position: sticky`), 값 칸만 옆으로 밀린다. 긴 이름은 한 줄 말줄임, `title`은 지금처럼 전체 이름(`CompareMatrix.tsx` 141줄 근처).
