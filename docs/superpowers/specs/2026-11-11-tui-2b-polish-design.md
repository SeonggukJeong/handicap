## 사용자 스토리 (US)

**US1은 버그 — 재현 / 기대 / 실측**
- 재현: 응답 본문 `{"big":1e300,"tiny":2.5e-300}` → 요청·응답 `a` → `$.big` 줄 → `조건으로 추가` → `Enter`.
- 기대: 조건이 저장되고 다음 점검에서 통과한다.
- 실측: 값 칸에 `1` 뒤에 `0`이 300개 붙은 301자가 채워지고, 저장하면 서버가 `비교값은 200자 이하여야 합니다`로 거절한다. 원인: `crates/tui/src/pick.rs`의 `visit_f64`가 `format!("{v}")`(Rust `f64` `{}` — 지수 표기를 안 쓴다)로 글자를 만든다.

- **US1**: 운영자가 값 목록에서 아주 크거나 아주 작은 수를 골라 조건으로 추가한다 — 성공하면 조건 칸의 비교값이 짧은 지수 글자(`1e+300`·`2.5e-300` — GUI가 쓰는 표기 규칙)로 채워지고, `Enter`로 저장되며, 다음 점검에서 그 조건이 통과한다.
- **US2**: 운영자가 경로가 긴 본문 값의 조건을 새로 만들거나(값 목록) 이미 있는 조건을 고칠 때(칸 설정 11번) 어느 값에 대한 조건인지 확인한다 — 성공하면 조건 칸의 `대상`이 여러 줄로 이어져 끝까지 읽힌다(새 조건은 경로 뒤의 스텝 이름까지, 기존 조건은 경로 끝까지 — 11번의 대상에는 지금도 스텝 이름이 없다).
- **US3**: 운영자가 하위 화면(오류 보기·자세히·요청·응답·칸 설정·하위 목록·변수 화면·값 목록)을 보는 중에 그 화면이 그릴 칸이나 상태를 찾지 못하게 된다 — 성공하면 빈 화면 대신 맨 위 줄·안내 문구·돌아가는 법을 알리는 키 줄(창이나 확인창이 떠 있지 않으면 `Esc 뒤로`)이 보인다. (TUI 안에서는 칸이 지워지는 길이 없어 라이브로 재현할 수 없다 — 사용자 승인 2026-11-11: 단위 테스트로만 확인.)

## 1. 목표 / 비목표

**목표**: US1~US3.

**비목표**
- **숫자 글자를 모든 수에서 GUI와 같게 만들기** — 표기 *규칙*만 맞춘다. 수 자체가 다르게 읽히는 본문 글자가 있다(§2.1-4, §9 첫 항목 — 선재 서버 문제).
- 2^53을 넘는 정수 꼴 글자를 GUI와 맞추기 — `u64`·`i64`에 들어가는 범위에서 GUI는 정밀도를 잃은 값(`12345678901234567000`)을 쓰고 TUI는 본문 글자 그대로(`12345678901234567890`)를 쓴다. 판정은 같다(서버가 f64로 비교). 그 범위를 넘는 정수 꼴(`18446744073709551616` 이상)은 `f64`로 읽혀 §2.1-2를 따른다.
- 서버의 사유·화면 표시 값에 나오는 숫자 글자(`1e300`·`1.0` — 엔진 `extract::stringify`) 바꾸기 — §9.
- 기존 조건(11번)의 대상에 스텝 이름 붙이기.
- `받은 값` 줄 줄바꿈(받은 값 전체는 선택 창 머리가 보여 준다 — tui-2b §3.1) · 값 칸(입력줄) 줄바꿈.
- §B52 (2)의 나머지(비밀 짐작·GUI 선재 갭·서버 제어 문자 거절·`fit_head` 1칸·높이 6줄 이하) — 그대로 연기.

## 2. 동작 규칙 (정본)

### 2.1 숫자 글자 (US1 — tui-2b §2.4의 "숫자 글자" 불릿을 대체)

본문 값 줄의 숫자 글자(`PickValue::Number` — 값 목록의 `받은 값` 열, 선택 창 머리, 조건 칸 `받은 값` 줄, 조건의 비교값에 **같은 글자**가 쓰인다):

1. 정수 꼴 글자 중 `serde_json`이 `u64`·`i64`로 읽는 것은 그 값 그대로 십진 표기 — 지금과 같다.
2. 그 밖의 수는 **`serde_json`이 읽은 `f64` 값에 JavaScript `String(number)`의 표기 규칙**을 적용한다:
   - 값이 0이면(`-0.0` 포함) `0`.
   - 십진 지수 `e`(값 = `d.ddd… × 10^e`, 가장 짧은 왕복 자릿수)가 **−6 ≤ e ≤ 20**이면 지수 없는 십진 표기(지금과 같다 — `0.000001`·`100.25`·`100000000000000000000`).
   - 아니면 지수 표기: `{가수}e{부호}{지수}` — 가수는 가장 짧은 왕복 자릿수(소수점 뒤가 없으면 정수만), 지수가 0 이상이면 `+`(`1e+300`·`1.7976931348623157e+308`·`1e+21`), 음수면 `-`(`1e-7`·`2.5e-300`·`5e-324`).
3. 기준 벡터 — **`serde_json`이 정확히 읽는 글자**(§11 ①로 TUI 쪽 글자와 GUI `String(JSON.parse(x))`가 같은 것을 확인, 테스트가 이 표를 그대로 쓴다):

| 본문 글자 | 숫자 글자 | | 본문 글자 | 숫자 글자 |
|---|---|---|---|---|
| `1e300` | `1e+300` | | `1e-6` | `0.000001` |
| `2.5e-300` | `2.5e-300` | | `1e-7` | `1e-7` |
| `5e-324` | `5e-324` | | `0.00000123` | `0.00000123` |
| `1.7976931348623157e308` | `1.7976931348623157e+308` | | `1.5e-7` | `1.5e-7` |
| `1e21` | `1e+21` | | `-1e300` | `-1e+300` |
| `1e20` | `100000000000000000000` | | `-2.5e-10` | `-2.5e-10` |
| `1e299` | `1e+299` | | `-0.0` | `0` |
| `1.0` | `1` | | `0.0` | `0` |
| `1.5` | `1.5` | | `100.25` | `100.25` |
| `1e5` | `100000` | | `3.0e2` | `300` |
| `1E5` | `100000` | | `0.1` | `0.1` |
| `18446744073709551616` | `18446744073709552000` | | `12345678901234567890`(1번) | `12345678901234567890` |

4. **`serde_json`이 한 끝자리 다르게 읽는 글자**(이 워크스페이스는 `float_roundtrip` 기능을 켜지 않는다 — §11 ②): 숫자 글자는 **서버가 읽은 그 값**의 글자다. GUI(JS는 정확히 읽는다)와 글자가 다르다. 기준 벡터(테스트가 그대로 쓴다):

| 본문 글자 | TUI 숫자 글자 | GUI 글자 |
|---|---|---|
| `1.5e-300` | `1.4999999999999998e-300` | `1.5e-300` |
| `9.720979928970337e2` | `972.0979928970336` | `972.0979928970337` |
| `4.5e250` | `4.4999999999999993e+250` | `4.5e+250` |

   이 글자가 맞는 쪽이다 — 서버는 실제 값을 같은 `serde_json`으로 읽고(`check.rs` `n.as_f64()`) 비교값은 `parse_finite`(`str::parse` — 정확)로 읽어 `==`로 비교하므로, TUI 글자로 만든 조건은 통과하고 GUI 글자로 만든 조건은 통과하지 못한다(선재 서버 문제 — §9 첫 항목). TUI와 서버는 한 프로세스의 같은 `serde_json`이라 읽은 값이 같다.
5. 숫자 글자는 26자를 넘지 않는다(§6 테스트가 `f64` 극값으로 단언). 서버 한도 200자·GUI 기준 40자에 걸리지 않는다.
6. 모든 숫자 글자는 `str::parse::<f64>()`로 읽으면 `serde_json`이 읽은 그 `f64`와 같다(가장 짧은 왕복 자릿수) — 그래서 `=` 조건이 통과한다. `"1e+300".parse::<f64>()`는 `Ok(1e300)`(§11 ③).

### 2.2 조건 칸의 `대상` 줄 (US2 — tui-2b §3.2·2a 조건 수정 칸)

조건 칸은 두 화면에 뜬다 — 값 목록(새 조건)과 하위 목록 11번(기존 조건). 두 화면에 같은 규칙:

1. `대상` 글자(`sanitize` 뒤)를 값 칸 폭 `fw`(= 조건 칸 폭 − 라벨 칸 9)로 **표시 폭 기준 줄바꿈**한다(`view::wrap_width` — 도움말 경로 줄과 같은 함수). 둘째 줄부터는 라벨 칸이 빈칸이다.
2. **`fw`가 8칸 미만이면 줄바꿈하지 않는다** — 지금처럼 한 줄 `fit`(폭 0에서 `wrap_width`는 글자마다 한 줄을 만든다).
3. 줄 수 우선순위는 지금 규칙 뒤에 붙는다: **필수 줄(대상 첫 줄·규칙·값·체크·오류) → `받은 값` → 안내 → 대상의 이어지는 줄**. 대상이 한 줄에 들어가면 화면은 지금과 글자까지 같다.
4. 이어지는 줄은 **위 목록에 3줄이 남는 한도까지만** 늘린다 — 조건 칸 높이 `h = min(본문 높이, 지금 높이 + min(이어지는 줄 수, 본문 높이 − 3 − 지금 높이))`(뺄셈은 0에서 멈춘다). "지금 높이"는 필수 줄 + `받은 값`·안내 줄 중 있는 것(현행 `cond_form_lines`). 목록 3줄로 보이는 것: 값 목록은 제목·표 머리·고른 줄, 하위 목록(표 머리가 없다)은 제목 + 목록 2줄 — 어느 쪽이든 고른 줄이 보인다.
5. 줄이 모자라 다 못 보이면 **보이는 마지막 대상 줄을 `…`로 맺는다** — 그 줄부터 남은 글자 전체를 폭 `fw`로 `fit`한 것(줄바꿈된 한 줄은 이미 폭 안이라 그 줄만 `fit`하면 `…`가 붙지 않는다).
6. 조건 칸 안의 줄 순서: 대상(1줄 이상) · `받은 값` · 규칙 · 값 · 체크 · 오류 · 안내 — 대상 줄이 늘어도 순서는 그대로.

### 2.3 칸·상태를 못 찾은 하위 화면 (US3)

1. 하위 화면(`Screen::Errors`·`Record`·`Body`·`Settings`·`EditList`·`EnvVars`·`ScenarioVars`·`Values`)을 그리는 갈래가 **아무것도 그리지 못하고 돌아오는 모든 경우**에 대체 화면을 그린다. 지금 코드의 그런 경우: 그 칸이 보드에 없음(`Errors`·`Record`·`Settings`·`EditList`·`EnvVars`·`ScenarioVars`·`Values`) · 화면 상태 없음(`views.errors`·`views.record`·`views.body`·`ui.values` — `Body`는 칸을 찾지 않으므로 이 경우뿐) · 하위 목록 종류를 못 정함 · 편집 상태가 없는데 칸 설정 화면도 못 만듦 · `draw_sub`의 `_` 갈래. 세션이 없거나 머리 줄을 만들 수 없는 경우(`running`·`monitor_screen()`이 `None`)는 대상이 아니다 — 하위 화면이 뜰 수 없는 상태다.
2. 대체 화면 = 다른 하위 화면과 같은 틀(맨 위 줄 + 본문 + 키 줄). 본문 첫 줄부터 `이 칸을 찾을 수 없습니다 — Esc로 돌아가세요`(흐리게, 폭이 좁으면 `wrap_width` 줄바꿈).
3. 키 줄(하위 화면은 `q 종료`를 싣지 않는다 — 현행 `sub_keys` 규칙): 종료 확인창이 떠 있으면 다른 하위 화면과 같은 확인 키 2개. 편집 화면(`is_edit_screen` — 칸 설정·하위 목록·변수 화면 둘·**값 목록**)이고 편집 상태(`views.edit`)가 있으며 창(`overlay`)이 열려 있으면 **그 창의 키 줄**(현행 `edit_keys` — `저장 중`·확인·알림 창처럼 지금도 키 줄이 비는 창은 대체 화면에서도 빈다) — 키가 창으로 먼저 가므로(`Esc`는 창부터 닫고, 조건 칸에서는 글자가 입력줄로 간다) `Esc 뒤로`라고 쓰면 틀린다. 그 밖에는 `Esc 뒤로` 하나.
4. 키 동작은 바꾸지 않는다.
5. 정상 경로(칸이 있다)의 화면은 글자까지 같다. 대체 화면에서 메뉴 줄 클릭 영역(`menu_rows`)은 비어 있다.

## 3. TUI 구조

- **`pick.rs`**: `fn number_text(v: f64) -> String`(순수) — `format!("{v:e}")`를 `e`에서 갈라 지수를 정수로 읽고 §2.1-2의 갈래로. `visit_f64`가 이것을 쓴다. `PickValue::Number` 주석을 "정수는 그대로, 그 밖은 `String(number)` 표기 규칙"으로.
- **`view/edit.rs`**: 순수 함수 `cond_form_height(v, body_w, body_h) -> u16`(§2.2-4)이 `cond_form_lines`를 대체한다(호출 2곳 — `render_list_with_form`·`view/values.rs` `render_values`). `render_cond_form`은 받은 `area.height`에서 `받은 값`·안내 줄 표시 여부(현행 `extras_shown`)를 정한 뒤 **남는 줄 수만큼** 대상의 이어지는 줄을 그린다 — 높이를 정한 쪽과 그리는 쪽이 같은 줄 수 계산(순수 함수 하나)을 쓴다.
- **`view/inspect.rs`**: `render_missing(f, head, keys)` — 틀(`render_frame`) + 안내 줄.
- **`app.rs`**: `draw_sub`의 화면별 갈래(`draw_edit`·`draw_values` 포함)가 "그렸는가"를 `bool`로 돌려주고, `false`면 `draw_sub`가 `render_missing`을 부른다. 키 줄은 순수 함수(§2.3-3의 세 갈래)로.
- **`text.rs`**: `SUB_MISSING` 한 줄.

## 4. 영향 범위

- 저장되는 조건의 `value` 글자가 지수 범위 수에서 달라진다(301자 → `1e+300`). 십진 글자가 200자를 넘는 수는 지금 저장이 거절되므로 이미 저장된 조건이 없다. 지수 범위이면서 십진 글자가 200자 이하인 수(예: `1e21`·`1e-7`)는 옛 글자(긴 십진)로 저장된 조건이 있을 수 있고, 판정은 같다(두 글자 모두 같은 `f64`로 읽힌다 — §2.1-6).
- 보드 파일 형식·와이어 0-diff.

- 새 입력 경로·새 저장 값 없음. 숫자 글자는 `f64`에서 만든 ASCII(숫자·`.`·`e`·`+`·`-`)뿐이다.
- 대상 줄은 지금처럼 `sanitize` 뒤에 폭을 잰다(`crates/tui/CLAUDE.md` — 원격 문자열은 폭 계산 전에). §6 ⑤의 `\u{FFFD}` 긍정 단언이 지킨다.

## 9. 알려진 한계 / 연기

- **선재(서버·GUI) — `serde_json`이 한 끝자리 다르게 읽는 소수는 GUI에서 만든 숫자 비교 조건이 틀리게 판정된다**: 워크스페이스의 `serde_json`은 `float_roundtrip` 기능이 꺼져 있어 일부 소수를 한 끝자리 다르게 읽는다(`1.5e-300`·`972.0979928970337`·`4.5e250` — §11 ②. 자릿수나 지수 크기로 가를 수 없다 — `1e300`·`2.5e-300`은 정확히 읽고 보통 범위의 `972.0979928970337`은 다르게 읽는다). 서버는 실제 값을 그렇게 읽고 비교값은 정확히 읽어 `==`로 비교한다(`check.rs` `op_passes` — `=`·`≠`·`∈` 세 규칙이 같은 비교). GUI는 정확한 글자를 비교값에 넣으므로 `=`·`∈` 조건은 통과하지 못하고 `≠` 조건은 늘 통과한다. TUI는 서버가 읽은 값의 글자를 넣어 통과한다(§2.1-4). 그 결과 같은 값을 GUI와 TUI에서 추가한 조건의 `value` 글자가 다르다. 이 슬라이스는 고치지 않는다(컨트롤러·엔진의 읽기와 판정이 바뀐다 — 범위 밖). 해소: 워크스페이스 `serde_json`에 `float_roundtrip`을 켜는 별도 슬라이스(엔진 추출·서버 판정·리포트의 숫자 읽기 전부에 영향, 성능 비용 확인). 켜면 §6 `pick_test` ②가 RED가 되어 알린다 — 그때 §2.1-4를 지운다.
- **숫자 글자가 세 가지다** — 서버가 사유·화면 표시 값에 쓰는 글자는 엔진 `extract::stringify`(`serde_json` 표기: `1e300`·`1.0`)다. 시나리오 추출과 같이 쓰는 함수라 건드리지 않는다. 판정에는 영향 없음. 해소 방향: 모니터 판정 쪽만 쓰는 숫자 표기 함수를 따로 두기(컨트롤러 변경).
- 2^53을 넘고 `u64`·`i64`에 들어가는 정수 글자는 GUI와 다르다(§1 비목표).
- 기존 조건(11번)의 대상에는 스텝 이름이 없다(지금과 같다 — 스텝 이름은 11번 목록 줄에 있다).
- 500자 경로는 좁거나 낮은 화면에서 끝까지 보이지 않는다(`…`) — 화면에 줄이 없다. 한글처럼 넓은 글자 경로는 80×24에서도 그럴 수 있다. 전체는 값 목록의 선택 창 머리(새 조건)에서 본다. 11번(기존 조건)에는 그 길이 없다.
- `draw_sub` → `render_missing` 연결은 단위 테스트·라이브 어느 쪽으로도 확인하지 못한다(§2.3-1의 경우를 만들 길이 없다). 틀리면 지금과 같은 빈 화면이 남는다.
- cloud 세션 제약: `cargo-nextest` 없음(`cargo test --workspace`로 대신) · GUI 클릭 경로 대조 불가 — 맥에서 확인할 것으로 §B 블록 머리에 남긴다.

## 10. 판단 기록 (설계자 몫)

- **표기 규칙은 GUI에 맞춘다**(Rust `{:e}`의 `1e300`이 아니라 `1e+300`): 상위 규칙이 "GUI와 같은 설정"이고(tui-2b US1), `serde_json`이 정확히 읽는 수에서는 GUI와 TUI가 만든 보드 파일이 글자까지 같아진다.
- **값은 서버가 읽은 값을 따른다**(리뷰 1라운드 F1): GUI 글자를 흉내 내면(본문 글자를 `str::parse`로 다시 읽기) 글자는 같아지지만 그 조건이 서버에서 실패한다. 운영자에게는 "저장한 조건이 통과한다"가 "GUI와 글자가 같다"보다 먼저다. `float_roundtrip`을 켜는 것은 서버 판정을 바꾸므로 이 슬라이스에 넣지 않는다.
- **대상 줄바꿈의 우선순위를 맨 뒤에 둔다**: 낮은 화면에서 지금 보이는 것(받은 값·안내)이 사라지지 않게 — 변경 전 화면이 변경 후의 부분집합이 된다.
- **대체 화면을 "그리지 못한 모든 경우"에 한 곳에서**: 갈래마다 문구를 넣으면 새 갈래가 빠진다(US3 선택 때 사용자에게 제시한 "모든 하위 화면에").

## 11. 사실 주장 근거 (claims ledger)

- ① §2.1-3·-4 표: 워크스페이스와 같은 `serde_json =1.0.150`(기본 기능)으로 본문 글자를 읽어 §3의 `number_text`를 적용한 작은 프로그램의 출력과 `node -e 'for (const x of process.argv.slice(1)) console.log(x, String(JSON.parse(x)))' <글자들>`(node v22.23.4)의 출력을 줄 단위로 비교 — §2.1-3의 행은 전부 같고(`12345678901234567890` 한 행만 뜻대로 다르다) §2.1-4의 행은 표대로 다르다(2026-11-11 실행). 리뷰어의 독립 실행(무작위 글자 2만 개)에서 글자가 다른 5,638건은 전부 `serde_json`이 값을 다르게 읽은 경우였다 — 표기 규칙 자체의 차이는 0건. - ③ Rust 쪽: `format!("{:e}", 1e300_f64)` = `1e300`, `format!("{}", 1e300_f64).len()` = 301, `5e-324` → 326자, `"1e+300".parse::<f64>()` = `Ok(1e300)`(rustc 1.99.1).
