# 0054. 보드 파일 형식 — `handicap-bundle` v1(보드·시나리오·환경) + ID 보존·내용 비교 + 모르는 키 거부

- **상태**: Accepted
- **날짜**: 2026-10-29

## Context

운영 모니터 보드([ADR-0053](0053-ops-monitor-mode.md))는 QA 자리 PC에서 만들고 미리 실행으로 조건을 맞춘 뒤, 운영실의 모니터링 PC로 **파일 하나만 들고 가서** 넣어야 한다. 모니터링 PC엔 그 시나리오·환경이 없을 수 있으므로 파일은 자기완결이어야 한다. 후속으로 "시나리오만 내보내기"가 같은 형식을 재사용할 계획이라, 이 형식은 한 슬라이스를 넘어 지켜질 **계약**이다. 슬라이스는 ②a(내보내기 + 겹침 없는 가져오기, 이번)와 ②b(겹침 질문 흐름, 다음)로 나뉜다. 설계 원천: `docs/superpowers/specs/2026-10-29-ops-monitor-export-design.md`.

## Decision

**한 JSON 파일 `handicap-bundle`(`format_version` 1)에 세 칸을 담는다.**

- **구조**: 최상위 `format`·`format_version`·`exported_at`·`app_version`(뒤 둘은 정보용) + `boards[{id,name,config}]`·`scenarios[{id,yaml}]`·`environments[{id,name,vars}]`. `config`는 `BoardConfig` serde 그대로. 시나리오 이름은 YAML 안 `name`이 원천이라 따로 두지 않는다. 같은 시나리오·환경을 여러 보드가 쓰면 ID 기준 한 번만 담는다. 환경 `vars`는 **평문**(사용자 결정 — 내보내기 근처 안내 문구로 알린다).
- **ID 보존**: 가져올 때 원래 ID로 넣는다. 그래야 두 번째 가져오기부터 "같은 것"을 ID로 찾는다. 이름 매칭은 쓰지 않는다.
- **같음 판정 = ID + 내용**: 시나리오는 YAML 문자열 완전 일치, 환경은 `vars` 완전 일치(**환경 이름은 비교하지 않는다** — 이름 충돌로 `운영 (2)`가 된 환경이 다음 가져오기에서 영원히 "다름"이 되지 않도록). 상태는 `absent`/`same`/`different`.
- **겹침 정의**: 보드가 겹침 = (보드 ID가 이 PC에 있음) ∨ (그 보드가 쓰는 시나리오·환경 중 `different`가 있음). 겹치지 않는 보드는 묻지 않고 꺼진 채로 추가한다. 쓰는 리소스가 `same`이기만 하면 어떤 결정이든 결과가 같으므로 겹침이 아니다.
- **모르는 키 거부**: 파일 구조체(최상위·`boards[]`·`scenarios[]`·`environments[]` 항목)는 `deny_unknown_fields`. 보드 `config`는 DB 행 호환 때문에 `deny_unknown_fields`를 걸 수 없으므로, 원본 JSON과 `BoardConfig`로 읽어 다시 쓴 JSON의 키 집합을 재귀 비교해 원본에만 있는 키가 있으면 거부한다. 거부 문구는 "핸디캡을 업데이트하세요".
- **`format_version`은 파일 최상위 구조나 기존 필드의 의미가 바뀔 때만 올린다.** `BoardConfig`/`PanelConfig`에 필드를 추가하는 것만으로는 올리지 않는다(위 거부 규칙이 옛 핸디캡을 막는다). 읽는 쪽은 `format_version`이 자기가 아는 값보다 크면 거부한다(머리 `format`·`format_version`을 먼저 읽어, 모양이 바뀐 새 파일에서도 이 사유가 먼저 나온다).
- **가져오기 검증**: 파일 전체를 R0~R7 순서로 검증(JSON·형식·버전·모르는 키·개수·정규형 ULID·시나리오·환경·참조 정합·보드 `validate_and_normalize`)하고, 오류 문구에는 파일 속 **값**을 넣지 않는다(위치·경로만). 가져온 보드 설정이 `validate_and_normalize`를 통과해야 한다는 점이, `judge`가 실행 시 경로를 재검사하지 않는 데 대한 유일한 방어다. 내보내기도 같은 검증을 자기 파일에 돌려 모니터링 PC에서 처음 알게 될 문제를 내 자리에서 막는다.
- **적용**: 전부 아니면 전무 — SQLite 트랜잭션(`BEGIN IMMEDIATE`) 하나. 가져오기 요청은 파일 텍스트를 그대로 끼워 보내고(재직렬화로 서버가 다른 파일을 보는 일을 막는다), 서버는 두 가져오기 라우트에만 32 MiB 본문 상한을 둔다.

**②a 범위(이번 슬라이스)**: 내보내기 전부 + 겹침이 **없는** 파일의 가져오기. 겹치는 보드가 하나라도 있으면 아무것도 넣지 않고 거부한다(분석 응답과, 분석 후 PC가 바뀐 경우를 막는 `import`의 409 + `{"error":"conflicts","boards":[…]}` 구조화 본문 — UI가 같은 컴포넌트로 그린다). 지문(fingerprint)·덮어쓰기·보드만 덮어쓰기·새 보드로 추가·복사본·점검 재시작은 **②b 예정**이다.

**귀결**: `BoardConfig`에 필드가 하나라도 추가된 뒤의 핸디캡이 내보낸 파일은, 그 필드가 기본값이어도(직렬화가 항상 모든 필드를 쓴다) **옛 핸디캡에서 거부된다** — 모니터링 PC도 같이 업데이트해야 한다. 설정이 조용히 사라지는 것보다 낫다고 판단했다.

**기각**:
- **이름 매칭**(이름이 같으면 같은 리소스) — 우연히 이름이 같은 다른 시나리오·환경을 같은 것으로 묶어 덮어쓸 위험. 환경 이름은 UNIQUE라 가져오기가 바꿔 저장하기도 한다.
- **`format_version` 규율만으로 새 필드 처리** — 필드를 추가하고 버전 올리는 것을 잊으면 옛 핸디캡이 새 설정을 조용히 버린다. 모르는 키를 기계적으로 거부하는 쪽이 사람의 기억에 기대지 않는다.
- **클라이언트 재직렬화**(파싱 후 다시 stringify해 보내기) — 큰 숫자 정밀도·중복 키 처리 차이로 분석과 적용이 다른 파일을 볼 수 있다.

## Consequences

**Positive**: 파일 하나로 시나리오·환경이 없는 PC에서도 보드가 돈다 · 같은 파일을 다시 가져와도 같은 ID로 안정 판정(복사본 누적 없음) · 새 설정 필드가 검증을 우회해 들어오거나 조용히 사라지지 않는다 · 시나리오 내보내기가 같은 형식을 재사용할 수 있다.

**Negative / Trade-offs**: 환경 값(비밀번호·토큰)이 평문 파일로 PC 밖에 나간다(새 sink — 안내 문구만, 암호화·마스킹 비목표) · 보드 설정 필드 추가 후엔 두 PC를 함께 업데이트해야 한다 · 시나리오 YAML의 모르는 키는 `ThinkTime` 등 일부에서 거부되지 않는다(영향 작음, 수용) · ②a는 겹치는 파일을 거부만 한다(②b 전까지 덮어쓰려면 PC에서 보드를 먼저 지워야 한다).
