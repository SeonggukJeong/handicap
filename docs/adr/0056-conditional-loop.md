# 0056. 조건 반복 — loop + 선택적 `while`(do-while) + `keep_think` + 본문 너그러운 추출 + `EndIteration`

- Status: Accepted (2026-11-13, 1차 = 실행·에디터. spec-plan-reviewer 검토 4회차 반영)
- Date: 2026-11-13
- 관련: ADR-0020(loop — 이 결정이 확장), ADR-0023(조건 트리·lenient 평가), ADR-0026/0047(시험 실행), ADR-0049(실행 전 신뢰도), ADR-0053(운영 모니터)
- 설계: `docs/superpowers/specs/2026-11-13-loop-do-while-design.md`

## Context

사용자 원문: 여러 가상 사용자가 계정 하나를 공유해 반복 호출하면 성공할 때도 있지만 동시 요청 탓에 "대기" 응답을 받을 때도 있다. 대기 응답은 상태 코드 200이고 본문의 코드 값만 다르다. 이때 기다렸다가 같은 요청을 다시 보내고 싶은데 지금 모델로는 불가능하다 — loop은 고정 횟수(`repeat: N`)만 돌고, if 스텝은 되돌아가지 못한다.

막히는 곳이 둘 더 있었다(둘 다 코드로 확인). (1) 추출은 전부 아니면 전무다 — 항목 하나라도 실패하면 전체가 `Err`라서, 대기 응답에 없는 값(주문 번호)을 `code`와 함께 뽑으면 `code`도 안 뽑혀 반복이 첫 대기 응답에서 끝난다. (2) 요청이 실패하면 추출이 일어나지 않고 `iter_vars`는 이전 값을 지우지 않아, 1회차 `WAIT` 뒤 2회차가 연결 실패여도 `eq WAIT`이 계속 참이다.

## Decision

**loop 스텝에 선택적 반복 조건 `while`을 붙여 "본문 1회 실행 → 조건 확인 → 참이면 다시"(do-while)를 표현한다.**

- **모델**: `LoopStep`에 `while`(if 스텝 `cond`와 같은 조건 트리, 엔진 필드 `while_`)과 `keep_think`(기본 켜짐)를 더하고 `repeat`를 `Option<u32>`로 바꾼다. `while`이 있으면 `repeat`은 "최대 회차"이고 생략하면 무제한이다. `while`이 없으면 `repeat`은 UI가 필수로 강제하고 동작은 그대로다.
- **R0(지킬 조건)**: `while` 없는 loop과 기존 YAML은 전 계층에서 지금과 똑같다 — 실행 순서(`repeat: 0` = 0회 포함), YAML round-trip 글자, 메트릭, 리포트 JSON, trace JSON, 신뢰도 지문. 새 필드는 전부 생략 직렬화(`skip_serializing_if`), 엔진은 `while` 유무로 **경로를 나눈다**(`plain_repeat()` vs `max_passes()`). `while`이 있고 `repeat: 0`이면 엔진은 `max(1)`로 취급한다(do-while은 최소 1회).
- **본문 너그러운 추출**: `while`이 있는 loop의 본문(그 안 if 분기·중첩 loop 포함 — 표지 상속) http 스텝은 추출 항목을 하나씩 평가해 못 뽑은 변수를 **빈 문자열**로 두고 스텝 에러로 세지 않는다. 추출 전에 이미 `error`가 있으면(전송 실패·시간 초과·status assert 실패 등) 그 스텝이 선언한 추출 변수를 전부 빈 문자열로 둔다 — 에러 응답을 근거로 재시도하지 않게. 지우지 않고 빈 값으로 두는 이유: 조건 평가에서 빈 값과 없는 값은 같고, 요청 템플릿의 엄격 렌더는 없는 변수에서 엔진 에러(VU 종료)를 내기 때문이다. `while` 없는 loop·loop 밖은 지금처럼 엄격 추출이다.
- **`StepFlow::EndIteration`(새 변형)**: 조건 반복이 최대 회차까지 풀리지 않으면 "이번 시나리오 반복을 여기서 끝낸다(실패 아님, 다음 반복은 정상 시작)". parallel 합치기 우선순위는 `Aborted > DeadlineReached > EndIteration > Continue`. 무제한 loop은 매 회차 앞의 기존 deadline 확인으로 run 종료 시각에 멈춘다 — 새 종료 장치 없음.
- **`keep_think`**: "이 반복 안의 think time은 think time을 무시하는 실행에서도 적용한다"(loop마다, 기본 켜짐). think를 무시하는 세 경로(open-loop 기본 think 무시의 `maybe_strip_think`·에디터 시험 실행·운영 모니터)가 대상 loop 본문의 유효 think(스텝 값, 없으면 시나리오 기본값)를 보존한다. 대상 loop이 없으면 세 경로 모두 결과가 지금과 같다.
- **시험 실행 trace**: `while` loop은 매 회차 뒤 판정 행 하나(`StepKind::Loop`, 와이어 `"loop"`, branch `again|done|exhausted`)를 남기고, `exhausted`는 `ScenarioTrace.ended_by_loop`(loop id)로 알린다. 판정 행은 `MAX_LOOP_JUDGE_ROWS = 200`을 넘으면 `truncated`로 끝낸다(요청 없는 본문이 `max_requests`에 안 걸리고 도는 경우의 상한). 운영 모니터는 `ended_by_loop`가 있으면 흐름 칸의 점검을 실패(`REASON_LOOP_EXHAUSTED`)로 보고, 스텝 칸은 소진된 반복 본문 안의 스텝과 돌지 못한 스텝만 같은 사유로 실패시키며 반복 앞에서 돈 스텝은 평소대로 판정한다.
- **에디터 경고(저장·실행을 막지 않음)**: ① 쉬지 않는 재시도(본문에 유효 think 없음 / think는 있는데 `keep_think` 꺼짐 — 약한 안내) ② 실패해도 반복(조건을 "본문이 뽑는 변수 = 빈 문자열"로 평가해 확실히 참). ②는 클라 순수 함수 `condWhenBodyVarsEmpty`의 3값 논리(`true|false|unknown`)로 엔진 `eval_compare`를 거울하며, JS에서 컴파일되지 않거나 Rust regex가 못 여는 패턴은 `unknown`으로 두어 경고하지 않는다. UI Zod는 `StepModel.superRefine` 한 곳에서 교차 검사한다(`repeat required when loop has no while`, `keep_think needs while`).
- **범위**: 1차 = 실행·에디터. 메트릭 proto·DB·리포트 JSON은 건드리지 않는다. (2차에서 리포트 집계를 더했다 — 아래 "리포트 집계".)

**리포트 집계 (2차, loop-while-report 2026-11-14)**

- 엔진이 조건 반복 진입이 **끝날 때마다** `(loop id, 회차 칸, 끝난 방식)` 건수와 실제 회차 합을 센다. 회차 칸 = `min(회차, 21)`(21 = "21번째 이후"), 끝난 방식 = 0 완료 · 1 중단(최대 횟수) · 2 마치지 못함(run 종료·중지·오류로 도중에 끊김 — 1차 부록 A의 "잘린 진입은 세지 않는다"를 뒤집음: 끝내 풀리지 않는 무제한 반복의 재시도가 안 보이면 안 된다). 본문을 한 번도 시작하지 못한 진입은 세지 않는다.
- 운반은 send 실패 종류 집계(ADR-0050)와 같은 counts-only 길: `MetricFlush.loop_exit_stats` → proto `MetricBatch.loop_exit_stats = 11` → 컨트롤러 ingest(워커 입력의 칸은 1..=21로 clamp, 범위 밖 방식은 버림) → `run_loop_exit_metrics`(migration 0023, upsert 누적 — 워커 여럿의 델타가 합쳐진다) → `ReportJson.loop_exits`(빈 배열이면 키 생략).
- 화면은 순수 뷰 모델 하나(`ui/src/components/report/loopExitView.ts`)를 표지·풀이 줄·분포 패널·맨 위 안내가 같이 쓴다. `재시도 = 회차 합 − 진입`. 「재시도 포함」 표지는 실제로 2번째 이후 회차에서 요청된 본문 스텝에만(회차별 요청 수가 없으면 재시도가 있는 loop의 본문 스텝 전부).
- **R0**: 조건 반복 집계가 없는 run은 batch·DB 행·리포트 JSON·화면이 그대로다. 내보내기·인쇄·비교·유효성·인사이트·TUI·시험 실행 trace는 바꾸지 않았다(연기 — roadmap §B60).
- **응답 시간 분리 (3차, loop-while-latency-split)**: 조건 반복 본문 응답을 회차가 끝날 때 세 갈래로 기록한다 — 끝냄(조건이 풀려 반복을 마친 회차)·이어짐(조건이 안 풀려 다음 회차로 간 것)·끊김(최대 횟수·run 종료 등으로 끊긴 회차). 구간 이름 여섯 개(`loop_final`/`loop_retry`/`loop_cut` + 각 `_err`)는 새 와이어 없이 기존 `phase_stats` 길을 탄다(스텝별 HDR + 에러 수 counts-only). 컨트롤러가 `ReportStep.loop_split`로 말아 올리며 화면의 `retry` = 이어짐 + 끊김, `final` = 끝냄이다. 표시 조건 = 이어짐 건수 합 ≥ 1(끊김만 있는 스텝은 키 생략 — R0). 음수 건수는 0, 에러 수는 건수로 자르고, 깨진 BLOB은 건수만 더한다(`download`와 같다). 회차 표본 상한은 1,024.

**기각**
- **본문 실행 *전에* 조건을 보는 while**: 사용자 판단 — 나중에 if 스텝과 결합해 해결.
- **loop 전용 대기 시간 설정**: 사용자 결정 — 기존 스텝 think time으로 해결(성공 뒤에도 한 번 쉬는 것은 수용).
- **`keep_think`를 실행할 때마다 고르는 방식**: 사용자 "일단 loop별 고정". 도그푸딩 뒤 재평가.
- **loop 본문 추출을 엄격하게 두고 사용자가 항목을 나눠 뽑게 하기**: 대기 응답마다 스텝 에러가 쌓이고 반복이 첫 대기에서 끝난다 — 사용자가 풀 수 없는 문제.
- **`while` 없는 loop까지 너그러운 추출**: R0 위반.

## Consequences

**Positive**: 대기 응답 재시도가 모델로 표현된다. R0로 기존 시나리오·리포트·지문이 안 바뀐다. 무제한 반복이 새 종료 장치 없이 기존 deadline에 묶인다. 조건 평가는 if 스텝의 `eval_condition` 재사용이라 규칙이 한 벌이다.

**Negative / Trade-offs**: 조건 반복 안에서는 "성공 응답인데 값이 빠진" 경우가 그 스텝의 에러로 잡히지 않고 그 값을 쓰는 다음 스텝에서 드러난다. loop 전부터 있던 값도 덮인다(본문 스텝이 `token`을 다시 뽑다 실패하면 뒤 요청에 빈 토큰이 실린다). 조건 반복 안에서 빈 값이 된 값이 뒤 요청의 주소(경로와 쿼리 전체, `request.url`)에 쓰이면 그 요청은 보내지 않는다(blank-var-url-guard — `DELETE /orders/{{orderId}}`가 `DELETE /orders/`로 나가 다른 리소스를 가리키는 일을 막는다). 엔진이 "비워진 이름 → 비운 스텝" 표를 반복(회차) 변수와 같은 수명으로 들고, http 스텝 실행 직전 주소 템플릿이 실제로 읽는 이름 중 표에 있고 값이 지금도 빈 문자열인 것이 있으면 차단한다(runner·trace 같은 규칙, 조건 반복 안팎 모두). 차단된 요청은 그 스텝의 에러로 세되(요청 수·에러 수 +1, 새 분류 `blank_var`) 응답 시간 분포·status 분포에는 넣지 않고, 에디터 시험 실행과 무인 운영 모니터는 「앞 단계 실패」로 보인다. 같은 이름을 다시 뽑는 스텝이 실제로 값을 뽑으면(빈 문자열이어도) 표에서 지워지고 차단은 풀린다. 조건 반복 안에서 추출(본문 경로, 또는 본문·헤더·쿠키 값을 디코딩한 JWT/base64 `claim`)이 JSON `null`을 찾으면 "응답에 없는 값"으로 본다(빈 값으로 비우고 표에 올려 주소 사용을 막는다 — `""`는 받은 값; 엄격 모드는 그대로 `""`로 뽑는다). 한 회차에서 요청을 하나도 보내지 않고 막힌 http 스텝이 하나라도 있으면(안쪽 if·loop·parallel 포함) 다음 회차도 새로 뽑을 값이 없어 같으므로, 최대 횟수에 닿았을 때와 같이 이번 반복(시나리오 회차)을 끝낸다 — 조건이 기대는 값을 가져오지 못해 반복이 끝났다고 볼 수 없으므로(그 회차는 조건을 평가하지 않는다) 반복 뒤 스텝(조건이 풀려야 갈 곳, 예: 작업이 DONE이 된 뒤의 `POST /jobs/{{id}}/confirm`)으로는 가지 않고(fail-closed), 리포트에는 「마치지 못함」으로 센다(막힌 회차 포함 회차 수; 시험 실행은 그 회차 판정 행 없이 `ended_by_loop`을 달고 멈추며 잘림이 아니다; 운영 모니터는 그 끝을 행으로 판정한다 — 막힌 행이 첫 실패면 「앞 단계 실패」, 그 앞에 진짜 실패가 있으면 그 실패의 사유; 「조건 반복 최대 횟수 도달」은 반복이 실제로 최대 횟수를 다 썼을 때(`exhausted` 판정 행이 있을 때)만). 처음엔 "조건이 거짓이 된 것처럼 반복 뒤로 계속"으로 정했으나, 조건이 참인 채 뒤 스텝을 보내는 fail-open이라 정정했다. 대가: `${loop_index}`에 기댄 if로 다음 회차에 다른, 막히지 않은 스텝을 고르는 손 YAML 반복은 일찍 끝난다. 헤더·본문에는 빈 값이 여전히 그대로 들어간다(연기 — spec §8). 자기 주소에 자기가 뽑는 값을 쓰는 스텝(커서 페이지네이션·회전 토큰)은 한 번 비워지면 요청이 안 나가 다시 뽑을 길이 없어 그 회차에서 회복하지 못하고(다음 회차는 빈 표로 시작), 빈 쿼리 값을 일부러 쓰려는 경우도 차단된다 — 둘 다 오늘은 그 값에 대한 if로 감싸는 것이 해소 경로이고, "추출 기본값" 지정은 후속 후보다. 최대 횟수로 끝난 반복은 1차 동안 리포트에 드러나지 않는다(2차가 채움 — 1·2차를 모두 끝낸 뒤 릴리즈). 실행 전 부하 추정은 무제한을 1회차로 계산한다. 새 YAML을 옛 워커가 읽으면 `deny_unknown_fields`로 run이 즉시 `failed`가 된다(릴리즈 노트 한 줄: 조건 반복이 든 시나리오는 워커도 새 버전이어야 함). `keep_think`(기본 켜짐)는 사용자가 think time을 켜지 않았어도 에디터 시험 실행이 본문 대기를 기다리게 한다(시험 실행 전체 제한 시간이 상한이고 취소 가능). UI 조건 평가 거울(`condEmptyEval.ts`)과 엔진 `eval_compare`는 두 벌이며 같은 연산자 표 테스트로 묶는다. yamlDoc의 loop 액션은 무효 조합을 막지 않는다(호출부 책임 — `ui/src/scenario/CLAUDE.md`).

## 사용 안내

저장소에 사용자 매뉴얼이 따로 없어(`grep -rln "반복(loop)\|loop 스텝" docs --include='*.md' | grep -v superpowers` → 0건) 이 절이 사용 안내를 맡는다. 화면 안 안내는 에디터 도움말·경고 문구가 맡는다.

**사용 예 — 대기 응답 재시도**: 주문 스텝이 응답에서 `code`(와 성공 응답에만 있는 `orderId`)를 뽑고 `think_time`을 갖게 한 뒤 그 스텝을 loop에 넣고, loop의 「반복 조건」을 `{{code}}` `eq` `WAIT`, 최대 반복 횟수를 3~5로 둔다. 대기 응답이면 think time만큼 쉬고 같은 요청을 다시 보내고, 성공 코드를 받는 즉시 다음 스텝으로 넘어간다. 조건은 "대기 값과 같다"처럼 **값을 받았을 때만 참이 되는** 형태를 권한다(`ne OK`는 요청이 실패해 값이 비어도 참이라 실패해도 반복한다 — 경고 ②).

**think time 선택**: 대기는 본문 스텝의 think time으로 정한다(전용 대기 설정 없음). 본문에 유효 think가 없으면 응답이 빠를 때 초당 수백 번 재요청할 수 있다(경고 ①). `keep_think`(기본 켜짐)를 끄면 도착률 기준 실행·시험 실행·운영 모니터에서 대기 없이 재시도한다. 닫힌 루프 run과 "think time 적용"을 켠 실행은 원래 think를 적용하므로 `keep_think`와 무관하다.

**너그러운 추출의 대가 2가지**: ① 조건 반복 안에서는 응답에 값이 빠져도 그 스텝의 에러로 세지 않고 값이 빈 문자열이 되어, 그 값을 쓰는 다음 스텝에서 드러난다. ② loop 전부터 있던 변수도 본문 스텝이 다시 뽑다 실패하면 빈 값으로 덮인다(조건 반복 밖에서는 이전 값 유지). 성공한 회차의 값은 다음 회차로 넘어간다.

**빈 값과 요청 주소**: 조건 반복 안에서 못 뽑아 빈 값이 된 변수를 뒤 스텝의 주소(경로·쿼리 `?c={{code}}` 포함)에 쓰면 그 요청은 보내지 않고 에러로 센다(`/orders/{{orderId}}`가 `/orders/`로 나가지 않는다). 응답이 `{"orderId": null}`처럼 `null`을 주면(토큰을 디코딩한 claim 값이 `null`이어도) 응답에 없는 값으로 보고 같이 막는다(`""`는 받은 값이라 막지 않는다). 한 회차에서 아무 요청도 못 보내고 막히기만 하면 최대 횟수에 닿았을 때처럼 이번 반복이 끝나고(리포트 「마치지 못함」) 반복 뒤 스텝은 보내지 않는다. 헤더·본문에는 빈 값이 그대로 들어가니 그 값을 뒤에서 쓰기 전에 if 조건으로 확인한다. 자기 주소에 자기가 뽑는 값을 쓰는 스텝이나 빈 쿼리 값을 일부러 쓰는 경우도 같은 방법(if로 감싸기)으로 푼다.

**무제한 반복**: 최대 횟수를 비우면 run이 끝날 때까지 반복한다. 천천히 줄이는(graceful) 감소 구간에서 상한 시간(`graceful_ramp_down_seconds`)이 없으면 무제한 재시도 중인 가상 사용자는 빠지지 않는다 — 상한 옵션이 해법이다. 도착률(open-loop) 기준에서는 재시도 중인 반복이 슬롯을 계속 쥐어 `dropped`(원인 slots)가 늘고 기존 표시로 드러난다. 최대 횟수로 끝난 반복은 이번 시나리오 반복을 끝내고 다음 반복이 처음 스텝부터 시작한다.

**운영 모니터**: 조건 반복의 대기가 점검에도 적용된다(`keep_think` 켜짐). 응답 시간 기준이 **특정 스텝**인 칸은 그 스텝의 마지막 응답 시간만 보므로 대기가 들어가지 않는다(조건 반복 안 스텝을 기준으로 잡으면 재시도 끝의 마지막 응답 시간). 기준이 **전체**인 칸은 `trace.total_ms`를 쓰므로 재시도와 대기가 포함된다. 점검 제한 시간(`timeout_seconds`)은 스텝이 한 번씩 돈다고 보고 잡힌 값이라, 재시도와 대기가 이를 넘으면 시간 초과 실패다 — 조건 반복이 든 시나리오는 제한 시간을 넉넉히 잡는다. 최대 횟수까지 풀리지 않으면 그 점검은 실패(사유 "조건 반복 최대 횟수 도달")다.
