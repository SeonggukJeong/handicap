# 0059. 계단 자동 정지: 수신 흐름 감시 + 실행 중 판정 요약

- Status: Accepted (2026-11-19, 계단 시험 c = 실행 중 계단 패널)
- Date: 2026-11-19
- 관련: ADR-0009(라이브 대시보드 비목표 — 유지), ADR-0051(실행 중 진행 차트 — 이 결정이 넘어선다), ADR-0012(워커 1초 사전 집계)
- 설계: `docs/superpowers/specs/2026-11-18-stage-auto-stop-design.md` §3·§4.5·§7·§8, 계획 `docs/superpowers/plans/2026-11-19-stage-live-panel.md`

## Context

계단 시험(stair) run은 계단마다 목표 RPS를 올리며 시스템 수용 한계를 찾는다. b(stage-auto-stop)는 포화·즉시 정지 조건이 성립하면 run을 자동으로 멈추게 했지만, 운영자는 run이 끝날 때까지 어느 계단이 정상·실패였는지, 다음 계단에서 멈출지, 즉시 정지 기준에 얼마나 가까운지를 볼 수 없었다. 리포트의 계단 판정은 run이 끝난 뒤에만 계산된다.

ADR-0051은 이미 폴링 중인 1초 windows를 클라이언트가 차트로 그리는 것까지만 허용했다. 계단 판정에는 계단별 p99(HDR 머지)와 리포트 판정 규칙이 필요한데, 이 값은 화면 API(`/metrics`)에 없다.

## Decision

**컨트롤러가 받은 MetricBatch 흐름으로 계단·초를 판정하고(감시 작업), 그 실행 중 요약(`auto_stop_live`)을 기존 1초 run 폴링 응답(`GET /api/runs/{id}`)에 싣는다.**

- **감시 상시화**: 감시 작업은 계단 run이면 자동 정지 칸과 무관하게 항상 만든다(b는 칸이 켜졌을 때만). 칸이 꺼진 run은 정지하지 않고 판정·요약만 한다.
- **수신 흐름 감시**: 감시는 `ingest_metrics`가 DB에 쓴 배치를 소유권째 무제한 채널로 받는다(추가 DB 조회 0·HDR 복사 0). 리포트와 같은 누적기·같은 판정 함수(`StairAccumulator`·`judge`)를 쓴다.
- **요약 전달**: 감시가 메시지를 처리할 때마다 요약을 결정하는 값이 바뀌었으면 `tokio::sync::watch` 채널에 새 요약을 넣는다. 정지를 결정한 메시지에서는 보내지 않고, `CoordinatorState::auto_stop`이 `stopped_at_ms`를 채운 기록을 돌려준 뒤 한 번 보낸다. 핸들러는 `runs` 잠금 안에서 수신자만 복제하고 잠금 밖에서 마지막 값을 복사한다.
- **와이어**: `RunResponse.auto_stop_live`는 run이 `running`이고 profile에 `stair`가 있을 때만 `GET /api/runs/{id}`가 싣는다(그 밖에는 키 생략 — 계단 아닌 run의 응답은 바이트 단위로 이전과 같고 coordinator 조회도 하지 않는다). 목록·생성·라벨 응답에는 싣지 않는다.
- **유지되는 비목표(ADR-0009)**: WebSocket/SSE·서버 push·시계열 DB·전용 라이브 대시보드는 계속 비목표다. 이 결정이 넘어서는 것은 ADR-0051의 「이미 폴링 중인 windows의 클라이언트 표시」 한도 하나 — 서버가 실행 중 계산한 p99·판정을 기존 폴링에 싣는다.

## 대안 (기각)

- **B. 실행 중 리포트를 몇 초마다 재계산**: 화면 작업은 가장 적지만, 리포트 계산은 매번 전 run의 HDR을 다시 해석한다(§B68 N3). 진행 중 계단의 판정이 재계산마다 깜빡여 오해를 부른다.
- **C. 브라우저가 판정**: 판정 코드가 Rust·TypeScript 두 벌이 되고, p99용 HDR이 화면 API에 없다.

## Consequences

- **계단 run마다 감시 상시**: 자동 정지를 끈 계단 run도 감시 비용(HDR 해석·누적·판정)을 낸다. 비용은 spec §7의 2·3(종단 A/B·최악 조건 메모리)을 「켬」 조건으로 재측정해 확인한다. 계단 아닌 run의 추가 비용은 `Option` 확인 한 번 그대로다.
- **칩은 숫자를 싣지 않는다**: 요약은 계단별 상태와 즉시 정지 현재값만 싣고 해제된 계단의 숫자(`details()`)를 쓰지 않는다 — 해제된 계단 숫자가 0으로 보이는 §B69 (2) 문제가 이 경로에서 생기지 않는다.
- **잠정 판정은 하나뿐**: 리포트 판정 규칙상 판정 계단의 상태는 다음 계단이 판정돼도 바뀌지 않는다. 예외는 마지막 판정 계단의 「확인 못 한 실패」(`unconfirmed`)로, 다음 계단 판정 뒤 「튄 계단」이나 「포화」가 된다. 화면은 정지·동결 전까지 이 칩을 「실패(다음 계단 확인 중)」라고 잠정으로 표시한다.
- **실행 중 = 리포트의 예외(수용)**: ① 조기 종료 워커로 동결된 뒤 계단은 실행 중 「판정 중단」, 리포트는 남은 데이터로 판정 ② 정지 결정 뒤 중단 신호가 닿기 전에 모든 워커가 자연 완료하면 기록 `stop: null` ③ 자동 정지 뒤 외부 중단은 `aborted`·기록 없음. 셋 다 run 꼬리 경합이다.
- 요약은 정지 뒤에도 run이 coordinator 맵에서 빠질 때까지 마지막 값을 유지한다. run이 끝난(`running`이 아닌) 응답에는 싣지 않으므로 화면은 리포트로 넘어간다.
