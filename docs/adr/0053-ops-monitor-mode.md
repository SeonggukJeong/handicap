# 0053. 운영 모니터 모드 — 엔진 1패스 trace 재사용 주기 점검 보드 + 메모리 링버퍼 + 느림은 화면 계산

- **상태**: Accepted
- **날짜**: 2026-10-21

## Context

운영 현장(통신사 회선마다 PC 1대)에서 셸 스크립트가 10초마다 로그인 API를 호출해 200이 아니면 텍스트로 실패를 찍고 있었다. 글씨가 작아 멀리서 안 보이고, 줄 길이가 달라져야 가까이 가서 확인한다. 필요한 것은 멀리서 보이는 상시 점검 화면이다(분산 워커 불필요 — PC별 단독 실행, 로그인 전용 아닌 범용 API 모니터).

[ADR-0009](0009-no-live-dashboard-mvp.md)(라이브 대시보드 제외)의 범위는 **부하 테스트 실행 중의 실시간 대시보드**다(그건 APM으로 본다). 운영 모니터는 부하를 거는 도구가 아니므로 그 결정의 번복이 아니다(사용자 교정, 2026-10-21).

## Decision

**Handicap 안에 별도 기능 영역 "운영 모니터"를 신설한다 — 주기 점검 보드(`monitor_boards`) + 엔진 1패스 trace 재사용 + 결과 메모리 링버퍼 + 느림 판정은 화면.**

- **점검 = 엔진 단발 trace 재사용**: 에디터 test-run과 같은 in-process 1패스(`trace_scenario`)를 칸(시나리오)마다 주기 호출. 바깥 `timeout`(기본 5초, 1–30 — 엔진 요청 타임아웃 30초와 정합)으로 강제하고 요청 수 상한 50 고정. think time 미적용.
- **run/리포트/스케줄러와 분리**: 점검은 `runs`·메트릭 테이블에 기록을 남기지 않는다. 부하 run 파이프라인 불변.
- **감독자**: 컨트롤러 내장 `MonitorSupervisor`가 루트 `CancellationToken`의 child 토큰을 보드 세대마다 하나 만들고, 칸마다 그 토큰을 공유하는 task를 띄운다. 켜진(`enabled=1`) 보드는 **기동 시 자동 재개** — standalone(`main.rs`)과 in-process(데스크톱 `in_process.rs`, 종료 토큰의 child + `shutdown()`에서 `stop_all`) 두 시작 경로 모두.
- **결과 저장 = 칸별 메모리 링버퍼(최대 300)**: 재시작 시 비어 있고 다시 채운다. 영속·외부 알림은 비목표.
- **느림은 서버가 판정하지 않는다**: 서버는 ms 값과 성공/실패 + 고정 사유 분류만 내고, 느림(기준선 초과)·색은 화면이 현재 기준선으로 계산 — 기준선을 바꿔도 과거 막대 색이 일관.
- **설정 저장**: 보드 1행 + `config_json` 한 컬럼(칸 최대 9·기준선 최대 5).

**기각**: 별도 프로세스/스크립트 모음(제품 밖 운영 부담) · 점검 결과를 run으로 기록(리포트·run 목록 오염) · 서버측 느림 상태 산출(기준선 변경 시 재계산 불가) · 결과 DB 영속(① 비목표).

## Consequences

**Positive**: 같은 프로그램·같은 시나리오로 운영 점검 + 부하 테스트 둘 다 · 기동만 하면 자동 재개 · 엔진 재사용으로 새 실행 코드 최소.

**Negative / Trade-offs**: 재시작 시 막대 이력 소실 · 점검 task가 컨트롤러 프로세스 수명에 묶임(컨트롤러 down = 점검 중단 → 화면은 "확인 불가"로 표시) · 두 시작 경로 배선은 통합 테스트가 못 잡아 라이브 검증 필요 · 켜진 보드가 많으면 컨트롤러 안에서 outbound 요청이 상시 발생.

## 보완 — ①b (2026-10-22)

"①b: 칸별 성공 조건(모니터 칸 설정, 시나리오 무변경) — 조건 판정 결과일 때 사용자가 고른 경로의 실제 값(객체면 JSON 일부, 200자 상한)과 사용자가 입력한 비교값을 벽·`/status`(최신 결과만)에 표시한다. ①a의 '벽엔 고정 문구만' 원칙의 의도된 예외이며, 그 외 응답 조각·URL은 여전히 미노출. 화면 방식 A(fill)·C(focus) 추가 — C는 칸 크기가 결과에 따라 바뀌지만 글자 배율은 가능한 모든 C 배치를 설정 시점에 미리 재어 고정한다(①a '배율은 설정으로 고정' 유지)."

## 보완 — ops-monitor-polish (2026-10-28)

①b는 "벽엔 고정 문구만"에 **조건 실패 값** 예외를 뒀다. 이번엔 **사용자가 고른 표시 전용 값이 정상일 때도** 벽에 나간다(칸당 ≤2, `shown` 정규화·200자, `/status`는 최신 결과에만). 평균·최대는 보관 구조 변경 없이 화면 계산(원칙 "느림은 화면 계산" 확장).

평균·최대 켜기/끄기(`show_latency_stats`)는 점검을 다시 시작하지 않는(reconcile 없는) 화면 표시 옵션이다 — 전용 `PUT /api/monitor-boards/{id}/latency-stats`가 `config_json`의 그 필드만 단일 원자 SQL로 바꾼다.

## 보완 — ops-monitor-polish-2 (2026-10-29)

점검 결과 링버퍼 옆에 **점검 기록(요청·응답) 메모리 보관**을 둔다 — 칸별 막대 구간(`bar_count`)만큼, 보드 단위 본문 합계 상한(`record_limit_kb`, 기본 128KB, 16–1024), 인증 헤더·쿠키·URL 비밀번호는 보관 전 가림(스킴·이름 유지), 흐름 변수 폐기, 요청 본문은 화면에서 기본 가림 + `보기`, 재시작 시 소멸. "결과 DB 영속 비목표"는 그대로다.

## 보완 — 점검 묶음 (2026-11-04)

감독자는 칸이 아니라 **실행 단위**마다 task를 띄운다 — 점검 묶음(같은 시나리오·환경·주기를 공유하는 스텝 칸들) 하나 = 회차마다 trace **1회**를 소속 칸이 공유(같은 `at_ms`, 기록 본문 `Arc` 1벌·판정은 칸별), 단독 실행 칸 = 지금처럼 하나. 동시 점검 상한은 실행 단위당 허가 1개. 흐름 전체(`step_id` 없음) 칸의 타이밍·기록·사유는 무변경.
판정 상태 2종 추가: `upstream_failed`(확인 못 함 — 앞 단계 실패로 이 스텝까지 못 감)·`branch_skipped`(분기 제외 — IF가 이 스텝 없는 분기를 고름). 둘 다 연속 실패 수에 넣지 않는다.
스텝 칸은 칸별 요청 제한(1–30초, 칸 없는 스텝 = 시나리오 값 ≤30 또는 5초)을 시나리오 사본에 덮어쓰고, 묶음 흐름 상한 = 그 합(최대 120초), 바깥 제한 = 흐름 상한 + 32초. 1–30 `timeout_seconds` 상한이 흐름 상한인 것은 **흐름 전체 칸에만** 해당한다.
`/status`의 `check_budget_seconds`(칸 실행 단위의 바깥 제한 — 회차마다 저장, 첫 회차 전·reconcile 직후 스텝 칸 152초/흐름 칸 `timeout_seconds`)가 화면 stale 기준이다(`/status`는 시나리오를 읽지 않는다).
분기 제외 칸은 IF 비교 대상의 렌더 값을 벽에 낸다(①b 예외의 확장) — 단 `left`/`right` 원문에 `${`가 있으면 엔진이 값을 **저장하지 않고** 화면은 `(환경 값)`으로 표시한다(비밀 식별 로직 없음, 환경 변수 값 비노출).
