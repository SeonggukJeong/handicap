# 0062. 준비 구간: 시나리오의 `setup: { steps }` + VU당 한 번 + 본 집계와 분리한 구간 통계

- Status: Accepted (2026-11-22, vu-setup-steps 슬라이스 A1)
- Date: 2026-11-22
- 관련: ADR-0014(변수 표기), ADR-0018(VU별 쿠키 저장소), ADR-0022(데이터셋 바인딩), ADR-0026(test-run trace), ADR-0031·ADR-0037(open-loop·VU 곡선), ADR-0049(실행 전 신뢰도), ADR-0050(전송 실패 kind), ADR-0053(운영 모니터), ADR-0061(유지 구간 창)
- 설계: `docs/superpowers/specs/2026-11-22-vu-setup-steps-design.md` D1–D14·§2-1. 슬라이스 A1(엔진·와이어·저장·리포트·UI 최소 대응)만 구현했다. 에디터·test-run 화면·run 생성 창 안내는 A2, 주기 재실행은 그 뒤다. A1과 A2 사이에는 릴리즈하지 않는다.

## Context

로그인이 필요한 API는 시나리오에 로그인 스텝을 넣으면 반복마다 다시 로그인한다. 추출 변수는 반복마다 새로 만들고(`seed_iter_vars`) 리포트 요약·SLO 판정·계단 판정은 모든 스텝의 행을 합산하므로, 로그인이 부하와 측정 숫자에 섞여 로그인 뒤 기능만의 측정이 어렵다. 쿠키 저장소는 run 내내 유지되지만(ADR-0018) 「첫 반복에만 실행」을 표현할 방법이 없다.

## Decision

**시나리오에 `setup: { steps }` 구간을 두고, VU가 첫 반복 머리에서 한 번 실행한다. 준비 요청은 본 집계기에 기록하지 않고 구간 이름을 가진 별도 통계로 보내 별도 표에 저장한다.**

1. **모델 — 객체 꼴, http만**: `setup`은 목록이 아니라 객체이고 스텝은 그 안의 `steps`다(엔진 `Scenario.setup: Option<SetupSection>`, `deny_unknown_fields`). 구간 설정(주기 재실행 간격 등)을 키로 더할 수 있게 하기 위해서다. 준비 구간에는 http 스텝만 둔다 — http 아닌 스텝은 역직렬화에서 거절해 `Scenario::from_yaml`을 부르는 모든 곳이 같은 방식으로 실패하고(시나리오 생성·수정 400, test-run 422, 보드 가져오기·워커도 기존 파싱 실패 경로), UI Zod도 같은 모양을 거절한다. `run_section`과 trace의 준비 패스는 http 아닌 스텝이 어떻게든 닿으면 조용히 건너뛰지 않고 실패한다. `setup:`(null)은 「준비 없음」, `setup: {}`는 양쪽 다 거절. 준비 스텝이 없는 시나리오의 `to_yaml`·리포트 JSON·와이어 바이트는 변하지 않는다. 「준비가 있는가」는 어디서나 `setup_steps()`가 비었는지로 판단한다(`setup` 키의 유무가 아니다).
2. **실행 시점 — VU의 첫 반복 머리에서 첫 반복의 값으로 한 번**: 세 부하 진입점(`run_vu`·`run_vu_curve`·`run_arrival`)이 각자 배선한다. 준비는 「시나리오 변수 + 첫 반복이 받은 데이터셋 행」의 사본 위에서 돌고, 끝나면 첫 반복 변수를 다시 짠다 — 이미 만든 시나리오 변수 결과와 이미 고른 행을 재사용하고 `seed_iter_vars`·`select_index`를 다시 부르지 않는다(공유 카운터는 준비가 없을 때와 똑같이 한 번만 전진). VU 곡선은 park 뒤 재개 때 다시 하지 않고(준비 도중 은퇴 취소면 준비 「안 됨」으로 남아 `interrupted`로 세지 않으며, run 전체 취소는 센다), open-loop는 슬롯마다 한 번(슬롯 첫 도착의 머리)이다.
3. **이어받기**: 쿠키는 같은 `VuClient`로, 변수는 준비 스텝이 실제로 추출한 이름·값만 VU 변수로 보관해 반복 머리에서 「시나리오 변수 → 준비 추출 덮기(`mark_written`) → 데이터셋 바인딩 → 반복 중 추출」 순서로 시드한다. 반복 중 같은 이름을 다시 뽑아도 그 반복에서만 덮인다.
4. **준비 통계는 본 집계와 분리**: 준비는 본 `Aggregator`를 건드리지 않고 별도 누적기(`SectionStats`)에 스텝별 요청 수·오류·상태 코드·지연 HDR·실패 종류와 구간 실행 결과(`ok`·`failed`·`interrupted`·`last_done_ms`)를 센다. 그래서 `MetricWindow`·요약·판정·진행 차트는 코드 변경 없이 준비 요청을 보지 못하고, 본 스텝의 요청 경로(`execute_steps`의 http 가지)에 준비 여부 분기가 없다. 와이어는 `MetricBatch`의 `SectionStepStat`·`SectionOutcome`(둘 다 `section` 문자열 필드를 싣고 엔진·컨트롤러 안에서는 열거형 `Section`), 저장은 마이그레이션 0027의 추가 전용 표 둘(`run_section_step_metrics`·`run_section_outcomes`)이고 읽을 때 합친다(수는 합, HDR merge, `last_done_ms`는 워커별 최대). 구간 이름을 와이어·표·trace 표지에 둔 것은 teardown 같은 다른 구간이 새 메시지·새 표 없이 받게 하려는 것이다.
5. **실패 = 첫 실패에서 멈추고 다시 시도하지 않는다. 빈 값 = 실패**: 전송 실패(ADR-0050 kind)·`read_body`·`status_assert`·`extract`(못 뽑음 또는 빈 문자열, JSON `null` 포함)·렌더 단계 엔진 오류(`unknown_var`·`malformed_template`·`cast_failed`)가 준비 실패다. 종류는 문자열 앞머리가 아니라 `ExecOutcome.error_class` 구조화 필드로 가른다. 준비 추출은 기본값 없는 엄격 방식(`ExtractMode::StrictNoDefaults`)이고, `run_section`·trace 준비 패스는 `fill_missing_extracts`를 부르지 않는다(기본값이 있어도 실패 — 빈 토큰이나 기본 토큰으로 본 스텝을 보내지 않기 위해서다). 실패한 VU는 반복 없이 끝나 `failed`에 들어가고(전부 실패하면 `AllVusFailed`), open-loop 슬롯은 run에서 빠지며(큐로 돌려주지 않음) 그 도착은 시작·완료·`dropped` 어디에도 넣지 않는다. 준비 도중 run이 끝나거나(deadline) 취소되면 그 도착도 어떤 계수에도 넣지 않고, 슬롯은 큐로 돌려주며, 준비 결과는 `interrupted`로 센다. 모든 슬롯이 빠지면 run이 `failed`이고 스케줄러 루프 머리에서 확인하므로 다음 예정 도착에서 알아챈다. 재시도하지 않는 것은 틀린 계정을 run 내내 되풀이해 계정 잠금을 만들지 않기 위해서다. 실패 종류 문자열의 단일 원천은 `section.rs`의 `KIND_*`·`is_section_failure_kind`·`ErrorKind::ALL`이고 컨트롤러 수신 필터가 같은 함수를 쓴다.
6. **본 숫자에 닿는 길마다 처리**: VU 고정의 유지 구간 창 시작은 워커별로 `max(계산값, 그 워커의 마지막 준비 완료 시각)`으로 보정한다(open-loop는 창을 바꾸지 않고 리포트 구획이 안내). 리포트에는 `setup` 블록(`ok`·`failed`·`interrupted`·스텝별 표)을 시나리오에 준비 스텝이 있을 때만 싣고(없으면 키 자체가 없다), `failed > 0`이면 유효성에 「준비 실패로 부하가 설정보다 적었음」 항목을 더한다. 시작 감시를 위해 준비 통계를 주기 flush에도 싣고, `MetricFlush`의 드레인 여섯 곳·송신 가드·워커 건너뛰기 가드(`flush_to_batch`)가 모두 이를 본다.
7. **trace·모니터**: `trace_scenario`는 준비 → 본 순서로 한 번 실행하고 준비 행에 `section: "setup"`을 단다. 준비 요청에 미바인딩 변수가 하나라도 있으면 그 요청을 보내지 않고(부하 경로의 엄격 렌더와 같은 결과 — 모니터가 점검마다 빈 비밀번호로 로그인을 보내 계정을 잠그지 않게) 렌더한 요청·변수 이름과 고정 오류 `setup: unbound variable`을 행에 싣는다. 준비 실패면 본 스텝을 실행하지 않고 `setup_failed`(`RowsTrace`도 같음)를 단다. `setup_ms`를 싣는다. 행 모드는 준비를 첫 행 앞에 한 번 하고 행은 `RowsTrace.setup_steps`에 싣는다(행이 0개면 준비를 하지 않는다). 운영 모니터의 스텝 훑기·인증 변수 가림·think 제거·검증은 준비 스텝도 보고, SLO 스텝 기준·인사이트·유효성의 스텝 점검은 본 스텝만 본다.

## 대안 (기각)

- **스텝마다 「VU당 한 번만」 스위치(JMeter 방식)**: 측정 대상 경계가 스텝마다 흩어져 리포트 분리가 흐려진다.
- **리포트에서만 제외**: 서버는 여전히 로그인 부하를 받는다는 점은 그대로고, 실행·집계 양쪽에서 걷어내지 못한다.
- **컨트롤러가 스텝 id로 걸러 낸다**: 기록은 그대로 두고 읽는 곳마다 준비 스텝 id를 뺀다. 읽는 곳마다 걸러야 해서 한 곳만 빠뜨려도 숫자가 섞인다. 엔진이 따로 세는 쪽은 기존 집계 전부가 손대지 않아도 준비 요청을 볼 수 없다.
- **`per_vu` 열만 준비 스텝에 보이게 한다**: 데이터셋 정책에 따라 보이는 열이 달라지고 정책 때문에 준비가 실패한다. 「첫 반복이 쓰는 값을 본다」는 규칙 하나로 통일했다.
- **목록 꼴 `setup: [...]`**: 구간 설정 키(주기 재실행 간격 등)를 더할 자리가 없어 형식을 깨야 한다. 객체 꼴은 키만 더하면 된다.

## Consequences

- 준비 스텝이 없는 시나리오는 YAML·배치 바이트·리포트 JSON·DB 행이 변경 전과 같다. 워커와 컨트롤러는 함께 올려야 한다(옛 워커는 `setup` 키를 거절해 run이 즉시 `failed`, 릴리즈 노트에 적는다).
- 준비 스텝의 1초 단위 시계열은 없다(스텝별 run 전체 합계만). 준비 통계는 요약·판정·인사이트·SLO에 들어가지 않는다.
- 연결 통계(dns·connect·재사용 비율)는 준비가 먼저 연 연결 때문에 본 스텝에서 줄어든다 — 로그인 뒤 상태 측정이 목적이라 그대로 둔다.
- open-loop 로그인 횟수는 약 `min(max_in_flight, 도착 수)`다. 유지 구간 창은 open-loop에서 준비 시간을 반영하지 않는다. 워커가 여럿일 때 준비 실패는 워커마다 판정한다. 이 셋과 준비 구간의 loop·if·parallel, teardown, 모든 VU 준비 후 동시 출발은 roadmap §B에 연기했다.
- 해소: 에디터·화면 구획·안내(A2), 인쇄·내보내기·비교·실행 중 진행(B), 주기 재실행(그 뒤). 구현하며 정한 것·연기 상세는 roadmap §B와 `docs/build-log.md`.
