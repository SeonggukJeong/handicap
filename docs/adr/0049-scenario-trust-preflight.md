# 0049. 실행 전 시나리오 신뢰도 — 네 번째 판정 축 + 검증 상태를 등급에서 분리

- 상태: 채택됨 (2026-07-25, 설계 사용자 승인)
- 관련: [ADR-0028](0028-run-level-slo-criteria.md)(run verdict — 별 축), [ADR-0022](0022-data-driven-datasets.md)(데이터셋 바인딩 — B 점검과의 상호작용), [ADR-0013](0013-scenario-runconfig-separation.md)(시나리오 ⟂ run config — 판정이 run config를 보지 않는 근거), [ADR-0033](0033-parallel-node.md)(분기 네임스페이스 — 지문·변수 스코프), [ADR-0035](0035-ui-korean-copy-message-catalog.md)(ko 카탈로그), [ADR-0044](0044-editor-outline-not-canvas.md)(에디터 아웃라인 — 칩/모달이 사는 표면). 설계: `docs/superpowers/specs/2026-07-25-scenario-preflight-design.md`. 카피 정본: `docs/dev/scenario-preflight-copy.md`.

## 맥락

§A11 1차(`f93544a`)는 run이 **끝난 뒤** 결과 해석 가능성(`validity` + narrative)을 라벨했다. 그러나 에픽이 요구한 것은 "시나리오 신뢰도 점수 + 개선 가이드"였고, 사후 라벨로는 **부하를 걸기 전에** 막을 수 있는 낭비를 막지 못한다 — 요청은 전부 정상 전송되는데 아무것도 검증하지 않는 시험(assert 없음), 시작 즉시 전 VU가 죽는 시험(미정의 변수), 인증 토큰이 끊긴 시험(추출했으나 아무도 안 씀)은 모두 **실행 전 정적으로** 판별 가능하다. 1차 회고에서 이 갭을 인정하고, 밀도 피로를 이유로 "배지 확산 2차"는 기각한 상태였다.

또한 "이 시나리오를 실제로 한 번 돌려봤는가"라는 별개 질문이 있다. 이건 정적 분석이 원리적으로 답할 수 없고(값이 틀린 변수는 못 잡는다), 사람·기기에 따라 답이 다르다.

## 결정

**정적 신뢰도를 실행 *전* 판정하는 네 번째 사용자 대면 축을 신설하고, "실제로 돌려봤는가"(D)는 그 축에서 분리한다.**

- **판정 축 4종은 서로 직교한다**: `신뢰도`(시나리오 텍스트가 실패를 감지할 수 있는가 — 이 ADR) ⟂ `validity`(끝난 run의 결과를 해석할 수 있는가 — 1차) ⟂ `verdict`(SLO 합격 여부 — ADR-0028) ⟂ `status`(run 실행 상태). **등급 어휘를 축마다 분리**한다 — 신뢰도는 `양호`/`보완 필요`/`취약`이며, 1차의 해석 어휘(`해석 가능`/`제한적 해석`/`해석 주의`)와 부분문자열조차 겹치지 않아야 한다(겹치면 사용자에게 두 축이 같은 것으로 보이고, 문자열 단언이 두 표면 모두에 걸려 테스트가 공허해진다).
- **판정은 클라이언트 순수 함수 단일 소스**(`evaluateTrust(scenario)`): 세 표면(에디터 칩·`TrustBoard` 모달·RunDialog 한 줄)은 렌더만 하고 아무것도 재도출하지 않는다. 서버 판정을 두지 않은 이유 — 판정 입력이 전부 시나리오 텍스트이고, 편집 중 즉각 반응해야 하며(고치면 등급이 곧바로 오른다), 서버 왕복은 그 반응성을 죽인다.
- **등급은 2축 증폭 모델**: 증폭 조건은 "응답 검증 **전무**"이지 "A 점검 실패"가 아니다. 부분 검증(9/10)은 그 9개가 시끄럽게 실패하므로 증폭기가 아니다. 이 구분이 진리표 행 2(전무+체인끊김=`취약`)와 행 4(부분+체인끊김=`보완 필요`)를 갈라놓는다.
- **`na`는 분모에서 제외**: 추출이 없는 시나리오에서 "3개 중 2개 통과"는 거짓이다 — `applicable`로 센다.
- **D(시험 실행 검증)는 등급에 관여하지 않는다** — 이것이 이 ADR의 두 번째 결정이며 **타입으로 강제**한다: `evaluateTrust`는 test-run 상태를 인자로 받지 않고 `TrustReport`에도 담지 않는다. 근거: D는 브라우저-로컬(localStorage)이라 다른 기기·다른 사람에겐 `never`인데, **등급은 누가 보든 같아야** 한다. D를 등급에 섞으면 같은 시나리오가 사람마다 다른 등급으로 보인다. D는 칩 접미 `(미확인)`(등급어·색 불변)과 모달 전용 줄로만 표현하고, 문구에 "이 브라우저 기준"을 명시한다.
- **D의 근거는 실행 지문 해시 + 시나리오별 버킷**: *test-run이 실제로 행사하는 실행 표면만* 담는다(제외: 시나리오/스텝 이름·메모·`request.disabled` / 포함: url·method·headers·body·assert·extract·스텝 순서·`if` 분기 정체성·`elif` 순서·parallel 분기명·`timeout_seconds`). 이름 수정으로 무효화되면 사용자가 이 점검을 **무시하게 되므로** 배제 목록이 기능의 일부다. 반대로 실행 표면 변경을 놓치면 도구가 거짓말을 한다. 버킷을 시나리오별로 분리해 `never`(기록 없음)와 `stale`(기록 있으나 내용 변경)을 구분한다.
- **성공 판정은 HTTP 200이 아니라 trace 내용**(`ok && !truncated`): 전 스텝이 connection-refused로 죽은 test-run을 "확인했습니다"로 기록하면 이 에픽이 싸우는 거짓말을 우리가 만든다.
- **soft only**: run 제출을 막지 않는다. 정당하게 assert 없는 스텝(워밍업·teardown)이 존재하고, 점검을 침묵시키는 opt-out은 이 에픽이 싸우는 대상을 **정확히** 숨기므로 두지 않는다.
- **밀도 상한이 1급 제약**: 상시 칩 +1 이내·상시 배너 +0·리포트 표면 0-diff·RunDialog는 `level !== "good"`일 때만. 1차가 반려된 사유가 밀도였고, "작성자 외 모든 운영자에게 상시 노출"은 그 반려의 재발이다(FR1).
- **판정 규칙은 변수 패널과 한 벌**: 끊긴 추출 체인 점검은 `VariablesPanel`이 `미사용` 배지를 붙이는 조건과 **동일 코드**여야 한다 → 패널의 행 빌더를 `varRows.ts`로 추출해 공유. 규칙이 두 벌이면 같은 변수가 패널엔 `미사용`, 모달엔 `사용됨`으로 갈린다.

## 결과

- `crates/**`·`proto/**`·migration·`ui/src/api/schemas.ts` **0-diff** — 판정·지문·버킷이 모두 클라이언트에 산다. 서버 계약 변화 없음.
- **데이터셋 바인딩과의 상호작용이 설계상 남는다**: 데이터셋 열로 공급되는 변수는 선언·추출이 없어 B 점검이 실패로 보고하고 등급은 `취약`이 된다(D4가 run config를 판정에서 제외하므로 의도된 결과). 다만 RunDialog는 바인딩이 있을 때 "시작하자마자 전 VU 실패" **단정 문구를 억제**한다 — 그 화면은 자기 문장을 반증하는 사실(`bindings`)을 이미 갖고 있고, 실제로 그 run은 성공한다. 에디터는 run context가 없으므로(ADR-0013) 억제하지 않으며, 문구가 "**이대로** 부하를 걸면"이라 문자 그대로 참이다. 상세·잔여 한계는 spec §11.9.
- **검증 상태의 서버 승격 경로를 이 ADR이 기록한다**: 팀 공유가 필요해지면 D를 서버 영속으로 올린다(별 슬라이스). 그때까지 "작성자 아닌 브라우저에서 `(미확인)` 영구 표시"는 버그가 아니라 D 분리의 정직한 결과다 — **등급에 섞어 해결하려 하면 FR1이 재발한다.**
- 접근성: 칩의 접근명은 **가시 라벨을 포함**해야 한다(WCAG 2.5.3 Label-in-Name). 가시 텍스트를 한 번만 만들어 `aria = 가시 + 꼬리`로 조립하므로 드리프트가 구조적으로 불가하다. 문구 정본과 조립 규칙은 카피 정본이 소유한다.
