# 작업 규칙 — 로컬 자동메모리 밖에서도 보여야 하는 것

> **왜 이 파일이 있나**: 사용자 피드백·결정의 상당수는 로컬 맥의 자동메모리(`~/.claude/projects/…/memory/`)에만 있었다. cloud 세션(claude.ai/code 컨테이너)은 그 메모리를 **읽지도 쓰지도 못한다**. 2026-11-12 점검에서 cloud 세션이 대부분 우연히(선례·spec 표 덕에) 따랐지만, 실수 1건(§B 번호 중복)과 사용자 지시 1건 미적용(TUI 칸 개수별 검증)이 나왔다. 그래서 **모든 세션이 지켜야 할 규칙의 정본을 여기 둔다**. 로컬 메모리 파일은 같은 규칙의 사례·서사를 가진 보조 기록이다. 규칙을 고치면 이 파일을 먼저 고친다.
>
> 루트 `CLAUDE.md`의 전역 규칙·슬라이스 파이프라인과 겹치는 것은 다시 적지 않는다. 여기에는 메모리에만 있던 것만 둔다.

## 1. cloud 세션 ↔ 로컬 맥 세션

- **cloud는 자동메모리를 쓸 수 없다** → 사용자 결정과 작업 방식 피드백("앞으로 이렇게 해라")은 반드시 **repo에** 남긴다. 결정은 그 슬라이스 roadmap §B 블록의 `사용자 결정(날짜, 다시 묻지 않는다)` 줄에, 작업 방식은 **이 파일에** 적는다. 대화에만 있던 피드백은 다음 세션에 사라진다.
- **cloud는 지정 브랜치(`ccr-*`)에만 push한다(master 불가)**. 슬라이스를 끝냈으면 roadmap §B 블록 머리에 **로컬 머지 절차**를 남긴다(선례 §B52 (0): 지금 상태 → 로컬 master 확인 → 단계별 ff-merge + 단계마다 맥 전체 게이트 → 맥에서 확인할 것 → push와 기록). 로컬 세션은 그 블록을 그대로 따르고, 끝나면 완료 표시를 한다.
- **cloud에서 못 한 검증은 "못 했다"고 남긴다**(nextest 미설치 → `cargo test --workspace` 폴백, `pnpm build` 메모리 부족, macOS 전용 동작). Linux에서만 실측한 테스트는 맥에서 깨질 수 있다. 실제로 엔진 connect 정체 픽스처가 macOS에서 RST로 끊긴 일이 있다(`crates/engine/CLAUDE.md`).
- **로컬 세션끼리 작업을 넘길 때는 넘기는 쪽이 먼저 워크트리에서 나간다**(사용자 지시 2026-11-20). `EnterWorktree`로 들어간 워크트리는 그 세션이 잠그고 있어서 다른 세션의 `EnterWorktree(path)`가 "belongs to another running Claude Code session"으로 거부된다. 그래서 다른 세션에 작업을 보내기(`SendMessage`) **전에** `ExitWorktree(action: "keep")`을 부른다(디렉토리·브랜치는 남는다). 사례: stage-live-reasons spec·plan 뒤 구현을 handicap-50 세션에 넘겼는데 잠금으로 재진입이 거부됐다.
- **로컬 맥 세션은 cloud 작업을 시작하기 전에 master를 push한다**. cloud는 `origin/master`에서 갈라지므로, 로컬에 push 안 된 커밋이 있으면 ff가 안 되고 §B 번호도 겹친다(2026-11-11 merge `78abf72`에서 §B49 재번호).

## 2. roadmap §B 블록

- **새 §B 번호는 `grep -n '^### B' docs/roadmap.md`로 마지막 번호를 확인한 뒤 +1**로 정한다. 기억이나 현황판으로 정하지 않는다. 2026-11-11 cloud가 이미 있던 Windows §B48과 같은 번호로 1b 블록을 만들었고, 2026-11-12에 `§B48b`로 분리했다.
- **판단(ruling)은 비용과 해소법을 함께 §B에 기록한다**(사용자 지시 2026-10-16). 고치지 않은 리뷰 finding, 연기, 약한 테스트를 그대로 둔 것, 선재 버그를 각각 `무엇을 정했나 · cost-if-wrong · 구체 해소 경로`로 적는다. SDD ledger(`.superpowers/sdd/`)는 gitignore라 워크트리와 함께 사라진다. 블록 구성: (1) 다음 슬라이스 후보 (2) 판단과 비용·해소 (3) 선재 버그 (4) spec 연기 (5) 보안·성능 메모 (6) 테스트 공백. 선례 §B30.
- **공용 개념을 한 경로에만 적용하면 사용자에게 묻고 §B에 연기로 남긴다**(사용자 지적 2026-11-09). 응답 본문 JSON 해석, 템플릿 규칙, 판정 규칙처럼 여러 화면·경로에 걸친 개념이 대상이다. 축소를 spec 비목표 한 줄로 혼자 처리하지 않는다. 그 개념을 고치는 소형 수정에서는 `grep`으로 **같은 개념을 쓰는 형제 경로**를 함께 보여 준다. "연기 — 없음"은 그 sweep을 한 뒤에만 쓴다(감싼 JSON 풀기를 모니터에만 적용하고 시나리오 쪽을 놓친 사례 §B47).

## 3. 보안 게이트

- **`finish-slice` §0 grep은 하한선이다** — 매치가 없어도 diff가 **값을 새 sink로 옮기면**(로그 → DB, 내부 → API 응답, 임시 → 영속) `security-reviewer`를 돌린다. 그 sink에 이미 알려진 노출이 있는지 도메인 `CLAUDE.md`를 grep한다(parallel-var-scope: grep N/A였지만 평문 시크릿이 run 레코드에 들어가는 blocker가 나왔다).
- 연기 노트에는 **연기 조건**을 적는다(예: `operator-logs-only`). 그래야 나중에 그 조건이 깨진 것을 알아챌 수 있다.
- 시크릿 가림 테스트의 픽스처 값은 `{:?}` escape를 그대로 통과하는 문자셋으로 쓴다. 따옴표나 비-ASCII가 든 값은 escape되므로, 누출하는 빌드에서도 테스트가 green이 된다.

## 4. 라이브 검증

- **극단값에서도 읽혀야 한다**(사용자 지시 2026-10-22). 최대 개수, 촘촘히 몰린 값, 가장 긴 문자열, 큰 숫자, 최대 글자 크기, 범위 밖 값을 넣고 겹침(사각형 교차)과 잘림(`scrollWidth>clientWidth`)을 실측한다. 극단 설정에서 판독이 안 되면 "수용 한계"가 아니라 결함이다. 폭 제약 보드와 높이 제약 보드는 따로 본다.
- **컴포넌트가 마운트되는 모든 진입 화면에서** 확인한다. 소비처를 grep해 진입 경로를 열거하고 각각에서 US를 실행한다(신규 생성 화면은 정상인데 저장된 리소스 편집 화면에서는 기능이 없던 사례). 반대로 "부재"가 단계 차이일 수도 있으니 게이트(템플릿 갤러리 등)를 먼저 확인한다.
- **버그는 스펙보다 구현에서 나온다**(사용자 2026-06-29: "스펙은 항상 좋아. 구현했을 때 버그가 문제"). spec 의식에 과투자하지 말고 구현 뒤 검증에 rigor를 쓴다. 시각 표면은 DOM 존재나 텍스트만으로 PASS하지 않는다(rect 높이·폭 단언 또는 스크린샷). 새 UI는 스크린샷 전체를 눈으로 먼저 훑는다.
- **사용자 관람은 요청했을 때만**(사용자 지시 2026-11-16: "내가 원할때만 눈으로 봤으면 해. 내가 자리 비울때도 있어서"). 기본은 관람 없이 평소대로 돌리고, 관람할지 묻지 않는다. 그 슬라이스에서 요청이 있으면 시작 전에 접속 주소(GUI)와 붙을 수 있는 tmux 세션 이름(TUI)을 먼저 알리고 보이는 브라우저 창에서 조작한다. 요청이 있었더라도 응답을 기다리며 멈추지 않는다 — 사용자가 직접 정해야 할 화면(배치, 항상 보임 여부 등)은 끝에 모아 묻는다. 관람용 조작은 메인 세션 요청 수와 컨텍스트를 늘린다(extract-default: 작업이 절반인데 메인 비용이 그대로).

## 5. 작업 크기·UI 선호

- **소형 수정은 spec/plan 없이 해도 된다**(사용자 허용 2026-11-01). 파일 3~4개, UI 한정, 엔진·와이어·마이그레이션 무접촉이 조건이다. 먼저 변경 범위(파일·줄 수·안 건드리는 층)를 제시하고 동의를 받는다. 최소 절차는 지킨다: 테스트 먼저(일부러 망가뜨려 RED 확인) → 커밋 게이트 → 라이브(극단값 포함) → build-log에 "사용자 요청 소형 수정 — spec/plan 없음" 한 단락 → ff-merge.
  - **작업은 `EnterWorktree`로 만든 워크트리에서 — 메인 체크아웃에서 `git switch -c`로 브랜치를 만들지 않는다**(사용자 결정 2026-11-20). 다른 세션들은 메인 체크아웃이 늘 master라고 보고 `git -C <메인> merge --ff-only`로 합류한다. 2026-11-20 메인을 소형 수정 브랜치에 둔 사이 `stage-live-reasons` 세션이 그 절차를 못 쓰고 `git fetch . worktree-…:master`로 우회했고, `git switch`마다 git-guard 확인창이 떴다. 합류: `EnterWorktree`로 들어간 세션은 격리돼 `git -C <메인>`과 git 복합 명령(`&&`·`;`)을 거부하므로(2026-11-20 실측) 워크트리 안에서는 단독 git 명령으로 커밋만 하고, `ExitWorktree(keep)`로 메인에 돌아와 `git merge-base --is-ancestor master worktree-<X>` → `git status --porcelain -uno`(비었는지) → `git merge --ff-only worktree-<X>`(메인은 이미 master라 switch 불필요) → `git worktree remove .claude/worktrees/<X>` → `git branch -d worktree-<X>`. UI를 건드리면 워크트리에서 `pnpm install` 한 번. UI만 바꾼 수정의 라이브 검증은 백엔드가 master와 같으니, 메인에서 컨트롤러·워커를 증분 빌드해 메인 바이너리에 `--ui-dir <워크트리 절대경로>/ui/dist`를 붙여도 된다(워크트리 cargo 빌드 수 분·수 GB 회피). 워크트리가 `crates/`를 건드렸으면 루트 CLAUDE.md대로 워크트리 자체 바이너리로.
- **코드 파일 편집은 python 대신 Edit 도구를, 여러 곳이면 한 응답에 묶어서**(사용자 결정 2026-11-20). python으로 고치면 Write/Edit 훅(tdd-guard·spec-review-guard·자동 포맷)을 거치지 않는다. 한 응답에 Edit 여러 개를 보내면 왕복 한 번이고 토큰도 python과 비슷하다(같은 문자열 여러 곳은 `replace_all`). python은 포맷 훅을 일부러 피해야 하는 글자 보존 편집(ui/CLAUDE.md §빌드·타입 게이트)과 build-log 이어 붙이기·상태줄 스플라이스처럼 문서가 정한 경우에만.
- **선택적 폼 섹션은 기본 접힘 disclosure로, 대량 데이터 표·미리보기는 자동 노출 금지(명시 버튼 뒤 opt-in)**(사용자 선호). seed 값이 있으면 자동으로 펼치고, 접힌 채 값이 있으면 "N개 설정됨"을 표시하며, 인접 섹션과 간격을 둔다. 히트 영역은 크게, 시각 간격은 조밀하게. 이 사용자는 간격·일관성·a11y에 민감하므로, 리뷰가 Minor로 잡은 신규 UI 일관성 항목도 바로 반영한다.

## 6. 터미널 모니터(`handicap-tui`) 사용자 결정 (2026-11-07~08, 다시 묻지 않는다)

- 대상 아키텍처는 **x86_64 확정**이다. 운영 모니터 PC는 Ubuntu 19.04 저사양이고, 실사용은 보드당 6칸이다.
- **라이브 검증은 칸 개수별(1–9) 전부 확인**한다(사용자 지시 "검증 갯수별로 다 확인"). 모니터 화면의 칸 그리기·배치·머리 줄·키 줄을 바꾸는 슬라이스에 적용한다. 바꾸지 않았으면 그 근거를 build-log에 한 줄 남긴다.
- 조작은 TUI 관용(키 안내 줄·방향키·번호 메뉴), 상태 판정은 GUI와 같게 한다. 모니터 화면의 *표현*은 GUI 전시 화면을 따른다(칸 높이를 채우는 막대·기준선·큰 응답 시간).
- "json 파일이 곧 설정"이다. 매 실행마다 빈 임시 DB에 가져오고, 수정은 같은 파일에 되쓴다. 새 파일로 바꾸면 TUI에서 고친 내용이 버려지는 것은 수용했다.
- 마우스로 칸을 클릭해 고르는 것은 포함한다. 글자 복사는 거의 안 쓴다. 글자 크기는 터미널 글꼴(`Ctrl`±·`--zoom=`)로 정하며, 한글 픽셀 글꼴은 기각했다. 테두리는 굵은 선이 기본이고 `b`로 반 칸 블록과 전환한다. 실패 막대 위의 x 표시는 하지 않는다(사용자는 GUI의 ✖도 싫어함).
- 자동 시작은 `~/.config/autostart/*.desktop` + `gnome-terminal --full-screen --zoom=1.6`.
- 시각 결정을 위한 목업은 실제 터미널 문자 격자로 그린 HTML로 만든다(`docs/superpowers/specs/2026-11-08-tui-readability-mockups/`). 목업은 보여 주기 전에 repo에 저장하고 경로를 알려 준다(임시 폴더는 정리돼 사라진다).

## 7. 코드 주석 — 변호 대신 수정 (사용자 지시 2026-11-17)

- **놀라운 동작을 경고하거나 변호하는 주석이 필요하다면 그 동작이 결함이다.** "의도적이다·무해하다·수용한다·일단·호출하는 쪽이 처리해야 한다"처럼 이상한 동작을 설명하고 넘어가는 주석은 수정을 대신하지 못한다. 길은 둘뿐이다. 코드를 고쳐 주석이 필요 없게 하거나, 못 고칠 이유가 있으면 roadmap §B에 비용·해소법과 함께 기록하고(§2) 주석에는 사실만 남긴다.
- **리뷰어가 "주석·문서 보완"을 처방해도 코드로 고칠 수 있는지 먼저 본다.** 가장 싼 처방이라 리뷰어가 자주 고르고, orchestrator가 그대로 접으면 결함이 주석과 함께 굳는다. 사례(desktop-worker-mode 2a Task 3): 같은 값의 타이머 두 개가 경합해 연결 상한을 넘겼을 때 `ConnectTimeout`이 나올지 `Connect`가 나올지 정해지지 않았다. 리뷰 처방대로 "둘 다 나올 수 있으니 호출하는 쪽이 둘 다 처리하라"는 주석으로 덮었다가, 사용자 지적 뒤 타이머를 하나로 줄였다.
- **리뷰 판정**: 결함을 설명하거나 정당화하는 새 주석은 **Important**다(Minor 아님). implementer brief에도 같은 규칙을 넣는다.
- 사실을 적는 주석(불변식·순서 제약·외부 출처 — 무엇을 왜)은 그대로 좋다. "abort 표시는 잠금 안에서 전송 전에 세운다 — 전송 중 도착한 `Aborted`가 R8로 빠지지 않게"는 제약을 설명한 것이지 변호가 아니다.

## 8. 용어 (사용자 결정 2026-11-17)

- **「되돌려 확인(teeth check)」** — 회귀 테스트가 정말 그 버그를 잡는지, 고친 코드를 일부러 옛 상태로 되돌려 테스트가 실패(RED)하는지 보고 원복하는 절차. 대화·새 문서에서 「이빨 실증」·「이빨 있음/없음」 대신 이 말을 쓴다(영어 직역이라 어색하다는 사용자 지적). 회귀 테스트 = 남겨 두는 테스트, 되돌려 확인 = 그 테스트를 검사하는 1회 절차. 기존 문서의 「이빨 실증」은 일괄 교체하지 않았다(사용자가 요청하면 교체).
- **보고서·리포트에 찍히는 제목·소제목은 보고서 문체로**(사용자 지적 2026-11-18) — 인쇄본·화면 리포트·내보내기처럼 제출 문서에 들어가는 글에 구어체 질문형·말투(「어디가 문제인가」, 「말할 수 있는 것」)를 쓰지 않는다. 내용을 그대로 이름 붙인다(「단계별 결과」, 「결과 해석의 범위와 한계」 · 「이 결과로 확인된 것」 · 「이 결과만으로 판단할 수 없는 것」). 글자 순서만 다른 이웃 제목(「계단별」 ↔ 「단계별」)도 피한다. 입력 화면의 안내·도움말 말투는 이 규칙 밖(QA 입문자용 풀어쓰기, §9).
- **화면 문구에 번역투 명사구를 만들지 않는다**(사용자 지적 2026-11-20, stall-saturation). 「대상 멈춤부터 확인」·「도착을 시도한 초」·「이 구성의 전달 한계」처럼 설계 용어를 이어 붙인 말은 읽다가 걸린다. 「서버가 왜 멈췄는지부터 확인해 보세요」·「실행한 초」·「슬롯 설정이 부족해서는 아닙니다」처럼 누가 무엇을 했는지 동사로 풀어 쓴다. spec·코드의 내부 용어(stall·대상·도착)를 화면 문구에 그대로 옮기지 말 것 — 문구를 정할 때 소리 내어 읽어 보고 걸리는 명사구를 동사로 바꾼다.

## 9. 사용자 부재 중 판단 기준 (사용자 지시 2026-11-18)

- 사용자가 자리를 비운 동안 결정할 일이 생기면 묻고 멈추지 말고 이 순서로 정한다: **① 정직한 동작·성능**(숫자가 실제를 속이지 않는 쪽, 조용한 축소·추정 금지 — 추정이면 화면에 추정이라고 쓴다) → **② 화면이면 사용자의 사용성 최우선**. 사용자는 **QA 입문자 수준**이라고 가정한다(용어를 풀어 쓰고, 기본값으로 바로 쓸 수 있게, 실수하기 어렵게).
- 그렇게 정한 것은 roadmap §B 슬라이스 블록에 "부재 중 판단"으로 비용·되돌리는 법과 함께 남겨(§2), 사용자가 돌아와 한 번에 확인할 수 있게 한다.

## 10. 구현 성능 (사용자 지시 2026-11-19)

- **구현은 동작 정확성이 최우선이고, 그 안에서 성능을 극한까지 짜낸다.** 결과(판정·숫자·와이어)를 바꾸는 최적화는 하지 않는다 — 최적화 전후 결과가 같음을 기존 동등성 테스트나 새 테스트로 보인다. 계획 단계에서 비용이 큰 곳(디코드·복사·잠금·매 메시지 할당)을 먼저 찾아 「필요 없는 일을 하지 않기」로 줄이고, 성능 측정은 새 비용이 실제로 생기는 갈래를 기준선(그 비용이 없던 master)과 비교한다.
